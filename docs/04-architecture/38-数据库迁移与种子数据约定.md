# 38-数据库迁移与种子数据约定

> 本文主体定义目标PostgreSQL的迁移与种子规则。Stage 4另有已运行的SQLite schema v2最小迁移；两条Profile必须明确区分，不得把SQLite通过表述为目标107表/Alembic/RLS已通过。

## 0. Stage 4本地SQLite迁移（已实现）

- 启动或执行`make migrate`时，`SQLiteWorkflowStore`在单事务中读取`schema_migrations`并按版本顺序升级到v2；遇到高于代码支持版本的文件立即失败。
- v1创建planning纵向切片的聚合表、租户/Workspace索引、Trace、版本索引、审核关联和幂等表；v2创建Tenant、Workspace、User和Membership认证表。
- 数据库启用WAL、外键检查和10秒busy timeout，文件权限收紧为0600。
- 自动化测试覆盖空库创建、服务对象重建后数据恢复、摘要篡改、幂等、Workspace越权和第二租户隔离；浏览器E2E还验证了服务进程重启后四项批准状态保留。
- 该迁移只为单机本地Profile服务，不生成或替代Alembic迁移。

## 1. 基线与边界

| 项目 | 目标约定 |
|---|---|
| PostgreSQL | 16 |
| ORM/迁移 | SQLAlchemy 2.0 async + Alembic，版本在开发脚手架创建时锁定 |
| 扩展 | `uuid-ossp`、`vector` |
| 当前DDL规模 | 107张表，按八个产品模块及跨域治理分组（2026-08-14 第0周补丁 B1 更新，含 t_calibration_record/t_verify_verdict） |
| 迁移身份 | `qf_owner`或等价迁移专用身份 |
| 运行身份 | `qf_app_user`，无DDL权限，受RLS约束 |
| 产品阶段 | V0设计；无历史线上数据兼容义务 |

禁止从文档中的示例目录推断工程已经存在。进入开发阶段时，真实目录、依赖锁文件和迁移链需另行创建并验证。

## 2. 迁移命名与不可变规则

迁移文件命名为`YYYYMMDD_NNNN_<verb>_<scope>.py`。序号只增不复用；revision形成单向链。任何已经进入共享环境的迁移不得改写，只能新增纠正迁移。

每个迁移必须包含：

- 明确的`upgrade`和安全可行的`downgrade`；不可逆时在代码与发布说明中显式声明。
- 变更原因、影响表、预计锁表方式和数据回填策略。
- 结构变化前后的完整约束、索引、RLS和权限处理。
- 对大表使用分阶段添加、回填、校验、收紧约束，避免长事务锁表。

## 4. 表分组与依赖原则

迁移分组按33号文档章节和实体所有者执行，不按旧页面菜单分组：

1. 平台基础先于任何Workspace业务数据。
2. 任务看板与ReviewPolicy先于需要审核的正式产出物。
3. 知识版本先于TestingIR；TestingIR先于正式用例。
4. 自动化脚本版本绑定正式TestCaseVersion。
5. ExecutionPlanVersion冻结计划、脚本、用例、环境与数据资产的精确版本。
6. 质量分析和报告引用执行事实，不复制或覆盖结果。
7. Agent运行引用工作项、策略快照、授权决定和完整Trace。

跨域外键不得为了迁移方便长期降级为无约束UUID。若采用延后加约束，必须在同一首建链结束前补齐并校验。

## 5. RLS、权限与只追加数据

- 迁移由owner身份执行，不设置伪造的租户上下文。
- 应用连接必须在事务内设置并校验`app.current_tenant_id`、用户/服务身份及Workspace授权上下文。
- Tenant、Workspace或资源作用域数据必须默认拒绝；没有有效上下文时查询结果不能泄漏跨租户存在性。
- `t_audit_log`、审核决定、执行结果、证据、Trace、外部同步尝试等事实表仅允许追加；纠错通过新事件或更正记录完成。
- PlatformAdmin是平台管理权限，不自动获得所有Workspace业务内容权限，也不自动拥有正式产出物批准能力。

## 6. 种子数据

### 6.1 原则

1. 种子数据只建立系统运行所需的内置定义，不创建默认真实用户、密码、租户密钥或第三方凭据。
2. 每条内置记录使用稳定机器键和显式版本，不以展示名作为唯一标识。
3. 重跑相同迁移必须幂等；内容不同但机器键相同必须失败或显式生成新版本，不能静默忽略漂移。
4. downgrade只能删除该迁移明确创建且未被业务数据引用的内置版本；存在引用时必须阻止回滚。

### 6.2 权限、角色和审核策略（0013）

种子至少覆盖：

- 平台、租户、Workspace、资源四级作用域权限。
- `PlatformAdmin`、`TenantAdmin`、`WorkspaceAdmin`、`TestLead`、`TestEngineer`、`ViewerAuditor`角色定义。
- 人工专属能力，例如正式产出物批准、四眼复核、外部缺陷写入批准、报告签署、知识发布。
- `SINGLE_REVIEW`、`FOUR_EYES`、`CODE_REVIEW`、`EXTERNAL_WRITE`、`REPORT_SIGNOFF`、`KNOWLEDGE_PUBLISH`审核策略。

“Approver”是审核任务中的职责，不是一个脱离作用域与能力的全局角色。

### 6.3 Skill（0014）

来源为`prototypes/skills/`下30个原型。种子写入Skill稳定根与首个不可变版本，包括：机器键、说明、输入/输出契约摘要、实现/原型引用、内容摘要、风险分类和状态。

Skill原型文档不是已实现代码；只有完成结构校验、eval和开发准入后，才可把版本标记为可运行。目录新增、删除或更名时，迁移清单必须由目录清单自动生成并与30这一基线复核，不能手工用省略号代替。

### 6.4 Gate 0 Agent与Workflow（0015）

来源为`prototypes/agent-governance/`。种子写入：

- Supervisor和受限Subagent的稳定根与不可变版本。
- Prompt版本、Skill allowlist、数据与工具权限、外部访问策略。
- Gate 0 Workflow版本、节点、依赖和人工审核门。
- 配置内容摘要，确保数据库记录可与原型文件精确核对。

Agent/Service身份不得拥有人工专属批准能力；种子加载必须拒绝越权配置。

## 7. 环境发布与回滚

| 阶段 | 必须验证 |
|---|---|
| 生成 | 自动生成结果与33号DDL逐表、逐约束比对，人工审核差异 |
| 空库升级 | 从零执行到head，无错误且对象数量符合目标 |
| 重跑 | 已到head再次升级无变化；种子内容无漂移 |
| 降级演练 | 在临时环境验证可逆链；不可逆节点有恢复方案 |
| 多租户安全 | 无上下文、错误租户、跨Workspace访问均被拒绝 |
| 权限安全 | 应用身份不能DDL、不能改只追加事实、不能越过人工审核 |
| 数据一致性 | 外键、唯一约束、稳定根指针、版本摘要和索引全部有效 |

生产迁移前必须有备份/恢复演练、预计时长、锁表评估和失败停止点。文档静态检查不能替代真实PostgreSQL执行。

## 8. 当前阶段验收

现阶段只允许声称：迁移顺序、职责边界和种子规则已设计。进入开发后，至少要补齐以下证据才能声称“数据库迁移可用”：

- 实际Alembic工程与依赖锁。
- 从空库升级到head的日志。
- 107张表、外键、索引、RLS、权限和种子记录的自动核对结果。
- 升级幂等、降级/恢复、多租户隔离和人工专属权限的测试报告。
