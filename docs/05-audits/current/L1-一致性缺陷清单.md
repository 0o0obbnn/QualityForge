## 🔴 L1-001 · RequirementDocument 状态枚举跨文档冲突
**Severity: Blocker | Priority: High**

同一实体 `RequirementDocument` 的状态枚举，三个权威源给出三套不一致的值：

| 文档 | 定义 | 证据 |
|---|---|---|
| 04 核心领域模型（权威） | `Draft / Parsing / Completed / Failed` | 04-核心领域模型.md:828 |
| 32 API 规范（权威） | `Draft / Parsing / Completed / Failed` | 32-API规范.yaml:3101 |
| 11 TestDesign PRD | `PENDING / PARSED / FAILED`（全大写，仅 3 值）| 11-PRD-TestDesign.md:75 |

**问题**：① 大小写不一致（Draft vs PENDING）；② PRD 缺少 `Parsing`（解析中）状态，无法表达"正在解析"这一关键中间态；③ 领域模型有 4 值，PRD 只有 3 值。
**影响**：开发时无法确定以哪套为准；状态机实现会因枚举缺失产生死代码或漏分支。

## 🔴 L1-002 · DesignTestCase 概念未进入正式领域契约
**Severity: Blocker | Priority: High**

`DesignTestCase`（设计阶段草稿用例）是 TestDesign 模块的**核心实体**——有独立数据表（11-PRD-TestDesign.md:101 §3.1.4）、独立状态机（DRAFT/GENERATING/REVIEWING/APPROVED，行 112/120-125）、独立字段（含 `confidence_score`）。但它：

- ❌ 不在术语表 03
- ❌ 不在领域模型 04 的 38 实体中
- ❌ 不在 API 规范 32 的 Schema 中
- ❌ 不在 DB Schema 33 中

**且与正式 `TestCase` 存在双重冲突**：
1. **状态机冲突**：DesignTestCase 用 `DRAFT/GENERATING/REVIEWING/APPROVED`，TestCase 用 `Draft/Reviewed/Deprecated`。两套状态机并行，草稿用例"入库转正式"的映射关系**完全未定义**（PRD 行 106 仅一句"入库转 TestCase 时由资产服务分配正式编号"，无状态流转规则）。
2. **职责边界模糊**：DesignTestCase 有 `expected_result`（预期结果断言），TestCase 也有 `expectedResults`——同一信息存两处，同步规则缺失。

**影响**：核心价值链"需求→测试资产"的数据落地无统一契约；前后端、AI 服务、资产服务将各按各自理解实现。

## 🔴 L1-003 · 可信链核心概念全部未进入正式契约
**Severity: Blocker | Priority: High**

以下 6 个概念在 29 个 Skill 原型中高频使用（构成 AI 测试的核心数据流），但在术语表/领域模型/API/DB **四处全部零命中**：

| 概念 | Skill 命中文件数 | 术语表 | 领域模型 | API | DB |
|---|---|---|---|---|---|
| Assertion（断言） | 76 | 0 | 0 | 0 | 0 |
| Source Trace（来源溯源） | 39 | 0 | 0 | 0 | 0 |
| Review Task（评审任务） | 27 | 0 | 0 | 0 | 0 |
| Testing IR（测试中间表示） | 14 | 0 | 0 | 0 | 0 |
| Business Rule（业务规则） | 11 | 0 | 0 | 0 | 0 |
| Coverage Report（覆盖率报告） | 7 | 0 | 0 | 0 | 0 |

**证据**：`grep -ric` 扫描结果（见 `概念权威基线.json` `skills_used_concepts_not_in_domain`）。
**影响**：Skill 是平台目前唯一接近"可运行"的制品，它产出的 `Testing IR / Assertion / Coverage` 等核心数据**无处持久化、无 API 可查、无领域模型可依**。正式产品契约严重落后于已形成的原型方法。这是可信链的物理断层。

## 🟠 L1-004 · TestPlan 丢失 Requirement 外键关联
**Severity: Critical | Priority: High**

领域模型 04 §4 TestPlan（行 365-377）字段表无任何 `requirementId` / `requirementDocumentId` 外键。ER 图（行 101-106）也确认 TestPlan 仅关联 TestScenario，不直接关联 RequirementDocument。

**影响**：无法从"测试计划"回溯到"需求文档"，破坏正向追踪性（RTM Forward）。需求变更时无法自动评估受影响的 TestPlan。结合 L1-002（DesignTestCase 也无 Requirement 关联），整个 TestDesign → TestAsset 链路的可追踪性断裂。

## 🟠 L1-005 · 覆盖率（Coverage）无正式领域语义
**Severity: Critical | Priority: Medium**

- 领域模型 04：无 Coverage 实体（grep `coverage` 零命中）
- API 规范 32：无 coverage 相关路径
- Skill 原型：`coverage_report` 在 4 个 skill 中使用，`Coverage Report` 在 3 个中使用

PRD 中覆盖率仅以"比例"形式出现（如 passRate），但**无分子/分母定义、无版本化实体、无覆盖率类型**（需求覆盖率 vs 接口覆盖率 vs 分支覆盖率）。

**影响**：NFR 和质量门禁（QualityGate）依赖覆盖率判定，但覆盖率本身无契约定义。门禁规则 `rulesConfig`（04 行 699）将基于无定义的指标，无法实现。

## 🟡 L1-006 · DB Schema 表数（43）与领域模型实体数（38）不匹配
**Severity: Major | Priority: Medium**

- 领域模型 04：声明 38 实体
- DB Schema 33：43 张 `CREATE TABLE`

差值 5 张表未在领域模型登记。可能是：① 映射表/关联表（如 TestSuiteCaseMapping 这类）；② DB 多出的业务表未抽象为领域实体；③ 领域模型滞后。

**待复核**：需逐表比对确认差额性质（关联表属合理，业务表属缺口）。此项标 Major，待 L2 进一步核实。
