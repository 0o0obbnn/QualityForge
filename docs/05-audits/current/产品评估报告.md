## 0. 执行摘要

### 总体裁决

QualityForge 作为**内部效率工具**（单一测试工程师 + AI），产品方向正确，技术选型保守合理，审计整改已清除核心契约断层（B-1/B-2/B-3 已修复）。但三大问题仍阻碍开发启动：**收益指标不可验收（B-6）**、**AI 可信度未建立（B-4/B-5）**、**范围与资源严重错配（企业级基础设施 vs 3-5 人团队）**。在激进裁剪企业级能力、重建收益指标、建立 AI 校准基线后，V1 核心闭环在 3-5 人 × 3 个月内可行。

> **v1.1 修订**：本版完成 10 份模块 PRD 逐份通读，§1/§3/§4 的裁剪与判断已全部替换为 PRD 一手证据（见各节"一手证据"标注）。

**总体评分：B-**（方向正确，执行前提未满足）

### 六维度评分表

|---|:---:|---|
| 1. 产品定位与价值主张 | **B** | 单人定位自洽，工作流合理，但收益指标需全部重建 |
| 2. 范围与 MVP 审视 | **B-** | V1 范围合理，V2/V3 企业级能力需大幅裁剪 |

### 前三大风险

1. **AI 可信度风险（高概率 × 高影响）**：B-4/B-5 未解决，AI 输出无法验证，用户信任无法建立。若不先建校准集和外部 oracle，V1 上线后工程师将拒绝采纳 AI 生成内容。

2. **范围蔓延风险（高概率 × 高影响）**：98 API / 50 表 / 42 实体对应企业级平台，3-5 人团队无法在 12 个月内完成全部。若不裁剪 V2/V3 企业级能力，项目将陷入"永远在开发"状态。

3. **单人 HITL 悖论（中概率 × 高影响）**：12 个 AI 介入点中 8 个默认 L2（需人工确认），但单人定位下生成者与审批者是同一人。若不重新定义审批语义，工程师将面临"自己审自己"的认知负担，导致审批流于形式或被绕过。

### 核心建议（≤5 条）

1. **立即裁剪企业级能力**：多租户 RLS、Vault、KEDA、LDAP、分布式 Runner 移出 V1-V3 范围，简化为单机版（见维度 2 裁剪清单）。

2. **重建收益指标**：用建设型指标替代四大作废指标，每条带 Given/When/Then + 测量方法（见维度 1 替代指标）。

3. **建立 AI 校准基线**：在 V1 开发前，为 12 个 AI 介入点建立最小校准集（每个介入点 ≥50 条标注样本），解决 B-4。

4. **重新定义单人 HITL**：将 L2 介入点的"人工确认"改为"工程师自审 + 延迟生效"，降低认知负担（见维度 3 建议）。

5. **按新定位重排路线图**：V1 聚焦核心价值链（需求→用例→执行→RCA），V2 增强 AI 能力，V3 企业级内容整体移出（见维度 6 路线图）。

### 修订说明（v1.1，2026-08-07）

v1.0 的范围裁剪与工作流检验主要基于审计转述与关键词检索。v1.1 完成 **10 份模块 PRD 逐份通读**（~2,900 行），§1.1（B 组矛盾）、§1.2、§3.1（#16-21）、§3.2、§4.5、§6.2 全部替换/增补为 PRD 一手证据。核心增量发现（审计未指出）：**0.95 双用**（17-PRD L9 的 RAG KPI 与 L164 自治阈值同值混淆，§4.5 发现 5）、**自治度与可验证性倒挂**（Agent ≥0.88 档是全平台最高自治、最难验证的输出，且丢失写操作确认保护，§4.5 发现 6）、**Token 成本是单人内部工具唯一持续 OPEX，但成本管控仅 P2**（§6.2）。另有：团队假设已物化进 DB 字段层（owner_id/git_author/updated_by）、自治等级冲突共 3 处（TestDesign/QI/KnowledgeCenter）。

### 1.3 收益指标重建

**审计判定**（L5-收益可验收性表）：四大核心收益指标全部不可验收（3 个 UNSUPPORTED + 1 个 AMBIGUOUS）。

**D9 裁决**：四大指标因基线≈0 全部作废，改写为建设型指标。

**替代指标**（基于"从零建设"基线 D8）：

#### 替代指标 1：V1 后核心业务场景 E2E 覆盖数

**原指标**："测试设计耗时缩短 80% 以上"（11-PRD L15）

**作废理由**：基线≈0（无现有 E2E），"缩短 80%"无从谈起。

**建设型替代**：

> **Given** 被测系统有 N 份需求文档（N 由项目实际确定，建议 ≥5 份）
> **When** V1 上线后 30 天内，工程师使用 QualityForge 生成并执行 E2E 测试
> **Then** 核心业务场景 E2E 覆盖数 ≥ N × 10 条（每份需求文档平均 10 条用例）
> **且** 用例评审通过率 ≥ 85%（工程师自审后采纳）
> **且** 执行通过率 ≥ 70%（排除环境问题后）

**测量方法**：
- 基线：0（无现有 E2E）
- 测量窗口：V1 上线后 30 天
- 统计口径：t_test_case 表中 status=Reviewed 且 test_type=E2E 的记录数
- 通过率：t_execution_result 中 passed / total

#### 替代指标 2：AI 生成用例人工采纳率

**原指标**："测试设计耗时缩短 80% 以上"（11-PRD L15）

**作废理由**：同上。

**建设型替代**：

> **Given** AI 生成 M 条设计用例（DesignTestCase）
> **When** 工程师完成评审并执行
> **Then** AI 生成用例人工采纳率 ≥ 60%
> **采纳定义**：DesignTestCase.status 从 DRAFT 迁移为 APPROVED，且 30 天内未 Deprecated

**测量方法**：
- 基线：0（无历史数据）
- 测量窗口：V1 上线后 60 天
- 统计口径：t_design_test_case 中 status=APPROVED 且未在 30 天内 Deprecated 的记录数 / 总生成数
- 分层统计：按需求文档类型（功能需求/接口需求/业务规则）分别统计

#### 替代指标 3：失败定位可用性

**原指标**："AI 失败分类 15 秒内完成 + 降低 80% 排查时间"（14-PRD L9）

**作废理由**：基线≈0（无现有排查流程），"降低 80%"无从谈起；15 秒 SLA 无 LLM 推理时延论证。

**建设型替代**：

> **Given** 测试执行产生 K 条失败记录（K ≥ 10）
> **When** AI 执行 RCA 分析
> **Then** 失败定位可用性达标：AI 给出 RCA 假设且工程师确认可操作 ≥ 70%
> **可操作定义**：工程师在 RCA 结果上标记"可操作"（能指导下一步排查）

**测量方法**：
- 基线：0（无现有 RCA 流程）
- 测量窗口：V1 上线后 60 天
- 统计口径：t_failure_analysis 中 engineer_feedback=actionable 的记录数 / 总 RCA 数
- 注：不要求 15 秒 SLA，改为"AI 给出假设的时间 ≤ 60 秒"（P95）

#### 替代指标 4：交付可见性

**原指标**："CI 回归时间缩短 60% 以上"（18-PRD L9）

**作废理由**：基线≈0（无现有回归流程），"缩短 60%"无从谈起。

**建设型替代**：

> **Given** 每次代码发布（Git tag 或 MR merge）
> **When** QualityForge 执行回归测试
> **Then** 交付可见性达标：每次发布有机器生成的质量报告（覆盖率/通过率/风险）
> **报告内容**：覆盖率（需求覆盖率 + 接口覆盖率）、通过率、失败分类统计、风险评估

**测量方法**：
- 基线：0（无现有质量报告）
- 测量窗口：V1 上线后 90 天
- 统计口径：t_test_report 中有完整覆盖率字段的记录数 / 总发布次数
- 注：不要求"缩短 60%"，改为"每次发布有报告"（从 0 到 1）

**每条指标的基线=0 测量起点与统计窗口**：

| 指标 | 基线 | 测量起点 | 统计窗口 |
|---|---|---|---|
| E2E 覆盖数 | 0 | V1 上线日 | 30 天 |
| AI 采纳率 | 0 | V1 上线日 | 60 天 |
| 失败定位可用性 | 0 | V1 上线日 | 60 天 |
| 交付可见性 | 0 | V1 上线日 | 90 天 |

## 2. Build vs Buy 专章（维度含于 D5）

**评分：B+**（分析完整，结论有条件成立）

### 2.1 三方案对比表

| 维度 | 自建 QualityForge | 开源组装（Playwright + pytest + LLM API） | 商业工具（mabl/Testim/Functionize） |
|---|---|---|---|
| **初始成本** | 高（3-5 人 × 12 个月） | 低（$0 + LLM tokens） | 中（$499-$1,199/月） |
| **维护成本** | 高（持续开发） | 中（社区维护 + 自定义） | 低（厂商维护） |
| **AI 能力深度** | 高（需求→用例→RCA 全链路） | 低（仅执行层，无需求理解） | 中（UI 自愈，无需求理解） |
| **数据私有** | ✅ 完全私有 | ✅ 完全私有 | ⚠️ 依赖厂商（SOC 2 认证） |
| **与内部系统集成** | ✅ 深度定制 | ⚠️ 需自行开发 | ⚠️ 有限集成 |
| **需求→用例生成** | ✅ 核心能力 | ❌ 无 | ❌ 无 |
| **RCA 根因分析** | ✅ 核心能力 | ❌ 无 | ⚠️ 有限（日志分析） |
| **知识沉淀闭环** | ✅ 核心能力 | ❌ 无 | ❌ 无 |

**商业工具事实**（来源：[Fora Soft 2026 AI Testing Buyer's Guide](https://www.forasoft.com/blog/article/ai-testing-optimization)）：

| 工具 | 定位 | 价格（2026） | 私有部署 |
|---|---|---|---|
| mabl | All-in-one UI/API/mobile | ~$499/月 Starter, $1,199/月 Pro, $40k+/年 Enterprise | ❌ 未核实 |
| Testim (Tricentis) | Salesforce, enterprise web | Free tier + quote | ❌ 未核实 |
| Functionize | Fast-changing SPA UIs | Quote | ❌ 未核实 |
| QA Wolf (managed) | "Coverage in 8 weeks" | $60k-$250k/年 | ❌ 托管服务 |
| Playwright MCP + Stagehand | OSS hybrid | $0 + LLM tokens | ✅ 完全私有 |

**关键发现**：
1. **商业工具无"需求→用例"能力**：mabl/Testim/Functionize 均为 UI 执行层工具，无需求理解和用例生成能力。QualityForge 的核心差异化（需求→用例→RCA 全链路）在商业工具中无对标。
2. **开源组装无 AI 深度**：Playwright + pytest + LLM API 直调仅覆盖执行层，无需求解析、用例生成、RCA 分析。
3. **数据私有是硬约束**：内部工具要求数据不出域，商业工具的 SaaS 模式不满足（除非私有部署，但未核实）。

### 2.2 结论

**判定**：**自建 QualityForge**，但需满足以下成立条件：

1. **AI 深度定制是核心诉求**：需求→用例→RCA 全链路是商业工具无法提供的，这是自建的核心价值。
2. **数据私有是硬约束**：内部工具要求数据不出域，排除 SaaS 商业工具。
3. **3-5 人团队可承载 V1**：V1 核心闭环（需求→用例→执行→RCA）在 3-5 人 × 3 个月内可行（见维度 4 工作量估算）。

**结论翻转条件**（什么情况下应改为 Buy/开源组装）：

| 条件 | 翻转方向 |
|---|---|
| AI 深度定制不是核心诉求（仅需 UI 执行） | → 商业工具（mabl/Testim） |
| 数据私有不是硬约束（可接受 SaaS） | → 商业工具 |
| 3-5 人团队无法保障（资源 <3 人） | → 开源组装（Playwright + LLM API） |
| V1 核心闭环无法在 6 个月内完成 | → 开源组装 + 逐步增强 |

## 4. AI 能力可信度（维度 3，产品视角）

**评分：C+**

### 4.1 审计发现翻译为用户信任后果

**B-4：6 种 AI 阈值散落无校准**（L4-002）

**产品后果**：工程师面对"0.85 置信度"的用例，无法判断它到底对不对。阈值无校准意味着 0.80 和 0.85 的差异无依据，纯粹是拍脑袋。用户信任无法建立。

**B-5：LLM 输出无外部 oracle**（L4-007）

**产品后果**：AI 生成用例后，无非 LLM 的客观验收手段，陷入"AI 自评 AI"循环。工程师无法独立验证 AI 输出，只能选择"全信"或"全不信"。

**C-5：AI 正确性评测协议完全缺失**（L4-004）

**产品后果**：RCA 分类准确率、聚类纯度、TIA Recall 均无定义、无标注集。工程师无法知道"AI 的 RCA 有多准"，只能凭感觉判断。

### 4.2 L2 介入点在单人定位下的 HITL 悖论

**12 个 AI 介入点默认级别**（21-降级矩阵）：

| 介入点 | 默认级别 | 单人场景下的 HITL 问题 |
|---|---|---|
| Workspace 系统扫描与知识图谱生成 | L2 | 生成者与审批者是同一人 |
| Test Design 需求分析与用例生成 | L2 | 同上 |
| Test Design 覆盖率补齐 | L2 | 同上 |
| Test Asset 用例优化与重构 | L2 | 同上 |
| Test Asset Locator 自愈 | L1 | 无 HITL（可逆 + 高阈值） |
| Execution 运行期异常检测 | L1 | 无 HITL（只读观测） |
| QI 失败根因分析与缺陷提交 | L2 | 生成者与审批者是同一人 |
| QI 发布风险预测与放行/阻断 | L2 | 同上 |
| Skill Center 自定义 Skill 生成与发布 | L2 | 同上 |
| Agent Center Multi-Agent 编排 | L1 | 无 HITL（编排过程可控） |
| Knowledge Center Pattern 沉淀 | L2 | 生成者与审批者是同一人 |
| CI/CD 智能选择与质量门禁 | L2 | 同上 |

**HITL 悖论分析**：

12 个介入点中 8 个默认 L2（需人工确认）。单人定位下，生成者与审批者是同一人，面临以下认知负担：

1. **自审偏差**：工程师审核自己触发的 AI 生成，倾向于"确认偏误"（confirmation bias），更容易通过而非驳回。
2. **审批疲劳**：高频 L2 介入点（如用例生成）会导致审批流于形式，工程师"无脑点通过"。
3. **责任模糊**：AI 生成错误时，工程师作为审批人承担责任，但实际未充分审核。

**修订建议**（以 21-AI介入点降级矩阵.md 为唯一事实源）：

| 介入点 | 现行默认 | 建议修订 | 理由 |
|---|---|---|---|
| Test Design 用例生成 | L2 | **L2 + 延迟生效** | 保留人工确认，但改为"生成后 24 小时生效"，降低即时审批压力 |
| Test Design 覆盖率补齐 | L2 | **L2 + 批量审批** | 允许批量审批（一次审批多条），降低审批频率 |
| QI RCA 与缺陷提交 | L2 | **L2 + 可选自动** | 高置信度（≥0.90）可自动提交，低置信度需确认 |
| Knowledge Pattern 沉淀 | L2 | **L1 + 定期审查** | 自动沉淀，每周定期审查，降低即时审批压力 |

**注**：不另立阈值，仅建议修订默认级别和审批语义。阈值校准（B-4）需独立解决。

### 4.3 置信度来源未定义 → 产品层最低要求建议

**现状**：12 个介入点均使用"Confidence Score"，但置信度如何计算、是否校准过、无文档说明。

**产品层最低要求**：

1. **置信度来源必须文档化**：每个介入点的置信度计算方法必须在 21-降级矩阵中明确（如"LLM 输出的 logit 归一化"/"多模型投票一致率"/"规则匹配得分"）。

2. **置信度必须有校准集**：每个介入点的阈值必须配校准集（≥50 条标注样本），否则阈值无依据。

3. **置信度必须对用户可见**：AI 输出时，置信度必须在 UI 中展示，且附带"置信度含义说明"（如"0.85 = 在 100 条类似样本中，85 条被人工确认为正确"）。

**Skill 审计时（2026-08-07）**：5/29 有 evals/ 目录（仅计顶层）。

### 4.5 PRD 通读补充发现（v1.1 新增，一手证据）

**发现 1：自治等级冲突是系统性的，不止 TestDesign 一处**

审计 C-3/L4-001 只点名 TestDesign。逐份通读后发现同类冲突共 3 处：

| 介入点 | 矩阵默认（21 号，权威） | 模块 PRD 实际写法 | 一手位置 |
|---|---|---|---|
| Test Design 用例生成 | L2（入库前须人工终审，21:27） | "Level-1 自动门槛 >0.80，可批量自动入库" | 11-PRD L255-259 |
| QI 失败根因分析 | L2（写 JIRA，21:32） | "Level 1（AI 自动模式）：置信度 ≥0.90，自动写入数据库" | 14-PRD L157 |
| Knowledge Pattern 沉淀 | L2（须专家审核后发布，21:36） | "Level 1（完全自主入库）：置信度 ≥0.95，自动入向量库" | 17-PRD L164 |

三处 PRD 都写了"阈值以 21 号矩阵为单一事实源"的引用声明（11-PRD L255、12-PRD L244），但**引用声明与实质冲突并存**——声明改了，L1 自动路径没删。产品后果：单人工程师遇到"AI 说置信度 0.91，系统自动入库/自动入向量库"时没有任何拦截点，错误资产静默进入正式库，事后只能靠 Deprecated 清理。

**修订建议**（仍以 21 号矩阵为唯一事实源）：三处 PRD 的 L1 自动路径全部改为"达到阈值 → 进入自审队列并标记高置信，工程师确认后生效"；是否上调为 L1 走矩阵既有的 opt-in 机制（单人场景下 = 工程师本人在设置中显式开启并自担风险），不在 PRD 中预设。

**发现 2：置信度输出契约四种写法，无一说明计算方法**

| 模块 | 字段名 | 一手位置 |
|---|---|---|
| Execution 劣化嗅探 | `confidenceScore` | 13-PRD L204 |
| QI RCA | `confidence` | 14-PRD L152 |
| CICD TIA | `confidence` | 18-PRD L185 |
| Knowledge Pattern | `confidence_score` | 17-PRD L160 |

四种字段名、零处计算方法定义。产品层最低要求（呼应 4.3）：统一字段名为 `confidence`，并在 21 号矩阵中为每个介入点补一句计算来源（logit 归一化 / 规则匹配得分 / 多模型一致率），否则前端展示"94.5%"只是装饰。

**发现 3：15 秒 SLA 被硬编码进 API 契约**

QI 触发分析的 API 响应示例直接写死 `"estimatedSeconds": 15`（14-PRD L194）。这意味着未经校准的 SLA 已经固化到前后端契约里，开发会照抄。修订建议：改为真实测量值或移除该字段。

**发现 4：PRD 示例中存在不可信的置信度数值，会误导开发**

13-PRD L189-205 的劣化嗅探示例：历史耗时 [45,52,49,41,50,48,55,47,53,50]ms，本次 380ms，输出 `"confidenceScore": 0.99` 并声称"超过 70 个标准差"。这是统计上荒谬的表述（样本标准差 σ≈4.1，380ms 偏离约 80σ，但"置信度 0.99"与"偏离几个 σ"是两回事，混为一谈）。示例即规格——开发会照着示例实现。修订建议：把示例中的置信度改为基于校准集的真实值，删除"70 个标准差"类表述。

**发现 5：0.95 双用——同一个数字，两个完全不同的概念（审计未指出）**

| 出处 | 原文 | 概念性质 |
|---|---|---|
| 17-PRD L9（模块目标） | "使 AI Agent 设计测试用例时的信息关联相关度达到 **95%** 以上" | 产品 KPI：RAG 检索质量，需用 Recall@K/NDCG/人工一致率对金标准集测量 |
| 17-PRD L164/L169（降级策略） | "完全自主入库：置信度 **≥ 0.95**，自动入向量库" | 自治阈值：模型自评得分，控制"要不要人工审" |

两者语义完全不同：前者是**检索系统的外部质量指标**（需要评测集才能知道是否达成），后者是**单次输出的自评分数**（模型自己说自己有多确定）。同一个 95% 出现在同一份 PRD 的目标与阈值里，制造了"已经有数字在管"的假象——读者容易误以为 L164 的阈值就是在落实 L9 的 KPI。审计 B-6 判 L9 的指标 AMBIGUOUS（L5-收益表指标 3），但没有指出它与自治阈值的同值混淆。

**修订建议**：KPI 改名为"RAG 检索命中率"并绑定评测集定义；阈值保留数值但必须标注计算方法（呼应发现 2）。两个 95% 必须拆开表述，禁止共用。

**发现 6：自治度与可验证性倒挂——Agent 0.88 是全平台最高自治、却是最难验证的输出（审计未指出）**

对照两条 L1 路径：

| 介入点 | 自治条件 | 输出如何被验证 |
|---|---|---|
| Locator 自愈（12-PRD L246，L1） | >0.92 自动合并 | **可逆 + 下次执行自动验证**（状态机 Healed→Verified，12-PRD §3.2）|
| Agent 自主编排（16-PRD L181，L1） | ≥0.88 完全自主，"循环执行思考-调用，直接呈现最后结论" | 结论无执行验证、无自动回滚；工程师只看到结论，除非主动翻 Trace |

两个问题：

1. **自治度倒挂**：按 21 号矩阵自己的判据（21:18），默认 L1 要求"可逆 + 置信度阈值兜底与自动回退，且影响范围限于单个资产"。Locator 自愈符合（单资产、可逆、执行验证）；Agent 自主 Tool-use 链可能跨多个资产写操作、无自动回退，按判据不够格默认 L1——但矩阵 L35 给了 L1，16-PRD L181 进一步把 0.88 定为完全自主线。对比 TestDesign 用例入库（单资产、可逆）反而要求 L2 人工终审：**动作越可控越要人审，输出越难验证反而越自主**。

2. **16-PRD 内部自相矛盾**：L181 说 ≥0.88"完全自主决策所调用的 Tool，直接呈现最后结论"；L182 说写操作要"弹窗确认"——但确认条款只写在 [0.75, 0.88) 的 L2 档里。**≥0.88 的 L1 档没有写操作确认保护**：置信度越高，保护越少，方向正好反了。

**产品问题**（单人场景下尤其尖锐）：Agent 的"最终结论"是全平台最难独立验证的 AI 输出（对比 RCA 至少还有 14-PRD §5.2 的 I/O 契约和 Trace 证据链），单人工程师没有第二个大脑去复核。修订建议：Agent 的 L1 限定**只读 Tool 链**（查询、拉日志、读代码）；任何含写操作 Tool 的编排，无论置信度多高，强制 L2 确认——把 L182 的保护条款上移到所有档位。

**发现 7：单人场景下真正有价值的 AI 设计（应保留的亮点）**

- 11-PRD §3.3 的 DesignTestCase→TestCase 字段映射表（含 confidence_score 保留至 generatedConfidence，为 B-5 oracle 留了数据基础）——设计完整，保留
- 13-PRD §8 的"Execution 采集与打标，QI 诊断与归因"职责边界声明——全平台罕见的清晰去重，保留
- 14-PRD §5.2 的 RCA I/O 契约（错误信息+堆栈+gitDiff+日志 → 根因+建议+置信度）——全平台最具体的 AI I/O 规范，保留
- 12-PRD Locator 自愈三档阈值（>0.92 自动 / 0.80-0.92 确认 / 连续 3 次失败降级）——审计 L2 已评为最佳实践，保留

## 6. ROI 与投入产出（维度 5）

**评分：C+**

### 6.1 诚实框架

**D8 基线**：测试现状基本空白，从零建设（无正式 E2E，手工探索 + 少量接口脚本）。

**ROI 叙事**：基线≈0，ROI 不是"节省现有工时"，而是**质量风险可见化 + 未来效率**。

| ROI 维度 | 基线 | 建设型价值 |
|---|---|---|
| 测试覆盖率 | 0（无 E2E） | 从 0 到 N 条 E2E 用例，质量风险可见化 |
| 失败排查 | 手工探索 | AI 给出 RCA 假设，排查效率提升 |
| 交付可见性 | 无质量报告 | 每次发布有机器生成质量报告 |
| 知识沉淀 | 无 | 失败模式沉淀为可复用知识 |

### 6.2 投入侧

**工作量估算**（维度 4）：
- V1：~15 PM（3-5 人 × 3 月）
- V2：~15 PM（3-5 人 × 3 月）
- V3：~10 PM（按需引入）
- **总计**：~40 PM（3-5 人 × 12 月）

**人力成本估算**（按内部成本，非市场价）：
- 假设每人月内部成本 = C
- 总投入 = 40 × C

**持续运营成本：LLM Token 是单人内部工具唯一的持续 OPEX（v1.1 新增，审计未指出）**

人力投入是一次性的（40×C），但 Token 成本随使用量**永续发生**——每次需求解析、用例生成、RCA、RAG 检索都消耗 Token。这是 QualityForge 与开源组装路线（Playwright + pytest，零 Token）的核心成本差异，也是 Build vs Buy 判定的长期变量。三个事实：

1. **PRD 已设计了对的机制，但排错了优先级**：19-PRD 的 Token Router（§5.1，按任务复杂度在 Sonnet/廉价模型间路由，L171 示例"剩余预算 $4.50 时选 DeepSeek"）和成本统计（§2 功能清单 L23）方向正确，但成本统计标 **P2**——单人工程师没有运维团队替他盯预算，Token 超支是他唯一的持续现金流出，成本管控应该是 P0。
2. **行业参照**：agentic 测试流程的 Token 消耗约为确定性脚本的 4 倍（Fora Soft 2026 指南），且 agentic MCP 套件可达 $10-50/天/环境。QualityForge 的 12 个 AI 介入点中多数走 LLM 推理，单人场景下若无路由和预算控制，月均 Token 成本可能超过工具本身的价值。
3. **ROI 修正**：上表"总投入 = 40×C"不完整，完整形式是 `40×C + Σ(月度 Token 成本 × 使用月数)`。Token Router 的 P0 化不是锦上添花，是 ROI 成立的必要条件。

**修订建议**：Token 成本统计与预算熔断（月预算 80% 告警、100% 降级为仅规则兜底）升为 V1 P0；20-NFR L151 的"租户 Token 额度预警"（原本面向多租户）改造为单人预算告警，正好消化裁剪清单 #1 移除 RLS 后空出来的治理能力。
