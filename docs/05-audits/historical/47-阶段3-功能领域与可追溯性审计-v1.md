# QualityForge 阶段 3：功能、领域模型与可追溯性审计 v1.0

> 日期：2026-07-30  
> 重点链路：需求 → Testing IR → 策略 → 场景 → 用例 → 断言 → 覆盖 → 人工批准 → 正式资产  
> 当前裁决：`CONTRACT_REBASE_REQUIRED`

## 一、执行摘要

项目存在两套尚未统一的需求设计模型：

1. 产品/技术文档模型：`RequirementDocument → TestPlan → TestScenario → TestCase`；
2. Skill 原型模型：`Source → Requirement/BusinessRule/StateMachine → Strategy → Scenario → Case → Assertion → Verification → Coverage → HITL`。

第二套模型更接近当前推荐的“可信测试资产”价值主张，但它尚未进入术语表、核心领域模型、数据库 Schema 和 OpenAPI。结果是：原型已经能够检查来源、规则、状态和有效断言，正式产品契约却无法存储和查询这些证据。

当前不建议继续扩展更多模块接口；应先完成核心价值链的契约重新基线。

| 环节 | PRD | 领域/数据库 | API | Skill/验证 | 结论 |
|---|---|---|---|---|---|

| 冲突/歧义保留 | 无完整流程 | 无 | 无 | Requirement Compiler/IR Validator 支持 | 产品契约缺失 |

## 三、关键跨文档冲突

### C1：需求文档状态不一致

- Test Design PRD：`PENDING / PARSED / FAILED`；
- 核心领域、数据库和 OpenAPI：`Draft / Parsing / Completed / Failed`。

影响：前后端、任务状态和失败重试无法使用同一状态机。

### C2：草稿用例与正式用例模型冲突

- Test Design PRD 定义 `DesignTestCase`，状态为 `DRAFT / GENERATING / REVIEWING / APPROVED`；
- 核心领域只有 `TestCase`，状态为 `Draft / Reviewed / Deprecated`；
- 数据库没有 `DesignTestCase` 表；
- `/test-designs/cases` API 直接使用正式 `TestCase` Schema。

影响：无法清楚表达 AI 生成中、待人工审查、被驳回、批准发布和正式资产版本之间的关系；批量批准可能只是修改同一记录，也可能跨服务复制，但契约没有裁决。

### C3：需求到测试方案的关系丢失

- Test Design PRD 的 `TestPlan` 包含 `requirement_id`；
- 核心领域和数据库的 `TestPlan` 没有 Requirement 外键。

影响：无法从测试方案反查来源需求，也无法可靠计算需求覆盖。

### C4：现有“覆盖率”没有正式领域语义

PRD 只描述 Swagger 接口和需求节点覆盖率；Skill 原型定义规则、场景、状态和有效断言四维覆盖。正式领域模型没有 `CoverageReport`、覆盖项、阈值版本或 Gate Decision。

影响：页面显示的覆盖率可能无法解释分子、分母、缺口和统计版本，容易形成“覆盖率幻觉”。

### C5：断言没有独立生命周期

正式模型把预期结果嵌入 `TestCase.expectedResults`；Skill 原型将 Assertion 独立生成、静态检查、绑定规则并进行变异验证。

影响：无法区分“写了预期结果”和“该断言具有真实缺陷检测能力”，也无法保存 `PASS / REPAIR / REJECT` 证据。

### C6：Human-in-the-loop 只有动作，没有审计实体

产品 API 有批量审批，但没有 `ReviewTask`、审批策略版本、审阅人、审阅意见、修改差异、决策原因和 SLA。Skill Gatekeeper 已要求这些内容，但没有正式存储契约。

影响：无法证明高风险资产由谁基于什么证据批准，AI 质量也无法通过人工反馈校准。

### C7：事件只被命名，没有事件契约

`batch-approve` 声称触发 `TestCaseApproved`，但未发现事件 Schema、版本、幂等键、发布原子性、失败补偿或消费者约束。

影响：审批成功但资产入库失败、重复消费或部分发布时缺少确定处理方式。

## 四、现有 OpenAPI 与数据基线检查

新鲜解析结果：

- `32-API规范.yaml` 可被 YAML 解析；
- OpenAPI 版本为 `3.0.0`；
- 定义 88 个路径、37 个 Schema；
- Test Design 已有上传、列表、解析、草稿用例编辑和批量审批端点。

但核心可信链仍缺少：

- Requirement Source/Slice API；
- Conflict/Ambiguity API；
- Testing IR 查询、版本和人工修订 API；
- Business Rule/State Machine API；
- Strategy Contract API；
- Scenario 生成、查看和审核契约；
- Assertion 及验证证据 API；
- Coverage Report/Gate API；
- Review Task 和决策 API；
- 发布前预检与幂等发布 API。

因此，“OpenAPI 路径很多”不能说明核心价值链契约完整。

## 五、推荐领域模型重新基线

### 5.1 聚合边界

```text
Workspace
└── RequirementSet
    ├── SourceDocument
    ├── SourceSlice
    ├── Requirement
    ├── BusinessRule
    ├── Constraint
    ├── StateMachine / Transition
    ├── Conflict
    └── TestingIRVersion

DesignRun
├── StrategyContract
├── Scenario
├── DraftCase
├── Assertion
├── GenerationEvidence
└── ModelInvocation

QualityGateRun
├── ValidationFinding
├── AssertionVerification
├── CoverageSnapshot
├── GateDecision
└── MissingCoverageItem

ReviewBatch
├── ReviewTask
├── ReviewDecision
├── AssetDiff
└── AuditEvent

PublishedAssetSet
├── TestCaseVersion
├── ExportPackage
└── ProvenanceSnapshot
```

### 5.2 必须保持的追溯边

```text
SourceDocument CONTAINS SourceSlice
SourceSlice SUPPORTS Requirement/BusinessRule/Constraint
Requirement REALIZED_BY BusinessRule
BusinessRule DERIVES Scenario
Scenario COVERED_BY DraftCase
DraftCase VERIFIED_BY Assertion
Assertion HAS_VERIFICATION AssertionVerification
StrategyContract SETS_THRESHOLD CoverageSnapshot
ReviewDecision APPROVES PublishedAssetSet
PublishedAssetSet SNAPSHOTS 全部来源与生成证据
```

任何正式用例必须能反向追溯到来源切片；没有来源的 AI 内容只能作为建议，不能作为已确认规则。

## 六、状态机建议

### 6.1 RequirementSet

```text
DRAFT → PARSING → NEEDS_REVIEW → READY
               ↘ FAILED
READY → SUPERSEDED
```

存在冲突、歧义或缺失来源时进入 `NEEDS_REVIEW`，不得伪装为解析完成。

### 6.2 DesignRun

```text
QUEUED → GENERATING → VALIDATING → REVIEW_PENDING
                     ↘ GATE_FAILED
REVIEW_PENDING → APPROVED → PUBLISHED
REVIEW_PENDING → REJECTED → GENERATING
```

### 6.3 Asset

建议分离 `DraftCase` 和 `TestCaseVersion`。草稿批准后生成不可变的正式版本，而不是把同一行从 Draft 改为 Reviewed。这样可以保留生成前后差异、审批证据和回滚能力。

## 七、功能需求重写要求

每个核心功能应补充统一需求卡：

| 字段 | 要求 |
|---|---|
| 用户与触发 | 谁在什么条件下启动 |
| 前置条件 | Workspace、输入、权限和数据状态 |
| 主流程 | 明确到可观察状态变化 |
| 分支/异常 | 冲突、失败、重试、撤销、降级 |
| 输入/输出契约 | 结构、必填项、版本和大小限制 |
| 业务规则 | 确定性规则与 AI 建议分离 |
| 权限 | 创建、修改、批准和发布主体 |
| 幂等与并发 | 重复点击、并行生成、版本冲突 |
| 可追溯性 | 来源、父链、模型、Prompt、审核记录 |
| 验收标准 | Given/When/Then 和量化阈值 |
| 可观测性 | 事件、耗时、错误、成本、用户修改 |

## 九、整改顺序

1. 将 Testing IR、Business Rule、Assertion、Coverage、Review 概念纳入术语表；
2. 裁决 `DesignTestCase` 与 `TestCase` 的草稿/正式关系；
3. 冻结核心追溯图和 ID 规则；
4. 统一 Requirement、DesignRun、Asset 状态机；
5. 以核心链重写领域模型；
6. 同步数据库 Schema；
7. 同步 OpenAPI 和事件契约；
8. 用固定样本重跑 IR→Coverage→HITL；
9. 验证数据库、API 和导出产物均能重建同一追溯图；
10. 通过后再扩展 UI、Execution、RCA 和 CI/CD。

## 十、阶段结论

### 已验证

- 现有 OpenAPI 文件可解析，包含 88 个路径和 37 个 Schema；
- 正式领域模型包含 38 个实体，但不包含 Testing IR、Business Rule、Assertion、Coverage Report 和 Review Task；
- 当前数据库同样缺少这些核心可信链实体；
- Skill 原型已经使用这些概念，并能输出四维覆盖门禁；
- 当前 E2E Coverage 结果为 `GATE_FAILURE`。

### 推断

- 当前最大设计风险不是功能数量不足，而是“正式产品契约落后于已形成的质量方法”；
- 如果直接按现有 OpenAPI 和数据库研发，最终产品会退化成 AI 生成用例加人工批量审批，无法实现其宣称的可追溯和质量治理优势。

### 裁决

`CONTRACT_REBASE_REQUIRED`

核心领域、数据库、API、事件和 Skill 输出必须先统一为一条可重建的追溯链。完成前，不建议将阶段 3 判定为设计通过。
