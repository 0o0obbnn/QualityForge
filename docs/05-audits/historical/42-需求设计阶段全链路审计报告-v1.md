# QualityForge 需求设计阶段全链路审计报告 v1.0

> 审计日期：2026-07-29  
> 审计阶段：需求设计阶段、开发准入前  
> 审计方式：资料全量盘点、跨文档静态检查、结构化契约检查、关键链路走查、现有验证资产重放、外部标准印证  
> 变更边界：本报告只记录事实、推断、风险与建议；未修改任何现有设计文档、Skill、数据或验证结果。

## 一、执行结论

### 1.1 准入结论

**当前结论：HOLD（暂缓按现有范围全面进入 V1 开发），允许继续开展受控原型、用户验证和 P0 设计整改。**

这不是因为项目缺少技术设计。恰恰相反，QualityForge 已经具备较丰富的领域模型、数据库、API、鉴权、非功能、AI 降级以及测试流水线资产。当前主要问题是：

1. **产品和交付约束没有成为技术设计的输入**：内部工具、企业平台、商业 SaaS 三种语境仍并存，团队、预算、真实负载、使用规模和长期 Owner 未形成现行基线。
2. **V1 范围与证据成熟度倒挂**：V1 在 1–3 个月内涉及全部 9 个模块，但没有人员配置、周级里程碑、业务验收指标和风险缓冲。
3. **AI 治理“有阈值、缺测量”**：文档定义了大量置信度阈值和 L1/L2/L3 降级规则，但没有统一的置信度计算、校准、Golden Set、误报/漏报成本和版本回归标准；跨文档阈值仍有差异。
4. **新增 Skill 流水线与顶层架构脱节**：仓库已有 29 个 Skill、Testing IR、Traceability Graph 和 E2E 验证资产，但顶层 01–37 号设计文档没有纳入这些核心概念，现行系统架构无法解释当前资产。
5. **部分关键契约仍不具备直接开发条件**：OpenAPI 的路径覆盖完整，但鉴权声明、错误响应、请求/响应模型边界和 `operationId` 仍存在开发级缺口。
6. **多租户与 AI 安全仍有系统性漏洞**：RLS 设计较深入，但跨租户外键一致性没有数据库级保证；AI 侧未形成提示注入、知识投毒、供应商数据处理和敏感信息泄露的威胁模型。

### 1.2 允许与禁止的工作

当前允许：

- 用户访谈、现状基线采集、产品定位裁决；
- 选择一条核心价值链做原型或 PoC；
- AI Golden Set、评测框架和人工反馈闭环建设；
- 修复 P0/P1 契约、安全和文档基线问题；
- 模块化单体与微服务的可逆技术验证。

当前不建议：

- 按 9 模块 V1 范围同时启动全面开发；
- 将 20 号 NFR 目标直接作为对外 SLA；
- 将模型自报置信度直接作为自动入库、提单或发布门禁依据；
- 依据旧审计报告的“已修复”统计跳过当前版本回归；
- 把现有 E2E 样例标记为全链路验收通过。

## 四、P0 阻塞项

### P0-01：产品定位与运行约束未形成单一事实源

**状态：已验证。**

证据：

- [02-PRD总纲.md](../../01-product/02-PRD总纲.md) 将平台定义为 AI 原生端到端测试平台，并声明“用户只有一个：测试工程师”；
- [20-非功能需求.md](../../03-governance/20-非功能需求.md) 明确按多租户企业级平台设计；
- [41-内部工具评估报告-v1.md](./41-内部工具评估报告-v1.md) 又以“单组织内部工具、不商业化”为核心前提；
- 当前活跃产品文档未正式记录目标租户数、用户数、项目数、数据敏感级别、部署方式、团队人数和长期维护 Owner。

影响：无法判定多租户 RLS、7 个服务、K8s/KEDA、Vault、RabbitMQ、Jaeger/Langfuse、Skill 沙箱究竟是必要控制还是过度设计。

整改准入条件：新增一份产品与运行约束基线，至少裁决产品类型、用户规模、并发、数据边界、部署形态、团队、预算、上线周期和演进触发条件。

### P0-02：V1 范围缺少资源与业务验收闭环

**状态：已验证。**

[22-MVP版本规划v2.0.md](../../03-governance/22-MVP版本规划v2.0.md) 在 1–3 个月 V1 中安排了全部 9 个模块。虽然每个模块做了范围裁剪，但当前没有：

- 人员数量和角色配置；
- 周级里程碑与关键依赖到位日期；
- 现有工具迁移策略；
- 真实项目接入目标；
- AI 用例采纳率、RCA 准确率、排障耗时下降等业务验收；
- 延期或 AI 效果不达标时的范围退出机制。

整改准入条件：V1 收敛为一条可度量核心价值链，并形成“范围—人员—时间—依赖—验收—退出”计划。

推荐候选闭环二选一：

1. 需求材料 → Testing IR → 场景/用例草稿 → 人工评审 → 正式资产；
2. 执行结果 → 失败聚类/RCA → 人工核实 → 知识沉淀。

### P0-03：现有 Skill 流水线未进入系统级设计基线

**状态：已验证。**

顶层 01–37 号 Markdown 中，对以下关键词的直接引用均为 0：`Testing IR`、`Traceability Graph`、`requirement-compiler`、`ir-validator`、`scenario-generator`、`assertion-verifier`、`coverage-analyzer`、`hitl-gatekeeper`。

但这些概念已经成为 29 个 Skill 中多个核心能力的事实架构，例如：

```text
Source → Testing IR → IR Gate → Strategy → Scenario Graph
       → Test Case → Assertion → Verification → Coverage Gate
       → Plan / HITL / Governance
```

影响：开发者无法从现行产品、架构、领域、API 和数据文档推导出 Skill 流水线；现有 38 实体、43 张表、149 个 API 也没有承载 Testing IR、Traceability Graph、Gate Decision 和 Strategy Contract 的明确模型。

整改准入条件：裁决该流水线是正式产品架构、实验资产还是未来版本资产；若为正式架构，必须同步更新产品地图、领域模型、架构图、数据模型、API、事件、权限和 MVP。

### P0-04：AI 置信度与自主级别不可验收，且仍存在跨文档差异

**状态：已验证。**

优点：21 号矩阵已经确立 safe-by-default 和高后果动作默认 L2 的正确方向。

缺口：

- 未定义置信度来源：模型自报、规则校验、分类器概率还是多模型一致性；
- 未定义校准数据集、分桶可靠性、误报/漏报成本和版本回归；
- 未定义模型切换后阈值是否重校准；
- 未定义按租户、领域、语言、任务类型的阈值差异；
- `21` 与模块 PRD 仍存在 Execution 0.85/0.80、QI 0.85/0.90、Agent 0.85/0.88、Knowledge 0.85/0.95、CI/CD 0.90/0.80 等口径差异；
- Workspace 与 TestDesign 的模块 PRD 仍存在“高置信度自动写入”描述，与全局默认 L2 的运行时语义容易冲突。

整改准入条件：建立任务级评测规范；阈值必须来源于校准数据和风险成本，不能由文档作者直接指定。

### P0-05：多租户引用完整性没有数据库级闭环

**状态：已验证；若最终为单组织内部工具，可在定位裁决后降级。**

[33-数据库Schema设计.md](../../04-architecture/33-数据库Schema设计.md) 共有 43 张表：38 张 `tenant_id NOT NULL`、3 张 `tenant_id` 可空、2 张没有 `tenant_id`。文档 §4.2 仍写“36 张纯租户表”，统计已经漂移。

核心风险：

- `t_test_suite_case_mapping` 没有 `tenant_id`，不会被当前动态 RLS 逻辑覆盖；
- 多数表同时保存 `tenant_id` 和 `workspace_id`/父实体 ID，但外键只约束单列 ID，没有保证父子记录属于同一租户；
- 例如 `t_environment(tenant_id, workspace_id)`、`t_test_case(tenant_id, workspace_id, scenario_id)` 可以在数据库层形成跨租户引用；
- RLS 限制的是当前行可见性，不等价于保证引用目标与当前行具有相同 `tenant_id`。

整改准入条件：采用复合外键、租户一致性触发器或取消子表冗余租户列并通过不可伪造父链归属；关联表必须明确 RLS/租户校验策略，并增加跨租户插入测试。

### P0-06：AI 特有安全与数据治理威胁模型缺失

**状态：已验证。**

现行 01–37 号设计文档未覆盖：提示注入、间接提示注入、知识/RAG 投毒、模型供应链、训练/保留政策、数据驻留、删除权、DLP、供应商数据使用边界。

QualityForge 会读取 PRD、Swagger、日志、Trace、Git Diff、Jira 和知识库，这些都是不可信外部内容；Agent 又能调用 Skill、写资产、提缺陷和影响发布门禁，间接提示注入的后果较高。[OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)明确指出，来自文件、网页等外部来源的间接提示注入可能导致未授权行为和敏感信息泄露；[NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)也要求将用途、用户、部署环境、风险容忍度与 TEVV 指标一起文档化。

另外，当前多份文档将完整 CoT/思维链记录和展示作为 P0 能力。建议改为：

- 可审计决策摘要；
- Tool 调用、参数摘要和输出引用；
- 证据来源与模型版本；
- 策略命中、授权与人工确认记录；
- 敏感字段脱敏后的提示和响应摘要。

不应把供应商不可稳定提供、且可能扩大信息泄露面的原始隐藏推理作为产品契约。以 OpenAI 当前接口为例，正式提供了可配置的 [reasoning summary](https://platform.openai.com/docs/api-reference/responses-streaming/response/output_item) 事件与字段，产品应以供应商可支持的摘要/审计事件做兼容抽象，而不是假定所有模型都能返回同一种原始 CoT。

整改准入条件：完成 AI 数据流图和威胁模型，建立不可信内容隔离、最小权限 Tool、输出验证、高危动作人工确认、提示/响应脱敏和供应商数据治理控制。

## 五、P1 严重问题

### P1-01：API 总览与 OpenAPI 的鉴权契约存在 5 处硬冲突

**状态：机器检查已验证。**

| 操作 | 37 号总览 | 32 号 OpenAPI 实际 |
|---|---|---|
| `POST /executions/tasks/run` | JWT / API Key | 仅继承 Bearer |
| `GET /executions/tasks/{taskId}/status` | JWT / API Key | 仅继承 Bearer |
| `POST /skills/{id}/invoke` | JWT / API Key | 仅继承 Bearer |
| `POST /settings/runners/register` | JWT / Runner Token | 仅继承 Bearer |
| `POST /settings/runners/heartbeat` | Runner Token | 仅继承 Bearer |

影响：前后端、Runner 和 CI 客户端会根据不同文档实现不同认证方式；生成客户端也会得到错误契约。

### P1-02：OpenAPI 达到路径覆盖，但未达到开发级契约成熟度

**状态：机器检查已验证。**

已验证优点：

- YAML 可由 `yaml.safe_load` 解析；
- 88 个 path、149 个 operation、37 个 schema；
- 37 号总览与 32 号 YAML 双向操作差集为 0；
- 427 个 `$ref` 均可解析到已定义 Schema；
- 路径参数名称无错位。

缺口：

- 149 个 operation 全部缺少 `operationId`；
- 68 个 operation 没有任何 4xx、5xx 或 default 响应；
- 37 个 Schema 中只有 1 个声明 `required`；
- 没有 Schema 使用 `additionalProperties: false`；
- 33 个 POST/PUT/PATCH 直接复用领域/响应实体作为请求体，容易产生只读字段回写和 over-posting；
- 当前环境未安装正式 OpenAPI 规范校验器，因此只完成 YAML、引用、路径参数和自定义规则检查，标准级校验仍待补。

整改：拆分 Create/Update/Response DTO，补 required、格式、长度、枚举、错误响应、operationId，并在 CI 加入 OpenAPI lint/validation 和 breaking-change 检查。

### P1-03：现有 E2E 验证样例没有通过最终覆盖门禁

**状态：2026-07-29 新鲜重放已验证。**

重放结果：

- Testing IR 验证：PASS；
- 场景图验证：PASS；
- 正常用例契约：PASS；
- 孤儿用例复现：按预期 REJECT；
- 断言静态检查：PASS；
- 最终覆盖：`GATE_FAILURE`。

门禁失败数据：

| 维度 | 实际 | 阈值 | 缺口 |
|---|---:|---:|---:|
| 规则覆盖 | 75% | 100% | 25% |
| 场景覆盖 | 33.3% | 70% | 36.7% |
| 状态迁移覆盖 | 25% | 90% | 65% |
| 断言有效覆盖 | 100% | 85% | 通过 |

结论：该样例很好地证明“门禁能够拒绝不完整覆盖”，但不能证明全流程已经验收通过。

### P1-04：核心需求缺少统一、可追踪的验收合同

模块 PRD 普遍包含功能清单、数据表、用户路径、AI 介入、API 摘要和错误处理，这是明显优点。但缺少统一的：

- Requirement ID / Rule ID；
- 来源与变更记录；
- 前置条件和范围外说明；
- Given/When/Then 或等价可执行验收；
- 业务 KPI 与质量阈值；
- 需求 → API → Schema → 测试的追踪关系；
- Owner 与批准人。

现有 Testing IR/Traceability Graph 资产正好可以承担这一层，但尚未进入正式设计。

### P1-05：NFR 目标缺少负载与成本模型

20 号文档已经正确声明性能数字是待压测的设计目标，不是已验证 SLA。但仍缺少：

- 用户/租户/项目规模模型；
- API/UI 用例平均耗时和数据量；
- Runner 节点规格、网络、浏览器资源模型；
- 峰值持续时间、队列容忍时间和降级策略；
- LLM 输入输出 Token 分布、缓存命中和单任务成本；
- 截图、录像、日志、Trace 的保留期与存储预算；
- RTO/RPO、备份和恢复验收。

没有这些输入，50,000 API 并发、3,000 UI 并发等目标不能用于容量设计。

### P1-06：正式 Skill 评测覆盖不足

29 个 Skill 均有可执行 Python 校验脚本，脚本语法检查全部通过，这是良好基础。但只有 3 个 Skill 有正式 eval manifest；其余多数只有输入样例或校验夹具。

整改：每个 V1 Skill 至少建立正常、缺字段、越权、冲突、低置信度、提示注入、资源超限和版本漂移测试；生成型 Skill 还需 Golden Set、人工评分 rubric、稳定性和成本指标。

## 六、P2 一般问题

### P2-01：仍有命名与示例残留

### P2-02：历史报告存在 14 个失效本地链接

## 七、关键链路追踪结果

### 7.1 需求到测试资产链路

```text
需求文档 → 规则/领域/状态 → Testing IR → 场景 → 用例
         → 断言 → 验证 → 覆盖门禁 → 正式资产
```

判断：Skill 资产已形成较强的后半段治理逻辑，但正式 PRD 只描述“上传需求、AI 解析、生成用例、人工评审”，没有把 Testing IR、冲突裁决、来源追踪和覆盖门禁定义为系统行为。链路在“产品需求 ↔ Skill 事实架构”处断裂。

### 7.2 执行到质量分析链路

```text
执行计划 → ExecutionTask → Runner → ExecutionResult
         → TestReport → FailureCluster/Analysis → 人工核实/Jira
```

判断：领域、Schema、REST、WebSocket 和 Execution/QI 职责边界相对完整；主要风险是 API 鉴权差异、错误契约不足、AI RCA 验收缺失以及 Jira 高后果写入的安全控制需要落到 API/权限/审计合同。

### 7.3 CI/CD 发布门禁链路

```text
Git 变更 → TIA → 用例选择 → 执行 → Quality Gate → 发布决策
```

判断：功能路径完整，但 TIA 置信度、选择精度与发布门禁风险在 18/21 号文档中混用不同阈值；没有定义漏选用例的真实标注集、Recall 下限、冷启动行为和人工覆盖策略。该链路不能仅以 Precision 或模型自报置信度验收。

## 八、整改顺序与交付物

### Gate 0：产品与约束裁决

负责人建议：产品负责人 + 技术负责人 + 真实使用方负责人。

交付物：

1. 产品定位与运行约束基线；
2. 用户画像与现状证据册；
3. 现有工具链、痛点和基线数据；
4. 团队、预算、Owner 和维护承诺；
5. V1 核心链路选择。

### Gate 1：现行架构重新基线化

交付物：

1. Skill 流水线是否进入正式产品的 ADR；
2. 更新后的产品地图、C4、领域模型和数据流图；
3. Testing IR、Traceability Graph、Gate Decision、Strategy Contract 的模型与契约；
4. 现行/历史/实验资料台账。

### Gate 2：AI 可信性与安全

交付物：

1. AI 能力评测方法论和 Golden Set；
2. 置信度计算、校准与版本回归方案；
3. AI 数据流图、供应商处理矩阵和数据分类；
4. Prompt Injection/RAG Poisoning/Tool Misuse 威胁模型；
5. 高风险动作 HITL 与审计策略；
6. CoT 改为决策摘要的统一可观测契约。

### Gate 3：开发契约收口

交付物：

1. 修正 5 处 OpenAPI 鉴权冲突；
2. Create/Update/Response DTO；
3. operationId、错误响应和字段约束；
4. 多租户复合引用完整性方案；
5. OpenAPI、Schema、状态枚举和链接自动检查。

### Gate 4：V1 准入复审

准入条件：

- 所有 P0 已关闭或经责任人书面接受风险；
- V1 只保留一条核心价值闭环及其必要支撑；
- 每个 V1 需求都有来源、Owner、验收、API/数据、安全/NFR 映射；
- AI 核心能力在代表性数据集上达到事先约定阈值；
- 关键链路 E2E Gate 通过；
- 容量、成本和恢复目标有可执行验证方案；
- 团队与架构复杂度匹配。
