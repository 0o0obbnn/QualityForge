## 二、已确认产品定位

### 2.1 裁决结果

**已确认：V1 定位为“公司内部 AI 测试效能工具验证版”，保留未来企业化演进边界，但不在 V1 预付商业 SaaS 的全部复杂度。**

确认后的定义：

> QualityForge V1 面向公司内部测试工程师和测试负责人，通过一个可度量的 AI 测试闭环降低重复劳动并沉淀可追踪的测试证据。V1 优先验证使用价值和 AI 质量，不承担商业化销售、多客户零信任隔离、互联网级弹性和全量平台能力承诺。若真实使用数据达到晋级阈值，再进入企业级平台阶段。

### 2.2 推荐理由

- 当前没有付费客户、市场、定价、合同或多客户互不信任证据；
- 内部场景最容易获得真实用户、历史数据和人工反馈；
- 先验证价值可以避免围绕错误定位继续细化 9 模块；
- 现有领域中的 `tenant_id`、标准接口和模块边界可以保留演进兼容性，但 V1 不应以未验证的商业规模驱动部署复杂度；
- 若最终确认已经存在外部客户或强监管交付，本推荐必须被“企业私有化优先”方案替换。

### 2.3 企业化晋级触发器

满足以下任意两项后，重新评估多租户 SaaS、K8s、Vault、完整审计合规和微服务拆分：

- 两个以上互不信任组织需要使用同一部署实例；
- 已签订外部试点或合同，并有明确 SLA/数据隔离条款；
- 单组织实际并发、容量或故障域超过单体/单集群的验证上限；
- 第三方或不可信用户需要上传可执行 Skill；
- 监管、数据驻留、私有化部署成为成交或上线硬条件；
- 当前架构的可测性能或团队协作瓶颈证明必须拆分。

## 三、目标用户与决策角色基线

### 3.1 推荐角色模型

| 角色 | V1 关系 | 核心诉求 | Gate 0 责任 |
|---|---|---|---|
| 测试工程师 | 主要使用者 | 少写重复内容、少做重复排查、结果可信可改 | 提供场景、参与试点、标注 AI 结果 |
| 测试负责人/Test Lead | 业务 Owner/审批者 | 团队效率、资产质量、发布风险 | 选择核心痛点、批准指标和自治边界 |
| 技术负责人 | 技术 Owner | 可维护、可扩展、成本可控 | 承诺团队与架构边界 |
| 平台管理员 | 运维角色 | 配置、权限、模型、Runner 可控 | 提供运行环境和数据边界 |
| 安全/合规负责人 | 条件角色 | 敏感数据、外部 LLM、审计合规 | 批准数据分类和供应商使用规则 |
| 管理决策者 | 投资决策者 | 是否值得持续投入 | 批准预算、阶段目标与退出条件 |

“用户只有测试工程师”可以保留为体验原则，但不能再用作完整的利益相关方定义。

### 3.2 必须采集的现状基线

至少访谈 5 名测试工程师、1 名 Test Lead、1 名技术/平台负责人；覆盖不少于 2 个真实项目。每个项目采集：

| 基线项 | 口径 |
|---|---|
| 需求量 | 每迭代需求/用户故事数量 |
| 用例设计投入 | 每需求平均编写与评审人时 |
| 用例修改率 | 评审后需重大修改或删除的比例 |
| 执行规模 | 日均/峰值 API、UI 用例数和并发 |
| 失败规模 | 日均失败数、重复失败占比、Flaky 占比 |
| 排查投入 | 单个失败从发现到可信归因的 P50/P90 人时 |
| 知识复用 | 重复问题再次发生时是否能找到历史结论 |
| 当前工具 | 用例、执行、日志、缺陷、知识分别使用什么工具 |
| 数据边界 | PRD、日志、源码、客户数据中哪些禁止发往外部 LLM |
| 维护能力 | 可投入开发/AI/前端/运维/安全人员与时间比例 |

证据强度统一标记为：`MEASURED`（实测）、`INTERVIEWED`（访谈）、`INFERRED`（推断）、`UNKNOWN`（未知）。

## 四、V1 核心价值链选择

### 4.1 两条候选路线

#### 路线 A：需求到测试资产

```text
需求材料 → Testing IR → 冲突/来源校验 → 场景与用例草稿
         → 断言与覆盖检查 → 人工评审 → 正式资产/导出
```

必要能力：最小 Workspace、需求导入、Testing IR、Scenario/Case/Assertion、Coverage、HITL、资产导出。

推迟：Runner 分布式执行、UI 自愈、RCA、Knowledge 自动沉淀、CI/CD、Skill Marketplace、多 Agent 可视化编排。

#### 路线 B：失败分析到知识复用

```text
现有执行结果/日志 → 失败聚类与 RCA → 人工核实
                 → 知识条目 → 相似失败召回 → 排查提速
```

必要能力：结果/日志导入、失败分析、人工核实、知识检索、反馈统计。

推迟：自建完整执行平台、需求生成链、UI 自愈、CI/CD 门禁、Skill Marketplace、多 Agent 编排。

### 4.2 基于当前仓库证据的比较

评分 1–5，分数越高越有利；所有分数均为基于当前资产的推断，必须用访谈数据校正。

| 维度 | 权重 | 路线 A | 路线 B | 依据 |
|---|---:|---:|---:|---|
| 当前资产成熟度 | 25% | 5 | 2 | 现有 29 Skill 与 E2E 主要集中 IR→Scenario→Case→Assertion→Coverage |
| 数据获取难度 | 15% | 4 | 2 | A 只需需求材料；B 需真实日志、Trace、标签和历史归因 |
| 价值可感知性 | 20% | 4 | 5 | 两者均强，RCA 的节省人时更直接 |
| 可测量性 | 15% | 4 | 5 | A 看采纳率/编辑量/耗时；B 看准确率/排查耗时 |
| 安全与集成复杂度 | 10% | 3 | 2 | B 涉及日志、源码、APM、Jira 等敏感集成 |
| 最小闭环交付可能性 | 15% | 4 | 3 | A 已有验证资产；B 需先打通数据链 |
| **加权分** | **100%** | **4.15** | **3.20** | 当前资产条件下 A 更适合先做 |

### 4.3 裁决结果

**已确认 V1 选择路线 A“需求到测试资产”。**

这与 41 号报告偏向 RCA 的结论不同，原因是本次纳入了之后新增的 29 个 Skill 和 `e2e-validation` 资产。当前证据显示路线 A 已有明显更高的工程准备度。

但以下条件同时满足时，应改选路线 B：

- 真实基线证明失败排查消耗明显高于用例设计投入；
- 可获得不少于 100 条带可信人工根因标签的历史失败；
- 能合法、安全地获取必要日志/Trace/代码变更信息；
- Test Lead 承诺持续标注 `manual_verified`；
- 现有用例设计工具已足够好，AI 生成没有明确增量价值。

### 4.4 已确认的 V1 范围与 V0 最小切片

V1 只交付以下纵向闭环：

1. Markdown/PDF/OpenAPI 需求导入；
2. 需求来源切片与 Testing IR 编译；
3. IR Schema、来源、冲突、状态可达性校验；
4. Strategy、Scenario、Test Case、Assertion 生成；
5. Rule/Scenario/State/Assertion 四维覆盖门禁；
6. 人工评审、修改、批准与完整审计记录；
7. 正式测试资产导出（JSON/CSV，API 可后置）；
8. AI 质量与成本看板。

受“1 人 + MacBook + AI Agent”约束，V1 不一次性铺开。先实现可验证的本机 V0：

1. 先支持 Markdown 输入，PDF/OpenAPI 适配器后置；
2. 打通来源切片 → Testing IR → Scenario/Case/Assertion → Coverage；
3. 复用现有 Skill 中该链路必需的最小子集，不把 29 个 Skill 全部产品化；
4. 人工评审先采用 CLI/文件化审批记录，不建设完整多人审批 UI；
5. 先导出 JSON 和机器可读评测报告，CSV、API 和交互式看板后置；
6. 在本机样本集上证明来源可追踪、关键规则不漏、链路无孤儿资产、结果可重复回放。

V0 通过只代表技术可行性得到验证，不等同于 V1 业务价值通过。

V1 明确不做：

- 9 个产品模块的完整 UI；
- 分布式 Runner、K8s/KEDA；
- UI Locator 自愈；
- 深度 RCA 与自动 Jira 提单；
- CI/CD 发布门禁；
- 第三方 Skill Marketplace；
- 多 Agent 可视化编排；
- 多客户 SaaS 商业运营能力。

## 六、实际资源、Owner 与预算约束

### 6.1 已确认资源

| 资源 | 已确认值 | 对范围的影响 |
|---|---|---|
| 人力 | 1 人 | 同一人承担产品、架构、实现、验证与运维；必须串行交付 |
| 设备 | 1 台 MacBook | 以本机、低并发、可重复回放为验证环境 |
| AI 能力 | AI Agent | 可协助分析、编码、测试和审查，但不计为独立 FTE，也不能承担审批责任 |
| 外部团队 | 未确认 | 不假设存在前端、运维、安全或试点支持人员 |

因此，原“4–6 FTE、12 周完成 V1”的配置失效。当前只批准 V0 的 CLI/文件化纵向切片；完整评审 UI、多人协作、服务化部署和两个真实项目试点必须在资源或 Owner 到位后再启动。

### 6.2 Owner 模型

批注明确为“没有”。当前不得虚构实名 Owner，也不得把 AI Agent 记为 Owner：

| Owner | 必须拥有的权力 | 当前值 |
|---|---|---|
| Business Owner | 裁决痛点、验收和停止投资 | `OPEN：当前没有` |
| Product Owner | 管理范围、访谈和试点 | `OPEN：当前没有` |
| Technical Owner | 裁决架构与技术债 | `OPEN：当前没有` |
| AI Quality Owner | 批准评测集、阈值和模型升级 | `OPEN：当前没有` |
| Security/Data Owner | 批准数据分类和供应商使用 | `OPEN：当前没有` |
| Operations Owner | 承诺上线后的维护与响应 | `OPEN：当前没有` |

本机 V0 可以由当前实施者执行，但进入真实数据、真实用户试点或长期运行前，至少必须补齐 Business、Technical、Security/Data 三类责任确认；一人可兼任，但必须实名并明确决策权。

### 6.3 预算控制

当前仅确认已有的 1 人、MacBook 和 AI Agent，不确认任何人民币预算。V0 预算边界为：

1. 不采购专用服务器或新增平台服务；
2. 不因 V0 承诺持续性付费基础设施；
3. LLM 调用只使用当前已授权能力，具体月度金额上限仍为 `OPEN`；
4. 一旦需要新增付费、外部数据传输或长期托管，必须重新确认预算与授权。

推荐原则：试点阶段 LLM 与基础设施月成本不得超过预估月度人工节省价值的 20%；若连续两个月超过且没有质量/效率改善，应暂停扩量。

## 七、V1 验收与退出条件

### 7.1 业务成功指标

D-12 批注为“不确定”。下表保留为待校准建议，不构成已确认验收承诺；在获得真实项目基线前不得用于宣称成功：

| 指标 | 推荐目标 | 最低继续线 | 口径 |
|---|---:|---:|---|
| 用例设计总耗时下降 | ≥30% | ≥20% | 同类需求人工基线 vs AI+人工 |
| 测试点采纳率 | ≥60% | ≥40% | 直接采纳或轻微修改的测试点/全部生成点 |
| 重大修改/删除率 | ≤25% | ≤40% | 改变测试意图或删除的生成项 |
| P0/P1 规则来源追踪 | 100% | 100% | 每条关键规则可回溯原文证据 |
| 关键规则漏测率 | 0 | 0 | 人工金标中的关键规则未形成有效用例 |
| 用户持续使用 | ≥70% 试点用户周活 | ≥50% | 连续 4 周使用核心闭环 |
| 满意度 | ≥4/5 | ≥3.5/5 | Test Engineer + Test Lead 评分 |

正式阈值应在真实基线采集后冻结，不得事后为了通过而降低。V0 仅验证指标是否可被自动、稳定地采集。

### 7.2 AI 质量门禁

- 所有生成项必须带来源、模型、Prompt 版本、置信度和父链 ID；
- 关键规则与关键断言必须人工确认；
- 不允许未通过 IR/覆盖/人工 Gate 的资产发布；
- 模型或 Prompt 主版本变化必须回放 Golden Set；
- 发生无来源编造、跨项目数据混入或敏感信息泄露时立即停止自动生成并进入事件审查。

### 7.3 停止或转向条件

D-13 批注为“不确定”。以下条件保留为推荐草案，待真实试点和周期确认后冻结：

- 4 周试点后，用例设计耗时下降不足 20%；
- 测试点采纳率连续两周低于 40%；
- 关键规则漏测率大于 0 且无法通过门禁稳定拦截；
- 两个真实项目都不愿继续使用；
- 需要持续高强度人工修正，净投入高于节省；
- 外部 LLM 数据边界无法满足组织安全要求；
- 团队或 Operations Owner 无法承诺后续维护。

转向路线 B 的条件：用例设计价值不足，但失败排查基线显示存在高频、高耗时、可获得标注数据的问题。

## 十、当前裁决与后续准入标准

### 10.1 当前裁决

- **本机 V0：条件批准。** 可开始路线 A 的最小可验证实现、回归和证据产出；
- **真实项目试点：未批准。** 项目/用户名单、Owner、数据授权和指标未冻结；
- **V1 Gate 0：未通过。** 不得把 `OPEN` 项写入正式 PRD、架构或验收基线；
- **Gate 1 边界：** 只允许形成面向本机 V0 的架构重新基线，不得按原 4–6 FTE、12 周假设建设完整平台。

### 10.2 V1 Gate 0 通过仍需满足

- D-05、D-12、D-13 已确认；
- 至少两类真实使用者已进入访谈/试点名单；
- Business、Technical、AI Quality、Operations Owner 已实名，或有明确且被接受的一人兼任方案；
- 数据发送外部 LLM 的边界已由 Data/Security Owner 批准；
- V1 唯一核心链路、范围外清单、指标和停止条件已冻结；
- 单人资源经 V0 实测证明能够覆盖确认范围，或已补充人员；
- 基础设施和 LLM 预算上限已明确；
- 未确认项保留为 `OPEN`，不得被下游文档当作既定事实。

在以上条件完成前，本文件保持 `CONDITIONALLY_APPROVED_FOR_LOCAL_V0`。V0 之外的 V1 承诺继续冻结。
