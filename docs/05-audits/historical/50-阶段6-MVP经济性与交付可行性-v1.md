# QualityForge 阶段 6：MVP、经济性与交付可行性评估 v1.0

> 日期：2026-07-30  
> 当前裁决：`V0_FEASIBLE_FULL_V1_NOT_FEASIBLE_WITH_CURRENT_SCOPE`

## 一、核心结论

现有“1–3 个月 V1 跑通 9 模块”的计划与当前设计量、风险和单人资源不匹配。可行的不是缩短每个模块，而是只交付一条纵向闭环。当前已有 Skill 和样本资产使“需求到可信测试资产”的本机 V0 具备可行性；完整平台 V1 不具备可信工期和维护能力。

## 二、现有 MVP 的结构性问题

现行 V1 同时涉及：Workspace、需求解析、用例生成、资产 CRUD、API/UI 执行、报告、AI 失败分析、内置 Skill、Agent、RAG、Webhook 和质量门禁。即使每项只做基础功能，也需要完成：

- 前后端和交互；
- 核心领域及数据库迁移；
- 模型接入和评测；
- 文档解析；
- API/UI Runner；
- 实时状态与日志；
- 权限、凭证和集成；
- 部署、监控和恢复；
- 端到端测试与试点支持。

这是多个产品的首版组合，不是最小价值验证。

## 三、推荐 V0 范围

### 必须做

1. Markdown 需求导入与版本哈希；
2. 来源切片、Requirement/Rule/Constraint/State IR；
3. 冲突、来源、Schema 和状态可达性验证；
4. Strategy、Scenario、Case、Assertion 草稿；
5. 断言静态验证和可选的受控动态验证；
6. 规则、场景、状态、有效断言四维 Coverage Gate；
7. 文件化或轻量 UI 人工审阅、修改和批准；
8. JSON 导出、审计清单和可重复评测报告；
9. 模型、Prompt、Token、时延和成本记录；
10. 固定 Golden Set 回归。

### 明确不做

- 完整 9 模块 UI；
- 自建分布式 Runner 和执行云；
- UI Locator 自愈；
- 通用 Skill Marketplace；
- 多 Agent 可视化编排；
- 自动 Jira 提单和深度 RCA；
- TIA 和发布门禁；
- 多客户 SaaS；
- Kubernetes、KEDA、完整微服务和复杂观测栈。

## 四、推荐里程碑与退出证据

| 里程碑 | 目标 | 必须交付的退出证据 |
|---|---|---|
| M0 契约基线 | 统一 IR、资产、Gate、Review | Schema、术语、状态机、追溯图 |
| M1 输入到 IR | Markdown 可重复编译 | 来源完整、冲突不静默、固定样本回放 |
| M2 IR 到测试草稿 | 生成 Strategy/Scenario/Case/Assertion | 父子关系完整、无孤儿 |
| M3 质量门禁 | 四维 Coverage 和断言验证 | 缺口可解释，失败真实阻断 |
| M4 人工批准与导出 | 未批准不可发布 | Diff、审阅人、版本、导出哈希 |
| M5 评测和成本 | Golden Set 稳定回归 | 质量、耗时、Token、金额报告 |
| M6 真实试点决策 | 判断是否进入 V1 | Go/Revise/Stop 和资源申请 |

不建议先承诺周数。先对 M0–M2 实测工时和返工，再形成区间估算。

## 五、经济性模型

### 5.1 成本

```text
总成本 = 产品与研发人时
       + 模型调用
       + 基础设施
       + 集成和迁移
       + Golden Set/人工标注
       + 安全与运维
       + 用户学习和流程切换
       + 错误输出造成的返工与风险
```

### 5.2 收益

```text
净收益 = 用例设计节省人时
       + 评审和追溯节省人时
       + 关键漏测减少的期望损失
       + 资产复用收益
       - 总成本
```

当前没有真实基线，不能计算 ROI。V0 的目标应是证明指标可测，而不是宣称 80% 效率提升。

### 5.3 试点最小测量

- 同类需求人工设计总耗时；
- AI+人工总耗时，包括检查和返工；
- 测试点直接采纳、轻改、重改和删除比例；
- 金标关键规则漏测率；
- 无来源编造率；
- 人工审阅时长；
- 每个有效正式用例的模型成本；
- 用户是否在无强制要求下持续使用。

## 六、资源与 Owner

单人可以完成本机 V0，但不能同时可靠承担长期的产品、架构、实现、AI 质量、安全、运维和业务审批。进入真实试点前至少明确以下责任，即使一人兼任也必须显式：

- Business/Product：核心问题、范围、试点和停止条件；
- Technical：契约、架构和技术债；
- AI Quality：Golden Set、阈值和模型升级；
- Security/Data：输入数据和供应商边界；
- Operations：部署、故障、备份和维护。

AI Agent 可以提高执行效率，但不能被记为独立 FTE 或审批责任人。

## 七、Go / Revise / Stop 标准

### Go

- 关键规则来源追踪和漏测门禁稳定；
- AI+人工总耗时较人工基线有显著改善；
- 无来源编造被稳定拦截；
- 用户愿意连续使用；
- 成本和维护量可接受；
- 有明确 Owner 支持下一阶段。

### Revise

- 技术链可行但采纳低；
- 生成质量可修复但人工成本偏高；
- 只有部分需求类型有效；
- 数据边界要求改用本地模型或更严格脱敏。

### Stop/Pivot

- 净耗时不降反升；
- 关键规则漏测无法稳定拦截；
- 用户不愿采用；
- 输入数据无法合法使用；
- 长期维护成本高于价值；
- 失败排查等其他问题明显更有价值，应转向独立验证路线。

## 八、阶段裁决

`V0_FEASIBLE_FULL_V1_NOT_FEASIBLE_WITH_CURRENT_SCOPE`

批准的合理工作单元是 M0–M6 的单链 V0；完整 9 模块 V1 应冻结，直到真实试点证明价值并补充 Owner、资源、预算和维护能力。
