# QualityForge 设计文档全面审计报告

> **审计范围**：项目仓库全部 27 份设计文档（含 10 份 PRD、4 份基础文档、8 份技术设计、2 份分析报告、3 份规划文档 + v1 归档）
> **审计时间**：2026-07-14
> **审计方法**：逐文档全文审读 + 跨文档交叉一致性校验 + Oracle 深度分析代理辅助

## 一、总体评价

### 1.1 综合评分

| 维度 | 评分 | 说明 |
|:---|:---:|:---|
| 产品愿景与定位 | ⭐⭐⭐⭐⭐ | "AI 原生测试平台"定位精准，与 Gartner/Forrester 行业方向完全对齐 |
| 模块划分与架构 | ⭐⭐⭐⭐ | 9 模块高内聚低耦合，Agent-Skill 分离架构符合业界共识 |
| 工作流闭环 | ⭐⭐⭐⭐⭐ | 创建空间→设计→资产→执行→分析→知识沉淀，完整闭环 |
| PRD 详细程度 | ⭐⭐⭐⭐ | v2 PRD（10-19）质量大幅提升，含数据模型、API、状态机、线框图 |
| 数据模型完整性 | ⭐⭐⭐ | 核心领域模型定义了 26 个实体，但 ER 图基数错误、术语表覆盖不全 |
| 技术架构设计 | ⭐⭐⭐⭐ | Java+Python 混合架构决策有据，Saga/RLS/LLM Gateway 设计规范 |
| 非功能需求 | ⭐⭐⭐⭐ | 性能/安全/HA/可观测性/一致性 5 维度覆盖，指标量化 |
| 跨文档一致性 | ⭐⭐ | 术语表与领域模型状态枚举冲突、ER 图基数错误、元数据报告过时 |
| 文档维护与演进 | ⭐⭐ | v1→v2 多项功能静默删除、分析报告未同步更新、冗余文档未清理 |
| MVP 可执行性 | ⭐⭐⭐ | V1 范围覆盖全 9 模块但 1-3 个月时间紧张 |

### 1.2 总体结论

QualityForge 的**产品愿景和顶层设计优秀**——定位精准、闭环完整、AI 原生理念贯穿始终。v2 版本在 PRD 深度、数据模型、技术架构方面相比 v1 有**质的飞跃**（从"功能蓝图"进化到"可开发 PRD"）。

但存在 **3 类系统性问题**：
1. **跨文档一致性缺陷**：术语表、领域模型、PRD 之间的状态枚举、实体命名、ER 关系存在多处冲突（3 项阻塞级）
2. **文档演进失控**：v1→v2 有 6 项功能被静默删除无说明，2 份分析报告完全过时
3. **API 规范覆盖率不足**：OpenAPI 规范仅覆盖 6 个端点，远低于 PRD 描述的 50+ 接口

## 二、问题清单（按严重程度排序）

### 🔴 阻塞级（Blocking）— 3 项

#### B-1: Agent 状态在三处定义中互相矛盾
- **文档**：`03-术语表Glossary.md` 第86-87行 / `04-核心领域模型.md` 第528行 / `04-核心领域模型.md` 第633-641行
- **问题**：
  - 术语表定义 Agent 状态为：`Active / Inactive`
  - 领域模型 Agent 实体字段定义：`Draft / Active / Retired`
  - 领域模型 Agent 状态机定义：`Inactive / Active / Running / Degraded`
  - 三处定义**完全不同**，无任何交集说明
- **原文证据**：
  - 术语表 L86: `"Active | 启用 | Agent/Skill状态"`
  - 领域模型 L528: `"status | VARCHAR(20) | NOT NULL | 'Draft' | 状态 (Draft/Active/Retired)"`
  - 领域模型 L636: `"Active --> Running : 分配任务"`
- **影响**：开发者无法确定 Agent 状态字段的合法枚举值，前后端状态校验逻辑必然不一致
- **建议**：统一为 `Draft / Inactive / Active / Running / Degraded / Retired`，术语表、实体字段、状态机三处同步修改

#### B-2: Skill 状态在三处定义中互相矛盾
- **文档**：`03-术语表Glossary.md` 第86-87行 / `04-核心领域模型.md` 第515行 / `04-核心领域模型.md` 第647-653行
- **问题**：
  - 术语表：`Active / Inactive`
  - 领域模型实体字段：`Installing / Active / Disabled / Error`
  - 领域模型状态机：`Inactive / Active / Error`
- **原文证据**：
  - 领域模型 L515: `"status | VARCHAR(20) | NOT NULL | 'Installing' | 插件状态 (Installing/Active/Disabled/Error)"`
  - 领域模型 L648: `"[*] --> Inactive : 能力插件导入 (Install)"`
- **影响**：同 B-1，Skill 生命周期管理代码将因状态枚举不统一而产生 bug
- **建议**：统一为 `Installing / Inactive / Active / Disabled / Error`，三处同步

#### B-3: 领域模型实体数量声明与实际不符
- **文档**：`04-核心领域模型.md` 第234行
- **问题**：文档声明"本节展示所有 **24** 个领域实体"，但详细字段表实际定义了 **26** 个实体（#1-#26，含 FailureCluster 和 PipelineRun）
- **原文证据**：L234: `"本节展示所有 24 个领域实体的完整字段以及关联约束"`
- **影响**：开发者按"24个实体"理解会遗漏 FailureCluster 和 PipelineRun 的建表
- **建议**：修改为"26 个领域实体"

### 🟠 严重级（Critical）— 14 项

#### C-1: ER 图 ExecutionResult ↔ TestCase 基数错误
- **文档**：`04-核心领域模型.md` 第50行
- **问题**：`ExecutionResult ||--|| TestCase : "records"` 声明一对一关系。但同一 TestCase 在不同执行批次中会产生多条 ExecutionResult，应为多对一
- **影响**：按此建表会加 UNIQUE 约束，导致同一用例只能执行一次
- **建议**：改为 `ExecutionResult }o--|| TestCase`

#### C-2: ER 图 ExecutionTask ↔ Runner 基数错误
- **文档**：`04-核心领域模型.md` 第46行
- **问题**：`ExecutionTask ||--|| Runner` 暗示每个 Runner 只能执行一个 Task。Runner 是可复用节点
- **建议**：改为 `ExecutionTask }o--|| Runner`

#### C-3: ER 图 TestCase ↔ APIContract 基数错误
- **文档**：`04-核心领域模型.md` 第42行
- **问题**：`TestCase ||--o| APIContract` 暗示每个 APIContract 只属于一个 TestCase。一个 API 端点应能被多个用例测试

#### C-4: CI/CD 门禁 Quarantine 状态在数据模型中缺失

#### C-8: API 规范（OpenAPI）覆盖率严重不足
- **文档**：`32-API规范.yaml`（全文 369 行）
