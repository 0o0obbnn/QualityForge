# QualityForge 阶段 7：综合评估、Gate 与推荐路线图 v1.0

> 日期：2026-07-30  
> 评估范围：阶段 1–6 的重新取证结果  
> 最终裁决：`REVISE_AND_FOCUS`  
> 适用状态：需求设计研发阶段，不代表生产验收

## 一、执行结论

QualityForge 的方向具有潜在价值，设计覆盖面和安全意识明显高于普通“AI 生成用例”工具；但当前项目最大问题是先完成了大平台设计，尚未完成核心问题、单一价值链和正式契约的收敛。

推荐继续项目，但必须从“9 模块 AI 测试平台”调整为“需求到可信测试资产”的可验证产品。近期不应按完整平台方案研发。

## 二、专业框架校准

本轮结论与以下当前权威框架进行交叉校准：

- [ISO/IEC/IEEE 29148:2018](https://www.iso.org/cms/%20render/live/en/sites/isoorg/contents/data/standard/07/20/72089.html)：要求需求工程过程及信息项贯穿生命周期；对应本项目应补齐来源、需求属性、关系和变更追踪。
- [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)：产品质量模型用于需求完整性、设计目标、测试目标和验收标准；对应本项目应按质量属性场景重写 NFR，而不是直接使用远期规模数字。
- [NIST AI RMF Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)：强调在完整生命周期内识别、测量和治理生成式 AI 风险；对应本项目需要 Golden Set、TEVV、风险分级、审计和模型变更治理。
- [OWASP LLM Top 10 2025 — Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)：过多功能、权限和自治会放大 Agent 风险；对应本项目不应让置信度阈值直接授权写资产、调用外部系统或影响发布。
- [ISTQB CTFL v4.0](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/)：测试过程应与软件生命周期及实际交付方式结合；对应本项目不能只优化用例生成，还需验证评审、追溯、执行和反馈是否形成真实工作流。

## 三、综合成熟度评分

评分 1–5：1=未定义，2=有设想，3=已设计，4=有验证，5=真实规模稳定运行。

| 维度 | 权重 | 评分 | 加权 | 判断 |
|---|---:|---:|---:|---|
| 问题真实性与用户证据 | 15% | 1.5 | 0.225 | 无真实访谈、现状和基线 |
| 产品定位与范围 | 10% | 2.0 | 0.200 | 愿景明确，边界过宽 |
| 业务闭环 | 10% | 3.0 | 0.300 | 概念闭环完整，真实流程未验证 |
| 功能需求质量 | 10% | 2.8 | 0.280 | 页面和功能较细，规则/验收不足 |
| 领域、数据与追溯 | 15% | 2.0 | 0.300 | 正式契约落后于 Skill 原型 |
| AI 质量与治理 | 15% | 2.5 | 0.375 | 有降级/HITL 思路，阈值未校准、eval 不足 |
| 安全与隐私 | 10% | 3.2 | 0.320 | 目标设计较强，AI 数据治理仍缺口明显 |
| 架构适配性 | 5% | 1.8 | 0.090 | 远期目标过度驱动当前架构 |
| MVP 与交付可行性 | 5% | 2.0 | 0.100 | 单链 V0 可行，完整 V1 不可行 |
| 指标和经济性 | 5% | 1.5 | 0.075 | 收益数字无真实基线 |
| **综合** | **100%** |  | **2.27 / 5** | **需求设计未达到完整 V1 准入** |

分数不是对产品前景的否定，而是当前证据成熟度。强项集中在设计广度、安全意识和原型方法；弱项集中在用户证据、契约统一、AI 实证和交付聚焦。

## 四、P0 阻塞项

### P0-1 核心价值链没有正式契约

Testing IR、Business Rule、Source Trace、Assertion、Coverage、Review Task 已被 Skill 使用，却不存在于正式领域、数据库和 API。必须重新基线。

### P0-2 AI 自动写入规则冲突

全局策略默认 Test Design L2，模块 PRD 却允许高置信度自动入库。正式资产、契约、外部缺陷和发布动作必须强制人工责任。

### P0-3 完整范围与资源不匹配

单人无法在可信周期内建设并维护九模块、多引擎、微服务、Runner、RAG、Agent、CI/CD 和企业安全体系。必须冻结非核心范围。

### P0-4 缺少业务价值基线

80%、60%、95% 等指标不能进入验收承诺。需要用实际任务对照测量总耗时、质量、返工和成本。

### P0-5 AI 评测覆盖不足

29 个 Skill 中只有少数存在标准 eval；当前 E2E Coverage Gate 仍失败。完整链不得宣称通过。

## 五、P1 严重问题

1. Requirement、DesignCase、TestCase 状态和名称跨文档不一致；
2. TestPlan 丢失 Requirement 关联；
3. Assertion 没有独立验证生命周期；
4. Coverage 没有可解释分子、分母和版本化实体；
5. 批量批准缺少 ReviewDecision、Diff 和事件原子性；
6. Agent 按模块分级而不是按实际 Tool 动作继承风险；
7. Prompt、日志、源码和测试数据的分类及保留策略不完整；
8. 浏览器会话、Token 刷新/撤销和 API Key 生命周期不足；
9. 微服务、Saga、RabbitMQ、Redis Streams、K8s/KEDA 缺少当前触发证据；
10. MVP 横向铺开所有模块，没有真正的薄纵向切片。

## 六、推荐方案

### 方案 A：聚焦可信测试设计（推荐）

```text
需求导入
→ 来源与 Testing IR
→ 冲突/状态/Schema 校验
→ Strategy/Scenario/Case/Assertion
→ 四维 Coverage Gate
→ 人工审阅
→ 正式导出
→ 效率/质量/成本评测
```

优点：复用现有最成熟原型；价值链短；可离线验证；安全和集成风险较低；能形成差异化质量能力。  
代价：暂时不像“完整平台”，需接受范围收敛。

### 方案 B：继续完整平台

优点：远景完整。  
风险：研发面过大、契约持续漂移、基础设施先行、AI 质量无力覆盖、单人不可维护。  
结论：当前不推荐。

### 方案 C：转向失败分析/RCA

只有在真实数据证明失败排查价值显著更高，并可获得足量人工金标、日志、Trace 和代码上下文时考虑。当前作为独立实验保留。

## 七、推荐实施路线

### Gate A：需求和契约重基线

- 冻结单一价值链和不做清单；
- 统一术语、聚合、状态和追溯边；
- 重新定义数据库、API、事件和导出契约；
- 解决 DraftCase/正式 TestCase 关系。

### Gate B：可信链可重复

- 固定 Golden Set；
- 打通 Source→IR→Scenario→Case→Assertion→Coverage；
- 所有孤儿、编造、冲突和覆盖缺口可稳定拦截；
- 当前 Coverage Gate 修复至通过，或经人工正式调整策略阈值。

### Gate C：人工责任与安全

- ReviewTask、Diff、审批、审计和回放闭环；
- 数据分类、模型供应商和保留策略获批准；
- 提示注入、跨 Workspace、Tool 越权和输出处理测试通过。

### Gate D：真实价值试点

- 至少两个真实需求样本；
- 与人工流程对照；
- 同时测量时间、质量、返工、采用和成本；
- 输出 Go/Revise/Stop。

### Gate E：平台化晋级

只有真实采用、规模或故障域证明必要时，才逐步引入资产管理、执行、RCA、CI/CD、多租户和微服务能力。

## 八、近期可执行清单

1. 将 `46` 的单价值链和能力处置矩阵作为范围讨论基线；
2. 以 `47` 的推荐聚合重画领域模型；
3. 统一 Requirement 与 DraftCase 状态；
4. 将 Testing IR、Business Rule、Assertion、Coverage、Review 纳入术语表；
5. 设计可持久化 Traceability Graph；
6. 重写核心链 OpenAPI，暂停扩展外围端点；
7. 统一 AI 自治规则为“生成草稿、确定性验证、人工发布”；
8. 为核心 Skill 补齐 eval 和 Golden Set；
9. 修复当前 rule/scenario/state Coverage 缺口；
10. 采用模块化单体完成本机 V0；
11. 记录每次运行的质量、耗时和成本；
12. 用真实样本决定是否进入服务化 V1。

## 九、最终裁决

### 已验证

- 产品材料、契约和原型资产丰富；
- 核心 Skill 链具备局部技术可行性；
- 安全和 AI 降级已有较成熟意识；
- 正式产品契约与原型质量模型存在明确断层；
- 当前 Coverage Gate 未通过。

### 推断

- 聚焦单价值链后，项目可以形成有差异化的内部 AI 测试设计工具；
- 继续完整平台会使复杂度增长快于价值证据。

### 未验证

- 用户真实痛点排序；
- 实际效率和质量增益；
- 长期采用、维护和经济性；
- 企业规模和商业化必要性。

### 决策

`REVISE_AND_FOCUS`

项目应继续，但先暂停完整平台扩张，完成核心契约重基线、AI 质量门禁和本机单链 V0。真实试点通过后，再决定是否向执行、RCA、CI/CD 和企业平台演进。
