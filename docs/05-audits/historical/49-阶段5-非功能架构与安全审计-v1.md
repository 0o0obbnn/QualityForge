# QualityForge 阶段 5：非功能、架构、安全与数据治理审计 v1.0

> 日期：2026-07-30  
> 当前裁决：`TARGET_ARCHITECTURE_OVERBUILT_FOR_VALIDATION_STAGE`

## 一、总体判断

企业级目标架构覆盖性能、RLS、信封加密、Runner 沙箱、可观测、容灾和幂等，安全意识较强；但它面向一个尚未完成价值验证的多租户大规模平台，与近期单人、单机、单价值链不匹配。当前首要风险不是系统扛不住 50,000 并发，而是用复杂基础设施延迟核心契约和用户价值验证。

## 二、质量属性优先级重排

V0/V1 应按以下顺序：

1. 正确性与来源可追溯；
2. 数据安全与人工责任；
3. 可重复、可回放、可审计；
4. 可维护性和可替换模型；
5. 可用性与任务恢复；
6. 成本和响应时间；
7. 大规模并发与弹性。

现有 NFR 把 5,000/50,000 API 并发、500/3,000 UI 并发、KEDA 30 秒扩容、FCP 1 秒等远期目标写得过早。虽然文档注明这些是待压测目标，但仍会错误驱动架构。

## 三、架构评估

### 3.1 当前目标架构成本

当前方案包含 FastAPI 微服务、网关、PostgreSQL/RLS、PGVector、RabbitMQ、Redis、Redis Streams、Saga、Kubernetes/KEDA、Vault、S3、Prometheus、ELK、Jaeger/Langfuse 和分布式 Runner。

每项都可以合理，但组合后要求持续处理：

- 服务契约和部署版本；
- 分布式事务、重复消息和最终一致性；
- 队列、缓存和流的故障恢复；
- 多套可观测系统；
- 密钥和证书生命周期；
- Kubernetes、Runner 和网络策略；
- 多租户安全测试。

这超出验证“需求到可信测试资产”所需的最小架构。

### 3.2 推荐阶段架构

```text
CLI 或轻量 Web
    ↓
模块化单体应用
├── Requirement/IR
├── Design Pipeline
├── Validation/Coverage
├── Review/Publish
└── Audit/Export
    ↓
本地文件或 SQLite（V0）/ PostgreSQL（V1）
    ↓
单一后台 Worker（确有异步需求时）
    ↓
可替换 LLM Adapter
```

先使用进程内任务和数据库事务。只有出现可测瓶颈或独立扩缩需求时，再引入 Redis、消息队列和服务拆分。

### 3.3 技术选型结论

- Python/FastAPI 与 AI 文档处理场景相符；
- “纯 Python”不等于必须微服务；
- PostgreSQL 可作为 V1 主库，PGVector 应在检索价值验证后启用；
- LangGraph/LangChain 不是业务需求，简单有向流程优先使用普通 Python 状态机；
- RabbitMQ、Redis Streams、Saga、K8s/KEDA、图数据库均应由实际需求触发；
- OpenTelemetry 可保留统一埋点接口，V0 不必部署完整观测栈。

## 四、安全评估

### 已有良好基础

- PostgreSQL RLS 明确要求非 owner、`NOBYPASSRLS`、`FORCE RLS` 和 fail-closed；
- 网关注入身份 Header 的信任边界、Header 清洗和网络隔离已有说明；
- Secrets 使用 AES-GCM/信封加密并禁止日志泄漏；
- 自定义 Skill 已识别 RCE、横向移动、Secret 外泄和 DoS；
- Skill 沙箱包含非 root、只读根文件系统、资源限制、出站白名单和审计；
- 外部系统写入和高风险动作原则上有人审。

### 关键缺口

1. 未定义浏览器端 Token 的存储、刷新、撤销、会话并发和 CSRF 策略。
2. API Key 只描述哈希，未完整定义过期、范围、轮换、撤销、最后使用和泄漏响应。
3. Prompt、模型原始输出、日志、截图、PRD、源码的分类分级和保留周期不完整。
4. 可观测设计要求记录渲染 Prompt 和原始输出，可能与最小数据保留及敏感信息要求冲突。
5. 外部 LLM 的供应商、区域、训练使用、保留策略和数据处理协议未形成准入矩阵。
6. Prompt injection、间接提示注入、RAG 投毒、跨 Workspace 检索污染没有系统威胁模型。
7. Skill 依赖白名单存在，但缺少制品签名、SBOM、漏洞持续扫描和撤销策略。
8. 上传 PDF/Word/ZIP/YAML/代码涉及解析器漏洞、压缩炸弹、路径穿越和恶意宏，文件入口控制不足。
9. 备份加密有目标，但恢复演练、密钥丢失、删除请求和审计不可抵赖未闭环。
10. 多租户是远期边界，V1 若为单组织，不应让所有功能复杂度都围绕 SaaS 构建。

## 五、AI 与数据威胁模型

| 威胁 | 典型后果 | 最小控制 |
|---|---|---|
| 恶意需求文本提示注入 | 模型泄露上下文或调用越权 Tool | 输入不可信标记、Tool allowlist、参数验证、最小权限 |
| RAG 投毒 | 错误知识影响所有生成 | 来源签名、审核、版本和撤销 |
| 跨项目检索 | 商业数据泄漏 | Workspace 强隔离、检索过滤、越权测试 |
| 模型输出代码执行 | RCE/外联/Secret 泄漏 | 默认不执行、沙箱、零出站、人工批准 |
| 日志/Prompt 过度记录 | 敏感信息长期留存 | 字段级脱敏、采样、分类保留策略 |
| AI 自动修复掩盖缺陷 | 假通过 | 原断言不变、修复为候选、差异与重试证据 |
| 模型供应商漂移 | 质量静默下降 | Golden Set、版本固定、回放和回滚 |

## 六、NFR 重写示例

不要写“系统高性能”，应写质量属性场景：

| 场景 | 推荐 V0/V1 指标 |
|---|---|
| 上传 Markdown 需求 | 10 MB 内 1 秒返回任务 ID，解析异步进行 |
| 生成失败 | 保留输入版本和错误，重试不产生重复资产 |
| Coverage Gate | 固定样本同版本重复计算结果一致 |
| 人工批准 | 未批准资产无法进入正式导出；全部记录审阅人和 Diff |
| 模型不可用 | 用户仍可查看、编辑、验证和导出已有草稿 |
| 数据隔离 | 未提供 Workspace 上下文时查询 fail closed |
| 恢复 | 单次任务崩溃后可从最近持久化阶段恢复，不重复计费 |
| 成本 | 每次 DesignRun 可查询模型、Token、金额和重试成本 |

容量和 SLA 应通过真实使用量推导，不先指定万级目标。

## 七、阶段性架构 Gate

| Gate | 进入条件 |
|---|---|
| V0 本机 | 核心契约冻结、样本可回放、敏感数据禁止清单 |
| V1 内部服务 | 真实用户、PostgreSQL 迁移、认证、备份、审计和最小 SLO |
| Runner/异步扩展 | 有真实执行需求和队列/恢复压测 |
| 多租户 | 至少两个互不信任组织共享实例的真实需求 |
| 微服务拆分 | 团队边界、独立扩缩或故障隔离有实测证据 |
| Kubernetes | 部署规模和运维能力证明其净收益 |

## 八、阶段裁决

`TARGET_ARCHITECTURE_OVERBUILT_FOR_VALIDATION_STAGE`

远期安全设计可作为参考架构保留；近期应采用模块化单体、最少基础设施、严格数据边界和可回放审计。架构晋级必须由实际规模、团队和故障域触发，而不是由“企业级平台”标签触发。
