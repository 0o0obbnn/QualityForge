# QualityForge 产品全面评估报告 v1.0

> **方法论声明**：本报告基于对全部 24 份活跃文档的逐篇精读 + 跨文档交叉印证 + 行业三类赛道对标（测试管理 / AI 研发效能 / 智能项目管理）+ 安全/性能外部最佳实践（PostgreSQL RLS 官方行为、Gartner AI-Augmented Testing 定义）。每条关键结论标注**证据出处**（文档编号 + 章节/行号），无法证实者标 `待核实`。
>
> **与既有审计的差异**：00-审计报告-v2 已被 35-CHANGELOG 证伪（"0 冲突"结论不成立，未覆盖 9 份模块 PRD），且只做"一致性回归"，**未做产品-市场-技术三位一体的价值评估**。本报告在已修复的一致性问题之上，重点回答：**这套设计能不能成、好不好卖、值不值得投、哪里会塌**。

## 一、执行摘要（Executive Summary）

### 1.1 一句话定性

QualityForge 是一份**完成度位于行业前 15% 的 AI 原生测试平台设计文档集**——产品愿景清晰、架构推理扎实、安全设计深度罕见，但存在**"设计成熟度远超产品验证成熟度"的根本性倒挂**：在零代码、零用户访谈、零竞品量化对标的前提下，已投入相当于 3-4 人月的设计产能细化到字段级，导致大量决策（38 实体、149 端点、9 模块边界）缺乏需求证据回溯，存在"过度设计先行、市场验证缺位"的高风险。

### 1.2 综合评分：3.8 / 5.0（中上，偏科严重）

| 维度 | 评分 | 一句话判断 |
|---|:---:|---|
| A. 产品定位与市场 | **2.8** | 愿景动人，但用户画像单薄、无市场证据、护城河论证缺位 |
| B. 功能架构 | **3.7** | 模块划分专业、闭环完整，但 MVP 范围过大、AI 深度不均 |
| C. 技术方案 | **4.3** | 选型推理一流、降级设计扎实，少数环节复杂度超前 |
| D. 非功能性 | **4.5** | 安全/可观测/容灾设计堪称范本，个别 SLO 偏激进 |
| E. 商业与落地 | **2.5** | 商业模式空白、资源估算缺失、Go-to-Market 无规划 |

> 评分说明：5=卓越可作行业范本；4=扎实可落地；3=基本可用但有明显缺口；2=存在原则性问题；1=严重不足需重做。维度内扣分项见各章节"扣分明细"。

### 1.3 最关键的三个判断

1. **作为技术设计文档集，质量很高，值得作为企业级 SaaS 设计的教学案例**——尤其 RLS 多租户模型（含共享目录型表读写分离，见 33-§4.2.1）、LLM 降级级联（31-§5）、AI 介入点默认自主策略（21-§一·补）三处，已达到生产级严谨度。
2. **作为待研发的产品，存在"先射箭后画靶"的流程倒置**——整套设计在没有任何"用户是否真的要这个、愿意付多少钱、现有方案哪里不够"的证据下完成，功能广度（9 大模块 + V1/V2/V3 三级路线图）对一个 1-3 个月的 MVP 而言**严重超载**，极易陷入"什么都做了点、什么都不够深"的陷阱。
3. **最大的风险不是技术能不能实现，而是做出来后没人用**——文档未定义任何成功指标（North Star、activation rate、retention），无法在 V1 交付后回答"我们成功了没有"。

## 二、A. 产品定位与市场分析（评分：2.8 / 5.0）

### A.1 发现

**A.1.1 产品定位陈述清晰且具差异化意图。**
02-PRD总纲 §1.1 明确区分"AI 原生（AI-Native）全生命周期闭环"与"AI 聊天窗口被动辅助"两种范式，并给出了 Agent-Skill 协同模型（§3.1）与向量排障循环（§3.2）作为差异化技术载体。这套叙事在 2026 年的市场语境下是成立的——多数竞品（Testim、Mabl、Katalon）仍停留在"AI 辅助脚本生成"阶段，未做到"AI 介入排障-知识沉淀闭环"。

**A.1.2 目标用户画像单薄到危险。**
全文档集仅出现一个角色：**"测试工程师"**（02-§4"用户只有一个"原则）。但证据表明真实购买与使用决策涉及至少 4 类角色，且诉求冲突：

| 角色 | 文档是否覆盖 | 该角色核心诉求 | 文档是否回答 |
|---|---|---|---|
| 一线测试工程师 | ✅ 主用户 | 少写脚本、快速定位失败 | ✅ 回答充分 |
| 测试经理 / QA Lead | ✅ 有 TestLead 角色（34-§2.1） | 团队效能度量、发布风险决策 | 🟡 仅 14-PRD 提"发布风险预测"，无度量看板设计 |
| 研发负责人 / CTO | ❌ 未出现 | ROI、是否替换现有工具链、合规审计 | ❌ 完全空白 |
| 采购 / IT 治理 | ❌ 未出现 | 私有化部署、数据出境、SLA | ❌ 完全空白 |

**证据**：02-§4 原文"全平台所有的设计（包括智能体的引入）均是为了赋能测试工程师，而不是取代他们"——这是产品设计原则，不是市场切入策略。34-§2.1 的 RBAC 虽定义了 TenantAdmin / TestLead / TestEngineer，但**没有任何文档描述这些角色的购买动机、预算权限、替换成本**。

**A.1.3 场景闭环验证停留在文档自证，无外部证据。**
02-§5 给出了产品工作流图（创建空间 → 导入 PRD → AI 设计用例 → 执行 → 分析 → 沉淀 → 门禁），这是一条**逻辑自洽的闭环**，但：

- **零用户访谈证据**：全文档集无一处"基于 N 次访谈""X/Y 用户反馈"的引用。CHANGELOG（35）通篇是设计自洽性修复，无产品验证批次。
- **零行为数据**：无任何"当前用户在 X 环节耗时 Y 分钟、本方案预计降至 Z"的量化对比。14-§1.2 称"将人工排查时间降低 80% 以上"——**无任何基线数据支撑这个数字**。
- **无 Pilot / PoC 计划**：22-MVP 规划 §6 的"交付检查"全部是技术验收（性能压测、安全扫描），**没有产品验证验收**（如"3 个种子客户完成首个测试任务""周激活率 > X%"）。

**A.1.4 竞品对标严重缺位，是本评估发现的最大产品级风险。**
全文档集**无任何一份竞品分析文档**。基于行业知识补齐对标矩阵（待核实，需产品负责人确认）：

| 赛道 | 代表竞品 | QualityForge 的相对位置 |
|---|---|---|
| **AI 测试自动化** | Mabl / Testim / Tricentis Tosca | QualityForge 的 Self-Healing（12-PRD Locator 自愈）与这些竞品同维；但**缺少无代码录制能力**（Mabl 的核心卖点），定位偏"赋能已有技术能力的测试团队" |
| **测试管理平台** | TestRail / Zephyr / Xray | QualityForge 的 TestCase/TestSuite 管理（12-PRD）功能完整度对标 TestRail 80%，但**缺少与 Jira/Xray 的深度双向同步**（仅 14-PRD 提单向提单） |
| **AI 研发效能 / DevOps** | GitHub Copilot / LinearB | 赛道不同，但**侵蚀风险高**——若 Copilot 类工具向"测试生成"延伸（已部分实现），QualityForge 的 TestDesign 模块会被降维打击 |
| **专项 RCA 工具** | Rollbar / Sentry（生产侧） | 14-PRD 的 RCA 定位测试侧，**无直接冲突但价值主张重叠**，需说清"测试期 RCA"的独立价值 |

**关键缺口**：QualityForge 声称的"AI 原生闭环"护城河（02-§3.2 向量排障循环）**理论上可被任何具备 LLM + RAG 能力的竞品在 6-12 个月内复制**。文档未论证：为什么是 QualityForge 做成、为什么别人做不成、数据飞轮（用得越多越聪明）的冷启动如何解决。

**A.1.5 商业模式与市场规模的完全空白。**
全文档集**未出现任何关于**：定价模型（按席位数 / 按执行量 / 按租户）、目标市场 TAM/SAM/SOM、销售模式（PLG vs SLG）、私有化 vs SaaS 比例规划的内容。22-MVP 规划通篇是功能与 NFR，**无一行商业约束**（如"V1 必须支持私有化部署以满足金融客户"）。

### A.2 扣分明细

| 扣分项 | 扣分 | 证据 |
|---|:---:|---|
| 用户画像单一只覆盖一线工程师，决策链上层角色空白 | -0.6 | 02-§4、34-§2.1 |
| 零用户访谈 / 行为数据 / PoC 计划，场景闭环仅文档自证 | -0.6 | 全文档集无；22-§6 仅技术验收 |
| 无竞品分析文档，护城河论证缺位 | -0.6 | 全文档集无 |
| 商业模式 / 市场规模 / GTM 完全空白 | -0.4 | 全文档集无 |
| **小计** | **-2.2** | 基准 5.0 → 2.8 |

### A.3 建议（可执行，指到文档级）

1. **新建 `05-市场分析与竞品对标.md`**：至少覆盖上述 4 类赛道 × 3 个代表竞品的功能矩阵 + 定价 + 差异化缺口；明确 QualityForge 的"必赢之战"（建议聚焦**测试期 RCA + 知识飞轮**，这是最不易被 Copilot 类工具侵蚀的细分）。
2. **新建 `06-用户画像与场景证据册.md`**：定义 3-5 个 P0 画像（含决策链上层），每个画像附 1-2 个真实场景引用（即便是公开案例），并标注证据强度（访谈 / 观察 / 假设）。
3. **在 22-MVP §6 增加"产品验证验收"小节**：V1 交付除技术检查外，必须包含 ≥ 3 个种子客户完成首个端到端测试任务、首个测试任务的 Time-to-Value < X 分钟、30 日周激活率 > Y%。
4. **在 02-PRD总纲 增加 §0"商业约束"小节**：明确 V1 是否必须支持私有化、目标客户行业（金融/政企可能强制本地化 LLM）、定价假设。

## 三、B. 功能架构评估（评分：3.7 / 5.0）

### B.1 发现

**B.1.1 9 模块划分专业，高内聚低耦合的边界基本成立。**
01-功能地图的 9 大模块（Workspace / TestDesign / TestAsset / Execution / QI / SkillCenter / AgentCenter / KnowledgeCenter / CICD）对应测试生命周期的清晰阶段，模块间依赖在 35-CHANGELOG CH-23 中专门做了 Execution 与 QI 的职责去重（"Execution 采集打标，QI 诊断归因"），这是**优秀的边界治理实践**。

**证据**：每个模块 PRD 的 §8"依赖关系"均明确定义了"依赖 / 被依赖"，且 31-架构 §3.1 的事件拓扑（`WorkspaceCreated` / `TestCaseApproved` / `LocatorBroken` / `TestRunCompleted` 等）与模块边界一致，无循环依赖。

**B.1.2 信息架构与用户旅程完整，但仅描述"理想路径"，异常路径严重不足。**
各 PRD §4.2 的 User Journey 均为"顺利路径"（如 10-§4.2.1 的空间创建成功跳转、16-§4.2 的 Agent 排查成功）。**几乎所有 PRD 缺失**：

- AI 生成结果质量差时用户的修正路径（仅在 11-PRD 提"人工优化 Review"，无具体交互）
- LLM 降级到 L3 后用户如何感知与接管（21-§三 提了"Degradation Alert"，但无任何 PRD 描述该通知的 UI 落点）
- 长时异步任务（如 AI 扫描、RCA）失败后的恢复与重试 UX（10-§7、14-§7 仅给错误码，无用户操作路径）

**B.1.3 AI 能力嵌入点设计是本项目的最大亮点，但有"广度不均 + 深度假定"问题。**

亮点（**行业领先水平**）：
- 21-降级矩阵对每个介入点明确了 L1/L2/L3 三级 + 置信度阈值 + 降级触发条件，且 CH-21 将默认级别按"可逆性 × 影响面"重定为"默认安全（opt-in 激进）"——这是企业级 AI 治理的**通行最佳实践**，多数同类产品未做到此级别。
- 31-§5 的 LLM 网关降级链（Sonnet → GPT-4o → DeepSeek V3 → 本地规则 / 转人工），且 CH-11 修复了"置信度校验恒返回 True"的致命桩代码，使整套阈值体系真正生效。

问题：
- **AI 深度假定**：多处 PRD 假定 LLM 能力"开箱即用"达到生产可用，但未定义**评估方法**。例如 14-§1.2 假定 RCA"在 15 秒内将失败类型精准分类"，**无任何评测集（golden set）定义**——怎么知道"精准"？11-TestDesign 假定"将手工编写耗时缩短 80%"，**无对比基线**。
- **AI 广度不均**：TestDesign（11）与 QI（14）的 AI 设计深度很足，但 **TestAsset（12）的"AI 用例优化"仅一句话**（"单点按钮，提示缺失的断言"），KnowledgeCenter（17）的"Pattern 自动沉淀"也仅概念级。建议要么深化，要么从 V1 砍除避免承诺落空。
- **置信度来源未定义**：21-矩阵大量使用 Confidence Score（0.80/0.85/0.92 等），但**全文档集未定义这个分数如何计算**——是 LLM 自报？是校验模型打分？是规则引擎？这是 AI 工程化的核心问题，直接决定降级链是否可信。31-§5.2 伪代码注释也承认"必须真实取值比较，不能恒返回 True"，但**未给出真实取值的方法**。

**B.1.4 MVP 范围严重超载，是产品落地的高危信号。**
22-MVP §3.2 的 V1（1-3 个月）功能范围包含**全部 9 个模块的某种程度实现**：

| V1 承诺（22-§3.2） | 工程量评估 |
|---|---|
| Workspace 基础创建 + 环境配置 + 全局 LLM 凭证 | 中（含多租户 RLS、双信封加密） |
| TestDesign AI 需求解析 + 场景树 + TestCase 生成 | **高**（LLM 工程化、Prompt 治理） |
| TestAsset CRUD + AI 用例优化 | 中 |
| Execution API + UI 单机 Runner | 中（含 WebSocket 流） |
| QI 基础看板 + AI 失败解析 | **高**（LLM 工程化） |
| SkillCenter 内置 API + Playwright Skill | 中 |
| AgentCenter 内置 2 Agent + Trace 查看 | **高**（LangGraph + Trace 基础设施） |
| KnowledgeCenter 手工上传 + RAG | 中（向量库 + 检索） |
| CICD Webhook 触发 | 低 |

**判断**：这**不是 1-3 个月能交付的 MVP，这是 6-9 个月的产品**。对比行业，Mabl 早期 MVP 仅做 UI 录制 + Self-Healing，TestRail 早期仅做用例管理。QualityForge V1 试图同时做 9 个模块的"最小版"，极易导致每个模块都停留在 Demo 水平，无法形成真正可用的闭环。

**B.1.5 功能优先级与"必赢之战"未区分。**
01-功能地图与 22-MVP 给出了 V1/V2/V3 切分，但**未说明为什么是这个切分**。例如：
- 为什么 Self-Healing（Locator 自愈）放 V2 而非 V1？这是最易被用户感知价值的"魔法时刻"，适合做 V1 卖点。
- 为什么 Multi-Agent 协同放 V3？若 Agent-Skill 是核心差异化（02-§3.1），早期就应验证。
- CICD 质量门禁放 V2/V3，但若目标客户是"已有 CI/CD 想加测试智能"，门禁可能是**首要购买理由**。

### B.2 扣分明细

| 扣分项 | 扣分 | 证据 |
|---|:---:|---|
| MVP 范围严重超载（9 模块全上，1-3 月不现实） | -0.6 | 22-§3.2 |
| AI 置信度计算方法未定义，降级链可信度存疑 | -0.4 | 21-矩阵全篇；31-§5.2 |
| 异常路径 UX 缺失（降级通知落点、长任务失败恢复） | -0.3 | 10-§7、14-§7、21-§三 |
| 功能优先级未论证，"必赢之战"不清晰 | -0.3 | 01、22 |
| **小计** | **-1.6** | 基准 5.3（架构专业给加分）→ 3.7 |

### B.3 建议

1. **重做 22-MVP 的 V1 范围**：建议 V1（3 个月）只做 **3 个模块的深度闭环**——Workspace（最小版）+ TestDesign（AI 用例生成，核心卖点）+ Execution（API + 单机 Runner）。其余模块推迟到 V2，或在 V1 仅做"只读占位"。
2. **新建 `23-AI能力评估方法论.md`**：定义每类 AI 任务的评测集构建方法、置信度计算方式（建议：LLM 自报 + 校验规则双通道）、质量基线。**这是 V1 启动开发前必须解决的阻塞项**——否则所有"AI 能力"都是不可验收的。
3. **在各 PRD §4 增加"异常旅程"小节**：至少覆盖 3 类异常（AI 低置信度、LLM 不可用降级到 L3、长任务超时），明确用户可见的提示与操作路径。
4. **在 01-功能地图 增加"必赢之战"标注**：明确 1-2 个"必须做到行业最好"的能力（建议：测试期 RCA + 知识飞轮），其余能力标"及格线即可"，避免资源分散。

## 四、C. 技术方案评估（评分：4.3 / 5.0）

### C.1 发现

**C.1.1 技术选型推理质量高，"纯 Python 决策"论证扎实。**
30-技术选型 §1 对三种方案（纯 Python / 混合 / 纯 Java）做了 4 维评估，核心论据"AI 是第一性能力，生态必须在 Python"+"性能瓶颈在 LLM 调用而非 Web 框架"+"单语言栈降低总成本"**逻辑自洽且符合 2026 年的技术现实**。CHANGELOG CH-15 记录了从"Java+Python 混合"收敛到"纯 Python"的决策修正，并诚实承认了原 GIL 谬误——**这种决策可追溯性是优秀工程组织的标志**。

**C.1.2 架构复杂度与团队规模存在隐含错配。**
31-架构 §2 定义了 **7 个微服务 + 4 类存储（PG / Redis / MinIO / RabbitMQ）+ 外部 K8s/KEDA/Vault/Jaeger/Langfuse** 依赖。这套架构的运维复杂度需要：

- 至少 2 名专职 SRE / 平台工程师
- 至少 1 名安全工程师（双信封加密、RLS、沙箱）
- 完整的 CI/CD + IaC（Terraform/Helm）能力

**全文档集未提及团队规模与构成**。若实际团队 < 8 人，这套架构在 V1 阶段就会因运维负担拖垮迭代速度。**待核实**：请产品/技术负责人确认目标团队规模，若 < 8 人，建议 V1 采用**模块化单体（Modular Monolith）**而非微服务——同一个 FastAPI 进程内按模块分包，V2 再按需拆分。

**C.1.3 "知识图谱"从空承诺到落地，但深度遍历能力存疑。**
30-§2.3 + 35-CH-14 记录了知识图谱存储的设计演进：从最初"只有 graph_version 版本号无本体表"（空承诺），到补齐 `t_kg_node` + `t_kg_edge` 邻接表建模，并明确"不引入 Neo4j"的决策与升级触发条件（">4 跳深遍历高并发时再评估"）。

**判断**：这是**正确的渐进式决策**。但需注意：
- TIA（测试影响分析，18-CICD §智能测试选择）依赖"代码变更 → 受影响用例集"的图遍历，若代码-用例映射图深度普遍 > 3 跳，PostgreSQL 递归 CTE 的性能会显著下降。**待核实**：建议在 V1 末期用真实代码仓库做一次图深度分布测量，验证递归 CTE 是否够用。
- `t_kg_edge` 的 `graph_version` 版本指针 + "新版本写完再切指针，旧版本异步清理"（30-§2.3）是优雅的原子切换设计，但**异步清理的失败处理未定义**——若清理任务挂掉，旧版本数据会堆积。建议补充清理任务的重试与告警机制。

**C.1.4 AI 工程化路径基本可行，但有三处关键技术风险未解。**

| 风险点 | 现状 | 缺口 |
|---|---|---|
| **LLM 调用成本控制** | 19-PlatformSettings 有 LlmConfig，但**无任何预算 / 配额 / 熔断设计** | 缺租户级 Token 预算、超额阻断、成本看板；20-§4.4 仅提"Cost > 80% of Quota"告警，无阻断机制 |
| **Prompt 版本治理** | 16-§3.1.2 有 AgentPromptVersion 表 + is_active 切换 | **缺 A/B 测试的具体设计**（流量切分、对照指标、统计显著性判定），02 总纲 §3.1 提了 A/B 但无落地 |
| **Agent 死循环防护** | 16-§7 有 `AGENT_LOOP_DETECTED`（同 Tool 同入参 > 3 次或 Trace 深 > 10 层） | 阈值偏宽松——10 层 Trace 在复杂 ReAct 任务中常见，可能误杀；建议改为"token 消耗上限 + 时间上限 + 循环检测"三重 |

**C.1.5 数据库 Schema 设计的成熟度堪称范本，但存在一处矛盾。**
33-Schema 的整体质量是全文档集最高的：
- 多租户 RLS 三层硬约束（33-§4 IMPORTANT：非 owner 角色 + FORCE RLS + fail-closed）
- 共享目录型表的读写分离策略（33-§4.2.1）解决了"内置 Skill/Agent 对所有租户可见且不可被投毒"这一**多数多租户系统都处理不好的难题**
- `SET LOCAL` 事务陷阱的显式说明（33-§4.3）+ 参数化绑定（34-§3）

**矛盾发现**：
- 10-PRD-Workspace §3.1.2 的 `WorkspaceEnvironment.db_connection_string` 注为 "TEXT 密文（双信封加密）"，33-Schema 同步标注。但 **34-§5 双信封加密实现示例中的 `encrypt_data` 方法需传入 `dek: bytes`，而 `db_connection_string` 的加密入口未定义**——是 Workspace 级统一 DEK，还是每条 Secret 单独 DEK？10-PRD §3.1.3 `WorkspaceSecret` 与 §3.1.2 `WorkspaceEnvironment.db_connection_string` 是否共用同一 DEK？**这影响密钥轮转与性能**，需明确。

## 五、D. 非功能性评估（评分：4.5 / 5.0）

### D.1 发现

**D.1.1 安全设计深度罕见，是全文档集的最强项。**
20-NFR §2 + 34-认证授权 + 33-Schema §4 + 15-SkillCenter §4.5 构成了**纵深防御体系**：

- **多租户隔离**：RLS + FORCE + fail-closed + 共享目录表读写分离（见 C.1.5）——行业领先
- **凭证保护**：双信封加密（KEK 托管 KMS + DEK 每租户 + AES-256-GCM）+ 内存解密不落盘（20-§2.2）——生产级
- **计算沙箱**：Skill 执行的一次性容器 + 非 root + 只读根 FS + seccomp + 网络默认零出站（15-§4.5）——这是**对"允许上传任意脚本执行"这一最高危攻击面的正确响应**，CHANGELOG CH-17 记录了这是后补的，且补得很到位
- **信任边界**：34-§1.2 的 WARNING 明确"下游直读 X-Tenant-ID 必须有网络层/mTLS 保证"——这种**自我警示**比假装安全可信得多

**D.1.2 可观测性设计完整且分层合理。**
20-§4 定义了 Metrics（Prometheus）+ Logs（JSON 结构化 + Correlation-ID）+ Traces（OpenTelemetry）+ LLM 专项（Langfuse，记录 Prompt/Token/Tool 调用）四层，且告警规则表（§4.4）覆盖了 LLM 错误率、Runner 耗尽、Agent 超时、Token 预警、越权探测 5 类关键场景。

**D.1.3 AI 降级策略的可信度极高。**
21-降级矩阵 + 31-§5 LLM 网关 + 20-§3.2 重试与级联，三者构成**完整闭环**：
- 静态层：每个介入点有明确的 L1/L2/L3 行为定义 + 置信度阈值 + 触发条件
- 动态层：连续 3 次低置信度或 LLM 失败自动降级，人工可恢复
- 默认安全：CH-21 将高危动作（提 JIRA、控门禁、发布 Skill）默认设为 L2 人工确认

**这是企业级 AI 产品的设计范本**，多数同类竞品降级设计远不及此。

**D.1.4 个别 SLO 偏激进，但已诚实标注。**
20-§1 的部分指标在真实条件下偏乐观：
- "单租户 5,000+ 并发 API / 平台 50,000+" —— 这要求 ~50 个 Runner 节点同时在线，V1 不现实
- "万级用例报告聚合 < 15s" —— 依赖下推 SQL，但跨租户聚合时 RLS 过滤开销未计入
- "AI 总结生成 P95 < 8s" —— LLM 供应商延迟不可控，这个 SLO 平台无法单方面保证

**肯定**：CH-24 已在 20-§1 顶部增加总注"指标为设计目标值，须经容量压测校准后方作为 SLA"——**这是负责任的做法**。建议进一步：将 SLO 按"平台可控"（如 Runner 启动时延、WebSocket 推送延迟）与"依赖外部"（如 LLM 响应、Jira 同步）分类，后者只承诺"尽力而为 + 降级"。

**D.1.5 合规与数据隐私的覆盖不均。**
20-§2 覆盖了加密与隔离，但**以下合规关键项缺失**：

| 合规项 | 现状 | 缺口 |
|---|---|---|
| **数据驻留 / 出境**（GDPR / 国内数据安全法） | 无 | 若目标含欧洲或国内政企客户，必须定义数据驻留策略 |
| **审计日志不可篡改** | 19-PRD 提"全局审计日志"未展开 | 缺审计日志的 append-only 设计、保留期限、独立存储 |
| **数据删除与被遗忘权** | 无 | 缺租户注销时的数据彻底删除流程（含向量库、备份） |
| **LLM 数据外泄防护** | 无 | 用户上传的 PRD / Swagger 发给外部 LLM 供应商，是否脱敏？是否合规？ |

最后一项尤其关键——**测试需求文档常含商业敏感信息**，若直接发给 Anthropic/OpenAI，可能违反客户保密协议。需定义"发往外部的 Prompt 脱敏策略"或"私有化部署 LLM 选项"。

## 六、E. 商业与落地可行性（评分：2.5 / 5.0）

### E.1 发现

**E.1.1 商业模式的完全空白是本维度的根本问题。**
全文档集**无任何关于**：定价模型、目标客户细分、销售模式、收入预测、单位经济性（Unit Economics，CAC/LTV）的内容。22-MVP 的"交付检查"全是技术项，**无任何商业里程碑**（如"V1 上线后 90 天内签约首付费客户"）。

**对比行业**：
- Mabl：早期明确定价按"应用 + 并发"，PLG 模式，30 天免费试用
- TestRail：按席位定价，SLG 模式，强依赖 Atlassian 生态集成
- QualityForge：**未定义**

这导致一个致命问题：**无法判断技术方案是否过度投资或投资不足**。若目标是"PLG 免费试用 + 小团队自助"，则多租户 RLS + 双信封加密 + K8s 弹性伸缩是过度设计；若目标是"金融企业私有化 + 年合同价百万级"，则合规缺口（D.1.5）必须 V1 解决。

**E.1.2 实施路径与资源估算缺失。**
22-MVP 给出了 V1/V2/V3 的功能切分，但：

- **无人员估算**：V1（1-3 个月）需要多少工程师、什么角色？
- **无里程碑**：1-3 个月内部哪周交付什么？
- **无风险缓冲**：1-3 个月是"开发完成"还是"上线可用"？
- **无依赖项**：V1 依赖的 K8s 集群、Vault、LLM 供应商账号何时到位？

**E.1.3 关键风险清单（技术/产品/市场/组织）未系统识别。**

- **影响**：轻度困扰，开发按约定（PRD 逻辑名 → 领域模型 → Schema 物理表）可消解，但应在术语表 03 明确三者映射关系。
- **建议**：在 03-术语表 增加"逻辑名 / 领域名 / 物理表名"三列对照表，一次性消解所有命名分裂。

### 新发现 3：TestDesign PRD 的"人工优化 Review"无数据模型支撑（建议）

- **01-功能地图 §2** 与 **22-MVP V1 §3.2** 均提"人工优化 Review"
- **11-PRD-TestDesign** 数据模型只有 RequirementDocument / TestPlan / TestScenario / DesignTestCase，**无"评审记录"实体**（谁审的、何时审的、改了什么、审批意见）
- **影响**：审计与协作场景无法支撑（如 TestLead 需查看某用例的评审历史）
- **建议**：在 11-PRD 与 04-领域模型 增加 `TestCaseReview` 实体（reviewer / decision / comment / reviewed_at / case_version）。

### 新发现 4：CICD 模块的 TIA 算法依赖未明确（建议）

- **18-CICD** 与 **01-功能地图 §9** 提"智能测试选择（TIA）"
- TIA 需要"代码变更 → 受影响用例集"的映射，这个映射的**构建时机与数据源**未定义：
  - 是执行时实时计算（依赖 t_kg_node/t_kg_edge 图遍历）？
  - 还是预先构建并维护（依赖额外的代码-用例映射表）？
- **影响**：V2 承诺 TIA，但数据基础可能在 V1 就需埋点（如执行时记录用例覆盖的代码路径）。
- **建议**：在 18-CICD 增加"TIA 数据基础"小节，明确映射来源（建议：V1 执行时记录用例-接口契约关联，V2 基于此做 TIA）。

### 新发现 5：执行计划 Saga 的隔离级别未明确（一般）

- **31-架构 §4** 与 **20-§5.1** 定义了工作空间初始化 Saga，但**未定义事务隔离级别**
- 多个 Saga 步骤并发执行时（如同时创建多个 Workspace），若隔离级别不当，可能出现幻读
- **影响**：低，Workspace 创建不是高频操作
- **建议**：在 31-§4 补充"Saga 隔离级别 = Read Committed + 业务层唯一约束"的说明。

## 九、关键建议（按优先级）

### P0 — 必须在 V1 启动开发前完成（阻塞项）

1. **停止文档细化，启动客户验证**：2 周内完成 5-10 个目标客户访谈，输出 `06-用户画像与场景证据册.md`。**理由**：当前所有设计的根基是"用户需要这个"，而这个根基无证据。访谈发现可能颠覆现有功能优先级。
2. **砍 V1 MVP 范围到 3 模块闭环**：Workspace（最小）+ TestDesign（AI 用例生成）+ Execution（API Runner）。**理由**：1-3 个月不可能交付当前 9 模块的哪怕最小版；广度优先会导致每个模块都不够深。
3. **建 AI 能力评测集与置信度计算方法**：输出 `23-AI能力评估方法论.md`。**理由**：所有 AI 能力（用例生成、RCA、自愈）目前不可验收；置信度来源未定义，降级链不可信。
4. **明确商业模式与目标客户**：输出 `07-商业模式与单位经济性.md`。**理由**：决定技术方案是过度还是不足；决定合规缺口是否 V1 致命。

### P1 — V1 开发期间并行完成

5. **确认团队规模与架构匹配度**：若 < 8 人，V1 采用模块化单体。输出 `38-团队与运维假设.md`。
6. **补合规设计**：输出 `24-合规与隐私设计.md`，重点覆盖 LLM 数据外泄防护（Prompt 脱敏 / 私有化 LLM 选项）。
7. **补竞品对标**：输出 `05-市场分析与竞品对标.md`，明确护城河与必赢之战。
8. **补风险登记册**：输出 `09-风险登记册.md`，覆盖产品/市场/组织三类当前空白风险。

## 十、结论

### 10.1 总体判断

QualityForge 是一份**技术成熟度远超产品验证成熟度**的设计文档集。作为技术方案，它在多租户安全、AI 降级、可观测性三方面达到了生产级严谨度，部分设计（共享目录型 RLS、LLM 降级链、默认安全自主策略）可作为行业教学案例。作为待研发的产品，它面临**"先射箭后画靶"的根本性流程问题**：在零用户证据、零竞品量化、零商业约束的前提下，已细化到字段级，导致功能广度严重超载、AI 可验收性存疑、商业可行性无法判断。

### 10.2 三句话给决策者

- **如果你是技术负责人**：这套设计的技术底座值得信任，可以启动开发——但请先确认团队规模与架构匹配，并把 V1 范围砍到 1/3。
- **如果你是产品负责人**：你的最大风险不在技术，而在"做出来没人用"。请立即启动客户访谈，用证据重新校准功能优先级，并补齐商业模式与成功指标。
- **如果你是投资/决策者**：这个方向的窗口期真实存在但正在关闭（12-18 个月）。值得投，但前提是团队接受"先验证再细化"的工作方式转型，而非继续在文档上雕花。

### 10.3 综合评分汇总

| 维度 | 评分 | 核心判断 |
|---|:---:|---|
| A. 产品定位与市场 | 2.8 | 愿景清晰但无市场证据，护城河论证缺位 |
| B. 功能架构 | 3.7 | 模块专业闭环完整，MVP 超载、AI 深度不均 |
| C. 技术方案 | 4.3 | 选型推理一流，复杂度超前于团队规模 |
| D. 非功能性 | 4.5 | 安全/可观测/降级堪称范本，合规有缺口 |
| E. 商业与落地 | 2.5 | 商业模式空白，资源估算缺失，风险识别偏科 |
| **加权综合** | **3.6** | **技术优秀、产品与商业维度急需补强** |

> 加权说明：A/B/E 各 25%，C/D 各 12.5%（因技术方案与非功能设计已有较高完成度，权重下调以突出产品/商业维度的紧迫缺口）。
