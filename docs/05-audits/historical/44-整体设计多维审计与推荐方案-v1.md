# QualityForge 整体设计多维审计与推荐方案 v1.0

> 状态：`HOLD_FOR_REBASE`（产品方向成立，但正式设计基线尚未统一）  
> 日期：2026-07-30  
> 审计目标：评估产品定位、功能设计、业务流转、数据闭环、系统架构、AI 治理、UI/UX、安全与单人实施可行性。  
> 已确认约束：公司内部项目；核心目标是软件测试提效、提升测试质量、为测试人员减负；路线 A；1 人 + MacBook + AI Agent。  
> 证据口径：`VERIFIED` 为仓库或本轮执行实证；`SUPPORTED` 为标准/论文支持；`INFERRED` 为基于当前资料的推断；`OPEN` 为缺少真实组织或用户数据。

## 一、执行结论

### 1.1 总体判断

**产品方向合理，但当前“九模块企业级 AI 测试平台”的整体设计不适合已确认的目标和资源约束；业务链路只有生成闭环，没有形成质量改进闭环。**

建议继续选择路线 A，但将产品定义进一步收敛为：

> **公司内部测试设计副驾驶 + 轻量反馈闭环**：把需求材料编译为可追踪、可评审、可导出的测试资产，并导入人工评审、执行结果和缺陷反馈，持续验证 AI 是否真正节省时间、减少漏测、提升测试资产有效性。

当前不应建设完整 Execution、RCA、Knowledge、CI/CD、Skill Marketplace、Multi-Agent 工作流和多租户云平台。它们可以保留为未来能力地图，但不得继续作为 V0/V1 的实现基线。

### 1.2 当前裁决

| 裁决项 | 结论 | 证据状态 |
|---|---|---|
| 产品问题是否真实 | 方向合理，但尚无真实基线证明优先级 | `INFERRED / OPEN` |
| 路线 A 是否合适 | 当前资产准备度最高，继续保留 | `VERIFIED` |
| 当前 V0 是否技术闭环 | 否；最终 Coverage Gate 仍失败 | `VERIFIED` |
| 当前设计是否业务闭环 | 否；缺少执行/人工/缺陷反馈回流 | `VERIFIED` |
| 九模块架构是否适合单人 | 否；范围与运维复杂度显著超出资源 | `VERIFIED + INFERRED` |
| 是否需要完整自建 Runner | V1 不需要；优先导入已有执行结果 | `RECOMMENDED` |
| 是否需要 UI | V0 不需要完整 UI；V1 只做 3 个核心界面 | `RECOMMENDED` |
| 是否允许进入 V1 开发 | 暂不允许；先完成基线重构与 V0 门禁 | `HOLD` |

## 四、业务关联、流转与闭环审计

### 4.1 当前主链

```text
需求材料
  → Testing IR
  → Strategy / Scenario / Case / Assertion
  → 四维 Coverage Gate
  → 人工评审
  → 批准 / 导出测试资产
```

这条链解决了“从需求到测试资产”的生产问题，但没有回答：

- 生成的测试点是否被测试人员采纳；
- 人工改了什么、为什么改；
- 用例是否实际执行、是否稳定；
- 是否发现真实缺陷；
- 漏测是否减少；
- 哪个模型/Prompt/规则组合表现更好；
- 是否真的节省了总人时，而不是把编写时间变成评审与返工时间。

因此当前只有**资产生成闭环**，没有**效能与质量闭环**。

### 4.2 本轮可执行验证

本轮重新运行仓库现有验证脚本，未覆盖写入原报告。验证过程中发现 IR 校验器自身存在非确定性：同一输入会在 `PASS` 与 `REJECT` 间变化。因此不能把仓库中已有的单次 `PASS` 报告作为稳定证据。

| 阶段 | 新鲜结果 |
|---|---|
| IR Schema/来源/冲突/可达性 | `NON_DETERMINISTIC`：同一输入交替出现 `PASS` / `REJECT` |
| Scenario 契约与状态覆盖映射 | `PASS` |
| Test Case 契约 | `PASS` |
| Assertion 静态检查 | `PASS` |
| 最终 Coverage Gate | `GATE_FAILURE` |

根因已定位到 [skills/ir-validator/scripts/validate.py](../../../prototypes/skills/ir-validator/scripts/validate.py) 的状态机初态推断：当状态机存在回边导致 `froms - targets` 为空时，代码使用 `next(iter(states))` 从无序 `set` 随机选择初态。选择 `DRAFT` 时所有状态可达；选择 `APPROVED` 时则报告 `DRAFT`、`GENERATING`、`REVIEWING` 不可达。通过固定不同 `PYTHONHASHSEED` 已稳定复现两种结果。

这属于 **P0 验证可信度缺陷**。在修复为“IR 显式声明 initial state，校验器禁止猜测”并增加确定性回归测试前，整条 V0 验证链不能宣称可重复。

最终门禁失败详情：

| 维度 | 实际 | 阈值 | 结果 |
|---|---:|---:|---|
| Rule | 75.0% | 100% | FAIL |
| Scenario | 33.3% | 70% | FAIL |
| State Transition | 25.0% | 90% | FAIL |
| Assertion | 100% | 85% | PASS |

Coverage 验证器已经表现出缺口拦截能力，是有价值的工程资产；但 IR 校验器的非确定性削弱了整条链的可信度。同时，V0-3 尚未达到 [43-Gate0产品与约束裁决包-v1.md](./43-Gate0产品与约束裁决包-v1.md) 所要求的“四维 Coverage”“无孤儿资产”和“结果可重复回放”退出证据。

### 4.3 推荐闭环

```text
需求/规则来源
  → IR/场景/用例/断言
  → 确定性校验与 Coverage Gate
  → 人工评审（采纳/轻改/重大修改/删除 + 原因）
  → 资产导出
  → 导入执行结果或人工结果
  → 缺陷/漏测/Flaky/无效用例反馈
  → 按模型+Prompt+规则版本回放评测
  → 保留、调整或回滚
```

这里的“执行反馈”不等于自建分布式 Runner。V1 只需支持 JSON/CSV/JUnit XML 等已有结果导入，或最低限度的人工反馈表。

## 六、数据与契约设计审计

### 6.1 当前缺口

数据库中的 `t_test_case` 只保存用例内容和基本状态；OpenAPI 的 `TestCase` 甚至没有暴露步骤、预期结果和来源。批量审批接口只接受 `caseIds`，无法说明评审人、决定、理由、版本或 Gate 证据。

建议增加以下最小逻辑对象；V0 可用 JSONL/文件实现，V1 再进入数据库：

| 对象 | 最小字段 |
|---|---|
| `SourceSlice` | source_id、document_hash、location、quoted_text、classification |
| `GenerationRun` | run_id、model、model_version、prompt_version、skill_version、parameters、cost、latency |
| `ArtifactLineage` | artifact_id、parent_ids、source_slice_ids、generation_run_id |
| `GateResult` | artifact_id、gate_type、verdict、finding_codes、threshold_version |
| `ReviewDecision` | artifact_id、reviewer、decision、reason、reviewed_at、before_hash、after_hash |
| `EditDelta` | artifact_id、field、change_type、semantic_severity、before、after |
| `AdoptionEvent` | artifact_id、adopted_as_is、minor_edit、major_edit、deleted |
| `ExecutionFeedback` | test_case_id、run_ref、status、duration、failure_type、flaky、evidence_ref |
| `DefectLink` | test_case_id、defect_ref、confirmed_fault、escaped_defect |

### 6.2 状态建议

统一为：

```text
DRAFT → GENERATED → GATE_FAILED | READY_FOR_REVIEW
READY_FOR_REVIEW → APPROVED | REJECTED | NEEDS_REVISION
APPROVED → EXPORTED → FEEDBACK_PENDING → VALIDATED | INEFFECTIVE | DEPRECATED
```

禁止：

- Gate 未通过仍进入 `APPROVED`；
- 数据源不足时将分析报告标记为 `COMPLETED`；
- 只凭模型自报置信度自动发布；
- 修改 Prompt 或模型后覆盖旧结果而不保留版本。

## 七、架构审计与推荐基线

### 7.1 当前架构问题

[31-系统架构设计.md](../../04-architecture/31-系统架构设计.md) 定义 API Gateway、7 个 FastAPI 服务、RabbitMQ 事件总线、Redis Streams 和 Saga；[20-非功能需求.md](../../03-governance/20-非功能需求.md) 进一步引入 K8s/KEDA、Vault、S3、Jaeger/Langfuse 和数千至数万并发目标。

这些设计不是绝对错误，但在“单组织、1 人、MacBook、先验证价值”的条件下会产生：

- 服务边界和契约维护成本大于业务价值；
- 本地开发、调试、迁移、监控和故障定位复杂；
- 大量时间用于平台底座，而不是验证提效和提质；
- 在没有负载、协作或故障域证据时提前支付分布式一致性成本；
- 无法由单人长期承担安全、数据、AI、产品和运维职责。

### 7.2 推荐 V0 架构

```text
CLI
 ├─ pipeline orchestrator
 ├─ skills adapters
 ├─ deterministic validators
 ├─ file-based HITL
 └─ evaluation reporter

storage: versioned JSON/JSONL + hashes
runtime: one local process, serial jobs
LLM: one configured provider
```

### 7.3 推荐 V1 架构

```text
轻量 Web UI
   │
模块化单体 API
 ├─ Intake
 ├─ Test Design
 ├─ Review & Asset
 ├─ Feedback Import
 ├─ Evaluation
 └─ Audit & Settings
   │
后台 Worker ─ LLM/长任务
   │
PostgreSQL（需要检索价值后再启用 pgvector）
```

暂不引入 RabbitMQ、Saga、微服务网关、K8s、独立向量库。后台任务可先用数据库任务表或进程内队列；只有出现多个独立部署单元、可测吞吐瓶颈或可靠性要求后再升级。

## 八、AI 治理、安全与质量审计

### 8.1 置信度不能作为自动发布依据

仓库多个模块用 `confidence >= 0.80/0.88/0.90` 决定自动化级别，但没有说明：

- 置信度如何计算；
- 是否与真实正确率校准；
- 在不同模型、Prompt、项目和任务上是否可迁移；
- 阈值如何通过历史数据冻结；
- 漂移后如何重新校准。

因此 V0/V1 应把置信度降级为“排序和提醒信号”，真正的准入依据是来源完整性、Schema、约束、覆盖、可执行性、变异/故障揭示能力和人工决定。

### 8.2 不保存或展示隐藏思考链

[16-PRD-AgentCenter.md](../../02-prd/16-PRD-AgentCenter.md) 设计展示和保存 CoT/Reasoning。建议替换为：

- 决策摘要；
- 输入证据引用；
- 调用的 Skill/Tool 与版本；
- 工具输入输出；
- Gate 结果；
- 人工批准与变更记录；
- 最终产物和失败原因。

这足以审计系统行为，也避免把不可验证的自由文本推理当作解释或事实。

### 8.3 关键安全问题

- 需求文档、日志、源码和 OpenAPI 都是潜在的间接 Prompt Injection 输入；
- LLM 输出在写入数据库、执行脚本、生成 CSV/HTML 前必须经过结构化校验和编码；
- 第三方 Skill/脚本属于可执行供应链，V1 不开放上传；
- [19-PRD-PlatformSettings.md](../../02-prd/19-PRD-PlatformSettings.md) 的 `curl ... | sh` Runner 安装方式不应作为默认产品操作；至少需要固定版本、校验和、签名验证和显式下载审查；
- V0 默认只处理脱敏、获准的数据，原始 Prompt/响应默认不持久化；
- 所有外部动作保持最小权限、显式允许列表和人工批准。

## 九、UI/UX 审计

### 9.1 审计边界

当前只有一个 TestCase Review Board Draw.io 静态线框，没有可运行页面。本轮无法验证：

- 实际布局、字体、间距、颜色与响应式；
- 键盘操作、焦点顺序、屏幕阅读器语义；
- Loading/Empty/Error/Partial/Offline 状态；
- 真实表格密度、长文本、批量操作和性能；
- 完整导航和跨页面任务完成率。

因此以下是**结构性 UX 审计**，不是视觉验收或 WCAG 合规结论。

### 9.2 核心旅程应缩短

当前 Workspace 旅程要求技术栈、环境、Secret、Swagger 和系统扫描后才进入价值链，对 V0/V1 过重。推荐首个成功路径：

```text
导入需求 → 查看来源与冲突 → 生成草稿 → 查看覆盖缺口
→ 对比修改 → 批准/退回 → 导出 → 记录反馈
```

Workspace 元数据作为可选增强，不阻塞第一次生成。

### 9.3 V1 只做三个核心界面

1. **导入与解析页**：输入、数据分类、解析状态、冲突和来源切片；
2. **生成与评审页**：规则/场景/用例/断言、来源证据、diff、Gate、批量决定；
3. **效果与质量页**：耗时、采纳、修改、漏测、执行/缺陷反馈、模型与成本对比。

### 9.4 Review Board 必须补充

- 每条用例显示来源证据、父链和 Gate 状态；
- AI 重生成前展示影响范围，生成后提供字段级与语义级 diff；
- “批量批准”只作用于当前明确选中且 Gate 通过的条目；
- 覆盖率显示分母、阈值、缺失项和计算版本，不能只显示百分比；
- 支持“采纳/轻改/重大修改/删除”及原因；
- 对不可逆操作二次确认并支持撤销；
- 提供生成中、部分完成、失败、限流、来源缺失、结果过期状态；
- 状态不能仅靠颜色表达；复选框、表格和操作必须有语义标签和键盘路径；
- 长步骤和断言应使用详情抽屉或分栏，而不是把全部内容压进一行表格。

## 十一、推荐选项

### 选项 A：维持当前路线 A，只生成和导出测试资产

- 优点：最省开发时间；最容易完成演示；
- 缺点：无法证明测试质量提升；可能只是把编写负担转成评审负担；
- 结论：**可作为 V0 技术验证，不适合作为 V1 产品闭环。**

### 选项 B：路线 A+，测试设计副驾驶 + 轻量反馈闭环（推荐）

- 保留需求→IR→场景→用例→断言→Coverage→HITL；
- 增加评审 diff、采纳/删除/修改原因；
- 增加已有执行结果/人工结果/缺陷反馈导入；
- 用同一 Golden Set 比较模型、Prompt、Skill 版本；
- 用“节省净人时 + 关键规则漏测 + 有效缺陷揭示 + 用户持续使用”联合决策；
- 不自建分布式执行平台。

结论：**最符合内部提效、提质、减负目标，也符合单人资源约束。**

### 选项 C：按现有九模块企业平台继续建设

- 优点：远期能力完整；
- 缺点：价值未验证、依赖链长、单人不可维护、上线周期和安全风险不可控；
- 结论：**当前明确不推荐。只在真实试点成功、团队与预算扩充、出现企业化触发器后重评。**

## 十二、建议指标与停止条件

### 12.1 指标树

| 核心目标 | 主指标 | 防作弊/质量护栏 |
|---|---|---|
| 测试提效 | 单需求测试设计净人时下降 | 包含生成、等待、评审、修改和返工全部时间 |
| 测试提质 | P0/P1 关键规则漏测率 | 必须为 0；来源追踪 100% |
| 测试有效性 | 真实缺陷揭示率、Mutation Score/故障暴露 | 不以用例数量或行覆盖率替代 |
| 为测试人员减负 | 周活、任务完成率、满意度、认知负担 | 同时记录重大修改率和工具绕过率 |
| AI 可靠性 | 采纳率、重大修改率、无来源编造率 | 按项目、模型、Prompt、Skill 版本分层 |
| 成本 | 每条获批有效测试资产成本 | LLM + 基础设施 + 人工评审成本 |

### 12.2 建议停止/转向条件

真实试点后满足任一项即暂停扩展：

- 连续两轮无法把关键规则漏测率稳定降为 0；
- 净人时没有下降，或评审/返工抵消生成收益；
- 重大修改和删除长期高于 40%；
- 两个项目均不愿持续使用；
- 无来源编造、跨项目数据混入或敏感信息事件重复发生；
- 单人无法持续维护评测、模型升级和数据治理；
- 真实基线证明失败排查远比测试设计更有价值，且具备可信 RCA 标签时，转向路线 B。

## 十三、推荐实施顺序

### Gate A：统一正式基线

1. 将本报告和 Gate 0 设为当前产品/架构裁决源；
2. 重写 02、11、12、20、21、22、30、31、32、33 的 V0/V1 相关口径；
3. 把九模块企业平台移入“远期能力地图”，不再混入 V1；
4. 删除或显式标记旧报告中的营销/竞品证据和未验证收益数字。

### Gate B：完成 V0 技术闭环

1. 修复 IR 校验器的非确定性：IR 显式声明初态，校验器不得从无序集合猜测；
2. 增加固定 Hash Seed/重复运行的确定性回归测试；
3. 修复当前 Rule/Scenario/State Coverage 缺口；
4. 增加生成版本、来源、Gate 和文件化 ReviewDecision；
5. 确保未通过 Gate 的资产无法批准；
6. 固定 Golden Set 并能从零重复回放；
7. 输出时间、成本、采纳和修改数据。

### Gate C：完成 V1 业务闭环

1. 选择 1 个脱敏真实项目进行影子试点；
2. 增加执行/人工/缺陷反馈导入；
3. 完成三个核心页面的可用原型；
4. 冻结数据边界、Owner、指标和停止条件；
5. 达标后再扩至第二项目。

## 十四、仍需组织确认的事项

以下不能由仓库或联网资料代替决策：

1. 第一个真实试点项目和测试人员；
2. 当前测试用例设计、评审、漏测与失败排查的实测基线；
3. 谁承担 Business、Technical、AI Quality、Security/Data、Operations Owner；
4. 哪些需求、源码、日志和客户数据允许发往哪个模型供应商；
5. LLM 月预算和人工时间上限；
6. V1 是否接受“导入执行结果”，而不是自建 Runner；
7. 业务成功和停止条件的最终阈值。

在这些事项确认、正式设计重新基线、V0 Coverage Gate 通过前，项目应保持 `HOLD_FOR_REBASE`，只继续最小验证和证据采集，不扩大功能范围。
