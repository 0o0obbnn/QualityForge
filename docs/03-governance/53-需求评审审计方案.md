## 一、审计目标与边界

**目标**：对一个尚未进入编码、纯文档驱动的 AI-Native 测试平台的需求体系，做一次独立、可追溯、结论可复现的评审审计。产出：① 缺陷清单（含定位、严重度、证据）；② 成熟度裁决；③ 整改优先级。

**边界**：
- 审需求与契约本身，不审实现（无实现可审）。
- 不预设"应收敛"或"应全量"——范围—资源匹配作为**证据维度**呈现，裁决权归决策者。
- 不复用已有报告结论，但允许交叉引用原始文档原文。

## 二、评审流程骨架（Fagan Inspection，简化 6 阶段）

> 出处：Fagan 1976；Wiegers《Improving Quality Through Software Inspections》。Fagan 原始流程针对代码，但被广泛适配到需求文档评审（Doolan 1991 已验证）。

对**每个被审模块**，按以下 6 阶段执行：

| 阶段 | 本项目具体动作 | 产物 |
|---|---|---|
| **① Planning 计划** | 选定被审文档、分配审查角色（作者/主持人/审查员）、确定审查速率（需求文档约 5~10 页/小时，依据 Wiegers 建议）| 审查包 |
| **② Overview 概述** | 建立被审文档的上下文（本模块依赖哪些其他模块、术语）| 上下文笔记 |
| **③ Preparation 准备（个体）** | 每个审查员独立按 check-list（第四节）+ PBR 视角（第五节）预先找缺陷，不依赖会议 | 个体缺陷笔记 |
| **④ Inspection Meeting 评审会** | 汇总缺陷、去重、定位、定级。**只记录缺陷，不讨论解决方案**（Fagan 铁律）| 缺陷日志 |
| **⑤ Rework 返工** | 由文档作者据缺陷日志修订（本审计只产出缺陷清单，返工由项目方执行）| — |
| **⑥ Follow-up 复验** | 主持人验证返工是否覆盖所有缺陷，关闭闭环 | 复验记录 |

> **单人项目的适配**：Fagan 传统需要多人。本项目可由 AI 审计员扮演多个独立审查员角色（tester / designer / user / ops / security 视角，见 PBR），并以"自我轮询"方式模拟 Preparation 阶段的多视角独立审查。这是对 Fagan 的合理裁剪，会在报告中注明。

## 三、需求质量特性 Check-list（IEEE 830 / 29148 + Wiegers）

> 出处：IEEE 830-1998 第 4.3 节 SRS 质量特性；ISO/IEC/IEEE 29148:2018；Wiegers & Beatty《Software Requirements》3rd, Ch.17 "Requirements Review Checklist"。
>
> **这是业界对"好需求"的共识定义**——不是自造维度。每个模块 PRD 逐条核对。

| 质量特性（IEEE/Wiegers 共识） | 在本项目要查的具体内容 |
|---|---|
| **Correct 正确性** | 业务规则是否与领域模型 / 状态机自洽；AI 能力宣称是否有技术依据 |
| **Complete 完整性** | 每个功能是否都有输入 / 输出 / 异常 / 前置条件；验收标准是否覆盖正常 + 异常路径；**是否缺 Given/When/Then** |
| **Consistent 一致性** | 与术语表、其他模块、技术契约是否冲突（交给第六节机器扫描兜底）|
| **Feasible 可行性** | 与 NFR（并发 / 延迟 / SLO）是否现实；与所选技术栈（Python/FastAPI/PG16）是否匹配；AI 能力在当前 LLM 能力边界内是否可达 |
| **Necessary 必要性** | 该功能是否真服务于某个被验证的痛点；是否有过度设计（YAGNI）|
| **Prioritized 已定优先级** | MVP 范围划分是否合理；P0/P1 是否真 P0 |
| **Unambiguous 无歧义** | "智能""自动""相关""及时"等模糊词；一词多义、多词同义 |
| **Verifiable 可验证** | **"相关度 95%""缩短 80%"等是否有定义、有基线、有测量方法**（本项目重灾区）|
| **Traceable 可追踪** | 能否上溯到目标 / 痛点、下溯到 API / DB / 验收标准（见第七节 RTM）|
| **Atomic 原子性** | 一个需求是否只表达一件事（可单独验收）|

**额外维度（Wiegers 强调，本项目必须）**：**Quality Attributes / NFR** —— 性能、安全、可靠性、可维护性、可观测性是否被主动 elicited 而非假设。对应项目文档 `20-非功能需求.md`。

## 四、视角驱动深审 PBR（Perspective-Based Reading）

> 出处：Basili V.R. et al., "The Empirical Investigation of Perspective-Based Reading", IEEE TSE；Shull & Rus, "How PBR Can Improve Requirements Inspections", IEEE Computer 2000。
>
> **PBR 的核心论点**（已被实证）：让审查员**分别**从不同利益相关方视角读需求，比自由阅读 / 单一 check-list 发现更多缺陷。每个视角带专属"场景脚本"（scenario）。

每个视角问一个核心问题：**"按这套需求，我能完成我的工作吗？卡在哪？"**

| PBR 视角 | 场景脚本（在本项目要模拟的思考路径）|
|---|---|
| **Tester 测试工程师**（主用者）| 我能从 PRD 导出可执行的测试用例吗？验收标准够具体吗？AI 生成的用例我怎么验证可信？|
| **Designer 设计师** | 领域模型 / 状态机够清晰支持我设计数据结构吗？实体关系闭环吗？|
| **User 终端用户**（Test Lead / 审批者）| 我能看懂 AI 的决策依据并做出审批吗？审批能驳回 / 回滚吗？|
| **Ops 运维 / 平台管理员** | 我能部署、监控、排障吗？Runner 节点池、LLM 网关怎么管？|
| **Security 安全 / 数据治理** | 凭证密钥、多租户隔离、审计日志、数据合规——需求里覆盖了吗？|
| **Dev 开发协作方** | 我消费的 API 契约、Mock、数据集稳定可对接吗？|

> PBR 原始论文用 tester/designer/user 三视角。本项目因是多角色治理平台，扩展到 6 视角。扩展依据是项目自身的利益相关方地图。

## 五、AI 系统专项审计（RE for ML / AI）

> 出处：Ahmad et al. "Requirements Engineering for Artificial Intelligence Systems", JSS 2023（被引 210）；SEI/CMU "Bridging the Gap between RE and Model Evaluation in ML"；Yoshioka et al. IEEE 2021。
>
> **为什么需要这一层**：普通 RE 方法（IEEE 830 等）默认系统是**确定性**的——给定输入有确定输出。AI/ML 系统是**概率性**的，传统"shall"句式难以表达，且引入了公平性 / 鲁棒性 / 可解释性等新 NFR。这是业界共识的 AI 系统需求工程难题（SEI 明确称其为"ML 开发中最难的任务之一"）。

本项目是 AI-Native 平台，必须专项审计五个 AI 特有维度：

| 子项 | 审什么 | 为什么（依据）|
|---|---|---|
| **1. 自治等级与降级矩阵一致性** | 全局矩阵（L0~L3）↔ 各模块 PRD 内嵌的自治规则是否冲突（如默认 L2 但 PRD 允许置信度>0.8 自动入库）| AI 系统的人机控制边界必须显式、一致（ISO/IEC 23053 框架要求）|
| **2. 阈值集中管理与校准** | 所有 AI 置信度 / 相似度阈值（0.80/0.85/.../0.95）登记成表，标注是否各有校准集 | 概率系统的阈值若无校准集则不可验证（ISO/IEC 25059:2023 functional correctness 不可在所有情形保证）|
| **3. 评测覆盖度** | 30 个 Skill 中有几个有标准 evals；E2E Coverage Gate 的规则 / 场景 / 状态转换覆盖率 | RE 与模型评估之间的鸿沟是 SEI 指出的核心难题 |
| **4. 可信链证据完整性** | Testing IR / Business Rule / Source Trace / Assertion / Coverage Report / Review Task——被 Skill 原型使用但可能未进入正式领域模型 / 术语表 / API / DB | AI 输出的可追溯性是 RE-for-ML 的关键 NFR |
| **5. 人机协作可逆性** | AI 决策是否可追溯、可驳回、可回滚 | 非确定性系统的容错与可控（ISO/IEC 25059:2023 adaptability / functional correctness）|

**v2.1 新增 · LLM-Native RE 视角**（对应用 LLM/Agent 做 RE 的平台）：

> 本项目是用 LLM+Agent 做需求解析/用例生成的 AI-Native 平台，自身即"LLM 增强的 RE 系统"。据 2025-2026 最新研究（LLM-for-RE SLR arXiv:2509.11446；Hemmat et al. 2025；Stein et al. 2026），这类系统在需求侧有特殊风险，增设以下检查点：
>
> | 检查点 | 审什么 |
> |---|---|
> | **LLM 输出可验证性** | AI 生成用例/IR 后，是否有非 LLM 的客观验收手段（否则陷入"AI 自评 AI"循环）|
> | **Prompt 契约工程化** | Prompt 版本是否作为受管理的需求制品（版本化、评审、变更控制），而非隐式知识 |
> | **LLM 幻觉 / 漂移防护** | 需求是否要求对 LLM 输出做来源溯源（Source Trace）与一致性校验 |
> | **数据-模型-集成三件套** | 对标 ISO/IEC 23053，审计"训练/示例数据 + LLM 模型 + 平台集成"是否在需求中分别有约束 |

## 六、跨契约一致性机器扫描（Consistency + 反向追踪）

> 出处：IEEE 830 一致性特性；RTM 反向追踪"无孤儿"原则（Inflectra："反向 RTM 确保不存在没有需求来源的设计 / 用例 / 测试"）。

文档、80条API路径、107张目标表和30个Skill（2026-08-14 第0周补丁 B1 口径更新）的人工交叉核对不现实，必须从当前工作区动态盘点，并用脚本兜底硬冲突：

- **术语表 ↔ 领域模型 ↔ API Schema ↔ DB DDL ↔ Skill 原型**：命名漂移、字段缺失 / 多出、类型不一致
- **状态机一致性**：同一实体在不同文档的状态枚举是否冲突（如 Requirement 状态值）
- **API 路径 ↔ 领域实体**：每个实体是否有对应 CRUD 路径、每个路径是否能映射到实体（双向）
- **外键 / 引用完整性**：TestPlan → Requirement 等关联在 DB / API 是否都存在
- **反向孤儿检测**：是否存在没有需求来源的 API / DB 表 / Skill（过度设计信号）

## 七、追踪性审计（RTM 双向追踪）

> 出处：IEEE 830 推荐双向追踪；Jama Software / SodiusWillert 最佳实践；Wang et al. 2018。

构建**端到端追踪矩阵**，标出断点：

```
用户目标 → 痛点 → 功能需求 → API 路径 → DB 实体 → 验收标准
    ↑                                          ↓
    └──────────── 反向追踪（无孤儿）────────────┘
```

- **Forward 正向追踪**：每个需求 → 是否有设计 / API / DB / 测试覆盖（保证"无遗漏"）
- **Backward 反向追踪**：每个 API / DB 表 / Skill → 是否能回溯到需求（保证"无镀金 / 无过度设计"）

断点即缺陷。

## 八、缺陷分级（ISTQB Severity + Priority 双轴）

> 出处：ISTQB Foundation Syllabus；行业统一实践（多源印证：Kualitee、TestSigma、Bird Eats Bug、QAMadness 2026 均一致）。

采用**双轴**，避免单轴混淆"技术严重度"与"业务紧急度"：

### Severity（技术影响，5 级）

| 级别 | 含义 | 本项目典型 |
|---|---|---|
| **Blocker** | 阻断后续工作 | 核心概念无定义、契约断层、自相矛盾 |
| **Critical** | 核心路径不可验收 / 不可测试 | 关键功能缺验收标准、收益指标无基线 |
| **Major** | 显著影响质量 | 歧义、阈值无校准、状态机冲突 |
| **Minor** | 影响有限 | 用词不一致、文档结构 |
| **Trivial** | 几乎无影响 | 排版、拼写 |

### Priority（业务紧急度，3 级）

| 级别 | 含义 |
|---|---|
| **High** | 影响核心价值链或 Gate，必须立即整改 |
| **Medium** | 影响次要功能，下个迭代处理 |
| **Low** | 不影响交付，有空再改 |

每条缺陷打 **Severity × Priority** 双标签。

## 九、成熟度裁决标准（基于质量特性达成度 + 缺陷密度）

> 出处：IEEE 830 对 SRS 的"可接受 / 需修订"定性判定；工业界 Stage-Gate / ASPICE 评分实践。

**每模块评分**：第三节的 10 个质量特性各打 1-5 分，取平均（对标 ASPICE 能力级别 0-5 的打分思路）：

| 平均分 | 裁决 | 含义 |
|---|---|---|
| `4.0 ~ 5.0` | `GATE_PASS` | 可进入设计 / 开发 |
| `3.0 ~ 3.9` | `PASS_WITH_ACTIONS` | 带整改项放行 |
| `2.0 ~ 2.9` | `REVISE` | 需修订后复审 |
| `1.0 ~ 1.9` | `REVISE_AND_FOCUS` | 需收敛范围后重做 |
| `< 1.0` | `REJECT` | 推翻重来 |

**全平台裁决** = 各模块加权（核心价值链权重高）+ **硬门禁**：任何核心模块存在 Blocker 即全平台不得 PASS。
