# 22-版本规划 v2.0

> 产品版本与API版本分离。V0-V3描述产品交付范围；`/api/v1`描述接口兼容代际。任何版本均不取消正式产出物人工审核、外部写入批准、报告签署、权限隔离和可追溯性。

## 1. 总体路线

| 阶段 | 核心问题 | 完成定义 |
|---|---|---|
| V0 设计/Gate 0 | 产品边界和AI治理是否可实现、可验证 | 权威契约一致；Gate 0原型可静态验证；独立复审给出开发准入结论 |
| V1 单Workspace试点 | 对话驱动的受控Agent协作是否在真实业务链中提升效率和质量 | 首屏对话与项目驾驶舱可用；真实API/手工测试闭环、独立评估、人工硬门与完整证据链可验收 |
| V2 团队协同 | 平台能否稳定支持团队、集成和多Runner | 权限/审核成熟；外部集成、知识反馈、门禁建议与恢复经过实测 |
| V3 企业规模 | 能否在更大规模提供受控L3代理能力 | 容量、安全、韧性、评测和运营SLO均有真实证据 |

## 2. V0：设计与开发准入

### 范围

- 8模块产品边界、核心旅程、八类正式产出物和人工审核契约。
- 03/04/21/32/33/34/55权威源及配套导航、PRD、架构、线框一致。
- 30个Skill原型、Gate 0的1 Supervisor+3 Subagent受限Workflow。
- 负例与Golden样例、结构验证器、现状独立审计。

### 非目标

- 不声称已有后端、前端、数据库迁移、Runner或真实Agent运行时。
- 不以静态Checker PASS宣称业务正确或产品可用。

### 准出门

所有Blocker/Critical有关闭证据或明确阻断；权威源无不可解释冲突；目标架构可拆成开发Backlog；V1试点、基线和验收数据已定义。

## 3. V1：最小端到端试点

### 产品范围

| 模块 | V1最小范围 |
|---|---|
| 项目与协作 | 最近更新项目驾驶舱、项目/Release切换、Conversation、Clarification、TaskCard/AgentPlan确认、WorkItem、审核队列、阻塞处理和真实运行命令 |
| 知识库 | Markdown/OpenAPI导入、SourceSnapshot、需求/API契约版本和基础检索 |
| 测试策划与设计 | TestingIR、TestStrategy、TestPlan、场景、TestCase草稿/版本与人工审核 |
| 自动化测试开发 | Web/API代码生成、版本、用例绑定、静态/受控检查和代码审核 |
| 测试执行 | 手工测试结果/证据记录；单资源池Runner、版本冻结、执行任务、结果、日志和证据 |
| 质量分析与缺陷 | 基础RCA草稿、Defect草稿、TestReport草稿与人工审核；外部同步可先手工（手工同步仍须落 DefectSyncAttempt+批准记录+回执，裁决 B2-4） |
| AI Agent中心 | 协调Agent+受限专业Agent+独立评估Agent，固定Workflow、allowlist、Trace、版本化Rubric/校准、预算与L0/L1/L2降级 |
| 平台管理 | 单租户/单Workspace试点所需的Release、成员、环境、Secret引用、RBAC和审计 |

### 明确不做

- 多租户商业化运营、可视化Workflow设计器、Skill市场、多云弹性和L3自治。
- 自动放行发布、自动对外提Defect、无人审核正式资产。
- 在基线建立前承诺固定并发/延迟/准确率或收益百分比。
- Web UI自动化执行不作为V1必须闭环；V1保留Web自动化代码产出与审核，但真实执行验收聚焦API与手工测试记录。

### 试点验收

选择一个真实但可控的Workspace和Release，完成“来源→策略/计划/用例→Web/API代码→执行→分析/Defect/报告→人工审核”全链；分别报告实例覆盖、设计覆盖、可执行覆盖、严格有效覆盖和人工验收，不混用分母。

## 4. V2：团队协同与集成增强

- 多Workspace/团队协作、大规模委派和审计运营。V1已允许对指定高风险产出物启用可配置四眼复核，V2将其扩展为团队级策略。
- 多Runner调度、失败恢复、计划并行和资源配额。
- 外部Defect/代码仓库/CI集成的逐次授权、幂等、冲突和回执。
- 质量门禁规则、智能回归建议、知识反馈、契约漂移和Locator候选修复。
- 以真实Golden Set持续评测Agent/Skill/Prompt/Workflow，并形成介入点的版本化校准记录。

准出需有容量、韧性、安全、成本和误放/误阻基线；不能只以功能页面完成判定。

## 5. V3：企业规模与扩展代理

- 经过实测的弹性Runner、资源隔离、区域/故障域策略和企业集成。
- 可管理的Skill/Agent/Workflow生命周期、供应链安全与Eval准入。
- 在批准的低/中风险范围启用L3跨工作项编排、自动纠错和恢复。
- 高级变化影响、性能/安全/视觉能力、风险预测和知识演进。

L3仍在正式资产批准、外部写入、报告签署、门禁放行和权限变更前暂停。

## 6. 指标建立顺序

1. V0定义指标、分母、样本与采集方式。
2. V1影子/人工流程建立基线，再做同任务对照。
3. 至少经过一个Release窗口后批准目标值。
4. V2/V3按Workspace规模、任务类型、风险和AI版本分层设SLO。
5. 模型/Prompt/Skill/Workflow或数据分布变化后重新校准。

## 7. 版本门禁

| Gate | 必需证据 |
|---|---|
| 产品 | 范围、非目标、核心旅程、用户验收和已知限制 |
| 质量 | 自动检查、独立验证、人工验收分层结果 |
| 安全 | 多租户、越权、Secret、外联、供应链和审计测试 |
| AI | Golden Set、人工修改率、误放/误阻、降级和越权率 |
| 运行 | 容量、延迟、恢复、成本和可观测证据 |
| 发布 | 精确版本/摘要、迁移/回滚、批准与签署记录 |

## 附录 C · 五类覆盖率权威口径(裁决 2026-08-14,试点前冻结)

> 出处:QF-REQ-024 整改 + QF-REQ-003 裁决(B2-1);与 04 CoverageReport.denominatorDefinitionRef 枚举、33 t_coverage_report CHECK 同步。
> 五类口径形成验证阶梯,分母互不推导、互不替代;任何试点报告必须声明所用口径,禁止混用分母。

| 口径 | 标识 | 回答的问题 | 分母 | 分子 |
|---|---|---|---|---|
| 实例覆盖 | INSTANCE | 被测对象实例是否至少有一处测试资产指向? | 冻结快照中被测实例总数(按 BusinessRule/状态转换/APIOperation/需求条目分层) | 被至少一个已批准用例版本引用的实例数 |
| 设计覆盖 | DESIGN | 需求条目是否都被追溯映射到用例? | inScope 需求条目总数(剔除策略明示排除项) | 已通过 SourceTrace 映射到至少一个已批准用例版本的需求条目数 |
| 可执行覆盖 | EXECUTABLE | 已批准用例是否都有可执行代码、且真的被执行? | ①已批准用例版本总数 ②ExecutionPlanVersion 选中用例版本总数 | ①已绑定 AutomationScriptVersionCaseBinding 的用例版本数 ②已产生 ExecutionResult 的用例版本数 |
| 严格有效覆盖 | EFFECTIVE | 断言是否真的验证通过? | 冻结范围内全部必需断言 | verdict=PASS 的断言数(仅限有效执行) |
| 人工验收覆盖 | HUMAN_ACCEPTANCE | 应人工审核的正式产出物版本是否都经人工批准? | 试点范围内必须人工审核的正式产出物版本总数(八类) | 全部必要 ReviewTask 均 APPROVED 且版本 PUBLISHED 的产出物版本数 |

规则:
1. 未检查/不可判定不计通过;空分母仅当 Strategy 显式声明 not_applicable_dimensions 时可标 N/A(04 CoverageReport 口径)。
2. REJECT 或重复/额外/畸形证据强制失败(assertion 维)。
3. 目标值不在此定义——按 §6 指标建立顺序,试点基线后批准。
4. 归属:实例/严格有效/人工验收由 15 号 CoverageReport 汇总;设计覆盖由 12 号中间产物提供(裁决 B2-1);可执行覆盖由 13 号绑定 + 14 号执行事实支撑。
