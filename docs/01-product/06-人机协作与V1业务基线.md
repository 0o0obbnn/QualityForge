# 06-人机协作与V1业务基线

> 状态：现行产品权威基线  
> 生效日期：2026-08-27  
> 来源：QF-PD-001～057 人工确认裁决  
> 权威范围：V1 产品定位、人机协作范式、统一业务旅程、功能分面、角色、首页职责与业务门禁

## 1. 裁决结论

QualityForge V1 是面向小型测试团队的**人机协同测试工作台**，不是单纯的 AI 产出物装配线，也不是无人值守测试平台。

平台采用“装配线硬门 + 过程协作回环”的融合范式：

- AI 负责完整授权资料的检索理解、方案草拟、影响分析、代码生成、执行辅助和结果整理；
- 人负责目标、范围、资料冲突、授权、正式资产审核、例外处理和发布裁决；
- AI 遇到影响结论的资料缺口或冲突时，必须发起可审计澄清并暂停，不得猜测；
- 正式资产、执行事实和人工决定仍保持不可变版本、精确引用与人工硬门。

## 2. V1 使用模式与角色

V1 面向小团队协作，允许单人部署兼任职责，但不删除职责分离语义。

| 产品角色 | 主要责任 | 明确边界 |
|---|---|---|
| TestEngineer | 资料整理、资产生产与修改、人工/API执行、证据和缺陷处理 | 不默认拥有高风险发布裁决或平台安全配置权 |
| TestLead | 目标范围、质量规则、正式审核、高风险例外和Release最终裁决 | 不因业务角色获得Secret明文或平台基础设施权限 |
| PlatformAdmin | 环境、Runner、成员、凭据引用、Agent/Skill/工具准入和审计 | 不自动获得业务资产批准和Release签署权 |
| ViewerAuditor | 查看授权范围内的资料、Trace、证据和决定 | 无写入、执行、批准或外部同步权 |

Approver仍由ReviewPolicy、作用域、能力和职责分离动态计算。单人模式可兼任TestEngineer、TestLead与PlatformAdmin，但关键动作必须保留身份、理由和审计记录。

## 3. 产品上下文

```text
Tenant
└── Workspace（UI：项目，所有业务操作的必选上下文）
    ├── 项目资料、代码、接口契约和知识
    └── Release（交付、执行和质量活动的必选上下文，可并行多个）
        ├── 测试依据基线
        ├── 父WorkItem与阶段WorkItem
        ├── 正式资产版本
        ├── ExecutionPlanVersion与执行事实
        └── 质量分析、报告和ReleaseDecision
```

- 知识探索允许不选择Release；一旦形成正式交付资产、执行、缺陷或质量结论，必须绑定Release。
- 同一Workspace可同时存在多个进行中的Release，但资产、执行、质量门槛和裁决严格隔离。
- 跨Release数据只用于趋势比较，不得混入当前Release的质量裁决。

## 4. 统一端到端业务旅程

```text
选择项目与Release
→ 导入文件/Git/OpenAPI/Postman并形成资料版本
→ 数据分级、完整性检查与冲突裁决
→ 用户对话或直接填写结构化任务卡
→ 协调Agent生成AgentPlan（步骤、范围、权限、预算、风险）
→ 人工确认计划与授权
→ 策略阶段：生成 → 评估 → 人工审核 → 发布
→ 计划阶段：生成 → 评估 → 人工审核 → 发布
→ 用例阶段：生成/导入/编辑 → 评估 → 人工审核 → 发布
→ API自动化阶段：生成 → 检查/试跑 → Code Review → 发布
→ 冻结全部正式版本形成ExecutionPlanVersion
→ Preflight检查环境、Runner、数据、凭据授权、依赖和预算
→ 人工或API自动化真实执行，可暂停/继续/取消/重试
→ 形成只追加ExecutionResult与不可变Evidence
→ 生成并评估ResultAnalysis、Defect与TestReport
→ 人工审核，AI形成发布建议
→ TestLead作出通过/条件通过/不通过的ReleaseDecision
→ 形成KnowledgeCandidate，经人工审核后发布KnowledgeEntryVersion
```

### 4.1 阶段交接规则

1. 用户目标创建一个父WorkItem；策略、计划、用例、自动化、执行和分析分别创建阶段WorkItem。
2. 协调Agent可生成后续阶段草稿计划，但只有当前阶段产物达到`PUBLISHED`后，编排服务才能创建或激活正式下游阶段。
3. 阶段交接由WorkOrchestrationService依据已批准AgentPlan和WorkflowTemplate执行，产生WorkItemEvent；页面不得自行推进状态。
4. 上游输入、权限或关键配置变化时，仅失效受影响阶段及其下游，保留未受影响的检查点和历史证据。
5. 自动阶段推进必须在既定权限和预算范围内；新增外部写入、高风险执行或预算必须再次人工授权。

## 5. 四个产品分面

八个能力域继续作为领域Owner与专业工作台边界，业务设计以四个分面解释其关系。本基线不预先锁定一级导航数量；导航层级在首屏原型阶段裁决，但“测试产出物”不得恢复为一级创建模块。

| 分面 | 包含模块/能力 | 核心职责 |
|---|---|---|
| 测试业务工作面 | 知识库、测试策划与设计、自动化测试开发、测试执行、质量分析与缺陷 | 拥有测试业务正文、版本和领域规则 |
| 流程与人工控制面 | 任务看板、统一待办、ReviewTask、AgentPlan、Clarification、RunCommand、AuthorizationDecision | 目标、阶段交接、人工决定与运行控制 |
| AI控制面 | 协调Agent、专业Agent、独立评估Agent、Skill、Prompt、Workflow、Trace、Eval、预算 | 能力、运行和效果治理，不拥有业务产出物 |
| 平台控制面 | Workspace/Release、环境、Runner、RBAC、Secret、集成、审计与数据安全门禁 | 提供上下文、安全和基础设施边界 |

## 6. 人机协作入口

### 6.1 协调Agent

协调Agent是默认对话入口，负责理解意图、检索当前项目上下文、生成任务卡和AgentPlan、拆分阶段、调用专业Agent、汇总状态并路由人工待办。用户可以下钻查看专业Agent过程和结果，但不需要重复提供项目背景。

### 6.2 对话与任务的边界

- 对话可用于查询项目事实、解释风险、提出目标和回答澄清问题。
- 执行必须基于结构化任务卡和已批准AgentPlan；聊天文本不能直接成为授权。
- 结构化任务卡至少包含Workspace、Release、目标、范围、验收标准、约束、权限与预算。
- 人工回答ClarificationRequest后形成`evidenceClass=CONFIRMED`的可追溯协作事件，并触发受影响节点重新计算。

### 6.3 运行控制

运行中的AgentSession和ExecutionTask必须通过受控命令执行`PAUSE/RESUME/CANCEL/RETRY/AUTHORIZE/REVOKE`。命令到安全点生效，产生CommandReceipt；暂停后恢复必须重新检查版本、权限和预算。不得通过前端本地状态或WebSocket消息直接改写业务状态。

## 7. 资料完整读取与数据安全

“完整读取”指Agent可在授权项目空间内检索全部相关资料，不等于每次模型调用发送整库内容。

1. 项目资料目录记录来源、版本、摘要、权威等级、负责人、时效和数据级别。
2. 测试策划与发布分析前强制执行资料完整性检查；资料不足时只能输出草案与缺口清单。
3. 冲突资料由资料负责人裁决；AI不得自行选择有利版本。
4. 每次模型调用按任务最小化装载，受供应商白名单、数据分级、脱敏、区域和审批约束。
5. L1公开可发送批准模型；L2内部最小化并留痕；L3敏感需脱敏和审批；L4严格保密禁止发送，只可使用受控句柄。
6. AI对授权代码库默认完整只读；写入仅限隔离分支/工作区并经人工审查。

## 8. 正式资产、执行与质量门禁

- `APPROVED`表示审核通过待发布；只有`PUBLISHED`不可变版本可形成正式下游依赖或进入执行。
- ExecutionPlanVersion冻结计划、用例、脚本、契约、环境、数据配置和授权摘要。
- Preflight未通过时默认阻断；人工豁免必须记录范围、理由、批准人和有效期。
- 原始请求、响应、日志、截图、时间戳、Runner回执和Evidence不可修改；结论只能创建修订版本。
- 内部Defect是质量闭环真相源，外部缺陷平台是可选同步目标。
- AI提供Release建议；TestLead作出最终ReleaseDecision。
- 正式资产、审批、证据和发布结论不可普通物理删除，只能归档、失效或受控撤回。

## 9. 独立评估Agent

评估Agent与执行Agent身份、Prompt、模型、权限、预算和运行记录隔离，不能修改被评对象或评分规则。

评估顺序为：

`冻结资产版本 → 确定性硬门 → 语义分维度评分 → 风险等级与证据 → 人工审核 → 校准样本 → 离线基准回归`

- 评估对象包括策略、计划、用例、自动化代码、执行证据、缺陷分析和报告。
- 维度包括完整性、正确性、一致性、追溯性、风险覆盖、可执行性、证据充分性和合规性。
- 阻断项直接退回；高风险强制人工复核；中风险修改后重评；低风险进入正常审核。
- 总分只用于解释、比较和趋势，不单独决定通过。
- 项目质量评分综合覆盖、资产质量、执行、缺陷、证据和门禁，并同时展示资料完整度和置信度。
- 人工审核结果形成校准样本；规则、Prompt和模型配置不得自动自修改。

## 10. 首页和导航职责

登录后默认首页为**项目/Release驾驶舱**，不是“测试产出物”。

首页只读聚合以下信息：

- 最近有效业务事件更新的项目和Release，支持常用项目固定与切换；
- 当前阶段、完成度、风险、阻塞和最近活动；
- 当前上下文的协调Agent对话；
- 计划确认、审核、授权、异常、重试和发布裁决的统一待办；
- 项目质量评分、趋势、阻断、资料完整度与置信度。

“测试资产”降为二级跨域检索入口，只提供查询、版本、关联和追溯，不承担创建流程。Agent中心只管理能力、运行、Trace、成本和评估。

项目最近更新时间仅由资料基线、正式资产、审核、执行、缺陷、质量结论和人工决定等有效业务事件驱动；AI思考日志、轮询和未提交草稿不得刷新排序。

## 11. V1范围与真实验收

V1必须实现：

- 单租户体验与Tenant数据边界；真实Workspace/Release上下文；
- 文件、Git、Markdown、DOCX、PDF、表格、OpenAPI/Swagger和Postman Collection接入；
- 资料完整性/冲突/安全门禁；
- AI对话、任务卡、AgentPlan、父子WorkItem、统一待办和运行控制；
- 策略、计划、用例、API自动化的版本、评估和人工审核；
- 一个真实API Runner闭环，同时支持人工测试结果和证据；
- Preflight、检查点、预算、不可变结果与证据；
- ResultAnalysis、内部Defect、报告、质量门禁建议和人工ReleaseDecision；
- 独立评估Agent的在线评估与固定基准集离线回归；
- KnowledgeCandidate人工审核与知识回流。

V1后置：Web UI自动化生产化、任意工作流编排器、复杂设备实验室、多租户运营与计费、全量外部连接器和开放Skill市场。

V1只能通过代表性项目真实端到端验收完成。关键链路使用mock、无法人工控制、证据可被覆盖或不能反向追溯时，不得判定完成。
