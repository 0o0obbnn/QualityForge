## 一、产品定位

QualityForge 不是“传统测试管理平台增加若干 AI 功能”，而是一条以测试交付物为主线的智能测试生产线：

> **AI Agent 负责尽可能多的分析、生产、执行和修改工作；测试人员负责目标设定、审核、批改、纠偏和最终质量把控。**

平台围绕测试生命周期的正式产出物组织功能，而不是围绕 Agent、Skill、Runner、向量库等内部技术组件组织测试人员的日常工作。

核心目标：

1. **提高效率**：减少需求阅读、测试设计、代码编写、结果整理和报告编制中的重复劳动。
2. **提高质量**：通过来源追踪、AI 交叉检查、人工审核和确定性门禁减少遗漏与错误。
3. **保持人类责任**：AI 可以生成和执行，但正式产出物必须由有权限的测试人员审核后生效。
4. **形成持续学习闭环**：执行结果、缺陷和复盘经验经审核后回流知识库，提高下一轮 AI 产出质量。

## 二、模块划分裁决

### 2.1 产品平面与能力域

QualityForge的产品功能按 **4个平面** 组织：项目与协作、测试生产、质量交付、平台治理。以下8项继续作为业务能力域与实体Owner边界，不再强制一对一平铺为一级菜单。具体导航数量留待原型阶段裁决；测试产出物不再是一级创建模块。

#### 测试工作与产出物能力域（6 个）

1. **任务看板**
2. **知识库**
3. **测试策划与设计**
4. **自动化测试开发**
5. **测试执行**
6. **质量分析与缺陷**

#### 治理能力域（2 个）

7. **AI Agent 中心**
8. **平台管理**

### 2.2 不计入一级功能模块的全局对象

- **项目**：产品界面名称，技术实体继续使用 `Workspace/workspaceId`；它是数据与权限上下文，不是功能模块。
- **发布版本**：目标实体 `Release`；它是一次业务交付上下文，不是功能模块。
- **环境**：`Environment`；它是执行上下文，不是功能模块。
- **工作台首页**：任务看板的默认视图，不另计模块。
- **Agent/Skill**：在 AI Agent 中心内部保持独立资源和生命周期，不分别占测试人员一级导航。

### 2.3 关键调整

- 原 Workbench 升格为真正的**任务看板**，成为测试人员和 AI 协作的主入口，而不是只展示图表的 Dashboard。
- 原 KnowledgeCenter 和分散的项目资料视图统一为**知识库**。
- 测试策略、测试计划、场景和测试用例统一归入**测试策划与设计**。
- Web/API 自动化代码是需要 Code Review 的正式产出物，**自动化测试开发升格为一级模块**。
- 执行后的结果分析、Bug 和测试报告组成一个连续闭环，统一归入**质量分析与缺陷**。
- CI/CD 与发布门禁先作为质量分析与缺陷的交付集成能力；是否独立升格由后续版本价值和权限复杂度决定。
- AgentCenter 与 SkillCenter 在产品入口上聚合为**AI Agent 中心**，但领域实体、权限和发布生命周期不合并。
- PlatformSettings 重构为有明确子域的**平台管理**，不再作为无边界的设置抽屉。

## 三、整体工作模型

### 3.1 测试产出物主链

```text
项目知识与需求
    ↓
测试策略
    ↓
测试计划
    ↓
测试场景与测试用例
    ↓
Web / API 自动化测试代码
    ↓
测试执行与原始结果
    ↓
结果分析与 Bug 草稿
    ↓
测试报告与质量结论
    ↓
审核后的知识沉淀
```

### 3.2 人机职责

人机协作采用“对话入口 + 结构化工作台”双轨模式。对话负责表达意图、澄清和反馈；TaskCard、AgentPlan、ReviewTask、RunCommand和业务产出物负责可执行与可审计状态。对话文本本身不构成授权、批准或执行真相。

| 阶段       | AI Agent 主要职责                                  | 测试人员主要职责                 |
| ---------- | -------------------------------------------------- | -------------------------------- |
| 目标与输入 | 读取知识库、识别信息缺口、提出澄清项               | 确定目标、范围、约束和输入权威性 |
| 生产       | 生成策略、计划、用例、代码、分析、Bug 和报告草稿   | 审核、批注、直接修改、退回重做   |
| 执行       | 运行已批准任务、采集日志和证据、自动重试允许的动作 | 监控高风险任务、处理阻塞和例外   |
| 判断       | 提供覆盖、根因、风险和改进建议                     | 判断结论是否成立，批准正式产出物 |
| 沉淀       | 生成知识候选并关联来源                             | 审核适用范围、有效期和发布状态   |

AI Agent 是主要生产者和执行者，但不是最终质量责任人。正式测试产出、对外缺陷、知识发布和发布结论均由人批准。

### 3.3 正式产出物统一生命周期

```text
待创建
→ AI 生成中
→ 待人工审核
→ 人工修改 / 批注
→ 退回 AI 重做（可选）
→ 审核通过
→ 正式发布 / 入库
→ 使用 / 执行
→ 版本变更
→ 归档
```

以下是正式产出物的概念阶段，不直接作为 WorkItem 状态枚举；WorkItem 的精确状态及当前执行者规则以 §5.5.4 为准：

| 通用阶段         | 说明                         |
| ---------------- | ---------------------------- |
| `BACKLOG`        | 已登记但尚未进入生产         |
| `IN_PROGRESS`    | AI、人工或系统正在生产或修改 |
| `PENDING_REVIEW` | 等待测试人员审核             |
| `REWORK`         | 审核退回，等待 AI 或人工修改 |
| `APPROVED`       | 内容已审核通过               |
| `PUBLISHED`      | 已成为正式可用产出物         |
| `ARCHIVED`       | 已归档，仅保留追溯证据       |

不同正式产出物可以保留自身状态机，但必须能映射到上述概念阶段；任务看板展示以 WorkItem 状态为准。

### 3.4 必须人工审核与可自动执行的边界

#### 必须审核后才能正式生效

- 测试策略；
- 测试计划；
- 正式测试用例；
- Web/API 自动化测试代码；
- 批量修改既有测试资产；
- 结果分析结论；
- 写入正式缺陷系统的 Bug；
- 正式测试报告和最终质量结论；
- 正式知识条目；
- 控制发布、外部写入、放宽网络或 Secret 权限的动作。

#### 可以自动完成，但必须留痕和可追溯

- 原始资料解析和结构化；
- TestingIR、BusinessRule 等中间产物生成；
- 重复用例识别和覆盖缺口分析；
- 已批准脚本的常规执行；
- 日志、截图、视频、Trace 采集；
- 失败聚类和只读风险分析；
- 草稿保存、格式检查和根据审核意见重做；
- 满足现行 `21-AI介入点降级矩阵.md` 条件的低风险可逆动作。

## 四、8 个业务能力域

### 4.1 任务看板

**定位**：测试人员与 AI Agent 协作的任务控制中心，是默认首页和日常工作入口。

**核心功能**：

- 测试工作项创建、拆解、优先级、负责人和截止时间；
- AI Agent 分配、运行进度、中断、重试和重新生成；
- “待我审核”“审核退回”“AI 修改中”“待执行”“待分析”等队列；
- 审核、批注、直接修改、批准和退回；
- 项目、Release、环境、需求、产出物和执行证据关联；
- 阻塞、风险、SLA、超时和整体进度；
- AI 产出采用率、退回率、人工修改率和节省工时等效率指标。

**主要对象/目标对象**：`WorkItem`（已确认目标实体）、`WorkItemArtifact`、`WorkItemRun`、`WorkItemEvent`、`WorkItemDependency`、`ReviewTask`、AgentSession 引用。

**解决的痛点**：

- 测试人员必须进入不同模块寻找待办；
- 不知道 AI 正在做什么、为什么阻塞；
- AI 产出和人工审核没有统一队列；
- 任务、产出物和证据无法串联；
- 管理者只能看结果，无法看生产过程和效率。

**设计优势**：把“人操作多个工具”转变为“人管理一条 AI 测试生产线”。

### 4.2 知识库

**定位**：AI 工作的可信输入源和经人工确认的经验沉淀中心。

**核心功能**：

- PRD、OpenAPI、架构文档、代码变更、缺陷记录等原始来源；
- Service、Component、Endpoint、Entity、ExternalDependency 等项目结构；
- 项目与 Release 资料；
- 业务规则、术语、测试规范和历史资产检索；
- 知识候选审核、发布、版本、适用范围和过期管理；
- Source Trace、来源快照、哈希和检索证据；
- RAG 检索、索引和向量化作为内部实现，不作为用户一级模块。

**主要对象**：`RequirementDocument`、`APIContract`、`KnowledgeEntry`、`KnowledgeVector`、KG Node/Edge、SourceSnapshot（新增候选）。

**解决的痛点**：

- 需求、接口、架构、历史 Bug 和经验分散；
- AI 缺少完整、可信、版本明确的上下文；
- 产出无法追溯到原始依据；
- AI 自动总结直接进入知识库，可能污染后续生成。

**设计优势**：让 AI 基于项目事实工作，并通过人工审核形成可持续提高的知识闭环。

### 4.3 测试策划与设计

**定位**：把项目目标、需求和风险转化为经审核的测试策略、计划、场景和用例。

**核心功能**：

- 测试策略生成、审核和版本管理；
- Release 下的测试计划、范围、进度、资源和优先级；
- TestingIR 编译、BusinessRule 提取和信息缺口识别；
- 测试场景、测试用例和断言生成；
- 覆盖率分析、遗漏检查和补充建议；
- AI 草稿、人工审核、批改、退回和批准；
- 正式用例库、套件和版本历史。

**主要对象/目标对象**：`TestStrategy`（由现行 TestDesignPlan 迁移并重命名）、`TestPlan`、`TestingIR`、`BusinessRule`、`TestScenario`、`DesignTestCase`、`TestCase`、`Assertion`、`TestSuite`。目标态不再保留独立 TestDesignPlan。

**解决的痛点**：

- 人工阅读大量需求耗时且容易遗漏；
- 策略、计划、场景和用例之间缺少追踪；
- AI 用例直接入库，缺乏审核边界；
- 覆盖率只统计数量，无法证明业务规则是否被验证。

**设计优势**：形成“需求→规则→策略→计划→场景→用例→断言”的可信设计链。

### 4.4 自动化测试开发

**定位**：把经审核的测试设计转换为可审查、可调试、可执行的自动化测试代码。

**核心功能**：

- Web 自动化测试代码生成与维护；
- 接口自动化测试代码生成与维护；
- 后续扩展 App、性能和安全自动化；
- AI Code Generation、Diff、Code Review、批注和退回重做；
- 语法检查、静态检查、安全扫描和试运行；
- 脚本调试、版本历史、分支和代码仓库同步；
- 用例、代码、测试数据、Locator、Mock 和接口契约关联；
- Locator 自愈候选和人工确认。

**主要对象**：`AutomationScript`、`TestData`、`TestDataProfile`、`Locator`、`MockConfig`、代码审查记录（新增候选）。

**解决的痛点**：

- 手工编写自动化代码成本高；
- 自然语言用例与脚本长期脱节；
- AI 生成代码缺少可执行性、安全性和人工审查；
- 数据、Locator 和 Mock 分散，维护成本高。

**设计优势**：自动化代码作为正式测试产出物独立治理，既能大幅交给 AI，又保留工程级 Code Review 和版本控制。

### 4.5 测试执行

**定位**：将批准后的测试资产转化为完整、可观察、可复现的执行证据。

**核心功能**：

- 执行计划、测试集选择、参数和环境配置；
- Web、API 等任务调度和运行；
- Runner 选择与使用；
- 实时进度、日志、Screenshot、Video 和 Trace；
- 原始执行结果、取消、超时、重试和失败恢复；
- 项目、Release、环境、测试计划、用例和代码版本绑定；
- 人工测试结果补录和证据上传（手工测试已裁决纳入 V1，见下方范围声明）。

**范围声明（O2 裁决 2026-08-17）**：手工测试纳入 V1——作为平台记录的执行形态：测试人员手工记录步骤结果、实际结果与证据，AI 仅辅助整理，测试人员对手工结果负责（与 14-PRD §2 手工测试行一致）；不增加自动化执行实现面。

**主要对象**：`ExecutionPlan`、`ExecutionTask`、`ExecutionResult`；Runner 仅作为使用资源，节点注册和运维归平台管理。

**解决的痛点**：

- API、Web 和人工执行证据分散；
- 不知道某次结果对应哪个版本、环境、用例和代码；
- 执行过程不可见，失败难以复现；
- 任务异常与断言失败混为一谈。

**设计优势**：保留不可被分析结论反向改写的原始执行证据，为后续诊断和报告提供可信基础。

### 4.6 质量分析与缺陷

**定位**：把原始结果转化为经测试人员确认的分析、Bug、报告和质量结论。

**核心功能**：

- 结果汇总、覆盖率、失败聚类和 Flaky Test 识别；
- RCA 根因分析、影响范围和修复建议；
- Bug 草稿生成、证据组装、去重、严重程度和责任建议；
- Bug 人工审核、修改、提交和状态同步；
- 测试报告生成、审核、发布和归档；
- Release 质量趋势、风险和遗留问题；
- 质量门禁、CI/CD 集成和人工发布判断；
- 知识候选生成并送入知识库审核流程。

**主要对象/目标对象**：`TestReport`、`CoverageReport`、`FailureCluster`、`FailureAnalysis`、`Defect`（新增候选）、`QualityGate`、`PipelineConfig`、`PipelineRun`、KnowledgeCandidate（新增候选）。

**解决的痛点**：

- 报告只有通过率，没有可行动结论；
- 同类失败被重复分析和重复提 Bug；
- AI 根因判断缺少人工复核；
- Bug、报告和发布风险分散在不同流程；
- 执行结果没有沉淀为项目经验。

**设计优势**：把“执行后处理”形成闭环，同时区分原始证据、AI 推断、人类确认和最终发布结论。

### 4.7 AI Agent 中心

**定位**：管理 AI 生产力、责任边界、权限、运行证据和质量评估。

**核心功能**：

- Agent 注册、职责、版本和启停；
- Skill 注册、Tools Schema、版本、发布和隔离；
- Agent Workflow、Skill allowlist 和委派边界；
- Prompt 版本、灰度和评测；
- AgentSession、SkillInvocation、Trace、成本、超时和重试；
- HITL 策略、风险等级、审核路由和失败降级；
- Eval 数据集、准确率、采用率、退回率和质量趋势；
- 网络、Secret、外部写入和正式资产写入权限。

**主要对象**：`Agent`、`Skill`、`AgentWorkflow`、`AgentPromptVersion`、`AgentSession`、`AgentTraceNode`、`SkillInvocation`、WorkspaceAgent/SkillEnablement。

**解决的痛点**：

- AI 能力散落、权限不透明；
- Prompt 和 Agent 修改缺少版本与评测；
- AI 错误无法还原；
- 多 Agent 可能循环、越权或未经批准写入正式资产。

**设计优势**：业务人员从任务看板使用 AI，管理员在 Agent 中心治理 AI；Agent 与 Skill 同入口但保持独立生命周期。

### 4.8 平台管理

**定位**：提供租户、项目、安全、集成、模型和执行基础设施管理。

**核心功能**：

- 租户、用户、角色、成员和项目；
- Workspace/项目创建、归档和基础配置；
- Release 与 Environment 基础配置；
- Secrets 和双信封加密；
- LLM Provider、模型路由、额度、成本和健康度；
- Runner 节点注册、升级、健康和资源池；
- Git、Jira、LDAP/SSO、消息通知等外部集成；
- 全局审计、数据保留、归档和系统健康。

**主要对象**：`Tenant`、`User`、`Workspace`、`Release`（新增目标实体）、`Environment`、`WorkspaceSecret`、`LlmConfig`、`RunnerNode`、AuditLog。

**解决的痛点**：

- 用户、模型、Runner、Secrets 和集成配置散落；
- 管理员设置混入测试人员工作流；
- 高权限操作缺少统一审计和安全边界。

**设计优势**：保留统一管理入口，同时按身份、安全、模型、Runner、集成和审计划分内部子域。

## 五、模块关系与边界

### 5.1 主流程与反馈闭环

```text
                         ┌──────────────────────┐
                         │      任务看板        │
                         │ 任务 / AI / 审核 / 风险 │
                         └──────────┬───────────┘
                                    │编排与追踪
                                    ▼
知识库 → 测试策划与设计 → 自动化测试开发 → 测试执行 → 质量分析与缺陷
  ▲                                                        │
  └──────────── 审核后的知识、缺陷经验和质量模式 ────────────┘

AI Agent 中心：为上述各阶段提供受治理的 AI 生产和执行能力
平台管理：为全平台提供身份、安全、模型、Runner、集成和审计
```

### 5.2 关键边界规则

1. **任务看板拥有工作项，不拥有业务产出物内容**；它通过 Artifact 引用关联策略、用例、代码、Bug 和报告。
2. **知识库拥有来源和已发布知识**；其他模块只能生成知识候选，不能直接发布正式知识。
3. **测试策划与设计拥有策略、计划、场景、用例和断言**；自动化开发只消费已批准或明确允许试验的设计版本。
4. **自动化测试开发拥有代码及其配套数据、Locator 和 Mock**；执行模块只运行已选定的代码版本。
5. **测试执行拥有原始执行证据**；质量分析不能覆盖或篡改原始结果。
6. **质量分析与缺陷拥有分析、Bug 和报告**；AI 生成的结果在审核前均为草稿或候选。
7. **AI Agent 中心拥有 AI 配置和运行治理，不拥有业务产出物最终批准权**。
8. **平台管理拥有基础设施和高权限配置，不承担测试业务判断**。

### 5.4 项目与发布上下文

- 产品界面统一使用“项目”，技术契约继续使用 `Workspace/workspaceId`；不新增重复的 Project 实体。
- V1 不新增通用 `SystemUnderTest` 层；项目内部结构由 Service、Component、Endpoint 和 ExternalDependency 表达。
- 新增目标实体 `Release`，表达一次业务发布；资产自身版本不得与 Release 混用。
- `Release 1 → N TestPlan`；TestPlan 是测试活动计划，不再兼任业务发布里程碑。
- 一次执行必须能确定 `Workspace + Release + Environment + TestPlan/ExecutionPlan`。

### 5.5 WorkItem 与任务看板产品契约

#### 5.5.1 定位与边界

`WorkItem` 是测试工作生产线的统一编排单元，用于回答：谁或哪个 Agent 正在为什么目标工作、当前处于什么阶段、产生或审核什么产出物、依赖什么输入、为什么阻塞、完成证据在哪里。

`WorkItem` 不取代任何业务实体：

- 不取代 TestPlan、TestCase、AutomationScript、Defect 或 TestReport；
- 不保存正式产出物正文，只保存目标、状态和引用；
- 不取代 AgentSession；AgentSession 是某次 Agent 运行记录；
- 不取代 ExecutionTask；ExecutionTask 是一次物理测试执行；
- 不取代 ReviewTask；ReviewTask 是一次具体审核工单。

关系模型：

```text
WorkItem
├── 输入/输出/证据 → WorkItemArtifact → 正式业务实体及精确版本
├── AI/人工运行尝试 → WorkItemRun → AgentSession 或人工处理记录
├── 状态与审计事件 → WorkItemEvent
├── 审核工单 → ReviewTask
├── 物理执行 → ExecutionTask（适用时）
├── 父子任务 → parentWorkItemId
└── 前置依赖 → WorkItemDependency
```

#### 5.5.2 WorkItem 类型

| 类型              | 主要目标                     | 典型正式输出                      |
| ----------------- | ---------------------------- | --------------------------------- |
| `STRATEGY`        | 制定测试策略                 | TestStrategy                      |
| `PLAN`            | 制定测试计划                 | TestPlan                          |
| `TEST_DESIGN`     | 生成场景、用例和断言         | TestScenario、TestCase、Assertion |
| `AUTOMATION_WEB`  | 生成或维护 Web 自动化代码    | AutomationScript(Web)             |
| `AUTOMATION_API`  | 生成或维护接口自动化代码     | AutomationScript(API)             |
| `EXECUTION`       | 执行批准后的测试             | ExecutionTask、ExecutionResult    |
| `RESULT_ANALYSIS` | 分析执行结果                 | ResultAnalysis/FailureAnalysis    |
| `DEFECT`          | 生成、审核和提交缺陷         | Defect                            |
| `REPORT`          | 生成和审核测试报告           | TestReport                        |
| `KNOWLEDGE`       | 提炼和发布知识               | KnowledgeEntry                    |
| `GENERAL`         | 不属于上述类型的受控测试工作 | 由 Artifact 引用声明              |

类型只表示任务目标，不能代替关联产出物的类型和版本。

#### 5.5.3 WorkItem 最小字段

| 字段                    | 约束 | 说明                                               |
| ----------------------- | ---- | -------------------------------------------------- |
| `id`                    | 主键 | 工作项唯一标识                                     |
| `tenantId`              | 必填 | 租户隔离                                           |
| `workspaceId`           | 必填 | 所属项目                                           |
| `releaseId`             | 可选 | 关联发布版本；项目级长期工作可为空                 |
| `parentWorkItemId`      | 可选 | 父工作项，用于任务分解                             |
| `workItemType`          | 必填 | WorkItem 类型                                      |
| `title`                 | 必填 | 用户可读任务标题                                   |
| `objective`             | 必填 | 需要完成的测试目标，而非具体操作步骤               |
| `acceptanceCriteria`    | 必填 | 任务完成和产出物可接受条件                         |
| `constraints`           | 可选 | 范围、禁止项、成本、时间和安全约束                 |
| `priority`              | 必填 | `P0/P1/P2/P3`                                      |
| `riskLevel`             | 必填 | `LOW/MEDIUM/HIGH/CRITICAL`，用于决定审核和权限策略 |
| `status`                | 必填 | 统一任务状态                                       |
| `currentActorType`      | 必填 | `HUMAN/AGENT/SYSTEM/NONE`                          |
| `assigneeId`       | 可选 | 当前负责的测试人员（与 04/32/33 字段名对齐，裁决 2026-08-14 批次二） |
| `agentId`               | 可选 | 当前负责生产或分析的 Agent                         |
| `requiresReview`        | 必填 | 是否必须创建审核工单；正式产出默认 true            |
| `reviewPolicyId`        | 可选 | 审核策略、人数和权限要求                           |
| `dueAt`                 | 可选 | 截止时间                                           |
| `blockedReason`         | 可选 | 阻塞原因；BLOCKED 状态必填                         |
| `createdBy`             | 必填 | 发起人                                             |
| `startedAt/completedAt` | 可选 | 周期统计时间                                       |
| `createdAt/updatedAt`   | 必填 | 审计时间                                           |
| `lockVersion`           | 必填 | 乐观锁版本，防止并发审核覆盖                       |

`objective` 与 `acceptanceCriteria` 必须由测试人员创建或确认。AI 可以提出拆解建议，但不能自行扩大顶层目标和授权范围。

#### 5.5.4 统一任务状态机

为避免“AI处理中、人工处理中、系统处理中”演化成三套状态，任务生命周期与当前执行者分离：

| 状态             | 含义                                   | 允许的下一状态                           |
| ---------------- | -------------------------------------- | ---------------------------------------- |
| `BACKLOG`        | 已登记，尚未满足开始条件               | READY、CANCELLED                         |
| `READY`          | 输入、权限和依赖已满足                 | IN_PROGRESS、CANCELLED                   |
| `IN_PROGRESS`    | HUMAN/AGENT/SYSTEM 正在处理            | PENDING_REVIEW、BLOCKED、DONE、CANCELLED |
| `PENDING_REVIEW` | 正式产出等待人工审核                   | APPROVED、REWORK、BLOCKED、CANCELLED     |
| `REWORK`         | 审核退回，等待修改                     | IN_PROGRESS、CANCELLED                   |
| `APPROVED`       | 审核已通过，等待固化正式版本           | DONE、BLOCKED                            |
| `BLOCKED`        | 因输入、依赖、权限、环境或质量问题暂停；用户主动暂停=BLOCKED+blocked_reason=USER_PAUSED（裁决 2026-08-14 B4，语义用原因码承载、状态机不新增 PAUSED） | READY、IN_PROGRESS、CANCELLED            |
| `DONE`           | 目标满足且证据完整                     | 终态；重新工作须新建修订 WorkItem        |
| `CANCELLED`      | 工作被授权人员取消                     | 终态                                     |

界面展示标签由 `status + currentActorType` 组合派生：

- `IN_PROGRESS + AGENT` → “AI 处理中”；
- `IN_PROGRESS + HUMAN` → “人工处理中”；
- `IN_PROGRESS + SYSTEM` → “系统执行中”；
- `PENDING_REVIEW` → “待我/待人工审核”。

核心状态规则：

1. `requiresReview=true` 的工作项不得从 IN_PROGRESS 直接进入 DONE；
2. 进入 PENDING_REVIEW 前必须存在带版本的 OUTPUT Artifact；
3. 进入 APPROVED 前必须存在已解决的 ReviewTask 和审核人签名；
4. APPROVED 固化的 Artifact 版本必须与审核目标版本一致，发生并发修改则审核失效并回到 PENDING_REVIEW；
5. BLOCKED 必须记录结构化原因、责任方和恢复条件；
6. DONE 后不得原地修改产出物；修改必须创建新 WorkItem 或修订任务并保留关联。

#### 5.5.5 WorkItemArtifact

WorkItem 与产出物使用独立关联对象，避免在 WorkItem 上增加大量可空外键。

| 字段              | 说明                                                           |
| ----------------- | -------------------------------------------------------------- |
| `workItemId`      | 所属工作项                                                     |
| `role`            | `INPUT/OUTPUT/REVIEW_TARGET/EVIDENCE`（API/DB 侧字段名为 relation_type，取值含 SUPERSEDES，裁决 2026-08-14 批次二：命名与取值以 04/33 为准，本表为语义说明）                          |
| `artifactType`    | RequirementDocument、TestCase、AutomationScript、TestReport 等 |
| `artifactId`      | 业务实体 ID                                                    |
| `artifactVersion` | 精确版本；正式审核和执行证据必须填写                           |
| `sourceTrace`     | 工作项与产出物关系来源                                         |
| `createdAt`       | 关联时间                                                       |

规则：

- 一个工作项可以有多个输入、输出和证据；
- 一个产出物可以被多个后续工作项引用；
- 审核、执行和报告必须引用精确版本，禁止只引用“当前最新版本”；
- `artifactType` 必须来自受控注册表，服务端必须校验目标实体存在且与 WorkItem 属于同一租户和允许的 Workspace 范围；
- 删除工作项不得级联删除业务产出物和证据。

#### 5.5.6 WorkItemRun

每次 AI、人工或系统处理尝试形成一条 WorkItemRun：

| 字段                           | 说明                                     |
| ------------------------------ | ---------------------------------------- |
| `id/workItemId`                | 运行尝试及所属工作项                     |
| `attemptNo`                    | 尝试序号                                 |
| `actorType/actorId`            | HUMAN、AGENT 或 SYSTEM 及具体执行者      |
| `agentSessionId`               | AI 运行时关联 AgentSession               |
| `executionTaskId`              | 物理测试执行时关联 ExecutionTask         |
| `inputSnapshot/outputSnapshot` | 脱敏后的输入输出摘要或制品引用           |
| `status`                       | PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED(与 33 权威对齐,裁决见 8-14 批次二;TIMEOUT 归 error_code;tokenUsage/cost 由 AgentSession/SkillInvocation 侧汇总,不在本表冗余) |
| `errorCode/errorSummary`       | 失败分类，不保存敏感信息                 |
| `startedAt/finishedAt`         | 运行时间                                 |
| `tokenUsage/cost`              | AI 运行适用；用于成本统计                |

WorkItemRun 失败不等于 WorkItem 失败。系统可以在策略允许的次数内创建新 attempt；超过重试、成本或时间边界后，WorkItem 转 BLOCKED，等待人工处理。

所有状态变化另存为只追加的 `WorkItemEvent`，至少包含 `workItemId/fromStatus/toStatus/actorType/actorId/reason/correlationId/createdAt`。看板周期、等待时间和 SLA 指标必须从事件计算，禁止通过覆盖 WorkItem 当前字段伪造历史。

#### 5.5.7 ReviewTask 关系

- WorkItem 进入 PENDING_REVIEW 时按 reviewPolicy 创建一条或多条 ReviewTask；
- ReviewTask 必须指向 `WorkItemArtifact.role=REVIEW_TARGET` 的精确版本；
- 审核动作包括 `APPROVE/REJECT/REQUEST_CHANGES`，并保存审核意见和差异；
- `REQUEST_CHANGES` 或 `REJECT` 使 WorkItem 进入 REWORK；
- 所有必需 ReviewTask 均 APPROVE 后，WorkItem 才能进入 APPROVED；
- 审核人不得批准自己无权批准的产出物；AI Agent 永远不能作为正式批准人；
- ReviewTask 超时只产生 SLA 风险，不自动批准或自动拒绝。

#### 5.5.8 父子任务与依赖

- 复杂目标可以拆成父子 WorkItem；父任务的完成条件由子任务及父级验收标准共同决定；
- 前置依赖使用 WorkItemDependency 显式记录，不允许仅依赖文本描述；
- 默认依赖条件为前置任务 DONE，可配置为前置 Artifact 已 APPROVED；
- 检测到依赖环时拒绝保存或启动；
- 取消父任务不默认级联取消已开始或已产生正式证据的子任务，必须逐项评估。

#### 5.5.9 任务看板视图

任务看板至少提供：

1. **我的待审核**：按风险、截止时间和影响范围排序；
2. **AI 工作中**：显示 Agent、当前步骤、耗时、预算、重试和中断入口；
3. **审核退回/重做**：显示审核意见、差异和当前修改人；
4. **待执行/执行中**：关联环境、Release、脚本版本和 ExecutionTask；
5. **阻塞与风险**：按阻塞原因、责任方、持续时间和恢复条件分组；
6. **全部工作项**：支持项目、Release、类型、状态、人员、Agent、风险和产出物过滤；
7. **管理视图**：周期、吞吐、在制品、审核积压、返工和 AI 采用率。

#### 5.5.10 权限能力

角色名称在 RBAC 统一前暂不写死，WorkItem 定义以下能力点：

| 能力                 | 含义                             |
| -------------------- | -------------------------------- |
| `workitem:create`    | 创建目标和验收标准               |
| `workitem:assign`    | 分配人员或 Agent                 |
| `workitem:run`       | 启动、重试或继续处理             |
| `workitem:interrupt` | 中断 AI 或系统运行               |
| `workitem:edit`      | 修改非终态工作项                 |
| `workitem:review`    | 提交审核意见                     |
| `workitem:approve`   | 批准正式产出物                   |
| `workitem:cancel`    | 取消工作项                       |
| `workitem:admin`     | 修改策略、强制解锁和处理异常状态 |

最终允许动作取“用户 RBAC ∩ Agent 权限 ∩ Workflow 节点权限”的交集，任一层拒绝即 fail-closed。

#### 5.5.11 指标

任务看板至少统计：

- Lead Time：BACKLOG/READY 到 DONE；
- Cycle Time：首次 IN_PROGRESS 到 DONE；
- AI 处理时间、人工处理时间、审核等待时间和阻塞时间；
- 一次审核通过率、平均返工次数和人工修改比例；
- AI 任务成功率、超时率、重试次数、Token 和成本；
- 各类型在制品数量、吞吐量和 SLA 超时率；
- 产出物从生成到批准的时间；
- Agent 产出采用、修改、退回和废弃比例。

指标必须基于状态事件和运行记录计算，禁止依赖可人工编辑的汇总字段作为唯一证据。

#### 5.5.12 Given/When/Then 验收基线

1. **正式产出审核门禁**  
   Given 工作项 `requiresReview=true` 且存在 AI 输出，When AI 处理完成，Then 工作项只能进入 PENDING_REVIEW，不能直接进入 DONE 或发布正式产出。

2. **审核版本一致性**  
   Given 审核人正在审核 AutomationScript v3，When 脚本被并发更新为 v4，Then 原审核不得批准 v4，系统应提示版本冲突并要求重新审核。

3. **完整追溯**  
   Given 一个已完成的报告工作项，When 用户查看详情，Then 可以反查输入资料、策略/计划、用例、代码版本、执行结果、分析、审核记录和 Agent Trace。

4. **AI 越权阻断**  
   Given Agent 没有正式资产写入权限，When Agent 尝试发布 TestCase 或提交外部 Bug，Then 操作被拒绝、WorkItem 转 BLOCKED 或 PENDING_REVIEW，并记录审计事件。

5. **失败与重试分离**  
   Given 一次 Agent WorkItemRun 超时，When 重试策略仍有剩余额度，Then 新建下一 attempt，WorkItem 保持 IN_PROGRESS；超过边界后才转 BLOCKED。

6. **阻塞可恢复**  
   Given WorkItem 因缺少 APIContract 被阻塞，When 所需输入被补齐且权限校验通过，Then 工作项可以从 BLOCKED 恢复到 READY，并保留完整阻塞时长和原因。

7. **终态不可篡改**  
   Given WorkItem 已 DONE，When 用户尝试修改其已批准产出版本，Then 系统拒绝原地修改并引导创建修订 WorkItem。

8. **任务依赖无环**  
   Given A 依赖 B 且 B 已依赖 A，When 保存新的依赖关系，Then 系统拒绝并指出循环路径。

### 5.6 正式测试产出物与审核契约

#### 5.6.1 正式产出物范围

以下 8 类产出物是 QualityForge 人机协作生产线的核心正式交付物：

1. 测试策略；
2. 测试计划；
3. 测试用例；
4. Web/API 自动化测试代码；
5. 测试结果分析；
6. Bug/缺陷；
7. 测试报告；
8. 知识条目。

测试数据、Locator、Mock、断言、覆盖报告、截图、日志和 Trace 等属于支撑资产或证据，也必须版本化和追溯；它们默认随所属正式产出物或专项 WorkItem 接受审核，不强制为每个细粒度对象单独创建一级审核流程。

#### 5.6.2 通用产出物审核接口

每种正式产出物可以使用不同领域实体和状态机，但必须提供等价的通用审核信息：

| 字段/能力               | 要求                                                                          |
| ----------------------- | ----------------------------------------------------------------------------- |
| `artifactId`            | 产出物稳定标识                                                                |
| `artifactType`          | 受控类型，不允许自由字符串绕过审核策略                                        |
| `workspaceId`           | 所属项目                                                                      |
| `releaseId`             | 适用时关联发布版本                                                            |
| `version`               | 每次内容变化产生新版本；审核必须绑定精确版本                                  |
| `contentDigest`         | 规范化内容摘要；用于发现审核后内容变化                                        |
| `reviewStatus`          | `DRAFT/GENERATING/PENDING_REVIEW/CHANGES_REQUESTED/APPROVED/PUBLISHED/REJECTED/STALE/ARCHIVED`(与 03/04/32/33 九值权威对齐,裁决见 8-14 批次二) ｜ 语义(裁决 2026-08-15 B4):签署对象是 APPROVED 待发布版本;签署通过这一动作把状态推到 PUBLISHED |
| `sourceTrace`           | 原始来源、上游产出物和推导链                                                  |
| `generatedByAgentId`    | AI 参与生成时记录 Agent                                                       |
| `editedBy`              | 人工修改者列表或修改事件引用                                                  |
| `approvedBy/approvedAt` | 正式批准人和时间                                                              |
| `reviewTaskIds`         | 所有必要审核工单                                                              |
| `supersedesVersion`     | 当前版本替代的上一版本                                                        |
| `changeSummary`         | AI 或人工生成的版本差异摘要                                                   |

这是跨实体的产品契约，不要求立即建立一张通用 Artifact 表。具体实体可直接存储字段或通过版本表、ReviewTask 和事件表组合实现，但对外行为必须一致。

#### 5.6.3 参与者与责任

| 参与者         | 责任                                               | 禁止事项                                            |
| -------------- | -------------------------------------------------- | --------------------------------------------------- |
| AI Producer    | 基于输入和约束生成、修改产出物草稿，提供来源和差异 | 不得批准正式产出，不得扩大任务授权范围              |
| Human Editor   | 批改、补充、删除或重构 AI 草稿                     | 修改后不得沿用旧版本审核结论                        |
| Reviewer       | 检查正确性、完整性、来源、风险和可执行性，提交意见 | 不得审核无精确版本或证据不足的产出物                |
| Approver       | 对正式生效承担批准责任                             | 不得把批准权委托给 AI；高风险时不得由唯一编辑者自批 |
| Artifact Owner | 维护批准后的正式资产、版本和废弃规则               | 不得覆盖历史批准版本                                |
| System         | 执行确定性校验、权限、版本冲突和审计               | 不得以自动校验通过替代业务审核                      |

角色名称在 RBAC 统一前不写死，但责任必须映射到明确能力。建议低风险产出采用一名获授权测试人员审核批准；HIGH/CRITICAL、高影响批量变更、可执行代码发布、对外缺陷提交和最终质量结论采用“四眼原则”，Reviewer 与 Approver 不得为同一人。

#### 5.6.4 审核策略类型

| 策略                | 适用范围                                    | 最低要求                                       |
| ------------------- | ------------------------------------------- | ---------------------------------------------- |
| `SINGLE_REVIEW`     | LOW/MEDIUM 风险的一般策略、计划、用例和知识 | 一名有权限测试人员审核并批准                   |
| `FOUR_EYES`         | HIGH/CRITICAL、批量变更、最终质量结论       | Reviewer 与 Approver 两人分离                  |
| `CODE_REVIEW`       | Web/API 自动化测试代码                      | 确定性检查通过 + 人工代码审核 + 精确提交/摘要  |
| `EXTERNAL_WRITE`    | Bug/Jira/PingCode、发布控制等外部写入       | 写入前即时人工批准，批准内容与发送内容摘要一致 |
| `REPORT_SIGNOFF`    | 正式测试报告和质量结论                      | 数据快照校验 + 测试负责人签字                  |
| `KNOWLEDGE_PUBLISH` | 正式知识条目                                | 来源、适用范围、有效期和专家审核               |

租户可以把策略调严，不得绕过平台规定的最低要求；任何放宽必须由有权限管理员执行并写入审计日志。

#### 5.6.5 正式产出物审核矩阵

| 产出物            | AI Agent 负责                                                | 测试人员审核重点                                           | 推荐批准责任                                      | 正式生效条件                                                       |
| ----------------- | ------------------------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| 测试策略          | 分析项目资料、Release范围、风险和历史质量，生成策略草稿      | 目标、范围、测试类型、风险取舍、进入/退出标准、资源假设    | 测试负责人；HIGH/CRITICAL采用FOUR_EYES            | 来源完整、风险分级明确、审核通过、固化版本                         |
| 测试计划          | 基于策略拆解任务、优先级、人员/Agent建议、时间和依赖         | 与策略一致、范围可执行、资源和排期合理、责任明确           | 测试负责人或获授权计划审批人                      | 关联已批准策略和Release，依赖无环，审核通过                        |
| 测试用例          | 从规则/场景生成步骤、数据、预期和断言，按意见修改            | 业务正确性、边界/异常、数据、预期、断言、重复和可执行性    | 获授权测试人员；高风险用例FOUR_EYES               | DesignTestCase精确版本批准并迁移/发布为正式TestCase                |
| Web/API自动化代码 | 根据批准用例和契约生成代码、测试数据、Locator/Mock引用和Diff | 与用例一致、断言有效、代码质量、安全、幂等/清理、可维护性  | 代码Reviewer + 高风险Approver                     | 语法/静态/安全检查和受控试运行通过，CODE_REVIEW批准并绑定提交/摘要 |
| 结果分析          | 汇总执行证据、聚类失败、提出根因、影响和替代解释             | 证据充分、事实与推断分离、误报/环境问题、置信度和影响范围  | 测试工程师；高严重度由测试负责人批准              | 引用不可变执行证据，分析结论审核通过                               |
| Bug/缺陷          | 生成标题、步骤、实际/预期、证据、严重度和重复候选            | 是否真实缺陷、可复现性、严重度、责任建议、敏感信息和重复性 | 外部写入前由获授权测试人员批准；重大缺陷FOUR_EYES | 内部Defect批准；外部写入执行EXTERNAL_WRITE并保存回执               |
| 测试报告          | 汇总范围、覆盖、执行、缺陷、风险、遗留和质量建议             | 数据一致性、范围完整、未解决风险、结论与证据一致           | 测试负责人执行REPORT_SIGNOFF                      | 绑定不可变数据快照、所有必需章节通过校验、签字批准                 |
| 知识条目          | 从缺陷、分析和复盘中提炼知识候选、来源和适用条件             | 内容正确、非重复、适用范围、失效条件、敏感信息和可复用性   | 领域专家或获授权知识审批人                        | KNOWLEDGE_PUBLISH通过，状态Published并记录复审/过期时间            |

#### 5.6.6 各产出物最低内容门禁

| 产出物     | 不满足以下内容时不得进入 PENDING_REVIEW                    |
| ---------- | ---------------------------------------------------------- |
| 测试策略   | 目标、范围、风险、测试类型、优先级、进入/退出标准、来源    |
| 测试计划   | 所属策略/Release、任务、责任、时间、依赖、验收标准         |
| 测试用例   | 前置条件、步骤、数据、预期、断言、来源、优先级和类型       |
| 自动化代码 | 关联用例、框架/运行时、代码版本、依赖、执行说明、检查结果  |
| 结果分析   | 执行证据、事实、推断、置信度、替代解释、影响范围           |
| Bug/缺陷   | 标题、环境、版本、步骤、预期、实际、证据、严重度、去重结果 |
| 测试报告   | 范围、执行摘要、覆盖、缺陷、风险、遗留、结论、数据快照     |
| 知识条目   | 来源、正文、适用范围、验证证据、失效条件、敏感性检查       |

确定性门禁失败时，WorkItem 保持 IN_PROGRESS 或转 BLOCKED，不得通过创建人工审核工单掩盖缺失的基础字段和证据。

#### 5.6.7 审核操作与版本规则

审核动作统一为：

- `APPROVE`：内容满足正式生效要求；
- `REQUEST_CHANGES`：保留草稿并要求修改，WorkItem 转 REWORK；
- `REJECT`：当前方案或产出方向不可接受，必须记录原因；后续重新开展应产生新版本或新 WorkItem；
- `COMMENT`：仅提出意见，不改变审核状态。

版本规则：

1. AI或人工对正文、关键字段、断言、代码、结论或适用范围的修改必须创建新版本；
2. 拼写、展示格式等非语义修改也必须留事件，是否增加业务版本由实体策略决定，但不得改变 `contentDigest` 后沿用原批准签名；
3. PENDING_REVIEW 后内容发生变化，未完成 ReviewTask 自动失效，新版本重新进入审核；
4. APPROVED/PUBLISHED 版本不可覆盖，只能创建修订版本并通过新 WorkItem；
5. 下游执行、分析和报告必须引用被批准的精确版本；
6. 上游来源变化时，系统生成影响分析 WorkItem，不得静默把所有下游产出标记为继续有效；
7. 废弃不等于删除，历史执行和审计仍引用原版本。

#### 5.6.8 ReviewTask 最小审核记录

ReviewTask 除现行字段外，目标契约至少需要表达：

| 字段                                      | 说明                           |
| ----------------------------------------- | ------------------------------ |
| `workItemId`                              | 所属工作项                     |
| `artifactType/artifactId/artifactVersion` | 审核目标精确版本               |
| `contentDigest`                           | 审核时内容摘要                 |
| `policyType`                              | SINGLE_REVIEW/FOUR_EYES等      |
| `reviewRole`                              | REVIEWER/APPROVER              |
| `assigneeId`                              | 指定审核人                     |
| `decision`                                | APPROVE/REQUEST_CHANGES/REJECT |
| `comments`                                | 审核意见                       |
| `diffRef`                                 | 审核版本相对上一版本的差异     |
| `checkResults`                            | 确定性检查结果引用             |
| `decidedAt`                               | 决策时间                       |
| `signature`                               | 防抵赖签名或等价审计信息       |

审核分配、转交、超时和决定均必须写入只追加事件；转交不改变最低审核人数和职责分离要求。

#### 5.6.9 直接人工修改与AI重做

- 测试人员可以直接修改草稿，也可以附审核意见退回 AI；
- 直接修改后测试人员成为该版本 Editor，不自动获得批准结果；
- AI重做必须读取结构化审核意见，并输出变更摘要和未采纳意见及原因；
- 系统不得把AI重新生成的完整正文伪装为“局部修改”；必须显示真实Diff；
- HIGH/CRITICAL产出中，主要Editor不得作为唯一Approver；
- 多轮返工超过策略上限后WorkItem转BLOCKED，要求测试负责人决定继续、改为人工或取消。

#### 5.6.10 Given/When/Then 验收基线

1. **正式用例迁移**  
   Given DesignTestCase v2 等待审核，When 获授权人员批准，Then 系统固化v2并迁移/发布对应TestCase；v1和未批准v3均不得被执行计划选中。

2. **代码发布门禁**  
   Given API自动化代码静态检查失败，When 用户尝试批准，Then 系统拒绝批准并展示失败检查；仅人工备注不得绕过强制门禁。

3. **外部Bug写入**  
   Given Defect草稿已生成但未执行EXTERNAL_WRITE批准，When Agent尝试提交Jira/PingCode，Then 外部调用被拒绝并记录越权审计。

4. **报告数据一致性**  
   Given 报告引用的ExecutionResult快照发生变化，When 测试负责人签字，Then 系统拒绝沿用旧摘要并要求重新生成或重新审核报告。

5. **知识发布**  
   Given AI生成知识候选但缺少适用范围或来源，When 进入发布流程，Then 系统保持草稿并阻止创建可批准的发布任务。

6. **高风险职责分离**  
   Given HIGH风险脚本的主要Editor是用户A，When 用户A尝试作为唯一Approver批准，Then 系统拒绝并要求另一名有权限人员批准。

7. **人工修改使审核失效**  
   Given TestPlan v1已有一条未完成审核，When Editor修改关键范围形成v2，Then v1审核不得应用于v2，WorkItem继续针对v2进入PENDING_REVIEW。

8. **AI重做差异可见**  
   Given Reviewer要求修改三个问题，When Agent完成重做，Then 系统展示逐项采纳状态、v1→v2真实Diff和未采纳原因。

9. **批准后不可覆盖**  
   Given TestReport v1已PUBLISHED，When 用户修改质量结论，Then 系统创建v2修订工作项，不得覆盖v1正文、签名和引用。

10. **下游只使用批准版本**  
    Given AutomationScript同时存在v2 APPROVED和v3 PENDING_REVIEW，When 创建执行任务，Then 默认只能选择v2；选择v3必须进入明确的隔离试验流程且不得生成正式质量结论。

### 5.7 Release、TestStrategy、TestPlan 与 ExecutionPlan 契约

#### 5.7.1 概念裁决

目标态只保留四个不重叠的概念：

| 概念            | 中文          | 回答的问题                                                  | 是否正式审核产出物                           |
| --------------- | ------------- | ----------------------------------------------------------- | -------------------------------------------- |
| `Release`       | 发布版本/迭代 | 这次业务要交付什么版本？                                    | 否；属于项目业务上下文，但关键状态变化需授权 |
| `TestStrategy`  | 测试策略      | 针对该版本测什么、为什么测、采用什么总体方法和质量标准？    | 是                                           |
| `TestPlan`      | 测试计划      | 谁在什么时间完成哪些测试工作，依赖、资源和里程碑是什么？    | 是                                           |
| `ExecutionPlan` | 执行计划      | 批准后的哪些用例/脚本在什么环境、以什么参数和触发方式运行？ | 配置型产出；正式运行前需校验和授权           |

目标主链：

```text
Workspace（项目）
└── Release（业务发布）
    └── TestStrategy vN（一个当前已发布策略基线）
        └── TestPlan 1..N（功能、回归、性能等测试工作计划）
            ├── WorkItem 1..N（具体任务与审核）
            ├── TestScenario 1..N
            │   └── DesignTestCase → TestCase
            └── ExecutionPlan 0..N
                └── ExecutionTask → ExecutionResult
```

#### 5.7.2 TestDesignPlan 退场裁决

现行 `TestDesignPlan` 同时保存 `scope/strategy/testTypes`，实质上就是不完整的测试策略；现行 `TestPlan` 又被描述为“发版里程碑”，导致策略、方案、计划和发布四个概念相互重叠。

目标态裁决：

1. `TestDesignPlan` 不再作为独立领域实体和正式产出物；
2. 现行 TestDesignPlan 的策略性内容迁移至 `TestStrategy`；
3. 现行“测试方案”中文展示名废弃，统一使用“测试策略”；
4. TestScenario 从 `testDesignPlanId` 改为归属 `testPlanId`；
5. TestPlan 不再承担发布里程碑语义，发布上下文由 Release 独立承载；
6. TestDesignPlan 历史标识作为迁移来源保存在 Source Trace/legacyRef，不丢失追溯关系。

这一裁决减少一个重复实体，而不是再增加一层“测试方案”。

#### 5.7.3 Release 最小职责

Release 已在 §5.4 确认为项目的一次业务发布上下文，其职责限于：

- 业务版本标识和名称；
- 计划/实际发布时间；
- 发布范围摘要；
- `Planning/Testing/Released/Archived` 生命周期；
- 聚合策略、计划、执行、报告和门禁结果；
- 提供跨产出物的版本过滤和追溯锚点。

Release 不保存测试策略正文、任务排期、用例范围或执行参数，避免再次成为万能容器。

#### 5.7.4 TestStrategy 最小字段

| 字段                             | 约束       | 含义                                   |
| -------------------------------- | ---------- | -------------------------------------- |
| `id`                             | 主键       | 策略稳定标识                           |
| `tenantId/workspaceId/releaseId` | 必填       | 租户、项目和发布上下文                 |
| `version`                        | 必填       | 策略修订版本                           |
| `objective`                      | 必填       | 本次测试要证明或降低什么风险           |
| `inScope/outOfScope`             | 必填       | 明确包含和排除范围                     |
| `riskAssessment`                 | 必填       | 风险项、概率、影响和优先级             |
| `testTypes`                      | 必填       | API、Web、Performance、Security等      |
| `approach`                       | 必填       | 测试层次、方法、优先级和组合策略       |
| `entryCriteria/exitCriteria`     | 必填       | 进入和结束测试的质量条件               |
| `environmentStrategy`            | 必填       | 环境使用、隔离和一致性要求             |
| `dataStrategy`                   | 必填       | 数据准备、脱敏、清理和复用原则         |
| `automationStrategy`             | 必填       | 自动化范围、框架、人工保留项和维护原则 |
| `defectStrategy`                 | 必填       | 缺陷严重度、提交流程和关闭标准         |
| `sourceTrace/contentDigest`      | 必填       | 来源和审核内容摘要                     |
| `reviewStatus`                   | 必填       | 使用 §5.6 通用审核阶段                 |
| `approvedBy/approvedAt`          | 审核后必填 | 批准责任和时间                         |
| `createdAt/updatedAt`            | 必填       | 审计时间                               |

约束：

- 一个 Release 可以有多个历史策略版本，但同一时刻只能有一个 `PUBLISHED` 当前基线；
- 策略来源可以包含多份 RequirementDocument/APIContract，通过 WorkItemArtifact/Source Trace 关联，不再使用单一 `requirementDocumentId` 限制；
- 策略默认采用 SINGLE_REVIEW，高风险发布采用 FOUR_EYES；
- AI 可生成和修改策略草稿，但不能发布策略基线。

#### 5.7.5 TestPlan 最小字段

| 字段                             | 约束       | 含义                                                          |
| -------------------------------- | ---------- | ------------------------------------------------------------- |
| `id`                             | 主键       | 测试计划唯一标识                                              |
| `tenantId/workspaceId/releaseId` | 必填       | 所属上下文                                                    |
| `strategyId/strategyVersion`     | 必填       | 绑定已批准策略的精确版本                                      |
| `name/objective`                 | 必填       | 计划名称和具体目标                                            |
| `planType`                       | 必填       | `FUNCTIONAL/REGRESSION/AUTOMATION/PERFORMANCE/SECURITY/OTHER` |
| `scope`                          | 必填       | 本计划负责的策略范围子集                                      |
| `ownerId`                        | 必填       | 计划责任人                                                    |
| `participants`                   | 可选       | 人员、团队和Agent建议；实际权限另行校验                       |
| `startDate/endDate`              | 必填       | 计划周期                                                      |
| `milestones`                     | 必填       | 关键里程碑和验收点                                            |
| `resourceRequirements`           | 必填       | 人员、Agent、环境、Runner和工具需求                           |
| `dependencies`                   | 可选       | 外部依赖和其他计划依赖；任务依赖使用WorkItemDependency        |
| `acceptanceCriteria`             | 必填       | 计划完成条件                                                  |
| `reviewStatus`                   | 必填       | 计划审核阶段                                                  |
| `lifecycleStatus`                | 必填       | `NOT_STARTED/ACTIVE/COMPLETED/CANCELLED/ARCHIVED`             |
| `version/contentDigest`          | 必填       | 计划版本和内容摘要                                            |
| `approvedBy/approvedAt`          | 审核后必填 | 批准责任和时间                                                |
| `createdAt/updatedAt`            | 必填       | 审计时间                                                      |

约束：

- 一个 Release 可以有多个 TestPlan；
- TestPlan 必须绑定已 APPROVED/PUBLISHED 的 TestStrategy 精确版本后才能正式发布；
- TestPlan 可以在策略草稿阶段创建为草稿，但不得进入 ACTIVE；
- 计划范围不得超出策略 inScope，扩大范围必须先修订策略或获得明确的策略例外审核；
- WorkItem 是计划的具体执行单元；TestPlan 不复制 WorkItem 的实时状态和运行证据。

#### 5.7.6 TestScenario 与 TestPlan

- TestScenario 直接归属于 TestPlan；
- TestScenario 表达在该计划下需要覆盖的业务路径或质量场景；
- 相同业务场景跨 Release/计划复用时，复制或引用策略由后续版本设计决定，但必须保留来源和版本；
- DesignTestCase 归属于 TestScenario；批准后形成可跨计划复用的正式 TestCase；
- TestPlan 完成或归档不删除已批准 TestCase。

#### 5.7.7 ExecutionPlan 与 TestPlan

ExecutionPlan 是运行配置，不是测试计划的同义词：

| TestPlan                                   | ExecutionPlan                            |
| ------------------------------------------ | ---------------------------------------- |
| 描述测试工作、责任、时间、里程碑和完成标准 | 描述机器执行范围、环境、参数、触发和并发 |
| 可以包含人工、分析、审核和自动化任务       | 只负责可执行任务配置                     |
| 一个计划可以有多个执行计划                 | 一个执行计划只归属一个测试计划           |
| 需要人工审核批准                           | 正式运行前校验引用版本和执行权限         |

ExecutionPlan 目标增加：

- `testPlanId`：必填；
- `releaseId`：可通过 TestPlan 推导，若冗余存储必须校验一致；
- `case/script/version` 精确选择；
- `environmentId`、`scopeConfigs`、触发方式、并发和Runner策略；
- `configurationDigest`：防止批准后运行配置被静默修改。

只有满足以下条件才能创建正式 ExecutionTask：

1. TestPlan 已批准且处于 NOT_STARTED/ACTIVE；
2. 所有选中 TestCase/AutomationScript 版本已批准；
3. Environment 属于同一 Workspace，目标部署Release与计划要求兼容；
4. Secrets、Runner和外部访问权限通过校验；
5. 执行配置摘要与授权版本一致。

#### 5.7.8 变更影响规则

1. TestStrategy 新版本发布后，系统为所有绑定旧版本且未完成的 TestPlan 创建影响分析 WorkItem；不得自动切换策略版本；
2. TestPlan 关键范围、时间、验收标准或策略版本变化时必须形成新版本并重新审核；
3. TestPlan 新版本不会自动修改已生成的 TestScenario/TestCase，系统先生成影响清单，由测试人员选择保留、修订或废弃；
4. ExecutionPlan 更换用例/脚本版本、环境、触发或并发配置后，旧授权失效；
5. Release 归档后不得新建正式执行，但历史报告、Bug、知识和证据继续可查；
6. Release 状态从 Testing 进入 Released 必须引用已签字TestReport或明确记录例外决定。

#### 5.7.9 文档阶段迁移规则

当前项目尚无应用代码和生产数据，因此本轮只定义契约迁移，不执行数据库数据迁移：

| 现行对象/字段                        | 目标处理                                             |
| ------------------------------------ | ---------------------------------------------------- |
| TestPlan“发版里程碑”语义             | 迁移至 Release；TestPlan 恢复为测试活动计划          |
| TestDesignPlan 实体                  | 重命名/迁移为 TestStrategy，不再保留独立测试方案实体 |
| TestDesignPlan.scope                 | TestStrategy.inScope/outOfScope，需人工拆分确认      |
| TestDesignPlan.strategy              | TestStrategy.approach，并补齐风险、准入/退出等字段   |
| TestDesignPlan.testTypes             | TestStrategy.testTypes                               |
| TestDesignPlan.requirementDocumentId | 改为多来源 WorkItemArtifact/Source Trace             |
| TestDesignPlan.testPlanId            | 反转为 TestPlan.strategyId/strategyVersion           |
| TestScenario.testDesignPlanId        | 改为 TestScenario.testPlanId                         |
| ExecutionPlan                        | 增加 testPlanId 和精确资产版本绑定                   |

迁移时必须保留旧标识和来源映射，并重新验证 RequirementDocument → TestingIR → BusinessRule → Scenario → DesignTestCase → TestCase → Assertion 的可信链。

#### 5.7.10 Given/When/Then 验收基线

1. **概念唯一性**  
   Given 用户创建一个新发布版本，When 进入测试策划，Then 系统分别提供“测试策略”和“测试计划”，不得再出现独立“测试方案”实体或把TestPlan称为发布版本。

2. **策略先于计划生效**  
   Given TestStrategy v2仍在PENDING_REVIEW，When 用户尝试发布绑定v2的TestPlan，Then 系统拒绝正式发布，但允许保存计划草稿。

3. **一个版本多计划**  
   Given Release 2026.08已有功能测试计划，When 创建性能测试计划，Then 两个计划可以绑定同一已批准策略版本并拥有独立负责人、周期和验收标准。

4. **计划范围不得越界**  
   Given 策略明确支付模块 OutOfScope，When 计划尝试加入支付测试任务，Then 系统阻止发布并要求修订策略或提交策略例外审核。

5. **策略变更不静默传播**  
   Given 三个未完成计划绑定 TestStrategy v1，When v2发布，Then 系统生成三个影响分析项，所有计划仍引用v1直至人工确认迁移。

6. **场景归属明确**  
   Given 用户查看 TestScenario，When 打开其追溯关系，Then 可以直接定位所属TestPlan、策略精确版本、Release和来源需求，不依赖已废弃TestDesignPlan。

7. **计划与执行计划分离**  
   Given TestPlan包含人工探索测试和API自动化任务，When 创建ExecutionPlan，Then 只选择可执行资产和运行配置，不复制人工任务为ExecutionTask。

8. **批准版本执行**  
   Given ExecutionPlan引用AutomationScript v3 PENDING_REVIEW，When 启动正式执行，Then 系统拒绝；改为v2 APPROVED且其他校验通过后方可启动。

9. **发布状态有证据**  
   Given Release处于Testing且不存在已签字报告或例外决定，When 用户尝试改为Released，Then 系统拒绝并展示缺失证据。

10. **历史链不丢失**  
    Given 旧文档引用TestDesignPlan ID，When 完成目标契约迁移，Then 可以通过legacyRef/Source Trace定位新的TestStrategy及其下游计划、场景和用例。

### 5.8 自动化测试代码契约

#### 5.8.1 设计目标与现行问题

自动化测试代码是需要独立审核、版本固化和执行追溯的正式产出物。现行 AutomationScript 将元数据、可变代码正文和 Git 引用放在同一实体，并以 `testCaseId UNIQUE` 限制一个用例只能有一个脚本，无法满足：

- 同一用例存在 Web、API 或不同框架实现；
- 一段端到端脚本覆盖多个测试用例；
- 代码多版本并行审核；
- 平台托管代码与 Git 代码两种权威来源；
- 执行任务绑定精确、不可变的代码版本；
- AI 生成、人工修改、检查、Review 和发布证据分离。

目标态将“脚本身份”和“代码版本”拆分：

```text
AutomationScript（稳定身份与分类）
└── AutomationScriptVersion 1..N（不可变代码版本）
    ├── AutomationScriptCaseBinding 1..N（绑定用例精确版本）
    ├── AutomationCheckRun 1..N（确定性检查与试运行）
    ├── ReviewTask 1..N（人工代码审核）
    └── ExecutionPlan/ExecutionTask 引用（正式执行）
```

#### 5.8.2 自动化类型

| `automationType` | 当前支持范围                  | 典型框架               | V1状态         |
| ---------------- | ----------------------------- | ---------------------- | -------------- |
| `WEB`            | 浏览器UI流程、DOM/视觉证据    | Playwright             | 必须支持       |
| `API`            | HTTP/REST接口、契约和业务断言 | pytest/httpx或等价框架 | 必须支持       |
| `MOBILE`         | 移动端应用自动化              | Appium等               | 预留，不承诺V1 |
| `PERFORMANCE`    | 性能和负载脚本                | k6等                   | 预留，不承诺V1 |
| `SECURITY`       | 受控安全测试脚本              | 待裁决                 | 预留，默认禁用 |

Web和API是同一个一级模块内的两类正式代码产出物，不拆成两个一级模块，也不强迫共用完全相同的运行配置Schema。

#### 5.8.3 AutomationScript 最小字段

| 字段                   | 约束 | 说明                                    |
| ---------------------- | ---- | --------------------------------------- |
| `id`                   | 主键 | 稳定脚本标识                            |
| `tenantId/workspaceId` | 必填 | 租户和项目隔离                          |
| `name`                 | 必填 | 脚本名称                                |
| `automationType`       | 必填 | WEB/API/MOBILE/PERFORMANCE/SECURITY     |
| `framework`            | 必填 | Playwright、pytest/httpx等              |
| `language`             | 必填 | Python、TypeScript/JavaScript等         |
| `description`          | 可选 | 目标和适用范围                          |
| `ownerId`              | 必填 | 正式资产维护责任人                      |
| `primaryVersionId`     | 可选 | 当前默认批准版本；只能指向PUBLISHED版本 |
| `lifecycleStatus`      | 必填 | ACTIVE/DEPRECATED/ARCHIVED              |
| `createdAt/updatedAt`  | 必填 | 审计时间                                |

AutomationScript 不再保存 `codeContent/version/gitRepoUrl/gitFilePath` 等可变版本内容，也不保留 `testCaseId UNIQUE`。

#### 5.8.4 AutomationScriptVersion 最小字段

| 字段                       | 约束             | 说明                                        |
| -------------------------- | ---------------- | ------------------------------------------- |
| `id/scriptId`              | 主键/必填        | 代码版本及所属脚本                          |
| `version`                  | 必填，脚本内唯一 | 单调递增或语义化版本；具体格式在API阶段冻结 |
| `sourceMode`               | 必填             | `MANAGED/GIT`                               |
| `codeContentRef`           | MANAGED必填      | 平台对象存储或版本库中的不可变代码制品引用  |
| `repositoryIntegrationId`  | GIT必填          | 平台管理中的仓库集成，不直接保存Token       |
| `gitBranch`                | GIT可选展示      | 产生版本的分支；不得作为正式执行唯一定位    |
| `fullCommitSha`             | GIT必填          | 完整提交SHA，正式执行必须绑定               |
| `gitFilePath`              | GIT必填          | 仓库内相对路径                              |
| `gitBlobSha`               | GIT推荐必填      | 文件内容对象摘要，防止路径内容漂移          |
| `contentDigest`            | 必填             | 规范化代码内容摘要                          |
| `dependencyLockRef/digest` | 必填             | 锁定依赖及摘要                              |
| `runtimeSpec`              | 必填             | 运行时、入口命令和能力需求                  |
| `generatedByAgentId`       | 可选             | 生成或主要修改的Agent                       |
| `sourceTrace`              | 必填             | 用例、契约、审核意见等来源                  |
| `reviewStatus`             | 必填             | 使用§5.6通用审核阶段                        |
| `checkSummary`             | 必填             | 必需检查的状态摘要                          |
| `supersedesVersionId`      | 可选             | 被替代版本                                  |
| `approvedBy/approvedAt`    | 审核后必填       | 批准记录                                    |
| `createdAt`                | 必填             | 版本创建时间；版本正文不可原地更新          |

`MANAGED`和`GIT`只能有一个权威代码源：

- MANAGED以不可变`codeContentRef + contentDigest`为准；
- GIT以`repositoryIntegrationId + full commit SHA + file path + blob SHA`为准；
- 分支名、PR号和“最新提交”只能用于导航，不得作为正式执行证据；
- 平台可保存脱敏代码快照用于审核和复现，但必须校验与权威摘要一致。

#### 5.8.5 用例绑定

`AutomationScriptVersionCaseBinding`至少包含：

| 字段                         | 说明                             |
| ---------------------------- | -------------------------------- |
| `scriptVersionId`            | 脚本精确版本                     |
| `testCaseId/testCaseVersion` | 正式用例精确版本                 |
| `role`                       | `PRIMARY/COVERED/SETUP/TEARDOWN` |
| `coverageNotes`              | 脚本覆盖该用例的步骤/断言说明    |
| `createdAt`                  | 关联时间                         |

规则：

- 一个脚本版本可以覆盖多个用例版本；
- 一个用例可以有多个不同类型或框架的脚本实现；
- 用例新版本发布后，既有脚本不会自动宣称继续有效，系统创建影响分析WorkItem；
- 正式执行前必须检查脚本版本与用例版本绑定有效。

#### 5.8.6 Web 与 API 类型专属配置

通用字段放在 AutomationScriptVersion，类型专属配置使用受版本控制的Typed Schema：

**WEB至少包含**：

- browser、viewport、baseUrlRef；
- Locator精确版本引用；
- storage/auth state引用，不保存明文凭证；
- screenshot/video/trace策略；
- 浏览器和Playwright运行时版本；
- 数据清理与页面恢复策略。

**API至少包含**：

- protocol、baseUrlRef和APIContract精确版本；
- authProfile/Secret引用；
- request构造、签名和数据准备方式；
- 业务码、字段、Schema和副作用断言；
- 幂等、重放、数据清理和速率限制策略；
- HTTP客户端和运行时版本。

类型Schema变更必须版本化；不得用无约束JSON长期承载所有运行语义。

#### 5.8.7 AI生成、人工修改与Diff

AI Agent生成代码时必须同时提供：

- 目标用例和来源契约的精确版本；
- 生成代码和新增/修改文件清单；
- 依赖变化；
- 关键断言映射；
- 运行与清理说明；
- 已知限制和未实现项；
- 相对上一版本的真实Unified Diff；
- 自检结果及失败项。

人工或AI每次语义修改都创建新AutomationScriptVersion。AI根据Review意见重做时，必须逐项标记“已采纳/未采纳/部分采纳”并说明原因。

#### 5.8.8 确定性检查与试运行

`AutomationCheckRun`至少记录 `scriptVersionId/checkType/status/tool/version/resultRef/startedAt/finishedAt`。最低检查基线：

| 检查              |        WEB |        API | 阻断条件                                     |
| ----------------- | ---------: | ---------: | -------------------------------------------- |
| 格式/语法         |       必须 |       必须 | 任一错误阻断                                 |
| 类型或静态检查    | 按语言必须 | 按语言必须 | ERROR阻断                                    |
| Secret扫描        |       必须 |       必须 | 发现凭证阻断                                 |
| 依赖与许可证检查  |       必须 |       必须 | 禁止依赖/高危漏洞阻断                        |
| 代码安全扫描      |       必须 |       必须 | 高危问题阻断                                 |
| 用例/断言映射校验 |       必须 |       必须 | 缺关键断言阻断                               |
| 隔离试运行        |       必须 |       必须 | 无法启动、超时或未按协议产出结果阻断         |
| Locator健康检查   |       必须 |     不适用 | 关键Locator无效阻断                          |
| APIContract一致性 |     适用时 |       必须 | 路径/方法/Schema不匹配阻断或进入明确偏差审核 |
| 清理/幂等验证     |     适用时 |       必须 | 产生不可控副作用阻断                         |

工具名称可配置，但检查类型、严重度和阻断规则必须稳定、可审计。人工备注不得覆盖强制阻断；例外必须走单独、高权限、限时且可审计的豁免流程。

试运行默认使用隔离Runner：非root、只读根文件系统、最小资源、默认零外网、最小Secret、超时和产出目录限制。需要访问被测环境时只开放明确目标和方法。

#### 5.8.9 Git与外部写入

- 仓库凭证归平台管理的RepositoryIntegration/Secret，脚本实体只保存引用；
- AI可在内部草稿区生成代码；创建分支、提交、推送或PR属于外部写入，必须遵循EXTERNAL_WRITE策略；
- 正式批准必须针对commit/blob/contentDigest，不能只批准PR标题或分支；
- 外部仓库提交后必须回读commit和blob摘要，确认与审核版本一致；
- 仓库内容后续发生变化时，不得静默更新已批准脚本版本；必须新建版本和WorkItem。

#### 5.8.10 Code Review与发布

AutomationScriptVersion进入PENDING_REVIEW前必须完成所有强制检查。ReviewTask至少展示：

- 原始用例、契约和上一脚本版本；
- Unified Diff和文件树变化；
- 断言映射；
- 依赖变化和风险；
- 检查与试运行结果；
- AI未实现项和限制；
- 代码摘要、commit/blob或managed artifact摘要。

批准规则：

1. LOW/MEDIUM代码至少一名有自动化审查能力的Reviewer批准；
2. HIGH/CRITICAL、外部写入、Secret/网络权限变化采用FOUR_EYES；
3. Reviewer不得批准与审核摘要不一致的代码；
4. 所有检查和人工审核通过后，版本进入PUBLISHED并可设为primaryVersionId；
5. 已发布版本废弃只改变可选状态，不删除历史代码和执行证据。

#### 5.8.11 正式执行绑定

- ExecutionPlan必须引用`scriptVersionId`，不得只引用AutomationScript.id或primaryVersionId；
- ExecutionTask启动时保存代码摘要、依赖摘要、运行时、环境、Release、用例版本和权限快照；
- 默认只能执行PUBLISHED版本；
- PENDING_REVIEW版本只允许在隔离试验WorkItem中运行，结果标记EXPERIMENTAL，不进入正式质量报告或发布门禁；
- Runner缺少所需框架/浏览器/运行时能力时，任务在调度前失败并转BLOCKED，不得运行后才静默降级；
- 执行输出必须符合统一ExecutionResult协议，原始日志和制品不可被代码版本更新覆盖。

#### 5.8.12 文档阶段迁移规则

| 现行AutomationScript字段/约束 | 目标处理                                               |
| ----------------------------- | ------------------------------------------------------ |
| `testCaseId UNIQUE`           | 删除；改为AutomationScriptVersionCaseBinding多对多     |
| `scriptLanguage`              | 拆为AutomationScript.language和framework               |
| `codeContent`                 | 迁移为MANAGED模式不可变codeContentRef/contentDigest    |
| `gitRepoUrl`                  | 改为repositoryIntegrationId，不在脚本保存凭证或随意URL |
| `gitFilePath`                 | 下沉至AutomationScriptVersion                          |
| `version`                     | 下沉至AutomationScriptVersion并建立不可变版本记录      |
| 缺少审核/检查字段             | 通过ReviewTask、AutomationCheckRun和通用审核接口补齐   |

#### 5.8.13 Given/When/Then 验收基线

1. **一用例多实现**  
   Given 同一TestCase需要Web和API两种验证，When 创建脚本，Then 系统允许两个AutomationScript并分别绑定精确用例版本。

2. **一脚本多用例**  
   Given 一个端到端脚本覆盖三个TestCase，When 发布脚本版本，Then 三个绑定均记录用例精确版本和覆盖说明。

3. **Git精确定位**  
   Given 脚本使用GIT模式，When 进入审核或执行，Then 必须存在full commit SHA、file path、blob SHA和contentDigest；只有branch时系统拒绝。

4. **强制检查不可绕过**  
   Given Secret扫描发现高风险凭证，When Reviewer尝试批准，Then 系统拒绝并要求新版本修复；普通评论不能覆盖阻断。

5. **AI外部写入受控**  
   Given Agent已生成代码但未获得EXTERNAL_WRITE批准，When 尝试push或创建PR，Then 调用被拒绝并记录审计。

6. **审核摘要一致**  
   Given Reviewer批准contentDigest A，When Git文件内容变为digest B，Then 批准失效且B不能被设为PUBLISHED。

7. **试验与正式结果隔离**  
   Given v3仍在PENDING_REVIEW，When 在隔离试验中执行，Then 结果标记EXPERIMENTAL且不能进入正式TestReport或QualityGate。

8. **执行版本不可漂移**  
   Given ExecutionPlan绑定脚本v2，When primaryVersionId更新为v3，Then 既有ExecutionPlan仍运行v2，除非创建新版本并重新授权。

9. **用例变化影响分析**  
   Given 绑定用例发布新版本，When 系统检测到变化，Then 创建影响分析WorkItem，不自动把脚本标记为仍覆盖新用例。

10. **运行能力前置校验**  
    Given Runner缺少目标Playwright浏览器版本，When 调度任务，Then 任务在执行前BLOCKED并指出缺少能力，不得隐式改用其他版本。

### 5.9 Defect 与外部缺陷系统契约

#### 5.9.1 设计目标与现行问题

`Defect`是平台内部需要人工审核的正式测试产出物，不等于失败结果、AI根因分析、失败聚类，也不等于Jira/PingCode中的外部Issue。目标契约必须解决以下问题：

- `FailureCluster.jiraIssueKey`把业务分析对象与单一外部厂商耦合；
- 现行批量导出接口从聚类直接写Jira，缺少平台内Defect草稿、精确版本审核和批准证据；
- `FailureAnalysis.manualVerified`只有布尔值，无法表达谁审核了哪个版本、为何退回或批准；
- 外部写入失败、重复提交和远端修改缺少幂等、重试、冲突和回执模型；
- AI推断、执行事实、人工结论与外部系统状态混在同一链路，无法证明缺陷结论来自哪些证据。

目标链路为：

```text
ExecutionResult（执行事实）
        ↓
FailureAnalysis（AI/人工诊断）
        ↓
FailureCluster（相似失败分组）
        ↓
Defect + DefectVersion（平台内正式缺陷）
        ↓ 人工审核/批准
ExternalDefectLink + DefectSyncAttempt（外部系统记录与同步回执）
```

四层职责不得合并：

| 对象                 | 回答的问题                             |         是否正式产出物 | 是否可由AI最终批准 |
| -------------------- | -------------------------------------- | ---------------------: | -----------------: |
| ExecutionResult      | 实际执行发生了什么                     | 否，属于不可变执行证据 |             不适用 |
| FailureAnalysis      | 可能的失败分类和根因是什么             |       否，属于分析结论 |                 否 |
| FailureCluster       | 哪些失败可能属于同一问题               |       否，属于聚类候选 |                 否 |
| Defect/DefectVersion | 经审核确认的问题应该如何正式描述和跟踪 |                     是 |                 否 |
| ExternalDefectLink   | 平台Defect对应哪个外部Issue            |       否，属于集成映射 |                 否 |
| DefectSyncAttempt    | 某一批准版本是否成功写入外部系统       |   否，属于外部操作证据 |                 否 |

#### 5.9.2 聚类、分析与缺陷的基数关系

- 一个FailureAnalysis必须指向一个ExecutionResult；一个ExecutionResult可因重新分析产生多个FailureAnalysis版本，但只能有一个当前有效结论；
- 一个FailureCluster可包含多个FailureAnalysis；同一FailureAnalysis在同一聚类算法版本下只能属于一个当前有效Cluster；
- 一个FailureCluster可以不形成Defect，也可以因实际根因不同拆分为多个Defect；
- 一个Defect可以引用多个FailureCluster、FailureAnalysis和ExecutionResult；不得把clusterId设计为Defect上的单值必填外键；
- 聚类拆分、合并或重新计算不得改写已批准DefectVersion的证据快照；只能产生影响提示和新版本草稿；
- “非缺陷”“脚本问题”“环境问题”“重复缺陷”均须保留人工结论，不得通过删除聚类或分析掩盖。

#### 5.9.3 Defect 稳定身份与生命周期

`Defect`保存跨版本稳定身份和跟踪状态；可编辑正文必须进入不可变的`DefectVersion`。

| 字段                                | 规则                                                                        |
| ----------------------------------- | --------------------------------------------------------------------------- |
| id                                  | 平台内稳定唯一标识                                                          |
| workspaceId                         | 必填；唯一业务边界                                                          |
| releaseId                           | 必填；表示发现/影响的业务版本，跨版本影响另存受影响版本集合                 |
| defectKey                           | Workspace内可读唯一编号，由平台生成，不复用外部Issue Key                    |
| lifecycleStatus                     | `NEW/OPEN/IN_PROGRESS/RESOLVED/VERIFIED/CLOSED/REJECTED/DUPLICATE/ARCHIVED` |
| currentVersionId                    | 当前展示版本；只能指向同一Defect                                            |
| approvedVersionId                   | 最近一次批准版本；未批准时为空                                              |
| assigneeId                          | 当前内部负责人，可空；不等于审核人                                          |
| duplicateOfDefectId                 | 仅`DUPLICATE`时必填，必须属于同一Workspace且不能形成循环                    |
| createdFromWorkItemId               | 产生该Defect的WorkItem                                                      |
| createdByActorType/createdByActorId | 记录AI或人工创建来源                                                        |
| createdAt/updatedAt                 | 审计时间                                                                    |

`lifecycleStatus`与`reviewStatus`相互独立：

- `reviewStatus`属于DefectVersion，表达草稿是否经过人工审核；
- `lifecycleStatus`属于Defect，表达已确认问题的处理进展；
- AI新建Defect时，Defect.lifecycleStatus=`NEW`且首版DefectVersion.reviewStatus=`DRAFT`；
- 未存在批准版本时不得进入`OPEN`，更不得外部提交；
- `REJECTED`表示人工确认不是有效缺陷；`DUPLICATE`表示人工确认与另一内部Defect重复；二者都必须保存理由；
- `RESOLVED→VERIFIED`必须关联回归执行证据并由获授权人员确认；AI只能提出验证建议；
- `VERIFIED→CLOSED`由组织流程决定，可由同一能力执行，但仍须审计事件；
- 生命周期每次变化写入不可变`DefectStatusEvent`，禁止只覆盖当前状态。

#### 5.9.4 DefectVersion 最小字段

| 字段                          | 规则                                                                   |
| ----------------------------- | ---------------------------------------------------------------------- |
| id/defectId/version           | 不可变版本标识；`defectId + version`唯一                               |
| title                         | 必填；问题现象而不是根因猜测                                           |
| description                   | 必填；背景、影响和已知边界                                             |
| preconditions                 | 可复现前置条件                                                         |
| reproductionSteps             | 结构化步骤；无法稳定复现时必须明确说明                                 |
| expectedResult                | 必填；引用需求、规则、契约或批准用例                                   |
| actualResult                  | 必填；引用执行结果或人工观察证据                                       |
| severity                      | 影响程度；枚举由术语权威统一管理                                       |
| priority                      | 修复顺序；与severity分离，枚举由术语权威统一管理                       |
| defectType                    | `PRODUCT/SCRIPT/ENVIRONMENT/DATA/SECURITY/PERFORMANCE/USABILITY/OTHER` |
| environmentSnapshotRef        | 发现问题时的环境不可变快照                                             |
| affectedReleaseIds            | 受影响Release集合；至少包含Defect.releaseId                            |
| labels/component              | 可选分类，不承担权限或状态语义                                         |
| sourceTrace                   | 指向需求、业务规则、断言、用例、脚本、执行和分析来源                   |
| contentDigest                 | 对全部可审核正文、结构化字段和证据清单计算摘要                         |
| changeSummary                 | v2起必填，说明相对上一版本的变化                                       |
| generatedByAgentId/agentRunId | AI参与时必填；纯人工版本可空                                           |
| createdBy/createdAt           | 版本创建审计字段                                                       |

正文版本不得保存明文凭证、未脱敏个人信息或无限期有效的下载地址。截图、视频、日志和Trace进入受控制品存储，DefectVersion只保存不可变引用、摘要、权限等级和保留策略。

#### 5.9.5 DefectEvidence 证据关系

`DefectEvidence`把精确DefectVersion与发现依据关联，最少包含：

| 字段                       | 规则                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id/defectVersionId         | 证据关系标识和精确缺陷版本                                                                                                                                                |
| evidenceType               | `EXECUTION_RESULT/FAILURE_ANALYSIS/FAILURE_CLUSTER/TEST_CASE/AUTOMATION_SCRIPT_VERSION/LOG/SCREENSHOT/VIDEO/TRACE/MANUAL_OBSERVATION/REQUIREMENT/BUSINESS_RULE/ASSERTION` |
| evidenceId/evidenceVersion | 指向平台对象及精确版本；对象无版本时记录不可变快照ID                                                                                                                      |
| evidenceDigest             | 防止引用内容变化后仍沿用旧批准                                                                                                                                            |
| relationType               | `OBSERVED_IN/SUPPORTS_EXPECTED/SUPPORTS_ACTUAL/SUPPORTS_ROOT_CAUSE/REGRESSION_VERIFICATION/CONTRADICTS`                                                                   |
| sourceTraceId              | 纳入统一Source Trace链路                                                                                                                                                  |
| addedBy/addedAt            | AI或人工添加来源                                                                                                                                                          |

最低证据门槛：

- `PRODUCT/SECURITY/PERFORMANCE`类Defect必须同时具有期望依据和实际结果依据；
- `SCRIPT/ENVIRONMENT/DATA`类也必须保存执行或人工观察证据，不得仅凭AI置信度创建正式结论；
- 证据缺失时可保存DRAFT，但不能批准；
- 证据摘要变化、权限失效或制品过期时，批准状态转为`STALE`并创建复核WorkItem；
- AI推断必须标记为`INFERRED`，不得伪装为执行事实；人工补充观察必须记录观察人、时间和环境。

#### 5.9.6 生成、审核与发布

Defect采用通用正式产出物状态：

```text
DRAFT → PENDING_REVIEW → APPROVED
   ↑          ↓
   └──── CHANGES_REQUESTED

APPROVED → STALE（证据、正文或关键来源发生变化）
```

具体规则：

1. AI可根据FailureCluster生成一个或多个Defect草稿，也可建议“非缺陷/重复/需更多证据”；
2. 提交审核前执行确定性校验：必填字段、证据完整性、敏感信息扫描、链接有效性、外部目标字段映射和重复候选检查；
3. Reviewer必须审核精确`defectVersionId + contentDigest`，不能批准“当前最新版”这一漂移指针；
4. Reviewer确认是否为真实缺陷、复现性、严重度、优先级、证据、敏感信息和重复关系；
5. 严重或安全缺陷使用`FOUR_EYES`；普通缺陷至少`SINGLE_REVIEW`；具体映射由统一审核策略配置决定；
6. Agent永远不能批准；`FOUR_EYES`下Defect创建人或最近正文修改人不能充当最终Approver，`SINGLE_REVIEW`下允许同一获授权测试人员修改后批准，但必须记录为非独立审核；
7. 批准后任何正文、结构化字段或证据清单变化都必须创建新DefectVersion并重新审核；
8. 内部批准不等于已写入外部系统；外部写入还必须执行`EXTERNAL_WRITE`确认；
9. Defect被判定`REJECTED`或`DUPLICATE`时，仍保留草稿、证据、审核意见和状态事件，用于知识回流与模型评测；
10. 只有批准版本可进入正式TestReport、QualityGate输入或外部同步。

#### 5.9.7 外部缺陷映射

外部系统采用厂商中立的`ExternalDefectLink`，不在Defect或FailureCluster保存`jiraIssueKey`等厂商字段。

| 字段                               | 规则                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------ |
| id/defectId                        | 平台Defect映射；一个Defect可映射多个外部系统记录                               |
| integrationId                      | 指向平台管理中的集成配置；凭证不进入业务对象                                   |
| provider                           | `JIRA/PINGCODE/GITHUB_ISSUES/AZURE_DEVOPS/OTHER`，V1实际启用范围由版本计划决定 |
| externalTenantId/externalProjectId | 外部组织和项目稳定标识                                                         |
| externalIssueId                    | 外部稳定ID，优先于可读Key                                                      |
| externalIssueKey/externalUrl       | 展示用Key和URL，不作为平台主键                                                 |
| syncStatus                         | `NOT_SYNCED/SYNCING/SYNCED/FAILED/CONFLICT/DISABLED`                           |
| lastSyncedDefectVersionId          | 最近成功同步的精确批准版本                                                     |
| lastRemoteVersion/remoteUpdatedAt  | 外部乐观锁或变更检测依据                                                       |
| createdAt/updatedAt                | 映射审计时间                                                                   |

约束：

- `integrationId + externalIssueId`全局唯一，防止同一外部Issue被静默映射到多个内部Defect；
- 外部Key变化不影响内部Defect身份；
- 人工确认重复外部Issue时，可以建立映射或把内部Defect标为`DUPLICATE`，AI不能独立决定；
- 外部Issue删除、无权限或集成停用时保留历史映射并标记状态，不级联删除内部Defect；
- 从外部系统回写状态必须保存原始回执和映射规则，不得直接覆盖内部生命周期；
- 内外状态不一致时进入`CONFLICT`并创建WorkItem，由获授权人员解决。

#### 5.9.8 外部写入、幂等、重试与冲突

每次创建、更新、评论或关闭外部Issue均创建不可变`DefectSyncAttempt`：

| 字段                               | 规则                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------ |
| id/defectId/defectVersionId        | 必须绑定精确已批准版本                                                               |
| externalDefectLinkId               | 新建外部Issue时可空，成功后回填新映射                                                |
| operation                          | `CREATE/UPDATE/COMMENT/TRANSITION/ATTACH/LINK`                                       |
| payloadDigest                      | 对脱敏后的最终外部请求计算摘要                                                       |
| idempotencyKey                     | `integration + operation + defectVersion + payloadDigest`派生，重试不得生成重复Issue |
| approvalId                         | 对应EXTERNAL_WRITE批准记录，必须与请求摘要一致                                       |
| status                             | `PENDING/RUNNING/SUCCEEDED/FAILED/CONFLICT/CANCELLED`                                |
| remoteRequestRef/remoteResponseRef | 受控保存请求和回执引用，不保存凭证明文                                               |
| errorCode/errorMessage             | 失败分类和脱敏信息                                                                   |
| retryOfAttemptId/retryCount        | 重试链路                                                                             |
| startedAt/completedAt              | 操作时间                                                                             |

外部写入规则：

- 所有正式缺陷外部写入均须在调用前获得人工`EXTERNAL_WRITE`批准；不得通过租户开关降级为AI自主提交；
- 批准对象为`provider + integrationId + operation + defectVersionId + payloadDigest`，任一变化都使批准失效；
- 网络超时后先按幂等键或外部查询确认是否已创建，再决定重试，禁止盲目重复创建；
- 外部失败不回滚或篡改已批准的内部Defect，只更新同步状态并创建可重试WorkItem；
- 更新前比较`lastRemoteVersion/remoteUpdatedAt`；远端已变化时进入`CONFLICT`，不得静默覆盖；
- 附件应先脱敏和扫描，再逐个上传并保存回执；部分成功必须明确展示，不能把整批标为成功；
- 批量提交只是多个独立DefectSyncAttempt的编排，不存在一个“批量成功”替代逐条证据。

#### 5.9.9 重复识别与回归验证

AI可以根据标题、组件、堆栈、失败步骤、业务规则和历史Defect给出重复候选及相似度，但最终结论必须人工确认：

- 确定性规则先检查相同`externalIssueId`、相同错误指纹和相同已知问题映射；
- 语义相似度只产生候选，阈值由AI治理权威统一配置，不在本PRD散落；
- Reviewer选择“不是重复”时保存原因，作为后续Eval样本；
- 标记`DUPLICATE`必须填写`duplicateOfDefectId`，且保留各自发现证据；
- 主Defect关闭不会自动关闭重复Defect，状态映射由获授权人员或明确规则执行。

回归验证规则：

- `RESOLVED`只能表示开发或外部系统声明已修复，不等于测试通过；
- 转`VERIFIED`必须关联`REGRESSION_VERIFICATION`证据，至少包括Release、环境、用例版本、脚本版本（如适用）和ExecutionResult；
- 回归失败时转回`OPEN`或`IN_PROGRESS`并创建状态事件，不改写旧验证证据；
- 自动化回归成功可由Agent提出“建议验证通过”，最终状态变化仍由具备`defect.verify`能力的人员确认；
- 无法自动回归时允许人工观察证据，但必须记录步骤、环境、观察人和时间。

#### 5.9.10 文档阶段迁移规则

| 现行字段/能力                         | 目标处理                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `FailureCluster.jiraIssueKey`         | 删除；迁移到ExternalDefectLink.externalIssueKey并补externalIssueId/integrationId                       |
| `FailureAnalysis.manualVerified`      | 废弃；使用ReviewTask、reviewStatus和精确版本审核记录                                                   |
| `FailureAnalysis.assignedDeveloperId` | 诊断对象只保留负责人建议；正式负责人进入Defect.assigneeId                                              |
| `/intelligence/defects/export`        | 设计契约中直接替换；拆为Defect草稿/版本/审核资源与`/quality/defects/{id}/sync-attempts`，保留旧→新映射 |

本裁决形成时无生产数据，因此选择直接冻结目标契约。相关03/04/32/33、PRD14、AI治理矩阵与API弃用说明已在Gate D同步；历史审计保持原样。

#### 5.9.11 Given/When/Then 验收基线

1. **聚类不等于缺陷**  
   Given 一个FailureCluster包含脚本问题和产品问题，When Reviewer拆分结论，Then 系统允许只为产品问题创建Defect，并保留脚本问题的非缺陷结论。

2. **一缺陷多证据**  
   Given 同一问题在Web和API执行中出现，When 创建DefectVersion，Then 可关联多个ExecutionResult和FailureAnalysis且每条证据具有摘要和关系类型。

3. **证据不足不能批准**  
   Given Defect草稿只有AI根因猜测而没有期望与实际依据，When 提交批准，Then 系统拒绝并指出缺失证据。

4. **审核绑定精确版本**  
   Given Reviewer批准Defect v2的digest A，When 作者修改步骤形成v3/digest B，Then v2批准不适用于v3，v3必须重新审核。

5. **AI不能直接外部提交**  
   Given AI生成的Defect已内部批准但没有EXTERNAL_WRITE批准，When Agent调用Jira/PingCode，Then 调用被拒绝并写入越权审计。

6. **外部写入幂等**  
   Given CREATE请求超时但外部Issue实际已创建，When 相同幂等键重试，Then 系统先发现既有Issue并建立映射，不创建第二个Issue。

7. **远端冲突不覆盖**  
   Given Jira Issue在上次同步后已被人工修改，When 平台尝试UPDATE，Then 同步进入CONFLICT并创建处理WorkItem，不覆盖远端内容。

8. **部分附件失败可见**  
   Given 三个附件中一个因敏感信息扫描失败，When 外部提交完成，Then 每个附件均有独立状态，整体不得显示为完全成功。

9. **重复关系需人工确认**  
   Given AI认为两个Defect高度相似，When 未获得Reviewer确认，Then 系统只能展示候选，不能设置DUPLICATE或自动关闭任一Defect。

10. **修复不等于验证**  
    Given 外部Issue已标记Resolved但无回归结果，When 尝试把内部Defect设为VERIFIED，Then 系统拒绝；关联批准的回归ExecutionResult后方可由获授权人员确认。

11. **外部失败不损坏内部事实**  
    Given PingCode接口返回失败，When 同步任务结束，Then 已批准DefectVersion保持不变，同步状态为FAILED且生成可重试WorkItem。

12. **厂商映射与业务对象解耦**  
    Given 同一内部Defect需要同时跟踪Jira和PingCode，When 建立映射，Then 系统创建两个ExternalDefectLink且Defect身份与生命周期保持唯一。

### 5.10 APIContract 唯一写入所有者与基线契约

#### 5.10.1 裁决结论

`APIContract`及其版本的唯一业务写入所有者是**知识库**。其他模块只能消费精确版本、发起导入/变更请求或生成差异建议，不得各自保存和修改另一份“接口契约”。

| 模块/入口         | 责任                                                         | 可否直接修改APIContract正式版本 |
| ----------------- | ------------------------------------------------------------ | ------------------------------: |
| 知识库            | 原始来源接入、解析、规范化、版本、Diff、审核、发布和基线管理 |              是，唯一写入所有者 |
| Workspace创建向导 | 收集OpenAPI URL/文件并委托知识库导入命令                     |                              否 |
| 测试策划与设计    | 读取批准版本，生成覆盖策略、场景、用例和差异WorkItem         |                              否 |
| 自动化测试开发    | 读取精确Operation/Schema版本，生成请求、断言、Mock或校验代码 |                              否 |
| 测试执行          | 读取ExecutionContractBaseline并产生观察事实和契约检查结果    |                              否 |
| 质量分析与缺陷    | 消费契约偏差、覆盖结果和变更影响，生成分析/Defect草稿        |                              否 |
| 平台管理          | 管理仓库、URL、网关和认证集成配置                            |              否，不拥有契约内容 |
| AI Agent中心      | 编排解析/差异/影响分析Agent并保存Trace/Eval                  |                              否 |

该裁决解决三类重复写入：Workspace中的`swagger_schema`、TestAsset中的`APIContract` CRUD以及KnowledgeCenter中的Swagger解析不得形成三份事实。它们应收敛为同一知识库命令和同一领域聚合。

#### 5.10.2 三层对象不可混用

```text
SourceSnapshot（原始、不可变来源）
        ↓ 解析/规范化
APIContract + APIContractVersion（平台规范化契约）
        ↓ 人工审核/发布
APIContractBaseline / ExecutionContractBaseline（按用途绑定精确版本）
        ↓ 执行
APIObservation + ContractCheckResult（实际观察与偏差事实）
```

| 层级                      | 含义                                                      | 允许的变化方式                 |   是否可作为执行断言依据 |
| ------------------------- | --------------------------------------------------------- | ------------------------------ | -----------------------: |
| SourceSnapshot            | 某次上传、URL抓取、仓库文件、手工输入或流量样本的原始内容 | 只新增快照，不覆盖             |                       否 |
| APIContractVersion        | 对原始来源规范化后的完整接口契约版本                      | 只创建新版本并审核             |     是，但必须被基线引用 |
| APIContractBaseline       | 某Release/用途批准采用哪些精确契约版本                    | 创建新基线版本或替换指针并审计 |            设计/Mock可用 |
| ExecutionContractBaseline | 某ExecutionPlan实际采用的冻结基线快照                     | 创建后不可变                   |                       是 |
| APIObservation            | 运行时实际请求/响应的脱敏事实                             | 只追加                         | 否，不能反向改写声明契约 |
| ContractCheckResult       | 观察事实与执行基线比较得到的匹配/偏差结果                 | 只追加                         |             属于执行结果 |

流量录制只能形成`SourceSnapshot(sourceType=TRAFFIC)`和`APIObservation`，默认属于“观察到的行为”，不得自动替换产品声明的OpenAPI契约。AI可以提出差异建议，但正式版本仍需人工审核。

#### 5.10.3 APIContract 稳定身份

`APIContract`代表Workspace内一个逻辑API服务或契约集合，不再把每个`path + method`当作契约主实体。

| 字段                | 规则                                                      |
| ------------------- | --------------------------------------------------------- |
| id                  | 稳定唯一标识                                              |
| workspaceId         | 必填；唯一业务边界                                        |
| name                | Workspace内可读名称                                       |
| serviceKey          | Workspace内稳定唯一键，不因展示名或URL改变                |
| protocol            | `HTTP_REST/GRAPHQL/GRPC/ASYNC_API/OTHER`；V1优先HTTP_REST |
| description         | 契约范围和服务说明                                        |
| owningTeamRef       | 可选业务责任引用，不承担平台权限语义                      |
| currentVersionId    | 当前展示版本，可指向草稿                                  |
| publishedVersionId  | 当前已发布版本；基线只能引用已发布版本                    |
| status              | `ACTIVE/DEPRECATED/ARCHIVED`                              |
| createdAt/updatedAt | 审计时间                                                  |

`baseUrl`不属于契约稳定身份：不同环境的地址、认证和网关配置归Environment/Integration；APIContract只描述协议结构和语义。相同路径在不同服务中允许存在。

#### 5.10.4 SourceSnapshot 原始来源

每次导入必须先生成不可变`SourceSnapshot`，至少包含：

| 字段                                | 规则                                                       |
| ----------------------------------- | ---------------------------------------------------------- |
| id/workspaceId                      | 快照身份和业务边界                                         |
| sourceType                          | `OPENAPI_FILE/OPENAPI_URL/REPOSITORY/MANUAL/TRAFFIC/OTHER` |
| sourceIntegrationId                 | URL、仓库、网关等集成引用；上传文件可空                    |
| sourceLocator                       | 脱敏后的URL、仓库路径、文件名或采集会话引用                |
| fetchedRevision                     | ETag、full commit SHA、对象版本或采集批次                  |
| rawContentRef/rawDigest             | 原始内容的受控存储引用与摘要                               |
| mediaType/specVersion               | 媒体类型及识别出的OpenAPI/AsyncAPI等版本                   |
| fetchStatus                         | `PENDING/SUCCEEDED/FAILED/PARTIAL`                         |
| fetchedByActorType/fetchedByActorId | 人工、系统或Agent来源                                      |
| fetchedAt                           | 抓取时间                                                   |
| errorCode/errorMessage              | 失败时保存脱敏错误                                         |

约束：

- 相同来源再次导入也生成新快照；若摘要相同，可标记`NO_CONTENT_CHANGE`但不能伪造新契约版本；
- 在线URL导入必须防止内网探测、重定向绕过和超大响应；认证信息只通过Integration引用；
- 仓库来源必须绑定full commit SHA和file blob摘要，不能只保存branch；
- 原始文件解析失败仍保留失败快照和诊断，不创建假成功版本；
- 人工录入也必须形成快照，保证“修改前内容”可追溯。

#### 5.10.5 APIContractVersion 与 APIOperation

`APIContractVersion`是规范化后的不可变完整契约，最少包含：

| 字段                               | 规则                                                                |
| ---------------------------------- | ------------------------------------------------------------------- |
| id/apiContractId/version           | 不可变版本；`apiContractId + version`唯一                           |
| sourceSnapshotIds                  | 一个或多个原始来源；合并时必须保留全部来源                          |
| normalizedSpecRef/normalizedDigest | 规范化完整契约引用和摘要                                            |
| sourceKind                         | `DECLARED/OBSERVED/MANUAL/MERGED`                                   |
| parserName/parserVersion           | 可复现解析器信息                                                    |
| normalizationRulesVersion          | 规范化规则版本                                                      |
| reviewStatus                       | 通用`DRAFT/PENDING_REVIEW/CHANGES_REQUESTED/APPROVED/STALE`         |
| validationStatus                   | `PENDING/PASSED/FAILED/WARNING`                                     |
| breakingChangeLevel                | 相对基线的`NONE/NON_BREAKING/POTENTIALLY_BREAKING/BREAKING/UNKNOWN` |
| changeSummary                      | v2起必填，包含端点和Schema变化摘要                                  |
| sourceTrace                        | 来源、解析、人工修改和合并轨迹                                      |
| createdBy/createdAt                | 版本审计                                                            |

`APIOperation`是APIContractVersion的不可变子项，不是独立可写聚合。最少包含：

- operationVersionId、apiContractVersionId；
- stableOperationKey；OpenAPI存在`operationId`时优先使用，否则由服务键、规范化method/path派生；
- method、normalizedPath、summary、tags、deprecated；
- parameterSchema、headerSchema、requestBodySchemas、responseSchemas、securityRequirements；
- schemaDigest、sourcePointer；
- 服务器地址、环境凭证和运行时变量不进入APIOperation。

约束：

- 同一APIContractVersion内`method + normalizedPath`唯一；
- Operation内容变化产生新的APIContractVersion和新的operationVersionId；
- TestCase和AutomationScriptVersion必须绑定`operationVersionId`或稳定键加精确contractVersionId，不能只绑可漂移的APIContract.id；
- OpenAPI未声明的实际响应可形成偏差证据，不能静默追加到已发布版本；
- 手工修正解析结果必须生成新版本并记录Diff，不允许原地UPDATE。

#### 5.10.6 校验、Diff与人工审核

提交审核前执行确定性校验：

- 规范版本、语法、`$ref`可解析性和循环引用边界；
- operationId/stableOperationKey、method/path唯一性；
- 请求和响应媒体类型、状态码、Schema合法性；
- 外部引用锁定、摘要和可复现性；
- 示例与Schema的一致性；
- 敏感信息、真实Token、Cookie、个人数据和内网地址扫描；
- 相对当前批准基线的新增、删除、字段类型、必填性、枚举和安全要求Diff；
- Parser/AI警告必须分类为阻断、需复核或信息提示。

审核规则：

1. AI可解析、规范化、补充描述和提出合并建议，但不能批准正式APIContractVersion；
2. Reviewer审核精确`versionId + normalizedDigest + diffDigest`；
3. `BREAKING`或安全要求变化使用`FOUR_EYES`，普通新版本至少`SINGLE_REVIEW`；
4. 解析失败、阻断校验失败或来源摘要失效时不能批准；
5. 人工接受“声明与实际不一致”必须记录偏差理由、适用Release和失效条件，不能直接把观察值改成声明值；
6. 批准版本的正文、子Operation或来源集合改变时，必须形成新版本；
7. 发布版本不自动替换任何既有ExecutionContractBaseline，只生成影响分析WorkItem；
8. `FOUR_EYES`下Reviewer/最后修改人与最终Approver必须分离；`SINGLE_REVIEW`下允许同一获授权测试人员修改后批准，但必须记录为非独立审核。

#### 5.10.7 设计基线与执行基线

`APIContractBaseline`表示在特定上下文中批准使用的契约集合：

| 字段                     | 规则                                                          |
| ------------------------ | ------------------------------------------------------------- |
| id/workspaceId/releaseId | 基线身份、Workspace和业务版本                                 |
| purpose                  | `TEST_DESIGN/MOCK/CONTRACT_ANALYSIS`                          |
| version                  | 基线自身版本，不可原地覆盖成员                                |
| entries                  | `apiContractId + apiContractVersionId + normalizedDigest`集合 |
| status                   | `DRAFT/PENDING_REVIEW/APPROVED/RETIRED`                       |
| approvedBy/approvedAt    | 人工批准证据                                                  |
| createdFromWorkItemId    | 形成基线的任务                                                |

`ExecutionContractBaseline`由ExecutionPlan发布时冻结，至少包含：

- executionPlanVersionId、releaseId、environmentSnapshotId；
- 从APIContractBaseline复制的精确versionId/digest集合；
- 运行时服务器映射、认证引用、变量Schema和脱敏规则的快照；
- 创建人、创建时间、授权快照和baselineDigest；
- 只追加，不因知识库发布新版、环境配置更新或集成凭证轮换而漂移。

执行前若基线引用已撤销、权限失效或必需凭证不可用，则ExecutionTask转`BLOCKED`；不得自动切换到“最新版”。

#### 5.10.8 运行观察与契约偏差

测试执行产生`APIObservation`和`ContractCheckResult`：

| 对象                | 最小内容                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| APIObservation      | ExecutionResult、operationVersionId、请求/响应元数据、脱敏Body引用、状态码、时延、环境快照、内容摘要 |
| ContractCheckResult | baselineDigest、检查项、`MATCH/DEVIATION/NOT_CHECKED/INCONCLUSIVE`、预期引用、实际引用、严重度、原因 |

规则：

- 原始请求/响应属于执行证据，按权限和保留策略保存；
- 未检查不能计为通过，`INCONCLUSIVE`不能被报告为契约一致；
- 偏差可触发Defect草稿、契约变更建议或环境/脚本问题WorkItem，由人工分类；
- 观察结果只能生成新的SourceSnapshot/变更建议，不能直接写APIContractVersion；
- TestReport必须同时展示采用的执行基线摘要、已检查Operation数、偏差数、未检查数和不可判定数。

#### 5.10.9 写入命令与模块边界

知识库对外提供唯一命令面，其他入口只做代理或提交请求：

| 命令                            | 执行者                        | 结果                                 |
| ------------------------------- | ----------------------------- | ------------------------------------ |
| ImportAPIContractSource         | 知识库                        | SourceSnapshot + 解析WorkItem        |
| CreateAPIContractVersion        | 知识库解析/人工编辑流程       | DRAFT APIContractVersion             |
| SubmitAPIContractReview         | 具备提交能力的人工或受限Agent | ReviewTask                           |
| ApproveAPIContractVersion       | 获授权人工Reviewer            | APPROVED版本                         |
| PublishAPIContractVersion       | 知识库                        | 更新publishedVersionId并产生影响事件 |
| CreateAPIContractBaseline       | 测试策划发起、知识库持久化    | DRAFT基线                            |
| ApproveAPIContractBaseline      | 获授权人工Reviewer            | APPROVED基线                         |
| FreezeExecutionContractBaseline | 测试执行                      | 不可变执行快照，仅引用知识库版本     |
| ProposeContractChange           | 任意消费模块/Agent            | 变更WorkItem，不直接修改契约         |

删除操作只允许归档稳定APIContract或废弃版本；只要被TestCase、AutomationScriptVersion、Baseline、ExecutionResult、Defect或Report引用，就不得物理删除。

#### 5.10.10 文档阶段迁移规则

| 现行字段/能力                            | 目标处理                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| Workspace.`swagger_schema`               | 删除内容副本；改为APIContract/APIContractVersion引用或最近导入状态                     |
| `/workspaces/{id}/ai-scan`               | 设计契约中替换为ImportAPIContractSource/WorkItem；只有发现真实消费者时才提供限期代理   |
| TestAsset.`APIContract` CRUD             | 资产中心不再拥有写入；设计契约直接迁移到知识库命令，只有发现真实消费者时才提供限期适配 |
| `t_api_contract`一行一个path+method      | 拆为APIContract、APIContractVersion、APIOperationVersion及SourceSnapshot               |
| `UNIQUE(workspace_id, api_path, method)` | 改为APIContractVersion内唯一；不同服务允许相同path+method                              |
| `source=Swagger/Manual/Recording`        | 细分为SourceSnapshot.sourceType与APIContractVersion.sourceKind                         |
| 可变headers/request/response字段         | 下沉至不可变APIOperationVersion/Schema引用                                             |
| 直接PUT修改契约                          | 改为创建新APIContractVersion、Diff、审核和发布                                         |
| 用例只引用apiContractId                  | 迁移到operationVersionId或contractVersionId + stableOperationKey                       |

本裁决形成时无应用代码、生产数据和已知外部客户端，因此冻结目标契约。Gate D已按“先术语/领域，再DB/API和PRD10/11/12/17”的顺序完成同步；旧入口只保留迁移映射，不为未发现的消费者实现运行时代理。后续若发现真实消费者，再按§5.14升级为限期兼容处理。

#### 5.10.11 Given/When/Then 验收基线

1. **唯一写入所有者**  
   Given 用户从Workspace向导上传OpenAPI，When 提交文件，Then 向导调用知识库导入命令且系统只创建一套SourceSnapshot/APIContract对象。

2. **原始来源不可覆盖**  
   Given 同一URL先后返回两个不同摘要，When 再次导入，Then 系统保存两个SourceSnapshot并能追溯各自生成的契约版本。

3. **相同内容不伪造版本**  
   Given 新快照摘要与上一来源完全相同，When 解析完成，Then 系统标记NO_CONTENT_CHANGE且不生成虚假的新APIContractVersion。

4. **流量不能改写声明契约**  
   Given 流量中出现OpenAPI未声明字段，When Agent完成分析，Then 只生成Observation和变更建议，已发布契约保持不变。

5. **审核绑定精确摘要**  
   Given Reviewer批准version v4及digest A，When人工修正Schema形成digest B，Then 必须创建v5并重新审核，v4批准不适用于B。

6. **破坏性变更双人审核**  
   Given 新版本删除必填响应字段并被判定BREAKING，When 提交审核，Then 系统要求FOUR_EYES且单人不能完成最终批准。

7. **执行不跟随最新版漂移**  
   Given ExecutionPlan冻结契约v3，When 知识库发布v4，Then 既有执行仍使用v3并创建影响WorkItem，不自动切换。

8. **同路径跨服务共存**  
   Given order-service和billing-service均有`GET /health`，When 导入两个契约，Then 系统允许共存并以serviceKey和version区分。

9. **外部引用可复现**  
   Given仓库OpenAPI使用外部`$ref`，When创建待审核版本，Then所有引用均被锁定到精确revision和digest；只有branch引用时不能批准。

10. **未检查不等于通过**  
    Given基线含100个Operation但本次只检查60个，When生成报告，Then报告分别显示已检查60和未检查40，覆盖率不能按100个通过计算。

11. **真实旧消费者不产生双写**  
    Given后续扫描发现真实旧客户端调用`/assets/contracts`，When提供限期兼容适配器，Then内部仍调用知识库命令且不直接更新旧表副本；未发现消费者时不预建代理。

12. **引用资产不可物理删除**  
    GivenAPIContractVersion已被用例和执行基线引用，When管理员请求删除，Then系统拒绝物理删除并只允许废弃/归档。

### 5.11 统一角色、能力与批准权限契约

#### 5.11.1 裁决结论

平台采用“**角色模板授予能力，审核策略决定本次需要谁批准**”的模型，不把Reviewer/Approver固化为两个全局用户角色。

必须区分四个概念：

| 概念             | 含义                                    | 示例                                   |
| ---------------- | --------------------------------------- | -------------------------------------- |
| 产品角色/Persona | 描述用户为什么使用平台                  | 测试工程师、测试负责人、租户管理员     |
| RBAC角色模板     | 一组可授予的能力集合                    | TestEngineer、TestLead、WorkspaceAdmin |
| 审核职责         | 某个ReviewTask中的临时责任              | Editor、Reviewer、Approver             |
| 机器身份         | Agent、Workflow或服务账号的最小权限主体 | qf-test-design、runner-service         |

“审批人”是审核职责，不是第四种万能角色；“管理员”是管理范围，不天然具备测试业务判断能力；“测试负责人”是内置业务角色模板，可以承担部分批准职责，但最终仍以具体能力、作用域、风险策略和职责分离校验为准。

最终授权判定：

```text
允许动作 = 身份有效
        ∩ Tenant/Workspace成员有效
        ∩ RBAC能力允许
        ∩ 资源作用域匹配
        ∩ 审核策略与职责分离满足
        ∩ Agent/Service最小权限允许（机器参与时）
        ∩ Workflow节点权限允许
        ∩ 环境/集成/数据分级条件允许
        ∩ 无显式Deny和无过期限制
```

任一项不满足均fail-closed，并记录可解释的拒绝原因；UI隐藏按钮不能替代服务端授权。

#### 5.11.2 作用域模型

角色绑定必须具有明确作用域，不能只在User表保存一个全局`role`字符串。

| 作用域    | 用途                                                 | 约束                                                   |
| --------- | ---------------------------------------------------- | ------------------------------------------------------ |
| PLATFORM  | 平台运维、全局Runner/模型供应商和平台级审计          | 仅PlatformAdmin等平台角色；默认不能读取租户测试内容    |
| TENANT    | 租户成员、租户策略、共享集成和合规配置               | 仅对一个Tenant生效                                     |
| WORKSPACE | 某个项目/Workspace内的测试资产、执行、审核和成员协作 | 业务能力主要作用域                                     |
| RESOURCE  | 高风险资源的临时、最小授权                           | 可用于单个Integration、Environment、Secret或ReviewTask |

继承规则：

- PLATFORM权限不自动穿透为TENANT业务数据权限；平台运维访问租户内容必须走限时、带理由、强审计的支持访问流程；
- TenantAdmin可以管理租户成员和租户级策略，但不自动获得所有Workspace测试资产的批准权；
- WorkspaceAdmin可以管理Workspace成员、环境引用和一般配置，但不自动成为TestReport签署人或Defect外部提交人；
- 用户可同时持有多个作用域角色，最终权限取有效Allow并受显式Deny、条件和职责分离限制；
- 跨Workspace操作必须逐Workspace授权，不因属于同一Tenant而自动放行；
- Release不是独立权限边界，必要时通过RoleBinding条件限定releaseIds，不新增一套Release角色体系。

#### 5.11.3 内置角色模板

内置模板提供安全默认值，Tenant可以复制并收窄/扩展普通能力，但不能移除平台强制的人类检查点、职责分离、Secret和外部写入底线。

| 角色模板       | 默认作用域        | 主要责任                                                | 明确不默认拥有                                 |
| -------------- | ----------------- | ------------------------------------------------------- | ---------------------------------------------- |
| PlatformAdmin  | PLATFORM          | 平台级供应商、全局Runner、平台策略、运行健康和平台审计  | 租户测试内容读取、正式产出物批准、外部缺陷提交 |
| TenantAdmin    | TENANT            | 租户成员、租户策略、共享集成授权、配额和租户审计        | 各Workspace业务资产编辑/批准、报告签署         |
| WorkspaceAdmin | WORKSPACE         | Workspace成员、环境/集成引用、资源配置和Workspace审计   | 业务产出物批准、质量门禁豁免                   |
| TestLead       | WORKSPACE         | 策略/计划把控、高风险审核、报告签署、质量门禁和任务协调 | 租户管理、Secret明文读取、Agent自主授权        |
| TestEngineer   | WORKSPACE         | 草稿生成/编辑、用例/代码/执行/分析、普通审核和缺陷复核  | 高风险单人批准、报告最终签署、权限管理         |
| ViewerAuditor  | TENANT或WORKSPACE | 只读查看已授权资产、审核证据和审计日志                  | 生成、编辑、执行、批准、外部写入               |

可选的KnowledgeSteward、AutomationReviewer、SecurityReviewer等不新增硬编码产品角色，通过自定义角色或额外能力绑定实现。平台必须展示“该用户为什么拥有此能力”的完整来源，避免角色叠加后不可解释。

#### 5.11.4 权限领域对象

| 对象                  | 最小字段/规则                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| RoleDefinition        | id、tenantId可空、name、scopeType、builtIn、status、version；平台内置模板不可被租户原地修改                             |
| Permission            | resourceType、action、riskLimit、conditions；采用稳定能力键                                                             |
| RolePermission        | roleDefinitionId + permissionId；版本化并保存变更摘要                                                                   |
| RoleBinding           | subjectType/subjectId、roleDefinitionId、scopeType/scopeId、conditions、validFrom/validUntil、grantedBy、reason、status |
| ExplicitDeny          | subject、能力、作用域、原因和有效期；优先级高于Allow                                                                    |
| ReviewPolicy          | artifactType、riskLevel、requiredStages、requiredCapabilities、minApprovers、separationRules、blockingChecks            |
| ReviewAssignment      | reviewTaskId、assigneeId、reviewRole、requiredCapability、status、assignedBy、dueAt                                     |
| AuthorizationDecision | actor、action、resource、策略版本、角色绑定快照、条件结果、ALLOW/DENY、reasonCode、时间                                 |
| DelegationGrant       | 委托人、受托人、能力、作用域、有效期、原因、是否可再委托；默认禁止再委托                                                |

禁止仅在User表保存`role=Admin/Tester`作为最终授权依据。角色、权限和策略变更必须版本化；高权限变更写入不可变AuditLog。

#### 5.11.5 稳定能力键

能力命名采用`资源.动作`，至少包含：

| 能力族         | 能力键示例                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| WorkItem       | `work_item.create/assign/start/submit_review/cancel/force_transition`                                  |
| 正式产出物通用 | `artifact.read/create_draft/edit/submit_review/review/approve/publish/archive`                         |
| 策略/计划      | `strategy.approve`、`test_plan.approve`                                                                |
| 用例           | `test_case.review/approve/bulk_approve`                                                                |
| 自动化代码     | `automation.edit/review/approve/publish/push/create_pr`                                                |
| 执行           | `execution_plan.approve`、`execution.start/stop/retry`、`execution.experimental_run`                   |
| 分析/缺陷/报告 | `analysis.approve`、`defect.approve/verify/external_write`、`report.signoff`、`quality_gate.override`  |
| 知识/契约      | `knowledge.publish`、`api_contract.review/approve/publish/baseline_approve`                            |
| Agent/Skill    | `agent.run/configure/publish/grant_permission`、`skill.install/activate/grant_network/grant_secret`    |
| 管理           | `workspace.manage_members`、`tenant.manage_roles`、`integration.manage`、`secret.manage`、`audit.read` |

`artifact.approve`不能作为无限范围万能批准权；实际批准还必须匹配artifactType、riskLevel、Workspace、ReviewPolicy和所需专属能力。外部写入、报告签署、质量门禁豁免、权限授予和Secret管理必须使用独立能力，不能被普通`approve`包含。

#### 5.11.6 八类正式产出物的最低批准映射

| 正式产出物              | LOW/MEDIUM最低批准                                 | HIGH/CRITICAL最低批准                  | 额外约束                                          |
| ----------------------- | -------------------------------------------------- | -------------------------------------- | ------------------------------------------------- |
| TestStrategy            | 一名具`strategy.approve`的TestLead或等效自定义角色 | FOUR_EYES；至少一名TestLead能力        | 批准者不得为AI；范围/质量目标变化重审             |
| TestPlan                | 一名具`test_plan.approve`的TestLead或等效角色      | FOUR_EYES                              | 必须关联已批准策略和Release                       |
| TestCase                | 一名具`test_case.approve`的TestEngineer/TestLead   | FOUR_EYES或批量专属批准                | 批量批准另需`test_case.bulk_approve`              |
| AutomationScriptVersion | 一名具`automation.approve`的自动化Reviewer         | FOUR_EYES；至少一名非最后修改人        | 发布另需`automation.publish`；push/PR另走外部写入 |
| ResultAnalysis          | 一名具`analysis.approve`的TestEngineer/TestLead    | FOUR_EYES；严重结论需TestLead能力      | 事实与推断分离检查阻断                            |
| DefectVersion           | 一名具`defect.approve`的TestEngineer/TestLead      | FOUR_EYES；安全/重大缺陷需专属Reviewer | 外部提交另需`defect.external_write`即时批准       |
| TestReport              | 一名具`report.signoff`的TestLead或等效角色         | FOUR_EYES                              | 报告生成者不能替代签署人；门禁豁免独立            |
| KnowledgeEntry          | 一名具`knowledge.publish`的知识审批人              | 高敏/跨Workspace内容FOUR_EYES          | 必须检查来源、适用范围、敏感信息和过期策略        |

APIContract虽是正式知识资产，遵循`api_contract.approve/publish`专属能力；ExecutionPlan虽不是八类测试产出物之一，但正式执行前必须由`execution_plan.approve`批准。

#### 5.11.7 SINGLE_REVIEW 与 FOUR_EYES

为了同时支持单人试点和企业职责分离，策略定义如下：

- 所有正式产出物至少需要一名人类批准；AI PASS、确定性检查PASS和管理员开关都不能替代；
- `SINGLE_REVIEW`允许同一获授权测试人员先修改AI草稿再批准，系统必须标记`independentReview=false`并保留其修改Diff；
- `FOUR_EYES`至少需要两个不同的人类：Reviewer和Approver分离，最终Approver不能是最后修改人；
- 同一自然人拥有多个账号、角色或团队身份时仍视为同一人，不能满足四眼原则；
- 原作者为AI时不计作一只“眼”；独立Verifier Agent也不计作人类Reviewer；
- 单人Workspace遇到强制FOUR_EYES时，任务进入`BLOCKED`并说明需要增加获授权成员或降低业务风险/范围；不得由TenantAdmin一键绕过；
- Reviewer离职、权限撤销或批准过期后，既有审计证据保留；是否使资产STALE由ReviewPolicy决定；
- 四眼要求、风险分类和阻断检查只能调严；放宽平台最低要求需要产品级变更，不是租户配置。

#### 5.11.8 管理员、业务批准与紧急访问边界

- PlatformAdmin/TenantAdmin/WorkspaceAdmin只因“是管理员”不能批准测试策略、用例、代码、Defect或报告；如确有业务职责，必须另授相应Workspace业务角色；
- TenantAdmin可以授予角色，但给自己或关联账号授予高风险批准、Secret、外部写入或门禁豁免能力时需要另一名TenantAdmin复核；单管理员租户只能使用预置恢复流程，不能静默自授权；
- Platform支持人员临时访问租户数据必须使用`SupportAccessGrant`：指定Tenant/Workspace、工单、理由、能力、最长有效期和审批人；默认只读；
- Break-glass仅用于恢复可用性或阻止持续损害，不得用于伪造业务批准、篡改执行结果或绕过正式报告签署；
- 紧急访问启用时强提醒、全量审计、自动过期，并在事后生成复核WorkItem；
- Secret管理能力只允许创建、轮换、吊销和授权引用；普通UI/API不得返回Secret明文；
- 质量门禁豁免必须独立能力、限时、指定Release/环境、填写风险接受理由和补偿措施，并进入报告。

#### 5.11.9 Agent与服务账号边界

- Agent、Runner、Scheduler和集成Worker使用独立机器身份，不借用某个管理员的长期Token；
- Agent永远不得获得`artifact.approve`、`report.signoff`、`quality_gate.override`、`tenant.manage_roles`等人类责任能力；
- 人工批准后由应用服务执行发布或外部写入时，审计必须同时记录批准人和执行服务身份，不能把服务账号显示成批准人；
- Agent可提交审核、请求权限或生成外部写入草稿，但不能自行批准自己的请求；
- 最终允许动作仍取用户授权、Agent权限和Workflow节点权限的交集；人工批准不会扩大Agent原本被拒绝的网络、Secret或文件范围；
- Runner只读取单次ExecutionTask所需的限时凭证和冻结快照，任务结束即撤销；
- 机器身份的RoleBinding必须限定capability、resource、时间和runId/workItemId，禁止复用宽泛TenantAdmin角色。

#### 5.11.10 授权决策、并发与撤销

每次高价值动作必须在服务端重新授权并保存`AuthorizationDecision`，至少包括：

- actorType/actorId、tenantId、workspaceId；
- resourceType/resourceId/resourceVersion/digest；
- action和请求参数摘要；
- 命中的RoleBinding、Permission、ReviewPolicy和Deny版本；
- 职责分离、风险、时间、环境和集成条件的逐项结果；
- ALLOW/DENY、reasonCode和决定时间；
- 人工批准记录、执行服务身份和外部回执关联（如适用）。

授权在以下时点必须重新计算：提交审核、领取审核、批准、发布、开始执行、读取Secret、外部写入、质量门禁决策和角色变更。打开页面时有权限不代表点击时仍有权限。

角色撤销、成员停用、Workspace归档或风险升级应立即阻止新动作；已发出的短时执行Token按最大TTL尽快失效。批量操作逐资源授权，不能因第一项通过就默认全部通过。

#### 5.11.12 Given/When/Then 验收基线

1. **管理员不等于业务批准人**  
   Given用户只有TenantAdmin角色，When尝试批准TestReport，Then系统拒绝并说明缺少Workspace级`report.signoff`。

2. **Workspace隔离**  
   GivenTestLead只绑定Workspace A，When打开Workspace B的Defect审核，Then服务端拒绝，即使两者属于同一Tenant。

3. **单人低风险试点**  
   Given低风险TestCase采用SINGLE_REVIEW且唯一测试人员具备批准能力，When其修改AI草稿后批准，Then允许生效并记录`independentReview=false`和完整Diff。

4. **高风险四眼阻断**  
   GivenHIGH风险脚本只有一个获授权成员，When提交批准，Then任务BLOCKED并要求第二名独立人员，管理员开关不能绕过。

5. **多角色同一人不算四眼**  
   Given用户A同时拥有TestEngineer和TestLead，When其先Review后Approve同一FOUR_EYES任务，Then系统拒绝，因为自然人身份相同。

6. **AI PASS不能批准**  
   Given独立Verifier Agent输出PASS，When没有人类批准记录，Then正式产出物仍保持PENDING_REVIEW。

7. **权限点击时重算**  
   GivenReviewer打开页面后角色被撤销，When其随后点击批准，Then服务端重新授权并拒绝，不以页面缓存放行。

8. **外部写入独立授权**  
   Given用户具备`defect.approve`但不具备`defect.external_write`，When内部批准后提交PingCode，Then内部Defect可生效但外部调用被拒绝。

9. **平台管理员默认看不到租户内容**  
   GivenPlatformAdmin没有SupportAccessGrant，When查询某Workspace用例，Then系统拒绝并写审计；平台角色不穿透租户边界。

10. **机器身份不冒充批准人**  
    Given人工批准后integration-worker执行Jira写入，When查看审计，Then批准人和执行服务分别记录，worker不显示为Approver。

11. **批量逐项授权**  
    Given用户对10个用例中的8个有权限，When请求批量批准，Then系统逐项返回8个允许、2个拒绝，不把整批伪报为成功。

12. **紧急访问不能篡改业务结论**  
    Given平台启用break-glass恢复Runner，When操作者尝试修改TestReport结论，Then系统拒绝，因为紧急访问不包含业务签署能力。

### 5.12 全量实体唯一业务所有者矩阵

#### 5.12.1 所有权判定规则

“业务所有者”是唯一有权定义实体语义、创建命令、版本规则、状态机、归档策略和正式写入入口的模块，不等于：

- 数据库表所在Schema或实现服务；
- 页面上能展示或编辑建议的模块；
- 引用该实体最多的消费者；
- 发起Agent任务、审核WorkItem或保存外键的模块；
- 平台管理员拥有的技术管理权限。

跨模块协作遵循以下规则：

1. 一个实体只能有一个业务所有者；关系表、版本表和状态事件默认跟随聚合根；
2. 消费模块通过精确版本引用、查询视图或Owner命令交互，不直接更新Owner数据表；
3. 跨模块生成的“建议”属于WorkItem或Candidate，只有Owner接纳后才形成正式实体版本；
4. 通用审核任务归任务看板，审核策略和授权配置归平台管理，产出物正文仍归对应业务模块；
5. 原始执行证据归测试执行，任何分析、报告和缺陷都只能引用，不能反向覆盖；
6. AI运行证据归AI Agent中心，Agent生成的业务草稿仍由业务Owner持久化和治理；
7. 当前泛化实体若按type承载多个领域且需要不同状态机，必须拆分或退场，不能宣称“共享所有权”。

#### 5.12.11 完整性结论与后续约束

本矩阵在产品裁决时覆盖了当时领域模型主实体、`33-数据库Schema设计.md`中的50张旧表及目标新增实体；随后目标数据库已重构为107张表(2026-08-14 第0周补丁 B1 口径更新)并完成Gate E静态复审。这里的历史覆盖数字只说明迁移输入，不代表当前数据库规模。

后续修改必须遵循：

- 新增任何实体前先在本矩阵指定唯一Owner；
- 一个页面需要编辑多个Owner的对象时，由应用层编排多个命令，不使用跨域事务直接改表；
- 发现某实体同时出现在两个模块的“可编辑列表”时，至少一个入口必须改为只读、Candidate或代理命令；
- 03/04/32/33已为目标聚合补唯一写入API和外键方向；后续新增聚合继续遵循同一规则；
- 独立复审必须扫描所有POST/PUT/PATCH/DELETE，验证每个实体只有一个非兼容期写入命令面；
- 历史引用保留legacyRef/Source Trace，不以“退场”为由删除审计证据。

#### 5.12.12 Given/When/Then 验收基线

1. **任务与正文分离**  
   GivenWorkItem关联TestStrategy v2，When任务状态变化，Then只更新任务看板对象，不改策略正文或审核摘要。

2. **知识候选不能跨域发布**  
   Given质量模块生成KnowledgeCandidate，WhenAgent尝试直接创建Published KnowledgeEntry，Then系统拒绝并要求进入知识库审核命令。

3. **执行结果不可反写**  
   GivenFailureAnalysis认定某结果为环境问题，When分析被批准，ThenExecutionResult原始状态、日志和摘要保持不变。

4. **Runner所有权明确**  
   Given测试执行需要新浏览器能力，WhenRunner不满足，Then执行创建BLOCKED需求；执行模块不能直接修改RunnerNode能力声明。

5. **API契约无双写**  
   Given自动化开发发现Schema错误，When提交修正，Then生成知识库变更WorkItem，不直接更新Automation或Workspace内的契约副本。

6. **候选自愈不覆盖Locator**  
   Given执行中备用Locator成功，WhenAgent提出自愈，Then产生自动化开发候选版本；正式Locator在审核前保持不变。

7. **发布上下文不复制计划**  
   GivenRelease日期变化，When平台管理员更新Release，ThenTestPlan日期不被静默覆盖，只生成影响提示。

8. **集成配置与业务回执分离**  
   GivenJira凭证轮换，When平台管理更新IntegrationConfig，ThenExternalDefectLink和历史DefectSyncAttempt保持不变。

9. **Agent运行与业务草稿分离**  
   GivenAgentSession失败，When查看关联用例草稿，ThenSession状态归Agent中心，用例草稿归测试设计且只通过WorkItem关联。

10. **退场实体无新写入**  
    Given目标契约启用，When请求尝试写TestDesignPlan、AIContext或BaselineItem，Then新契约不提供这些写入；若存在经验证的限期适配器，则只能转换为目标Owner命令并返回弃用提示。

### 5.13 V0/V1/V2/V3 产品范围契约

#### 5.13.1 版本定义

版本按“可验证的业务闭环”而不是按文档数量、模块数量或AI功能数量划分：

| 版本          | 产品含义                                  | 核心目标                                                              | 不能宣称                                         |
| ------------- | ----------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------ |
| V0/设计验证   | 文档、原型契约和离线样例阶段              | 证明目标产出物、Agent权限、审核门禁和Source Trace设计可运行于受控样例 | 不能宣称平台、API、数据库或UI已经实现            |
| V1/单项目试点 | 面向一个Workspace的小规模端到端产品       | 跑通“来源→策略/计划/用例→Web/API代码→执行→分析/Defect/报告→人工审核”  | 不能宣称企业规模、高自治、多Runner或复杂集成完备 |
| V2/团队协作   | 面向测试团队的稳定协作与反馈闭环          | 提高并发、集成、缺陷同步、知识回流、变更影响和维护效率                | 不能宣称跨组织企业治理或AI自主发布决策           |
| V3/企业规模   | 面向多团队、多Workspace的治理和规模化交付 | 提供企业身份治理、弹性执行、高级门禁、多Agent和扩展能力               | 仍不能取消正式产出物的人类责任和审计底线         |

V0→V1是“从设计原型到可用产品”，不是普通功能迭代。当前Workspace属于V0设计阶段；30个Skill原型、Gate 0 Agent配置和文档校验只构成设计/原型证据，不构成V1产品完成证据。

#### 5.13.2 V0：设计与Gate 0验证

V0范围：

- 冻结8个一级模块、核心术语、领域对象、状态机、API/DB目标契约和RBAC边界；
- 以1个Supervisor + 3个受限Subagent验证需求解析、TestingIR、规则、场景、用例、断言和人工路由；

- 产出可进入研发的PRD、OpenAPI、DB、授权、WebSocket、治理配置和验收清单。

V0不包含：

- 可登录的生产级Web应用、可部署后端或实际数据库；
- 真实Runner调度、浏览器/API正式执行、Jira/PingCode写入；

V1正式产出物必须覆盖八类：TestStrategy、TestPlan、TestCase、Web/API AutomationScriptVersion、ResultAnalysis、DefectVersion、TestReport、KnowledgeEntry。所有正式产出物至少一名人类批准；V1不实现任何“租户开关让AI自动发布正式资产”。


- 记录人工净处理时间、AI草稿采用率、退回原因、执行稳定性和报告一致性，形成后续目标基线。

- Tenant/Workspace边界、服务端授权和Secret不明文；
- AI不能批准自己的正式产出物；
- 正式资产精确版本、contentDigest、Source Trace和审核记录；
- 执行证据不可被分析结论覆盖；
- 外部写入默认拒绝并绑定人工批准的最终Payload；
- Agent/Skill最小权限、allowlist、运行Trace和失败可解释；
- 未检查、跳过、不可判定和阻塞不得伪报为通过；
- 审计记录只追加，历史批准版本不可覆盖。

#### 5.13.7 版本范围变更规则

- 功能从后续版本前移，必须同时前移其安全、审核、数据和可观测性依赖，不能只前移UI按钮；
- 功能延期不得破坏当前版本主闭环；若会破坏，必须缩小该版本承诺或提供人工可审计替代流程；
- 目标模块在导航中可提前显示“规划中”，但不可进入可操作页面或被计入交付完成率；
- 每个版本项必须标注`MUST/SHOULD/LATER`、Owner、依赖、验收证据和明确非目标；
- NFR数字必须有工作负载模型、环境、基线、测量方法和验收阈值；旧规划中的50/200/1000/5000并发和FCP/P95数字在完成基线前均视为候选，不直接继承为承诺；
- 版本退出只采用当前版本一次完整验证证据，不能拼接历史样例宣称本轮通过。

#### 5.13.8 Given/When/Then 验收基线

1. **V0不冒充产品**  
   Given文档、OpenAPI和Skill原型检查通过，When汇报V0状态，Then只能声明设计/原型验证结果，不能声明Web平台已可用。

2. **V1闭环不缺模块**  
   GivenV1没有任务审核队列或报告签署，When评审版本范围，ThenV1不能被认定为端到端试点闭环。

3. **目标态不等于当前范围**  
   GivenV3规划有弹性Runner，When查看V1导航，Then可以显示规划状态但不能操作或计入V1完成。

4. **正式产出始终人工批准**  
   GivenV2启用更高AI自动化，WhenAgent生成Defect和报告，Then仍必须由具备能力的人批准/签署。

5. **前移功能带齐依赖**  
   Given团队希望把Jira同步前移到V1，When调整范围，Then必须同时纳入Integration、EXTERNAL_WRITE、幂等、冲突和审计验收。

6. **延期不破闭环**  
   GivenGit集成延期，WhenV1仍要求自动化代码产出，Then采用MANAGED代码版本和人工导出作为明确替代，不删除代码审核环节。

7. **无基线数字不能承诺**  
   Given旧规划写有1000并发但无环境和负载模型，When制定V2验收，Then该数字标记为待基线候选，不作为已批准SLA。

8. **单次证据验证退出**  
   Given历史上各子模块分别有成功样例，When本轮V1退出验收没有一次完整链路，Then不能拼接历史结果宣称V1通过。

### 5.14 展示名、领域名与API兼容策略

#### 5.14.1 三套名称的职责

产品展示名、领域实体名和API资源名服务不同目的，不要求字面完全相同，但必须有唯一映射：

| 层级       | 规则                                                    | 示例                                                  |
| ---------- | ------------------------------------------------------- | ----------------------------------------------------- |
| 产品展示名 | 面向测试人员，优先使用清晰中文业务语言                  | “项目”“测试策划与设计”“质量分析与缺陷”                |
| 领域名     | 面向产品/研发契约，使用稳定英文名，不随导航文案轻易变化 | Workspace、TestStrategy、Defect                       |
| API资源名  | 面向客户端，使用复数kebab-case资源和明确层级            | `/work-items`、`/test-strategies`、`/quality/defects` |
| DB物理名   | 使用snake_case表/列，由ORM映射                          | `t_test_strategy`、`workspace_id`                     |
| JSON字段   | 使用camelCase，以OpenAPI为线上权威                      | `workspaceId`、`contentDigest`                        |

不得用中文展示名变化驱动无意义的领域/API重命名；也不得为了保留旧技术名而让用户继续理解错误概念。

#### 5.14.2 一级模块名称映射

| 目标产品展示名 | 领域/服务边界名             | API前缀                                                                                  | 旧入口处理                                      |
| -------------- | --------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 任务看板       | Work Management             | `/work-items`、`/review-tasks`                                                           | 新增，无旧一级模块                              |
| 知识库         | Knowledge                   | `/knowledge`                                                                             | 保留Knowledge语义，吸收需求/API来源写入         |
| 测试策划与设计 | Test Planning & Design      | `/test-strategies`、`/test-plans`、`/test-scenarios`、`/test-case-drafts`、`/test-cases` | 替代旧TestDesign；不使用笼统`/test-designs`容器 |

| 测试执行       | Test Execution              | `/execution-plans`、`/execution-tasks`、`/execution-results`                             | 替代旧`/executions/*`层级                       |
| 质量分析与缺陷 | Quality Analysis & Defects  | `/quality`                                                                               | 合并旧Intelligence与CI/CD业务门禁入口           |

#### 5.14.4 当前阶段的兼容原则

当前项目没有应用代码、生产数据或已发布客户端，因此现行`32-API规范.yaml`是设计稿，不是已承诺的线上兼容面。结论：

1. Gate D直接把OpenAPI改为目标标准资源，不实现没有用户价值的运行时旧路径代理；
2. 所有旧路径仍进入“旧→新映射表”和CHANGELOG，保证文档/原型引用可机械迁移；
3. 若全局扫描发现真实外部消费者或可运行客户端，再把对应路径单独升级为兼容适配，不为不存在的消费者预建全套代理；
4. 现有`/api/v1`基础路由可保留，因为它将成为首个实际交付API代际；OpenAPI `info.version`按本次破坏性设计变更升级，并标记Draft状态；
5. 产品V0/V1/V2/V3与API URL中的`v1/v2`是不同版本轴，文档必须分开表述；
6. Gate D改动后，旧示例和原型不得继续写旧路径并声称兼容，必须统一迁移或明确标记历史。

一旦首个外部客户端或V1产品正式发布，后续适用公开兼容规则：

- 同一API代际内只允许向后兼容的新增字段、可选参数和新资源；
- 删除/重命名字段、改变状态语义、收紧必填、改变响应结构或路径属于破坏性变更；
- 破坏性变更进入新API代际或经过明确迁移窗口；
- 废弃端点必须在OpenAPI标`deprecated`并返回标准Deprecation/Sunset/Link信息；
- 迁移窗口必须在CHANGELOG写明最后支持日期、替代端点、数据/权限差异和验证方法；
- 服务端在窗口内记录旧端点使用量，未确认消费者迁移前不得静默删除。

#### 5.14.7 状态和错误兼容

- 领域状态使用稳定UPPER_SNAKE_CASE；UI负责本地化，不把中文状态写入API；
- 状态拆分时不得把旧状态简单映射成“成功”，必须说明审核状态、生命周期状态和运行状态分别对应什么；
- 未知新枚举值客户端应显示“未知/需升级”并保留原值，不默认当PASS；
- 错误采用稳定`code + message + details + traceId`，客户端逻辑只依赖code；
- 旧路径迁移后的权限可能更严格，文档必须把403视为预期安全变化而不是兼容Bug；
- 异步生成、导入、分析和外部同步统一返回WorkItem/attempt资源，不用HTTP 200掩盖后台失败；
- 删除资源默认归档/废弃，历史引用存在时返回409并提供阻塞引用，而不是级联丢失证据。

#### 5.14.8 Given/When/Then 验收基线

1. **展示名不制造新实体**  
   GivenUI把Workspace显示为“项目”，When创建项目，ThenAPI仍只创建Workspace并返回workspaceId，不产生Project副本。

2. **设计稿阶段不背负假兼容**  
   Given没有应用代码、生产数据或外部客户端，WhenGate D重写旧路径，Then不实现运行时代理，但必须保留完整迁移映射和CHANGELOG。

3. **真实消费者触发兼容升级**  
   Given扫描发现某可运行客户端仍调用旧`/assets/contracts`，When准备删除旧路径，Then必须先提供适配/迁移并验证客户端，不得按“纯文档”假设直接删除。

4. **API版本与产品版本分离**  
   Given产品进入V2，WhenAPI没有破坏性变化，ThenURL仍可保持`/api/v1`，不能机械改为`/api/v2`。

5. **旧资产入口不双写**  
   Given迁移期存在旧“测试资产”导航引用，When用户编辑用例，Then请求只进入`/test-cases`Owner，不同时更新旧Asset副本。

6. **旧缺陷导出被拆分**  
   Given客户端原来从clusterIds直接导出Jira，When迁移新流程，Then必须先创建/批准DefectVersion，再创建逐条SyncAttempt。

7. **字段冲突拒绝**  
   Given未来兼容请求同时传旧字段`projectId=A`和新字段`workspaceId=B`，When值不一致，Then服务端400拒绝，不能任选其一。

8. **未知状态不伪报通过**  
   Given旧客户端收到新状态`INCONCLUSIVE`，When无法识别，Then显示未知并提示升级，不能按成功状态渲染。

9. **废弃资源保留证据**  
   Given旧TestDesignPlan已有历史Source Trace，When迁移TestStrategy，ThenlegacyRef可反查历史ID，旧正文不作为可写实体继续存在。

10. **导航合并不合并实体**  
    GivenSkill和Agent均显示在AI Agent中心，When调用API，Then仍分别使用`/ai/skills`与`/ai/agents`及各自状态机。

#### 5.15.8 Given/When/Then 验收基线

1. **扫描范围可复现**  
   Given相同工作区快照和排除规则，When重新执行引用扫描，Then可得到相同受影响文件集合和匹配分类。

2. **历史审计不被改写**  
   Given旧审计使用TestAsset名称，When同步新8模块，Then审计正文保持原样，新导航说明其为历史时间点证据。

3. **直接命中不等于唯一影响**  
   Given某Skill未出现旧模块名但输出TestCase状态，When状态契约改变，Then该Skill仍进入语义复核，不能因零文本命中跳过。

4. **API与DB同批**  
   Given新增DefectVersion API Schema，When本批没有对应DB表/约束，ThenD2不得标记完成。

5. **旧自治规则转负例**  
   GivenE2E样例写“confidence>0.80自动入库”，When同步治理，Then将其改为应生成ReviewTask的负例或更新期望，不能继续作为成功路径。

6. **PRD迁移不丢需求**  
   GivenTestAsset旧PRD包含Locator和APIContract，When拆分模块，ThenLocator迁入自动化开发、APIContract迁入知识库，原功能均可在新Owner找到。

7. **允许引用不误报**  
   GivenCHANGELOG保留旧`/assets/contracts`，When执行全局扫描，Then将其分类为允许历史引用，不作为现行API残留。

8. **复审独立**  
   Given本方案宣称Gate D已同步，When独立审计发现34仍给TenantAdmin所有业务权限，ThenGate E保持未通过，不能用方案勾选覆盖事实。

## 六、为什么这样设计

### 6.1 以产出物而不是技术组件为中心

测试人员关心的是策略、计划、用例、代码、Bug 和报告，不需要先理解 Agent、Skill、RAG 或 Runner。技术能力退到业务流程和管理控制面之后，用户学习成本更低。

### 6.2 把 AI 生产与人工审核设计成系统主流程

审核不是产出后的附加按钮，而是每种正式产出物生命周期中的必要节点。任务看板把 AI 运行、待审核、退回重做和批准统一起来，避免 AI 功能成为无法治理的黑盒。

### 6.3 按责任和证据类型分离

- 知识库保存输入依据；
- 策划与设计保存测试意图；
- 自动化开发保存可执行代码；
- 执行保存原始事实；
- 质量分析保存推断和判断；
- Agent 中心保存 AI 行为证据；
- 平台管理保存安全和运维证据。

这种分离使“事实、AI 推断、人工决定”可以清晰追溯。

### 6.4 兼顾效率和质量

AI 可以连续完成解析、生成、编码、执行、分析和修改；人只在高价值决策点介入。相比每一步都人工操作，效率更高；相比 AI 全自动写正式资产，质量和责任边界更可靠。

### 6.5 支持逐步演进

8 个模块是目标产品边界，不要求 V1 全量实现。V1 可以先跑通“知识输入→AI 设计→人工审核→自动化生成→执行→分析/报告”的最小闭环，随后增强缺陷、发布门禁、多 Agent 和平台运营能力。

## 七、解决的核心痛点与优势

| 现有痛点                       | 新设计                                        | 直接优势                     |
| ------------------------------ | --------------------------------------------- | ---------------------------- |
| 测试人员在多个工具之间寻找工作 | 任务看板统一任务、AI进度和审核待办            | 降低切换和协调成本           |
| 需求、接口和经验分散           | 知识库统一来源、版本和已审核知识              | 提高 AI 上下文质量和可追溯性 |

| 执行过程与证据分散             | 测试执行统一日志、结果和制品                  | 提高复现和证据完整性         |

## 八、效果衡量

平台不能只用“生成数量”证明价值，应同时衡量效率和质量。

### 8.1 效率指标

- 从需求导入到首版测试策略/用例的时间；
- 单个正式用例的人工净处理时间；
- Web/API 自动化代码首版生成时间；
- 失败结果到 Bug 草稿的时间；
- 报告编制时间；
- AI 自动完成步骤占比；
- 测试人员跨模块和跨工具操作次数。

### 8.2 质量指标

- AI 产出一次审核通过率；
- 人工修改率、退回率及主要错误类型；
- 需求/规则/场景/断言有效覆盖率；
- 自动化代码静态检查和试运行通过率；
- RCA 人工确认准确率；
- Bug 有效率和重复率；
- 报告数据一致性；
- 知识条目复用命中率和过期率。

每项指标必须在对应 PRD 中补充基线、测量方法、样本范围和 Given/When/Then 验收标准，不能直接沿用无基线的百分比目标。
