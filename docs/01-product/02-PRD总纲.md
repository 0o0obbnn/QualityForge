# 02-PRD总纲

## 1. 产品定义

QualityForge面向测试工程师、测试负责人和平台管理员，提供“对话提出目标—结构化确认任务—受控Agent执行—独立评估—人工裁决—证据闭环”的AI原生测试工作台。详细业务基线见[06-人机协作与V1业务基线](06-人机协作与V1业务基线.md)。

核心分工：AI Agent尽可能承担资料解析、草稿生成、代码生成、检查、执行、证据整理、分析和改稿；测试人员负责审核、批改、业务取舍、例外裁决和最终质量责任。

## 2. 目标用户与职责

| 用户/身份 | 核心目标 | 典型职责 |
|---|---|---|
| TestEngineer | 高效完成日常测试交付 | 批改用例/代码、触发执行、分析和处理Defect |
| TestLead | 控制范围、风险和交付质量 | 审核策略/计划/报告、协调资源、裁决关键例外 |
| WorkspaceAdmin | 维护Workspace运行条件 | 成员、环境、集成引用和一般配置 |
| PlatformAdmin | 治理平台、租户和安全资源 | 成员/角色委派、配额、集成、安全运维和全局模板 |

V1产品角色只保留上述四类人类角色。`TenantAdmin`、`ViewerAuditor`是后续可拆分的权限模板；`Service/Agent`是机器身份，不纳入产品用户角色数量。

Approver不是固定全局角色，而是ReviewTask中由ReviewPolicy、能力、作用域和职责分离计算出的临时职责。

## 3. 产品目标与非目标

### 3.1 目标

- 缩短策略、计划、用例、自动化代码、分析和报告的有效产出时间。
- 提高需求/契约到用例、代码、结果、Defect和报告的可追溯性。
- 通过AI预检、确定性检查和人工审核减少遗漏、错误发布和重复劳动。
- 让AI行为、权限、输入输出、成本和效果可观察、可评测、可降级。
- 保持执行事实、AI推断和人工决定清晰分层。

### 3.2 当前非目标

- V0不交付可运行SaaS、分布式执行平台或完整Agent市场。
- V1不承诺无人测试、全自动发布门禁或替代测试人员。
- 不把Workspace复制成Project实体，不把Skill和Agent合并成同一概念。
- 不因AI高置信度跳过正式产出物审核、外部写入批准或报告签署。
- 在无实测基线前不承诺固定收益百分比、并发量、延迟或AI准确率。

## 4. 产品范围

产品功能固定按四个平面组织：项目与协作、测试生产、质量交付、平台治理。八个专业能力域继续用于划分实体Owner，但不默认全部作为一级导航。具体导航数量尚未裁决，但测试产出物已明确取消一级菜单资格。跨域通过ID、版本和事件引用，不复制可写真相源。

详细职责见01号功能地图，精确定义见03/04号，模块需求见10-17号现行PRD。

## 5. 核心业务规则

1. UI中的“项目”就是Workspace；Release是Workspace内版本/迭代交付批次。
2. WorkItem统一承载待办、AI运行、人工工作、阻塞和审核路由，但不取代业务产出物。
3. 正式产出物以稳定根+不可变版本保存；发布/批准绑定精确摘要。
4. ExecutionResult、Evidence、ReviewDecision、AuthorizationDecision、AuditLog和Agent Trace只追加。
5. AI自治默认L2受限代理；没有经批准且仍有效的Eval校准记录时，分数不能驱动高价值自治。
6. 管理员身份不自动获得业务批准；最终授权取多层权限交集并fail-closed。
7. Defect与FailureCluster分离；外部写入逐次审批、幂等并保留回执/冲突。
8. APIContract由知识库模块唯一拥有；设计、Mock和执行均引用精确版本基线。
9. AI开工前必须返回资料完整性、冲突和未解问题；无法安全假设时创建可审计ClarificationRequest。
10. 人工确认AgentPlan/TaskCard后才可执行；暂停、继续、取消、重试、调整范围均是服务端受权命令，不得仅更改前端状态。
11. 生产Agent与评估Agent职责分离；评分绑定版本化Rubric、冻结输入和校准证据，未校准分数只能用于排序和辅助判断。

## 6. 核心旅程

本产品只定义一条权威主旅程：进入最近更新项目/切换项目 → 对话明确目标 → 全量授权资料读取与完整性检查 → 人工澄清并冻结基线 → 确认AgentPlan/TaskCard → 按阶段产出策略、计划、用例和代码 → 冻结执行输入并执行 → 生成分析、Defect与报告 → 独立评估 → 人工批准/签署 → 知识回流。每个阶段交接均须显式满足输入完整、冲突已处置、产出物已批准和权限预检条件。

## 7. 成功度量方法

所有收益指标先建立人工基线，再以同类任务、同等复杂度和明确样本窗口比较。至少同时度量：

| 维度 | 指标示例 | 防误导约束 |
|---|---|---|
| 效率 | 首个可审核草稿时间、总交付周期、人工操作时长 | 不只统计AI生成时间 |
| 质量 | 人工修改率、遗漏率、误放率、重开率、可复现率 | 生成数量不是质量 |
| 追溯 | 正向/反向链完整率、版本摘要完整率 | HTTP成功不算链完整 |
| AI效果 | Golden Set准确率/召回率、路由正确率、越权率 | 模型自评分无效 |
| 运营 | 成功成本、P95延迟、降级率、人工接管率 | 需按介入点和版本分层 |

具体目标值必须在V1试点基线后批准，禁止沿用无测量方法的80%/95%等口号。

## 8. 全局验收原则

- 功能验收使用Given/When/Then，包含正常、异常、权限、陈旧版本和降级路径。
- 文档、API、DB和原型的静态一致不等于应用实现或业务验收。
- AI生成物必须通过确定性检查、独立验证和适用人工审核；三层证据分别报告。
- 版本交付必须列清范围、非目标、基线、测量方法、已知限制和恢复方案。
