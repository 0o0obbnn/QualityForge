# QualityForge 产品业务裁决记录 v1.0

> 状态：已确认（CONFIRMED）  
> 裁决日期：2026-08-27  
> 适用范围：QualityForge V1 产品、业务流程、Agent 治理、数据治理与验收  
> 后续用途：PRD、领域模型、API、数据库、前端信息架构、测试计划与验收标准的共同输入

## 1. 文档效力

1. 本记录汇总本轮逐项确认的 57 项产品裁决，是后续业务与产品设计的当前基线。
2. 本记录描述目标状态，不代表当前代码已经实现；实现状态仍以新鲜代码、运行结果和验收证据为准。
3. 与较早方案冲突时，以本记录为准；不冲突的既有决策继续有效。
4. UI 中“项目”对应技术实体 `Workspace`，不新增平行的 `Project` 实体。
5. “已批准正式版本”在实现中采用更严格语义：`APPROVED` 表示审核通过待发布，只有 `PUBLISHED` 的不可变版本可进入正式下游和执行。
6. “AI 完整读取项目资料”指 AI 可检索全部授权资料；每次模型调用仍按任务最小化装载，并受数据安全门禁约束。

## 2. 总体产品裁决

QualityForge V1 定位为面向小型测试团队的**人机协同测试工作台**。AI 负责资料理解、方案生成、影响分析、自动化开发和执行辅助；人负责目标、授权、正式资产审核、异常裁决与最终发布决定。V1 不追求所有模块浅层可见，而以一条真实、可控、可审计、可追溯的 API 测试纵向闭环作为完成标准。

## 3. 57 项正式裁决

### A. 产品定位、上下文与首页（QF-PD-001～012）

| ID | 正式裁决 | 约束与验收要点 |
|---|---|---|
| QF-PD-001 | V1 面向小团队协作，核心角色为测试工程师与测试负责人；单人部署允许兼任，四眼审核按需开启。 | 单人模式不删除多人职责语义；关键动作仍记录操作者。 |
| QF-PD-002 | 所有业务操作必须选择项目；知识探索可不选 Release，交付、执行和质量活动必须绑定 Release。 | 禁止页面自行生成或猜测 `releaseId`。 |
| QF-PD-003 | 首页 AI 对话同时支持项目查询与任务下达；任务执行前必须展示计划、影响范围、权限和预计消耗并由人工确认。 | 对话文本本身不是执行授权。 |
| QF-PD-004 | 一次用户目标采用“父 WorkItem + 阶段子任务”；策略、计划、用例、自动化、执行和分析分阶段审核。 | 正式下游只能引用已发布的上游版本。 |
| QF-PD-005 | Agent 必须支持暂停、继续、取消、重试、授权和撤销授权；命令在安全节点生效并产生回执与审计。 | 页面不得直接篡改运行状态。 |
| QF-PD-006 | AI 生成发布建议，测试负责人作出通过、条件通过或不通过的最终决定并记录依据。 | AI 无发布裁决权。 |
| QF-PD-007 | 正式资产和质量结论强制人工审核；中间草稿只保留过程追踪；高风险项目可启用双人复核。 | 正式范围含策略、计划、用例、自动化代码、缺陷结论和发布报告。 |
| QF-PD-008 | V1 必须打通真实 API 自动化闭环；Web UI 自动化后置；模拟数据不得作为执行完成证据。 | 生成、审核、环境选择、真实执行、证据和分析全部可验收。 |
| QF-PD-009 | 登录后默认首屏为项目/版本驾驶舱，默认展示最近有效更新的项目并支持切换。 | 首屏包括 AI 对话、阶段、风险阻塞、人工待办和最近活动。 |
| QF-PD-010 | 取消“测试产出物”一级菜单；产出物回归所属业务模块。 | 二级“测试资产”只承担统一检索、版本和关联查看，不拥有创建流程。 |
| QF-PD-011 | AI 协作入口嵌入首页及各业务页面；独立 Agent 中心只负责运行治理、配置、权限、成本与评估。 | Agent 中心不是唯一日常入口。 |
| QF-PD-012 | 建立统一待办中心，汇总计划确认、审核、授权、异常、重试和发布裁决，同时保留业务页面就地处理。 | 待办支持项目、Release、风险、处理人和时限筛选。 |

### B. 质量闭环、资料与资产治理（QF-PD-013～025）

| ID | 正式裁决 | 约束与验收要点 |
|---|---|---|
| QF-PD-013 | QualityForge 保存内部标准缺陷记录；Jira、禅道等作为可选外部同步目标。 | 外部平台不可用时不阻断内部质量闭环；保留双向映射与同步状态。 |
| QF-PD-014 | AI 只能创建知识候选，附来源、适用范围、证据和时效；人工审核后才能成为正式知识。 | 正式知识支持版本、失效和替代关系。 |
| QF-PD-015 | 每个 Release 必须建立可版本化的测试依据基线，包含需求、接口、验收标准和约束。 | 策略、计划、用例、缺陷和报告可追溯到具体依据版本。 |
| QF-PD-016 | 每次执行冻结计划、用例、脚本、环境和数据配置的精确版本；执行后输入不可原地修改。 | 修改生成新版本和新执行批次；紧急变更通过终止或重建处理。 |
| QF-PD-017 | 正式执行前设置强制 Preflight Gate。 | 检查资产发布状态、环境、数据、凭据授权、Runner、依赖和预算；失败默认阻断。 |
| QF-PD-018 | 原始请求、响应、日志、截图、时间戳和 Runner 回执不可修改；结论只能追加修订。 | 保留原结论、修改人、理由和版本历史。 |
| QF-PD-019 | 质量门槛由测试负责人按项目配置并可在 Release 级加严；AI 只能解释、预警和建议。 | 临时豁免记录批准人、原因、范围和有效期。 |
| QF-PD-020 | V1 采用测试工程师、测试负责人、平台管理员和只读成员四类精简角色。 | 单人可兼任前三类，但身份与审计不省略。 |
| QF-PD-021 | V1 提供标准主流程和少量受控模板，不建设任意拖拽流程编排器。 | 可配置审核节点、质量门槛、Agent 能力、预算和通知；模板结构版本化。 |
| QF-PD-022 | AI 对话生成结构化任务卡后才可提交；高级用户也可直接填写任务卡。 | 任务卡至少包含目标、Release、范围、验收标准、约束、权限和预算。 |
| QF-PD-023 | 项目“最近更新时间”只由有效业务事件驱动，排除 AI 思考日志、轮询和草稿噪声。 | 支持固定常用项目。 |
| QF-PD-024 | 项目阶段、进度、风险、阻塞和质量状态由业务事实自动汇总。 | 人工只能补充说明、调整优先级或执行暂停、归档等受控动作。 |
| QF-PD-025 | 一个项目允许多个并行 Release，但资产、执行和质量裁决严格按 Release 隔离。 | 跨 Release 数据只用于趋势比较，不混入当前 Release 裁决。 |

### C. 平台、安全与执行治理（QF-PD-026～040）

| ID | 正式裁决 | 约束与验收要点 |
|---|---|---|
| QF-PD-026 | V1 产品体验按单租户部署实现，数据和权限模型保留 Tenant 边界。 | 不建设租户自助开通、计费、跨租户运营和复杂配额系统。 |
| QF-PD-027 | 环境、凭据和 Runner 由平台统一登记治理，项目按授权使用。 | AI 与普通成员只能引用凭据句柄，不能读取明文。 |
| QF-PD-028 | 所有模型调用和外部工具访问必须经过数据安全门禁。 | V1 实现 L1～L4 分类、供应商白名单、最小化取数、敏感检测与脱敏、L3 审批、L4 阻断和审计。 |
| QF-PD-029 | AI 可检索全部授权项目资料；测试策划和发布分析前强制执行资料完整性检查。 | 资料不足时只能输出草案和缺口清单，禁止形成正式结论。 |
| QF-PD-030 | 项目资料必须定义权威等级和当前有效版本；AI 识别冲突但不得自行裁决。 | 影响范围或发布结论的冲突由资料负责人裁决并形成基线变更。 |
| QF-PD-031 | AI 默认拥有授权代码仓库完整只读权限；写入仅限隔离分支或工作区并经人工审查。 | 禁止直接修改受保护分支、自行发布或部署。 |
| QF-PD-032 | 需求或代码变化后自动生成影响分析和任务草案；正式动作需人工确认。 | 只有预批准、低风险、有预算上限和急停能力的规则可自动执行。 |
| QF-PD-033 | V1 以完整纵向闭环优先，避免所有模块各做一部分。 | 核心链为项目/Release、资料、AI 任务、测试设计、API 自动化、审核、真实执行、证据、质量和发布。 |
| QF-PD-034 | V1 完成标准采用代表性示例项目的真实端到端验收。 | 最终结论可反向追溯需求、资产版本和原始证据；关键链路无模拟数据。 |
| QF-PD-035 | 项目和单次任务分别配置模型费用、Token、时长、并发和重试预算。 | 临近上限预警，到达上限暂停；AI 无权自行增加预算。 |
| QF-PD-036 | 长流程按阶段保存不可变安全检查点；失败从最近有效检查点恢复。 | 输入基线、权限或关键配置变化时，只失效并重跑受影响阶段。 |
| QF-PD-037 | 正式资产、审批、证据和发布结论不允许普通物理删除，只能归档、失效或受控撤回。 | 合规删除由平台管理员执行专门流程并生成删除凭证。 |
| QF-PD-038 | V1 同时支持人工测试和 API 自动化，并汇入统一执行、结果、证据和缺陷模型。 | V1 不扩展复杂设备实验室管理。 |
| QF-PD-039 | 策略、计划和用例支持手工创建、导入、编辑及 AI 协同生成。 | 统一版本、审核、追溯规则，并标记人工、AI 或协同来源。 |
| QF-PD-040 | V1 资料来源先支持文件、Git 仓库和接口定义。 | 覆盖 Markdown、DOCX、PDF、表格、OpenAPI/Swagger、Postman Collection 和代码；同步形成版本与差异。 |

### D. 产品价值与评估 Agent（QF-PD-041～050）

| ID | 正式裁决 | 约束与验收要点 |
|---|---|---|
| QF-PD-041 | QualityForge V1 明确定位为人机协同测试工作台，不是无人值守全自动平台。 | AI 承担认知与执行辅助，人掌握目标、授权、审核和发布。 |
| QF-PD-042 | 产品价值指标关注追溯覆盖、资产质量、真实执行、证据完整、影响识别、缺陷有效和裁决周期。 | Token、产出数量和调用次数只作为成本指标。 |
| QF-PD-043 | 设置独立评估 Agent，负责评分、质量预警和退回建议。 | 不代替正式审核，不作发布裁决，不允许执行 Agent 自评作为正式结果。 |
| QF-PD-044 | 评估 Agent 同时执行产物提交前的在线评估和固定基准集的离线回归评估。 | 在线服务当前任务；离线检查模型、提示词和规则漂移。 |
| QF-PD-045 | 平台管理员维护安全、证据、合规规则；测试负责人维护项目业务评分标准与权重。 | 规则版本化、审核并在基准集回放；评估 Agent 无修改权。 |
| QF-PD-046 | 评估 Agent 纳入统一 Agent 平台，但使用独立身份、配置、权限、预算和运行记录。 | 执行 Agent 不能修改评估输入、规则和结果。 |
| QF-PD-047 | 评估结果由硬门禁和风险等级驱动业务动作，分数用于解释、比较和趋势。 | 阻断项直接退回，高风险人工复核，中风险修改重评，低风险进入正常审核。 |
| QF-PD-048 | 人工审核结果形成评估校准样本，用于分析误报、漏报和评分偏差。 | 未经审核不得自动修改提示词、规则或模型配置。 |
| QF-PD-049 | 首页展示项目级评分趋势与阻断；业务页展示维度得分和证据；Agent 中心展示评估治理。 | 评分展示必须可下钻到资产版本和规则版本。 |
| QF-PD-050 | 项目质量评分综合覆盖、资产质量、执行、缺陷、证据和门禁，不做简单平均。 | 严重阻断限制总评分上限，并展示数据完整度和置信度。 |

### E. 多 Agent 协作与能力治理（QF-PD-051～057）

| ID | 正式裁决 | 约束与验收要点 |
|---|---|---|
| QF-PD-051 | 采用“协调 Agent + 专业 Agent + 独立评估 Agent”，不建设无边界自由 Agent 群。 | 专业职责与权限隔离，评估平面独立。 |
| QF-PD-052 | 用户默认只与协调 Agent 对话，可下钻查看专业 Agent 过程和结果并指定重跑。 | 项目背景由系统统一传递，用户无需重复描述。 |
| QF-PD-053 | Agent 之间通过结构化任务契约交接。 | 契约包含项目、Release、目标、输入版本、权限、预算、验收标准、预期输出和回执。 |
| QF-PD-054 | Agent 失败时按类型有限重试或切换已批准备用模型；仍失败则转人工待办。 | 禁止无限重试；待办附已执行步骤、失败原因、消耗和建议。 |
| QF-PD-055 | Agent、提示词、模型、工具、Skill、规则和参数全部版本化。 | 配置变更先评估和人工审核，再逐步启用并支持回滚。 |
| QF-PD-056 | V1 不允许普通用户自由安装 Skill 或接入任意工具。 | 平台管理员完成来源审查、权限评估、沙箱验证、发布和项目授权。 |
| QF-PD-057 | 向用户展示计划、资料引用、工具调用、阶段结果、权限、预算、错误和人工干预等可审计轨迹。 | 不展示模型内部思维文本；用户摘要与管理员技术追踪均需脱敏。 |

## 4. 数据安全门禁基线

| 级别 | 典型数据 | V1 默认策略 |
|---|---|---|
| L1 公开 | 公开接口文档、通用模板 | 可发送至已批准模型 |
| L2 内部 | 内部需求、普通用例、非敏感日志 | 指定模型、最小范围、全程留痕 |
| L3 敏感 | 客户数据、内部地址、业务样本、敏感缺陷 | 脱敏并审批；不能可靠脱敏时阻断或转批准的私有模型 |
| L4 严格保密 | 密钥、Token、密码、个人敏感信息、生产核心数据 | 禁止发送；仅允许受控句柄引用 |

门禁链：`权限检查 → 数据分级 → 最小化取数 → 脱敏/DLP → 模型与区域匹配 → 必要审批 → 执行 → 输出检查 → 审计`。任何无法判断的情况默认阻断。

## 5. 决策覆盖与兼容说明

1. 较早“测试产出物作为一级聚合入口”的方案，被 QF-PD-009～010 覆盖。
2. 较早“V1 仅实现三类 ReviewArtifact 策略”可以保留为技术分期，但不得削弱 QF-PD-007 对正式资产必须审核的业务要求；不同正式资产可复用现有审核策略，发布报告需具备签署语义。
3. 较早的最短保留期限仍可作为合规下限，不应被解释为到期自动物理删除；正式记录的删除必须遵循 QF-PD-037。
4. 较早独立平台评审 Agent 与本轮评估 Agent 不等价：前者评审平台本身，后者评估测试业务产物和 Agent 效果；两者应保持职责与数据边界分离。

## 6. 变更控制

- 任何改变上述裁决语义的需求，必须新建决策变更记录，说明原因、影响对象、迁移方案和验收标准。
- UI 原型不得自行发明与本记录冲突的流程、状态、角色或权限。
- API、数据库与前端实现应分别建立“裁决 ID → 需求 → 接口/表 → 测试证据”的追溯关系。
