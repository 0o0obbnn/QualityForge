## 0. 一句话结论

QualityForge 把「**可信产出物**」这个问题解得极好（溯源、版本、诚实不变量、单一 Owner 契约都是稀缺且正确的资产），但**系统性地欠建了「人—AI 协作」这个问题**——而后者恰恰是一个「AI 原生」平台存在的第一性理由。它现在是一套优秀的**AI 产出物归档与检验系统**，还不是一套**人和 AI 一起做测试的系统**。你感觉到的三件事——没有交互、流程不清、模块关联发虚——是同一个根因的三个投影。

所以：**当前需求设计「不是不合理，而是不完整」，且缺口集中在一个可命名、可重构的地方。** 不需要推翻,需要补上一层。

## 1. 第一性原理框架

### 1.1 平台存在的根本理由（公理）

- **公理 A**：这个平台存在，是为了**用 AI 把「可信的软件验证」做得更便宜**。
- **公理 B**：它调动的两种稀缺资源性质相反——**AI**（快、廉、可扩展，但不可信、会幻觉、不担责）与**人的专家判断**（可信、担责，但慢而稀缺）。

### 1.2 由公理推出的「中心设计问题」

若 A、B 成立，那么一个 AI 原生平台**最核心、最不可回避的设计问题**就是：

> **人和 AI 如何分工、如何把工作来回交接，才能拿到 AI 的速度、又不丢掉人的可信与担责？**

其余一切（模块怎么分、页面怎么排、实体怎么建）都是这个问题的下游。谁把这个问题解对了，平台就成立；解错或漏解，再精致的其余部分都会「哪里不对」。

### 1.3 解决中心问题的两种范式

| | **范式 A：装配线 + 检验门** | **范式 B：协作回环 / 副驾** |
|---|---|---|
| 隐喻 | 工厂质检（AI 自动生产，人在终点验收） | 结对工作（人机在过程中来回） |
| 人的控制点 | 事前定目标 + 事中治理配置 + **事后硬门审核** | 事前 + **事中实时引导/追问/纠偏** + 事后 |
| AI 遇到不确定 | fail-closed 阻塞，或按假设猜 | **向人发起澄清**，得到答复后继续 |
| 缺陷发现位置 | 产出物成型后的**终点门**（最贵） | **过程中**（最便宜） |
| 自治度 | 版本化治理配置，静态设定 | 可按任务**实时上下调** |

### 1.4 QualityForge 明确选择了范式 A（有据）

这不是疏忽，是一次**清醒的、写进原则的选择**：

- 「**审核即主流程**」被列为设计原则（`docs/06-wireframes/QualityForge-UIUX-Design-Plan.md:12`）。
- 责任分工＝AI 生成草稿、人负责「审核、批改、例外裁决、最终质量责任」（`docs/01-product/02-PRD总纲.md:7`）。
- 生命周期是离散的异步跳转：待创建→AI生成中→待人工审核→人工修改→退回重做→通过→发布（`docs/01-product/05-功能模块重构方案.md:107-118`）。
- 人对 AI 的唯一「回话」通道是 `POST /review-tasks/{id}/decisions`（批准/退回/拒绝）；`/ai/*` 其余接口全是 `GET` 观测（`docs/04-architecture/37-API接口总览.md:49`）。
- 实时通道**明确禁止**「回话」：WebSocket「只推送状态/日志/Trace」「不接受 Abort/Pause/Approve 等业务命令」（`docs/04-architecture/36-WebSocket实时契约.md:3,77,148`）。
- AI 缺输入时的规定动作是 **fail-closed 阻塞**、而非发问（`docs/03-governance/21-AI介入点降级矩阵.md:11`、`55-…SOP.md:115`）。
- 早期定位甚至白纸黑字：「**AI 不是一个聊天窗口**」（`docs/05-audits/historical/13…:26`，历史稿、非权威，但反映范式取向）。

**范式 A 本身是正当的**——对高风险、强合规、要审计追溯的测试场景，「自动生产 + 人工硬门」给出干净的问责链和审计线索。问题不在选了 A，而在**只有 A、且 A 的结构性代价没有被补偿**。

## 2. 核心诊断：一个根因

### 2.1 论点

> **QualityForge 被建模成「可信产出物的装配线」，而不是「人机协作系统」。**
> 它把「中心设计问题」（1.2）悄悄降级成了「产出物如何被可信地生产和检验」——一个更窄、更好解、但不是同一个的问题。

### 2.2 为什么这是「根」，而不是又一条症状

范式 A 有一个结构性缺陷，**设计团队其实已经撞见了它，却当成局部 bug 处理**：

- A 的经济性只在「终点门审核**足够便宜**」时才成立。但若 AI 因为**不能发问**而误解了意图，人只能在**产出物完全成型后的终点门**才发现，然后整包退回、整轮重跑——这是**发现误解最贵的位置**（软件工程铁律：缺陷发现越晚，成本越高）。
- 人在门口要**从成品 + Trace 反向重建 AI 的推理**，无法在过程中问一句「你当时凭什么假设 X」，单次审核的认知负荷极高。
- 于是 AI 只能二选一：fail-closed 阻塞（制造一个人必须**线下**解决的停顿），或猜（制造一个**在门口才暴露**的缺陷）。两者都贵。
- 最终必然长出「**单人 HITL 悖论**」——单一审核人成为瓶颈；而当前审计给出的补救是「延迟生效 / 批量审批」（`docs/05-audits/current/产品评估报告.md:91,101`），这是**削弱门来缓解瓶颈**，等于在结构性伤口上贴创可贴、还牺牲了 A 唯一的价值（严格的门）。

**结论**：`单人 HITL 悖论` 不是一个待优化的体验问题，它是「只选了范式 A」这一根因的**必然产物**。你说的「没有人机交互」也不是一个缺失的功能——它是这个范式的**承重后果**。

### 2.3 你的三个直觉，归到同一个根

| 你的直觉 | 核实结论 | 归因（同一个根） |
|---|---|---|
| ①「没有人和 AI 交互的功能」 | **强确认** | 范式 A 的直接承重后果：过程中不允许人机来回，只有终点门 |
| ②「业务流程不明确」 | **部分确认** | 建模的是**产出物状态流转**，不是**用户作业旅程**；装配线没有「人的一天」，只有「物料的流转」 |
| ③「功能模块关联不够明确」 | **数据契约层其实是强项（要保住）**；不安真实，但错位 | 混合拆分基准 + 一切经中枢强耦合，让「干净的数据契约」与「发虚的使用体验」错位 |

## 3. 三个直觉的逐一归位（带证据）

### 3.1 直觉①「没有人机交互」——确认，且是范式的承重后果

**核实**：全平台的人—AI 触点**只有**「AI 产出 → 人审核（批准/退回/拒绝/批注）」这一种异步批处理门。缺席的是：

- 对话 / 澄清界面——领域模型 §9 只有 Skill/Agent/Workflow/Session/TraceNode/SkillInvocation/Eval，**没有 Conversation / ClarificationRequest 之类实体**（`docs/01-product/04-核心领域模型.md`）。
- 事中澄清、AI 向人发问——被 fail-closed 取代。
- 实时引导 / 纠偏——WebSocket 禁止回话命令（见 1.4）。
- 运行期调自治——L0–L3 只能靠版本化治理配置改，不能按任务实时调（`docs/03-governance/21`）。
- 「人工接管」是**整个 WorkItem 的粗粒度移交**（切 `currentActorType`），不是过程中对话。

值得注意：设计里**曾出现过一次「提出澄清项」的字样**，却没有任何实体 / 流程 / API / UI 支撑它——说明团队直觉到了这个需要，但没落地。而 AI Agent 中心 PRD 是**运维/配置/审计面**（管 Skill/Agent/Workflow/Trace/Eval、预算、降级，`docs/02-prd/16-PRD-AgentCenter.md:7`），其 UI 组件 `AgentRunPanel` 是**只读监控面板、没有输入框**（`docs/06-wireframes/QualityForge-UIUX-Design-Plan.md:53`）——它不是终端用户与 AI 协作的界面。

> 同目录 2026-08-27 分析的 P0-3 / P0-6 / §7.3 已经在往这个方向摸（「WorkItem 启动前确认 AgentPlan」「统一 RunCommand 命令模型」「Agent 对话定位：支持查询和命令」），但都被摆成**实现/首屏（P2）任务**，未被拔高为**需求层的一等范式**。本诊断的 R0 就是把它拔上来。

### 3.2 直觉②「业务流程不明确」——部分确认，根在「建了产出物流转、没建用户作业」

**核实**：端到端叙事**存在**，但只活在总览层（01/02/05）的**箭头图**里，且最完整的一张还是**非权威的 deliverable**（`deliverables/2026-08-14/qualityforge-user-flow.html`）。更实在的问题有四个：

1. **五种互不相同的「主流程」叙述**要读者自己对齐：3 条 Journey（`02 §6`）／5 模块链（`05 §5.1`）／6 阶段（deliverable）／8 步闭环（`01 §3`）／9 节点产出物链（`05 §3.1`）。边界还不一致（如 `01 §3` 把用例设计与自动化合并成一步，`05` 拆成两个模块）。
2. **阶段间「交接」未定义**：没有任何文档规定「阶段 N 的产出物一旦批准，由**谁 / 何时 / 自动还是手动**创建阶段 N+1 的 WorkItem」。流程都止于「产出已批准的 X」，下一段又从「选择已批准的 X」开始，中间那一跳是空的。（`WorkItemDependency` 有实体，但没有规则把「产出物批准」绑到「下游 WorkItem 创建」。）
3. **8 个模块里只有 1 个**（测试执行，`14-PRD §主流程`）在流程里点名了它的下游模块，其余全靠共享产出物类型隐式相连。
4. **人/AI 职责切分很清晰，却和流程脱钩**——它活在一张张独立的责任表里（`01 §2`、`05 §3.2`、各 PRD §3），而 7 个角色（`02 §2`）**从未被映射到流程步骤上**，旅程里只写笼统的「人工」。

**更深一层**：整套结构是围绕**产出物 / 数据流水线**组织的（产出物主链 `05 §3.1`、容器树 `05 §5.7.1`、按产出物端点命名的 Journey A/B/C），**不是围绕用户作业**。没有任何「一个测试工程师的一天」式的按角色端到端旅程。真实用户体验的是**作业**（「我要把这个 Release 测完」），不是**产出物状态迁移**。你觉得流程发虚，是因为**根本没有一个业务流程模型**——有的是一个穿着流程外衣的产出物流转模型。手工测试已被裁进 V1（`05 §4.5` O2 裁决 2026-08-17、`14-PRD §2`），却没被并进任何端到端旅程,进一步坐实这一点。

### 3.3 直觉③「模块关联不够明确」——数据契约层其实是**强项**，但你的不安真实

**这条要为设计正名**：模块间的所有权与数据交接被定义到了**异常高、可审计**的标准，是整个文档集最强的部分之一：

- 8 条边界规则（`05 §5.2`）、实体归属矩阵（`05 §5.3`）、**每个实体唯一写入 Owner** 的全量矩阵（`05 §5.12`，8 张分模块子表）。
- 教科书级的模块接口：APIContract（`05 §5.10`）给出各模块 ×「可否直接改正式版本」表 + 9 条命令接口面。
- 执行→质量单向链、设计→执行版本硬门（`05 §5.9.1`、`§5.7.7`）。
- ~110 条 GWT 验收基线，跨模块盘点为 57 条 `INV-00-01…57`（`deliverables/2026-08-13/…408条 §2.9`）。

**重构时务必保住这一层，别当洗澡水泼掉。** 那你的不安来自哪里？来自两处**真问题**：

- **拆分基准是混合的、且不自洽**：`05 §2.1` 一口气把 8 个分成「产出物模块 6 + 管理控制模块 2」——**两种基准**。核心 6 个按产出物/生命周期切，另 2 个按控制面切，自动化又是按「是否需要独立 Code Review」这**第三条**基准从测试设计里拆出来的。最刺眼的是**任务看板被归进「产出物模块」，却不拥有任何产出物**（`05 §5.2` 规则1：它只拥有编排实体、「不拥有业务产出物内容」）——它本质是流程/编排模块。而 2026-08-27 那份文档 `§6.1` 已经**悄悄换了一种分法**（工作面5 / 流程与人工控制 / AI 控制面 / 平台控制面），把任务看板移出了工作面。**同一批 8 模块，两份文档两种分组**——这就是你「关联发虚」的来源：不是关联没定义，是**模块没切在一致的关节上**。
- **一切经中枢强耦合**：5 个业务模块之间**没有任何两个直接对接**，每一次交接都要穿过 任务看板（WorkItem/ReviewTask）+ 平台管理（RBAC/授权）+ AI Agent 中心（Session/Trace）三个中枢。数据契约干净，但从用户视角看，一条业务线在模块间反复 ping-pong，体验上自然「纠缠」。

外加两处被「事后裁决」打的补丁（非干净设计）：覆盖率 CoverageReport 的设计覆盖 vs 执行覆盖归属靠 `05 §5.12.7` 裁决 B2-1 打补丁；CI/CD 归属「先挂质量域、以后再说」（`05 §2.3`）；默认首屏「测试产出物」是个**无 Owner 的跨模块只读投影**却占据了主入口（2026-08-27 `P1-1`）。

## 4. 必须诚实承认、重构中不能弄丢的优点

1. **需求→覆盖率信任链 + 三条诚实不变量**（缺证据不成 PASS、冲突留全版本、被拒断言不离分母）——这是同类平台里罕见的、正确的东西。
2. **稳定根 + 不可变版本 + 审批绑定 versionId/contentDigest**——问责链干净。
3. **单一 Owner 矩阵 + 命令接口 + 精确版本引用 + ~110 GWT 基线**——模块契约精确到可以拿去审计实现（2026-08-27 `P0-5` 正是靠它抓出了实现漂移）。
4. **证据分层（CONFIRMED/INFERRED/UNRESOLVED/CONTRADICTS）**——这恰恰是把「人机协作」补进来时**最好的挂载点**（见 R0）。

**范式 A 的选择本身也应保留**：终点硬门、AI 不得终审、可审计追溯，都是对的。R0 不是替换 A，而是给 A **补上过程中的协作回环**，让缺陷在便宜的地方被发现。

## 5. 可执行改进项（驱动重构）

> 优先级：R0 = 范式级（不补，其余都是打补丁）；R1 = 结构级；R2 = 一致性级；R3 = 清理级。每项含：问题 / 根 / 具体动作 / 目标文档。

### R0（范式级）把「人—AI 协作」提升为一等需求域

- **问题**：过程中人机不能来回，缺陷被推到终点门；单人 HITL 悖论。
- **根**：只建了范式 A。
- **动作**：
  1. **新增领域实体**：`Conversation` / `ClarificationRequest` / `ClarificationResponse`（挂在 Session 或 WorkItem 上），有自己的 Trace。**关键设计**：人的答复落成一个 `evidenceClass=CONFIRMED` 的人类决策**溯源节点**，直接喂进 `SourceTraceEdge`——**这不是「聊天窗口」，是「可溯源的协作事件」，与你们的诚实不变量完全一致，反而让溯源更强**。这样正面回应了「AI 不是聊天窗口」的旧顾虑：我们要的不是闲聊，是可审计的澄清回环。
  2. **改 AI 缺输入时的规定动作**：从「只能 fail-closed」升级为「fail-closed **或** 发起 ClarificationRequest 并挂起，得到已授权答复后 resume」。
  3. **运行期可调自治 + 命令模型**：把 2026-08-27 的 RunCommand（PAUSE/RESUME/CANCEL/RETRY/AUTHORIZE/REVOKE）从「实现任务」提为**需求层的人机控制契约**；允许按任务在授权边界内实时上下调 L0–L3（仍全程 AuditLog）。
  4. **相应放开实时通道**：WebSocket 或等价通道需要一条「人→运行」的受控回话路径（命令必须生成可审查记录，不把聊天文本直接当授权——沿用 2026-08-27 §7.3 的护栏）。
- **目标文档**：`04-核心领域模型.md`（新增实体与溯源挂载）、`16-PRD-AgentCenter.md`（协作/命令面）、`21-AI介入点降级矩阵.md`（增补「发问」这条降级路径）、`36-WebSocket实时契约.md`（受控回话）、新增一份《人机协作与运行控制 PRD》。

### R1（结构级）建立作业/旅程模型 + 显式阶段交接

- **问题**：五种流程叙述打架；阶段交接是空的；无 persona 旅程。
- **根**：建了产出物流转、没建用户作业。
- **动作**：
  1. **合并**五种「主流程」叙述为**一份权威端到端旅程文档**（把 2026-08-14 的 user-flow deliverable 提升为权威需求文档，与 01/05 对齐后收编进 `docs/`）。
  2. **定义阶段交接规则**：明确「产出物批准 → 下游 WorkItem 创建」由谁/何时/自动或手动触发，写成可验收的 GWT。
  3. **定义 persona 并把角色映射到旅程步骤**：至少工程师 / 负责人两类（与 R2、P0-1 联动），给出「按角色的端到端旅程」。
  4. 把**手工测试**并进端到端旅程。

### R2（一致性级）裁决模块拆分基准的不一致

## 6. 只有你能拍板的前置裁决（重构启动前）
