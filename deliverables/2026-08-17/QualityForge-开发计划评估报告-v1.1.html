本轮新发现问题（1 P1 + 4 P2）

P1N1 · Makefile 门禁整改未提交，按计划自身审计纪律不构成「已关闭」

问题计划修订记录称「P0-1 门禁整改已落地」，Makefile 的 test target 确实已聚合前端测试（实测确认），但 git status --short 显示 Makefile 为未提交修改（M Makefile），无对应 commit 与 CHANGELOG 条目。计划自身 §3.5 明文规定「未提交的工作区改动不得声称已修复/已关闭」，且验收以 git status＋git log 为证据——按此纪律，P0-1 整改目前只能算「落地」，不能算「关闭」。
证据git status：M Makefile；计划 §3.5 审计约束、§3.4
建议首个 WP 前完成：提交 Makefile（过三重门禁）→ CHANGELOG 回填提交 → 双提交进 main 后 P0-1 方可标 CLOSED。工作区同时存在的 AGENTS.md 未提交改动一并清理或落账，避免污染后续「git status 为证据」的验收复扫。

P2N2 · §3.0.4 前端设计基线「27 页 Fluent 原型」未钉死工件路径

问题双轨模型把「autoclaw 的 27 页 Fluent 原型」作为前端验收对照基线，但计划未给出该工件的仓库路径。实测该资产真实存在：deliverables/2026-08-12/prototype/（27 个编号页面 HTML + 2 个 apple 变体 + README）。验收基线引用无路径，执行期易起争议。
证据deliverables/2026-08-12/prototype/ 实测存在；计划 §3.0.4
建议§3.0.4 补一行路径钉死：前端设计基线＝docs/06-wireframes/（Page-Map、设计令牌）＋ deliverables/2026-08-12/prototype/（27 页 Fluent 原型）。

P2N3 · D4「人工/影子基线对照数据」未分配责任人与采集方式

问题V1 总验收定性标准 D4 要求「人工/影子基线对照数据归档」，但人工基线意味着要有真实的人把试点任务手工做一遍（或影子模式跑一遍），这是有实际工作量且需要提前安排的采集活动。计划未说明谁来做、何时做、以何种形式归档。
证据计划 §四 V1 总验收 4-D4
建议试点 Workspace 选定后（V1 总验收前）明确：基线采集人（建议用户本人或指定试点用户）、任务样本（与 Journey A/B/C 同任务）、归档格式（对照表或影子运行日志）。

P2N4 · M2 收缩预案与 M3 分派联调存在依赖未说明

问题M2 前端轨的收缩预案是「1 类视图＋导航骨架，其余视图递延」，但 M3 集成的「真实数据可筛可分派」依赖看板分派类视图作为 UI 载体。若收缩时未优先保留「分派」相关视图，M3 的集成演示将缺 UI 载体，收缩反而制造返工。
证据计划 §四 M2 前端轨 vs M3 集成
建议收缩预案补一句优先级：收缩时优先保留「任务分派」相关视图，保证 M3 集成链不因收缩断档；被递延视图登记入 R6 台账。

P2N5 · lingma 兼任协调人与后端轨，跨轨升级触发权未写明

问题§3.0.5 规定跨轨分歧两轮不收敛时「提交用户裁决」，但未写明哪一方可触发升级。当前协调人 lingma 同时是后端轨执行者，若分歧中的升级判断权默认归协调人，存在结构性偏倚（后端轨可在升级上自我设限）。
证据计划 §3.0.5、§七.3；wall 话题 coordinator=lingma
建议§3.0.5 补一句：任一方在两轮未收敛后均可直接提请用户裁决，协调人不得单方面否决升级请求。
