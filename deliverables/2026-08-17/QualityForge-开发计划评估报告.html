问题清单（共 10 项，已合并去重）

P0-1前端测试未接入质量门禁，PR 级门禁承诺不成立

问题计划 §3.4 定义 PR 门禁为 make lint && make contract && make test；WP-2 明确要求编写 vitest 组件测试与 Playwright 冒烟（审核台 12 项信息、禁用原因渲染）。但 Makefile 的 test target 仅覆盖「后端测试 + Skill eval + Agent 治理校验」，frontend target 只是类型检查与构建——计划 §3.4 承诺的本地 PR 门禁链不含任何前端测试；CI 的 frontend.yml 虽已跑 vitest，但 Playwright 冒烟在 make 与 CI 均无落点（此表述经协调人 qoder 复核修正，2026-08-17）。M2 是前端最重的里程碑（7 类看板视图 + 8 模块导航），其回归防线在计划承诺的门禁链中缺位。
证据Makefile test/frontend target；.github/workflows/frontend.yml（vitest 已在 CI，Playwright 无）；计划 §3.4、M1 WP-2
建议Makefile 增加 test-frontend（vitest run）并纳入 test 聚合或 PR 门禁清单；§3.5 的 GitHub Actions「frontend」workflow 明确含 vitest + Playwright 步骤，门禁文字同步修订。

P0-2需求评审「放行三条件」只承接了一条，6 Major 整改方案冻结未落位

问题需求全量评审报告 L265–267 的 PASS_WITH_ACTIONS 放行条件是三条：① 关闭 6 项开放决策（计划 M1 WP-3 ✓）；② 3 项高风险形成书面对策并纳入版本规划（R2 由分支 A+M5 承接、R3 由 C1/C3 承接，但未在计划中显式标注为「R1/R2/R3 对策落位清单」）；③ 冻结 6 项 Major（D1–D6）整改方案——计划全文无此条目，D1 命名漂移「机械重命名」完全缺失。计划同时引用评审报告与 VERDICT 为依据，放行条件未完整挂账即存在审核闭环缺口。
证据需求全量评审报告 L82 / L265–267；对照 计划 §一/§四/§五（无 D1–D6 冻结条目）
建议M1 WP-3 扩展为「放行三条件关闭」：6 开放决策 + R1–R3 对策落位清单（引用计划对应章节即可）+ D1–D6 整改方案冻结（可只冻结方案、执行排入后续里程碑），并请用户对 O1（定性成功标准）明确裁决。

P1-1现有测试基线薄弱，M1 改造前缺少 characterization 测试

问题当前 22 个已实现 operation 仅有 15 个测试函数（5 个文件），planning_workflow 的「生成→审核→批改→新版本→二次复核」核心链路覆盖极薄。M1 WP-1 要直接改造该服务的退回分支与版本递增逻辑，TDD 只约束新代码，改造前的既有行为没有基线测试保护，回归风险高。
证据backend/tests/ 5 文件 15 用例（grep 实测）；M1 实施计划 WP-1
建议WP-0 增补既有 planning 链路的 characterization 测试（先固化现状行为再改造）；同时给 auth/planning 现有 22 个 operation 的 happy-path 补一轮契约对齐测试。

P1-2M2 前端工作量与现状鸿沟未被估算，单人力假设未做容量检验

问题计划 §六.3 默认「单人 + AI 结对」，但 M2 要求从当前单页审核工作台（App.tsx + 少量组件）构建 7 类看板视图 + 八模块导航骨架 + 路由体系，是纯新增的规模化前端工程。计划对此没有任何规模/复杂度估算，也没有里程碑间的吞吐校验；验收按证据不按日历是合理设计，但「可行但时间未知」与「工作量超单人力容量」需要区分。
证据frontend/src/ 仅 App.tsx、api.ts、types.ts、statusBadge.ts（实测）；对照 计划 §四 M2 验收 1–2
建议M2 开工前的 writing-plans 输出中增加 T-shirt 规模估算（S/M/L）与容量声明（如「M2 预计 N 个 WP，按 2 天/WP 节奏」）；若超容量，先收缩 M2 范围为「1 类视图 + 导航骨架」的纵向切片，其余视图递延。

P1-3分支 A「并行开工」与单人结对假设冲突，无执行主体划分

问题计划 §二规定分支 A 自 M1 起并行开工（Provider 四项接口 + 坏 provider 防御测试），但 §六.3 的人力假设是单人 + AI 结对。单人力下「并行线」实质是串行抢占——谁来写坏 provider 防御测试、验收归 M5 意味着交付压力后置堆积，存在 M5 前突击风险。计划未定义并行线的执行主体（AI 主导 + 人审？）与节奏约束。
证据计划 §二「并行线」vs §六.3「单人 + AI 结对」
建议明确分支 A 为「AI 主导实现 + 里程碑末人审合入」的低抢占模式；或规定分支 A 的 WP 优先队列位置（如每里程碑完成主链切片后投入固定比例）；M5 前置 1 个里程碑（M4 起）冻结分支 A 代码，避免验收突击。

P2-1黄金集样本增长无速率跟踪，统计阈值可能长期不启用

问题评估集样本增长源＝Stage 4 人审决定（N=10 起步，≥30 启用 85% 统计阈值）。若试点审核量低，样本积累缓慢，M5 之后评估将长期停留在「结构判分零容忍」单一形态。计划未定义样本积累速率的跟踪机制或达量时间观察点。
证据计划 §3.3-B 末尾、§四 M5；VERDICT C8
建议在 M3/M4 证据包中增加「回放样本数」计数项，每里程碑报告一次；样本数长期停滞时在墙上触发讨论（是否引入受控人工构造负例）。

P2-2验收标准大量外链 GWT/章节编号，权威载体不自包含

问题§四 M1–M4 的验收标准多处引用 GWT-5.5.12-2/3、05 §5.13.6、Page-Map §3 等外部编号，计划自称「权威载体」但验收语义依赖多文档跳转拼装。文档版本若漂移，验收解读存在分歧空间。
证据计划 §四 M1 验收 1、M3 验收 2、M4 验收 1
建议每个里程碑验收证据包附「验收口径速查」——把被引用条目的关键句摘录进验收记录，引用与摘录并存，避免跳转解读。

P2-3「commit 哈希 + CHANGELOG 双落账」实际是双提交闭环，模式未书面化

问题git log 实测显示既有惯例为「内容提交 → 哈希回填提交」两段式（如「批次二十七回填：CHANGELOG 哈希回填 f98f9d5」），每条关闭至少 2 个 commit。计划 §3.5 只写了「双重落账」的结果要求，未描述这一两段式操作模式与门禁时序（回填提交本身是否也要过三重门禁）。
证据git log --oneline（回填提交模式）；计划 §3.5
建议§3.5 补一段「双落账操作序」：内容提交（过门禁）→ 回填提交（docs-only，免全量测试但过 lint）→ PR 合入。把既有惯例固化为明文，减少每次关闭的决策成本。

P2-4M3 三条隔离验证用例缺威胁模型定义

问题§四 M3 验收 3 只写「agent 无法绕过 digest 直写证据状态」，未定义绕过的具体路径集合（直写 sqlite_store？伪造 contentDigest 字段？重放旧摘要？）。到 M3 实施计划再补，可能造成测试设计口径漂移。
证据计划 §四 M3 验收 3；VERDICT §六.2（收敛条件）
建议M3 开工前的实施计划中列明 3 条用例各自对应的绕过向量与预期 fail-closed 行为，作为测试设计输入。

P2-5V1 总验收「运行类」证据在单机 SQLite 形态下未定义最薄口径

问题§四 V1 总验收要求六类证据中含运行（容量/延迟/恢复/成本/可观测）。其中「恢复」在 SQLite 单机 + 进程内串行形态下的最薄证据形态（如异常退出后数据完整性校验？）未定义；C3 只承诺「并发回归与最薄性能基线」，恢复类证据无承接处。
证据计划 §四 V1 总验收 3；对照 §二 并行线（C3）
建议在 C3 改造的实施计划中同时定义「最薄恢复证据」口径（如进程强杀后重启的完整性校验用例），避免总验收时临时造证据。

计划的突出优点

治理脉络完整闭合
逐条承接 VERDICT C1–C8 与三项用户裁决，硬约束写明「违反即 fail-closed」；里程碑×主链×验收证据×前置债四维映射清晰。
范围纪律强
「明确不做」六项全部带重启条件而非永久否决；86 个 operation 按需增量实现，拒绝横铺；指标只建基线不承诺目标值，符合防口号化设计。
反「假关闭」机制具体
commit 哈希 + CHANGELOG 双落账直击 L1 教训（8 项假关闭仅 1 项真关闭）；验收按证据不按日历；禁止未提交改动声称已修复。
评估闸门双层互补且务实
确定性层归 make test、LLM 判分层归 make eval，判分 v0 用 promptfoo icontains，本轮零 LLM-judge——与既有工具链实证（promptfooconfig.yaml 已存在）吻合。
Git 规范可落地
主干 + 短命分支、Conventional Commits、≤400 行/PR、force-push 禁令、标签与 CHANGELOG 互引闭环，均与仓库现状（单一 main、批次化 CHANGELOG）兼容。
事实基线准确
22/108 operation、30 Skill 原型、0 Blocker/6 Major/3 高风险、三项前置裁决状态等关键数字与仓库实测一致，未发现夸大或粉饰。
