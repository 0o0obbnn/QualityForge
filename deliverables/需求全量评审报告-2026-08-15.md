## 一、需求背景与目标澄清

### 1.1 业务价值（Why）

QualityForge 是 **AI 原生端到端测试平台**，核心分工是「AI 生产 + 人工审核」：AI Agent 承担需求解析、测试设计、自动化代码、执行、证据整理与质量分析；测试人员负责审核、批改、例外裁决与最终质量责任。

要解决的 7 类核心痛点（证据：01 功能地图 §5、05 §七）：

| 痛点 | 产品机制 | 价值主张 |
|---|---|---|
| 工作分散、AI 运行不透明 | 任务看板统一工作项/运行/审核队列 | 降低切换与追问成本 |
| 测试依据版本混乱 | 来源快照、契约版本、基线 | 结论可追溯可复现 |
| 策略/计划/用例手工重复 | AI 草稿 + 人工集中审核 | 提产提速、保留专业判断 |
| 自动化代码维护成本高 | 独立代码工作台 + Code Review | 代码成为可治理正式资产 |
| 执行结果与 AI 推断混淆 | ExecutionResult 只追加、分析独立版本化 | 防止推断污染事实 |
| 提 Bug/分析/报告重复 | AI 组织证据、生成草稿 | 缩短质量反馈周期 |
| AI 权限效果不可控 | allowlist、Trace、Eval、降级、humanOnly | 可控可审计可持续改进 |

**核心设计哲学（贯穿全体系的一致主线）**：事实 / 推断 / 决定三层分离——执行结果是绿/红事实，AI 推断是草稿标签，人工决定是审核动作。这一哲学在领域模型（ExecutionResult 只追加）、AI 治理（三层证据）、验收标准（AC 覆盖降级路径）中高度自洽。

### 1.2 用户角色（Who）

| 角色 | 核心目标 | 边界（不默认拥有） |
|---|---|---|
| TestEngineer 测试工程师 | 批改用例/代码、触发执行、分析 Defect | 高风险单人批准、权限管理 |
| TestLead 测试负责人 | 审核策略/计划/报告、裁决关键例外 | 租户管理、Secret 明文 |
| WorkspaceAdmin | 成员、环境/集成、Workspace 配置 | 报告签署、门禁豁免 |
| TenantAdmin | 租户成员、配额、共享集成 | Workspace 业务资产批准 |
| PlatformAdmin | 平台基础设施、安全运维 | 租户测试内容、业务批准 |
| ViewerAuditor | 授权范围只读审计 | 写入/执行/批准/外部写入 |
| Service/Agent | 授权交集内受限自动化 | 人工专属批准权 |

关键约束：**Approver/Reviewer 是 ReviewTask 临时职责，不是全局角色**；管理员身份不自动获得业务批准权（证据：02 §2、05 §5.11.8）。

### 1.3 使用场景（Where / When）

主闭环（证据：01 §3）：
`来源固化 → AI 生成策略/计划 → 人工审核 → AI 生成用例/代码 → 人工审核 → AI 编排执行（不可变结果）→ AI 生成分析/Defect/报告 → 人工审核/签署/外部写入 → 已审核经验回流知识库`

三条核心旅程（证据：02 §6）：
- **Journey A**：需求 → 可审核测试资产（策略/计划/用例）
- **Journey B**：正式用例 → 自动化结果（代码 → 执行 → 结果）
- **Journey C**：失败 → 质量交付（分析 → Defect → 报告 → 外部同步 → 知识回流）

### 1.4 产品目标与非目标

**目标**（02 §3.1）：缩短有效产出时间、提高可追溯性、减少遗漏/错误发布/重复劳动、AI 行为可观察可评测可降级、事实/推断/决定分层。

**非目标**（02 §3.2）——这是防止范围蔓延的关键约束：
- V0 不交付可运行 SaaS、分布式执行平台、完整 Agent 市场
- V1 不承诺无人测试、全自动发布门禁、替代测试人员
- 不把 Workspace 复制成 Project、不把 Skill/Agent 合并
- 不因 AI 高置信度跳过正式审核/外部写入/报告签署
- **无实测基线前不承诺固定收益百分比、并发量、延迟或 AI 准确率**

### 1.5 成功标准（How to measure）

成功度量方法（02 §7）明确"先建人工基线，再同任务对照"，并定义 5 维度 51 项受控指标（20 §1.1，metricKey 前缀 eff_/qual_/ai_/trace_/ops_）。

**评审发现（开放决策 O1）**：V1 的完成定义（22 §1）是"八模块最小入口贯通 + 代表性试点跑通完整证据链并建立基线"，**没有量化的成功阈值**。02 §7 明确"具体目标值必须在 V1 试点基线后批准"——这是刻意设计（防口号化），但副作用是 **V1 进入时无法回答"怎样算试点成功"**。需评审会确认是否接受"定性成功标准 + 基线后量化"的渐进路径。

## 三、可行性与风险评估

### 3.1 技术实现难度

| 领域 | 难度 | 依据 |
|---|---|---|
| 领域模型 + 版本治理 | 中高 | 100+ 实体、稳定根+不可变版本+contentDigest+ReviewTask 全链路，每实体都要落地 |
| AI 治理（L0-L3/介入点/降级） | 高 | 22 个介入点、三层证据、版本化校准、熔断回退，是平台最复杂子系统 |
| 多租户 + RBAC | 高 | 四级作用域 + humanOnly + ExplicitDeny + fail-closed 交集，需 PostgreSQL RLS |
| 执行引擎（Runner/调度/证据） | 高 | 租约、心跳、重试、制品脱敏、保留策略、实时流 |
| 外部集成（Git/Jira/PingCode/CI/KMS） | 中高 | 幂等、回执、冲突、逐次授权 |

### 3.2 时间成本与团队规模匹配（核心风险）

**R1（High）**：V1 范围 = 全八模块。"最小入口贯通"（22 §3）与每模块的 V1 功能清单（22 §3 表格列了完整功能集合）之间存在张力。若按字面执行，V1 交付规模接近完整产品，与当前**单人/极小团队**的资源配置严重不匹配。需评审会明确"最小入口"的量化边界（每模块的最小可验收切片是什么）。

### 3.3 依赖关系

| 依赖 | 状态 | 风险 |
|---|---|---|
| 真实 LLM Provider | 未就绪（当前 deterministic-local Provider） | R2 |
| PostgreSQL（RLS） | 未就绪（当前 SQLite 应用层隔离） | R3 |
| Git/Jira/PingCode/CI/KMS/Runner 池/消息队列 | 未就绪 | R4 |
| 真实模型效果评测 | 未完成（30 Skill 仅 14 确定性 runner，103 eval case） | R2 |

### 3.4 风险清单

| 编号 | 等级 | 风险 | 建议对策 |
|---|---|---|---|
| R1 | High | V1 范围=全模块，"最小入口"量化不足 | 评审会逐模块冻结 V1 最小切片（每模块 1 个"主闭环 AC"） |
| R2 | High | 真实模型评测缺失，制约 L2 默认模式"质量"维度验收；核心价值主张无法量化 | V1 明确"功能正确性可验收、AI 效果仅建基线"的边界，Golden Set 先行 |
| R3 | High | SQLite 本地方案 ≠ PostgreSQL RLS，多租户安全验收存在"假象"风险 | V1 明确区分"功能验收"与"安全达标"，RLS 安全项显式标注 deferred |
| R4 | Medium | 外部依赖多且未就绪，执行/外部同步环节受制 | V1 用 Mock/手工回执替代（15-PRD 已允许"手工同步落 DefectSyncAttempt"） |
| R5 | Medium | 领域模型体量大，工程落地成本高 | 按实体 Owner 分模块增量落地，先跑通 1 条完整证据链 |

**INVEST 关键发现**：8 个 Epic 均满足 Independent/Negotiable/Valuable/Estimable/Testable，但 **Small 全部不满足**——它们是模块级 Epic，需按第四层 F1-F26 拆分为 Story 级才能进入排期。这印证了 D 类缺陷之外的"粒度缺口"。

### 5.6 需求基线（Baseline）

**基线状态判定**：当前需求体系已形成**事实上的需求基线**——8 模块边界、8 类正式产出物、领域实体与状态机、AI 自治矩阵、V0-V3 版本契约均已冻结并经多轮裁决收敛（导航索引 §2"现行权威源"表明确裁决基线）。

**基线进入 V1 开发的前置条件**（本评审给出的 gate）：

1. 关闭 6 项开放决策（O1-O6，对应 T1-T7）；
2. 对 3 项高风险（R1/R2/R3）形成书面对策并纳入版本规划；
3. 冻结 6 项 Major 缺陷（D1-D6）的整改方案（其中 D1 命名漂移建议启动机械重命名）。

**全平台裁决：PASS_WITH_ACTIONS（有条件放行）**——需求质量足以支撑 V1 开发启动，但不得在未关闭上述 gate 前宣称"需求已验收"。
