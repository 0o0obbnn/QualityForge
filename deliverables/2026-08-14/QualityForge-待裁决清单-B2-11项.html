B2-1 · QF-REQ-003 CoverageReport 归属 (严重 · 直接影响 V1 覆盖度验收)

背景CoverageReport 同时被两处使用:12-PRD 列为"设计链实体/中间产物",AC-03 以"CoverageReport 声称 90%"为验收对象;而 05 §5.12.7 将 CoverageReport 唯一写入归"质量分析与缺陷";PRD15 全文零承接。V1 必交付"基础覆盖/风险汇总"(05 §5.13.3)。
冲突点同名产出物两个模块可写,违反 05 §5.12.1 唯一 Owner 边界。本质是两个不同语义共用一个名字:"设计覆盖"(需求→用例映射是否完整,设计阶段的中间产物)与"执行覆盖报告"(实际执行了多少、通过率多少,面向交付的报告)。
方案内容利弊
A(推荐)拆成两个概念:"覆盖分析"(设计链中间产物,归 12)+"CoverageReport"(正式产出物,归 15)语义清晰;符合"执行事实与 AI 推断分层";唯一 Owner 成立需要改 12-PRD AC-03、05 §5.12.7、04/32/33 标注
B统一归 15,12 只做"覆盖分析请求",所有产出物归质量模块改动最小(05 已如此裁决)"设计覆盖"无处表达,12 的覆盖能力悬空
C统一归 12,15 引用12 侧闭环推翻 05 §5.12.7 现有裁决,与执行报告语义不符
建议:方案 A——拆分两概念,这是唯一让"覆盖"语义自洽的方案。
影响:12/15-PRD 修订、04/32/33 归属标注、V1 覆盖度验收口径。

B2-2 · QF-REQ-004 ContractCheckResult 承接 (严重 · V1 义务冲突)

背景05 §5.10.8 强制"测试执行产生 APIObservation 和 ContractCheckResult;未检查不能计为通过、INCONCLUSIVE 不能被报告为契约一致";§5.12.6 归测试执行。但 PRD14 无任何需求、PRD15 报告无披露项;L1 纠正报告把缺口延到"测试执行模块开发时补"。
冲突点测试执行是 V1 必交付模块(05 §5.13.3 明列),延期声明与 V1 义务冲突——"延期≠销账",V1 验收前必须补,只是补多少的问题。
方案内容利弊
A(推荐)V1 完整承接:PRD14 补需求+AC,PRD15 报告补披露字段(已检查/偏差/未检查/不可判定数),32 补 schemaV1 契约偏差检测闭环,承诺不落空V1 工作量+1 个能力点
BV1 只落"检查结果存原始状态"(MATCH/DEVIATION 落库),分析与披露 V1.1事实留存,成本低披露承诺推迟,需同步改 V1 验收口径
C接受延期,V1 非目标明确写入"不承诺契约偏差检测"V1 范围最小"契约漂移检测"核心价值在 V1 缺失,与产品定位冲突
建议:A 或 B——至少 B 保证事实留存;若 V1 排期紧张可选 B 并在报告中明确。
影响:V1 验收标准、PRD14/15 修订、32 schema 补全。

B2-3 · QF-REQ-006 AI 校准记录载体 (严重 · 决定自治等级能否启用)

背景21 §4/AC-03 要求"无有效校准记录时模型分数只能排序、不得触发自治",并定义了校准记录字段(interventionKey/版本/datasetVersion/metricDefinition/threshold/sampleSize/baseline/validFrom/expiresAt/fallbackLevel)。但 33 的 t_eval_* 表只有 scope/metrics JSONB,没有 threshold/有效期/回退等级列,也没有"介入点↔阈值↔回退等级"登记表;32 只有 /ai/eval-runs 无校准注册 API;现有 30 套 Skill eval 全部是确定性结构校验。
冲突点治理机制已定义但无结构化落点——L2/L3 自治等级在 V1 试点真实模型接入后依然无法按契约启用,21 号 AC-03 永远 fail-closed。
方案内容利弊
A(推荐)33 新建校准记录表(含全部 9 字段)+ 登记表;32 补校准注册/查询 API;与真实模型 Golden Set 计划绑定程序化判定"有效校准记录";L2/L3 准入有底座需在 V1 真实模型接入前完成(排期压力)
B在 t_eval_run 上扩字段(轻量)改动小eval 与 calibration 语义混在一张表,回退等级/有效期语义弱
CJSONB + 应用层校验最快无法程序化判定,与 A 的差异就是 AC-03 判定底座是否真实存在
建议:方案 A——这是 21 号 AC-03 的判定底座,与 QF-REQ-033/风险 005 绑定,建议与真实模型 Golden Set 计划同批落地。
影响:33/32 契约、真实模型准入排期、L2/L3 自治启用条件。

B2-4 · QF-REQ-025 V1 手工外部同步的落地标准 (一般 · 安全底线)

背景22 §3 允许 V1"外部同步先手工";05 §5.9.8 要求 EXTERNAL_WRITE 逐次批准+幂等键+回执;但手工模式下 approvalId↔payloadDigest 一致性、幂等键、回执是否落库完全没有定义。
冲突点如果"先手工"=完全在系统外操作,V1 验收基线(05 §5.9.11-5/6:外部写入拒绝未授权调用/幂等重试)无法执行,越权审计断链——安全底线在 V1 悄悄退化。
方案内容利弊
A(推荐)手工同步也强制走 DefectSyncAttempt 数据结构+批准记录落库(执行者是人,但契约不降级)安全底线不降;V2 自动化无缝升级;审计完整手工操作多一步(在系统内录入)
B手工完全在系统外,V1 验收降级为"不验收外部写入"省事越权审计断链;V2 集成时数据结构返工
C半程:批准记录落库,回执不落折中回执缺失导致重试/冲突处理不可验证
建议:方案 A——成本低(一个数据结构),直接消解 QF-RSK-010。
影响:15-PRD 修订、V1 验收、QF-RSK-010。

B2-5 · QF-REQ-028 104 张表如何按 V1 裁剪 (一般 · 工程风险)

背景33 号目标架构共 104 张表;L1 纠正报告给出口径说明("聚合根以字段表呈现,非字面 1:1"),但 V1 实际需要哪些表无清单。若按图全建,迁移/RLS/索引/事务/运维成本全部放大,存在"按图全建"的工程误判风险。
冲突点目标态完整性 vs V1 试点最小集——没有裁剪原则,开发团队无法排期。
方案内容利弊
A(推荐)按 M1~M5 里程碑产出"每里程碑需建表清单",增量建表,主链优先与 Stage5 规划绑定;每阶段可验收需要先完成 B2-6 的里程碑顺序裁决
B按模块边界整块裁剪(开工哪个模块建哪个模块的表)简单直接与跨模块契约(ReviewTask/SourceTrace)冲突时需反复
C全建 104 表一步到位放大成本;违反"V0/V1 不生产化"定位
建议:方案 A——与里程碑绑定,顺带解决 QF-REQ-007 的"步骤↔版本↔验收"对照表。
影响:迁移计划、开发排期、V1 交付范围、QF-REQ-007。

B2-6 · QF-REQ-032 5 类产出物切片证据的补证顺序 (一般 · V1 准出威胁)

背景Stage4 只覆盖 TestStrategy/TestPlan/TestCase 三类产出物的审核切片;AutomationScript/ResultAnalysis/Defect/TestReport/KnowledgeEntry 五类无纵向切片证据;版本 Diff、"批改→新版本→再复核"未实现。
冲突点05 §十一 5 个后续步骤与 V1 准出绑定,5 类产出物缺口直接威胁 V1;但补证顺序影响开发节奏,需要先定优先级。
方案内容利弊
A(推荐)按 Stage5 已裁决主线:M3 执行与证据 → M4 分析与报告;Defect/外部同步放 M4 后尊重已裁决的 M1~M5,改动最小Defect 证据最晚,若客户重点在缺陷闭环需提前
B先补"证据成本最低"的(TestReport 可基于现有数据生成;KnowledgeEntry 审核流复用 ReviewTask)快速建立 5/8 证据覆盖打乱 M1~M5 主线,交付顺序与规划不一致
C接受缺口,V1 只验收 3 类产出物V1 范围最小需修改 V1 完成定义,与 05 §5.13.3 冲突
建议:方案 A,如果试点客户重点是缺陷闭环,可把 Defect 提前到 M4。
影响:V1 准出、05 §十一 步骤绑定、开发排期。

B2-7 · QF-REQ-034 V1 用 SQLite 还是 PostgreSQL (一般 · 技术路线)

背景8-13 已把技术栈降级为本地 SQLite(commit 1f562a5);PostgreSQL 的 RLS/并发/恢复能力未在任何环境验证;收口复核保留开放项 3;05 §5.13.6 跨版本不变项含多租户隔离。
冲突点SQLite 交付快(单机试点足够)vs 目标 PG(多租户安全底线);"单机可运行"≠"多租户隔离安全",若 V1 以 SQLite 交付需另行证明等价的安全/审计控制。
方案内容利弊
A(推荐)V1 用 SQLite 交付;试点前做一次 PG 冒烟(104 表迁移+RLS+核心链路并发),V2 切 PGV1 节奏最快;PG 风险提前暴露;符合技术栈演进需要一次 PG 冒烟投入
BV1 直接上 PG一步到位单机试点价值未验证就背上 PG 运维;成本高
C保持 SQLite,PG 验证推迟 V2零成本多租户安全论证缺失,QF-RSK-006 悬空
建议:方案 A——V1 前加一个"PG 冒烟"验收点(可挂到 M1 或 M2 门禁)。
影响:V1 交付形态、RLS 安全论证、QF-RSK-006。

B2-8 · QF-REQ-039 V1 代码试运行沙箱的验收口径 (建议 · 安全)

背景05 §5.8.8 要求 AutomationScript 试运行沙箱"非 root、只读根文件系统、默认零外网、最小 Secret";30/31 有容器化 Runner 目标架构;但 V1 单机 Runner 下如何量化证明"只读根""零外网"没有定义,13-PRD 也无失败判定阈值。
冲突点没有量化口径,沙箱要求无法验收——要么实现后无法证明,要么实现时随意解释。这直接关联 RCE 风险(QF-RSK-012)。
方案内容利弊
A(推荐)定义 V1 量化验收项:进程非 root 运行、工作目录只读挂载、网络命名空间禁外网、执行超时上限、产出目录白名单——每条给检查命令可验收、可自动化检查;成本低隔离强度弱于容器(仅进程级)
BV1 用 Docker 单容器隔离隔离强、接近目标架构依赖 Docker 环境,与"本地切片无容器"定位冲突
CV1 不承诺沙箱,本机直接执行零成本RCE 攻击面完全暴露,不推荐
建议:方案 A(量化进程级隔离);若试点环境允许 Docker 可升级为 B。
影响:13-PRD 修订、QF-RSK-012、V1 执行模块验收。

B2-9 · QF-REQ-042 Pipeline 触发归 V1 还是 V2 (建议 · 范围)

背景14-PRD §2 触发能力写"手工、计划、Webhook、Pipeline",但 §7 又说"V2 增强…流水线";05 §5.13.3 的 V1 测试执行无 Pipeline 字眼、§5.13.4 的 V2 质量分析含 CI 触发——PRD 内部自相矛盾。
冲突点V1/V2 归属不可判定,开发不知道要不要做 Webhook 端点,排期与验收口径悬空。
方案内容利弊
A(推荐)CI/Webhook 触发归 V2(采 05 §5.13.4 口径),V1 只做手工+计划触发;18-PRD 迁移说明同步V1 聚焦核心闭环;与 05 裁决一致试点客户若需 CI 联动需等 V2
BV1 就支持 Webhook(一个端点,成本低)客户价值前置范围蔓延;门禁联动逻辑(QualityGate)仍属 V2,单端点价值有限
建议:方案 A;若试点客户明确有 CI 需求,再单独评估 B。
影响:14-PRD/18-PRD 修订、V1 范围、22 号 V1 行同步。

B2-10 · QF-REQ-045 ReviewDecision 概念如何落地 (建议 · 一致性)

背景ReviewDecision 在 01/10/20/21/31/32/34 七处文档反复出现,但 04 领域模型无此实体、33 无表;实际决策数据落在 t_review_assignment.decision + t_authorization_decision;03 与 04 的迁移表目标表述还不一致(ReviewTask/ReviewDecision vs ReviewTask/ReviewAssignment)。
冲突点概念在文档中"存在"但无落地载体,实现者无所适从——按文档做找不到表,按表做找不到概念。
方案内容利弊
A(推荐)显式声明"ReviewDecision = ReviewAssignment.decision + AuthorizationDecision 的只追加投影"(不建新表,在 04/33 加说明),统一 03/04 迁移表措辞最小成本消除歧义;不引入冗余查询审核历史需要 join 两表(可接受)
B新建 t_review_decision 独立表审计链单一清晰与现有两表冗余,需同步写入逻辑
C改名统一为 ReviewAssignment(删除 ReviewDecision 概念)最彻底7 处文档大改,引用面广
建议:方案 A——文档说明 + 措辞统一,不动表结构。
影响:04/33 补说明、03/04 迁移表措辞统一、32 schema 注释。

B2-11 · N6 WorkItemType 的 TEST_DESIGN 与 21 号介入点同名 (新暴露 · 命名冲突)

背景QF-REQ-002 收敛时选择了"以 05 为准"方向,WorkItemType 枚举包含 TEST_DESIGN;而 21 号介入点矩阵也有 TEST_DESIGN 介入点——同名不同义(一个是任务类型,一个是 AI 介入点)。
冲突点代码/工具解析时按字符串匹配可能混淆;文档阅读者也可能误解。
方案内容利弊
A(推荐)不改名,在 03 术语表加注"同名不同义,按上下文区分"零成本;四源刚收敛完不再动解析时仍需人工注意
BWorkItemType 的 TEST_DESIGN 改为 TEST_CASE_WORK(或 TEST_DESIGN_WORK)彻底消除混淆四源枚举再动一次(刚收敛完),需重新验证
C21 号介入点改名保留 WorkItemType 语义介入点矩阵影响面更大(22 个 key 引用)
建议:方案 A——低风险先加注;若后续工具解析真出问题再升级 B。
影响:03 术语表加注(一行);潜在的四源再次变更。
