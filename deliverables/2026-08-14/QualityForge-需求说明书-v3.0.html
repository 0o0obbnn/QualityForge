    1.1 目的

    本需求说明书依据 GB/T 9385-2008 的章节骨架编制,对 QualityForge 产品的总体定位、八个一级功能模块、用户角色、全局约束、假设与依赖以及分版本需求分配进行系统化、可核对的描述。它的核心目的,是为产品设计、开发、测试与验收各方提供一份唯一可对照的总体基线:产品"做什么、不做什么、由谁负责、按什么顺序交付",都应以本文档及其引用的权威文档为准,而不是依赖口头约定或零散页面。

    本文档的预期读者包括四类人群。第一类是产品与业务人员,包括产品经理与需求分析师,他们据此核对产品承诺与版本范围;第二类是最终用户代表,主要是测试工程师与测试负责人,他们据此理解 AI 生产与人工审核的分工边界、自己在审核与批准环节的职责,以及系统不会代替他们作出的决定;第三类是研发与架构人员,包括前端、后端、测试开发与运维工程师,他们据此确定实现范围、模块边界与必须满足的审核门禁;第四类是质量与治理人员,包括平台治理人员、审计人员与项目管理者,他们据此检查权限隔离、审计留痕与版本交付证据是否满足要求。

    在阅读方式上,本文档遵循三条约定:其一,凡涉及术语、实体、状态与枚举的定义,一律以 03 号术语表为唯一权威源,本文档不再重复裁决;其二,凡涉及产品范围、模块职责与版本承诺的陈述,均在相应小节末尾以来源标注形式给出出处,读者可据此回溯核对;其三,本文档只描述"做什么、不做什么、由谁负责",具体的界面呈现、接口契约与数据库设计由项目的 04、32、33 号等文档另行规定。

    1.2 范围

    本文档描述的产品名称为 QualityForge,定位为 AI 原生端到端测试平台。它面向测试工程师、测试负责人和测试平台治理人员,提供从测试依据、策略、计划、用例、自动化代码、执行、结果分析、Defect 到测试报告的端到端工作平台。产品的一级功能模块固定为八个:任务看板、知识库、测试策划与设计、自动化测试开发、测试执行、质量分析与缺陷、AI Agent 中心、平台管理;其中前六个为测试工作与产出物模块,后两个为管理控制模块。

    本需求说明书所覆盖的内容包括:产品总体描述与核心理念、八个模块的功能概要、六类内置 RBAC 角色及其使用场景、法规与安全等技术约束、外部依赖与假设,以及 V1、V2、V3 三个交付版本的需求分配。本文档不包含数据库物理设计、API 详细规格与 UI 视觉规范,这些内容分别由项目的 04、32、33 号等文档承担;本文档也不重新裁决术语、实体与契约定义,相关内容一律以 03 号术语表及其指定的权威源为准。

    产品"不做什么"由当前非目标明确界定,主要包括:

  • V0 阶段不交付可运行的 SaaS、分布式执行平台或完整 Agent 市场;
  • V1 阶段不承诺无人测试、全自动发布门禁或替代测试人员;
  • 不把 Workspace 复制成 Project 实体,不把 Skill 和 Agent 合并为同一概念;
  • 不因 AI 高置信度跳过正式产出物审核、外部写入批准或报告签署;
  • 在没有实测基线之前,不承诺固定的收益百分比、并发量、延迟或 AI 准确率。

    • 在适用边界上,本文档适用于以"项目(Workspace)加发布版本(Release)"为组织单元的测试团队,覆盖从需求导入到质量交付的完整测试生命周期;不适用于把本产品当作通用项目管理工具、独立 CI 分发平台或无人值守测试系统来使用。需要特别强调的是,任何版本均不取消正式产出物的人工审核、外部写入批准、报告签署、权限隔离与可追溯性,这是贯穿全部范围描述的总边界。

    综上,本文档界定的产品是一条"人工负责、AI 生产、证据可溯"的智能测试生产线,而不是替代测试人员的黑盒工具。

    （来源:02-PRD总纲 §3.2、§4;22-MVP版本规划v2.0 前言;05-功能模块重构方案 §2.1）

    第 2 章 总体描述

    本章从整体视角描述 QualityForge 的产品本质、功能构成、使用人群与约束环境,并给出需求的版本分配,为后续逐条功能需求提供全局背景。

    2.1 产品描述

    QualityForge 是一个 AI 原生端到端测试平台,面向测试工程师、测试负责人和测试平台治理人员,提供从测试依据、策略、计划、用例、自动化代码、执行、结果分析、Defect 到测试报告的端到端工作平台。产品的核心分工是:AI Agent 尽可能承担资料解析、草稿生成、代码生成、检查、执行、证据整理、分析和改稿工作;测试人员负责审核、批改、业务取舍、例外裁决和最终质量责任。

    在测试领域的整体版图中,QualityForge 不是"传统测试管理平台增加若干 AI 功能",而是一条以测试交付物为主线的智能测试生产线。平台围绕测试生命周期的正式产出物组织功能,而不是围绕 Agent、Skill、Runner、向量库等内部技术组件组织测试人员的日常工作;测试人员看到的是任务、产出物与审核队列,而非 AI 基础设施。它的组织单元是持续存在的项目(Workspace)与项目内一次有范围、有时间、有质量结论的发布版本(Release)。

    产品的核心理念是"AI 生产、人工负责"的人机协作与责任分层。AI 可以生成草稿、执行已批准的任务、组织证据与提出建议,但正式测试产出物必须由有权限的测试人员审核后生效;执行事实、AI 推断和人工决定在系统中清晰分层,任何一方都不能越界冒充另一方。这一理念同时体现在权限设计上:管理员身份不自动获得业务批准权,AI 永远不能作为正式批准人,正式批准是审核任务中的临时职责而非全局角色。

    围绕这一理念,产品设定四个核心目标:提高效率,减少需求阅读、测试设计、代码编写、结果整理和报告编制中的重复劳动;提高质量,通过来源追踪、AI 交叉检查、人工审核和确定性门禁减少遗漏与错误;保持人类责任,让 AI 生成和执行的同时,由测试人员对正式产出物承担最终质量责任;形成持续学习闭环,使执行结果、缺陷与复盘经验经审核后回流知识库,提高下一轮 AI 产出质量。同时,产品要求 AI 行为、权限、输入输出、成本和效果可观察、可评测、可降级。

    在产出物层面,产品确立八类正式测试产出物:测试策略、测试计划、测试用例、Web/API 自动化测试代码、结果分析、缺陷、测试报告与知识条目。每类产出物采用稳定根加不可变版本保存,发布与批准绑定精确内容摘要;每个业务实体只有一个唯一所有者模块,跨模块通过 ID、版本和事件引用,不复制可写真相源。总而言之,QualityForge 的本质是一台由人设定目标与把关质量、由 AI 承担生产与执行的测试生产线,其所有设计都服务于"可控、可溯、可评测"这一总要求。

    （来源:01-产品功能地图v2.0 §1、§4;02-PRD总纲 §1、§3.1;05-功能模块重构方案 §1、§3.2）

    2.2 产品功能

    产品目标态划分为八个一级功能模块,其中任务看板、知识库、测试策划与设计、自动化测试开发、测试执行、质量分析与缺陷六个模块承载测试工作与产出物,AI Agent 中心与平台管理两个模块承担管理与控制职能。下面按测试主链的顺序介绍各模块的功能概要。

  • 任务看板:测试人员与 AI 协作的任务控制中心,是默认首页与日常工作入口;统一承载工作项创建与拆解、AI 运行进度、待我审核、审核退回、阻塞与风险等队列,以及审核决议和效率指标,把"人操作多个工具"转变为"人管理一条 AI 测试生产线"。
  • 知识库:AI 工作的可信输入源和经人工确认的经验沉淀中心;管理需求文档、API 契约等原始来源、项目结构、来源快照与溯源、已审核知识与知识候选发布,保证 AI 基于项目事实工作并可持续沉淀经验。
  • 测试策划与设计:把项目目标、需求和风险转化为经审核的测试策略、测试计划、测试场景、用例与断言,形成"需求、规则、策略、计划、场景、用例、断言"的可信设计链。
  • 自动化测试开发:把批准的测试设计转化为可审查、可调试、可执行的 Web 与 API 自动化测试代码,以及配套的测试数据、Locator 与 Mock;AI 承担代码生成与检查,工程级代码审核与版本控制保留给人工。
  • 测试执行:冻结精确的资产、环境与契约版本,调度 Runner 执行并保存只追加的不可变结果、日志与证据;原始执行证据不可被分析结论反向改写,保证结果可观察、可复现。
  • 质量分析与缺陷:将原始执行证据转化为经测试人员确认的结果分析、失败聚类、Defect、测试报告与质量门禁,并把已审核知识回流知识库,构成"执行后处理"的完整闭环。
  • AI Agent 中心:管理 Agent、Skill、Workflow、Prompt、Trace、Eval 与权限治理;业务人员从任务看板使用 AI,管理员在治理台管理 AI,该模块不拥有业务产出物的最终批准权。
  • 平台管理:提供租户、用户、项目、发布版本、环境、密钥、模型、Runner、外部集成与审计的基础设施管理,并按身份、安全、模型、Runner、集成和审计划分子域。

    • 八个模块并非并列孤立,而是沿主链协作:知识库、测试策划与设计、自动化测试开发、测试执行、质量分析与缺陷依次衔接,已审核的知识、缺陷经验与质量模式再回流知识库形成反馈闭环;任务看板贯穿全流程负责编排与追踪,AI Agent 中心为各阶段提供受治理的 AI 生产与执行能力,平台管理为全平台提供身份、安全、模型、Runner、集成与审计支撑。模块之间遵循清晰的边界规则:任务看板拥有工作项但不拥有业务产出物正文,知识库唯一拥有来源与已发布知识,测试执行拥有原始执行证据,质量分析与缺陷的分析、缺陷与报告在审核前均为草稿或候选。

    在上述模块之上,产品以三条核心旅程定义端到端的价值交付方式。旅程 A 是从需求到可审核测试资产:导入来源、固化来源快照、AI 编译测试中间表示、生成策略/计划/用例草稿、执行确定性检查与独立验证,再由测试人员在审核任务中查看差异、证据与风险,批准或退回新版本。旅程 B 是从正式用例到自动化结果:选择已批准的用例版本,AI 生成 Web/API 自动化代码版本,经过代码检查与人工审核后创建冻结资产的执行计划,由 Runner 执行并只追加保存结果、日志与证据。旅程 C 是从失败到质量交付:AI 基于执行事实聚类并给出根因分析,人工审核结果分析,AI 生成缺陷与测试报告草稿,人工批准与签署后经单次外部写入批准同步缺陷,已审核知识回流知识库。三条旅程共同覆盖测试工作的主要价值场景,也决定了各模块的职责边界与审核控制点。

    综上,八个模块以明确的单一所有权和跨模块引用关系构成一条完整的智能测试生产线,任何模块都不替代另一模块的业务判断。

    （来源:01-产品功能地图v2.0 §2、§3;02-PRD总纲 §6;05-功能模块重构方案 §2.1、§4、§5.1、§5.2）

    2.3 用户特点与角色

    产品的使用主体是测试组织中的各类人员,他们对测试业务有专业理解,但对 AI 技术细节的需求被刻意隔离。测试工程师的日常职责是批改用例与代码、触发执行、分析和处理 Defect;测试负责人控制范围、风险和交付质量,审核策略、计划与报告并裁决关键例外;平台治理人员维护工作区与租户的运行条件。系统要求使用者理解"AI 生产、人工负责"的分工,能够区分执行事实与 AI 推断,并对正式产出物承担审核与批准责任;使用者无需掌握模型、技能或运行节点等 AI 基础设施细节,这些能力由治理人员在 AI Agent 中心统一配置与评测。

    系统采用作用域 RBAC,内置六类角色模板,如下表所示:

    角色典型作用域允许职责明确不自动拥有
    PlatformAdmin平台级平台基础设施、全局模板、租户生命周期和安全运维全租户测试内容、业务批准、报告签署
    TenantAdmin租户级成员、租户策略、配额、共享集成和角色委派Workspace 正式产出物批准
    WorkspaceAdmin工作区级Workspace 成员、环境、集成引用和常规配置报告签署、质量门禁豁免、跨 Workspace 访问
    TestLead工作区/资源级策略/计划总体把控、风险裁决、具备授权时审核RBAC/Secret 管理、自动越过四眼复核
    TestEngineer工作区/资源级编写/批改资产、触发执行、分析、处理 Defect默认批准自己的产出物、权限管理
    ViewerAuditor租户/工作区级授权范围只读、审计和证据查看写入、执行、批准、外部写入

    从使用场景看,六类角色围绕审核链协作:日常流程中,TestEngineer 从任务看板的待审核队列接收 AI 草稿,进行批改、批准或退回;TestLead 对策略、计划、报告与高风险结论进行总体审核和签署,处理阻塞与例外;ViewerAuditor 以只读身份查看审核链与执行证据,承担审计职能;三层管理员分别维护平台、租户与工作区的运行条件。需要强调的是,角色只是权限模板,不是硬编码判断依据;管理员身份不自动获得业务批准,正式批准人(Approver)与审核人(Reviewer)是审核任务中的临时职责,由审核策略、能力、作用域和职责分离共同计算得出,只能由具备相应能力的人类承担。此外,系统还存在 Service 与 Agent 两类机器身份,它们只能在授权交集内受限执行,永远不能作为正式批准人。

    综上所述,六类角色与两类机器身份共同构成产品的权限主体体系,其设计原则是:权限按作用域显式授予,业务批准专属人类,任何身份都不能凭借单一角色属性获得超出职责的权限。

    （来源:02-PRD总纲 §2;03-术语表Glossary §5;34-认证授权设计 §4.1、§5）

    2.4 约束

    产品在法规合规、安全、技术与运营四个方面受到如下约束。这些约束适用于所有版本,是需求实现与验收的强制前提。

    法规与合规约束:

  • 正式产出物、执行证据与审核记录必须可审计、可追溯,高价值动作写入只追加的授权决定与审计日志;
  • 敏感信息受保护:明文凭证与未脱敏个人信息不得进入 API 响应、日志、Trace、产出物或 Agent 上下文;产出物正文不得保存明文凭证或无限期有效的下载地址;
  • 数据保留与归档受管理:平台提供全局审计、数据保留与归档能力,废弃不等于删除,历史执行与审计仍引用原版本。

    • 安全约束:

  • 默认拒绝,认证成功不等于有权访问任何 Workspace;平台、租户、工作区、资源四级作用域显式授权;
  • 用户权限、机器权限、工作流节点权限、资源状态与环境条件取交集,任一拒绝即失败关闭;
  • 正式产出物批准是人类专属能力,受审核策略、能力、作用域与职责分离共同约束;
  • 高价值动作逐次重新授权;Secret 只保存引用并加密存储,明文不返回普通接口;
  • 多租户隔离采用行级安全作为纵深防御,应用事务注入租户上下文,上下文缺失或伪造即终止请求。

    • 技术约束:

  • 每个业务实体只有一个唯一所有者模块,跨模块通过 ID、版本和事件引用,不复制可写真相源;
  • 正式产出物以稳定根加不可变版本保存,发布与批准绑定精确内容摘要;执行结果、证据、审核决定、授权决定、审计日志与 Agent Trace 只追加;
  • 审核、执行与报告必须引用精确版本,禁止引用"当前最新版本";内容摘要变化使旧批准失效,下游引用随之失效;
  • 正式产出物必须通过确定性检查、独立验证和适用的人工审核,三层证据分别报告;确定性门禁失败不得用人工审核工单掩盖;
  • AI 自治默认受限代理;没有经批准且仍有效的评测校准记录时,分数不能驱动高价值自治;
  • 外部写入逐次审批、幂等执行并保留回执与冲突处理。

    • 运营约束:

  • V1 以单租户、单 Workspace 试点闭环为交付形态,不做多租户商业化运营、可视化工作流设计器、Skill 市场、多云弹性与 L3 自治;
  • 收益指标先建立人工基线,再按同类任务、同等复杂度和明确样本窗口比较;具体目标值必须在试点基线后批准,禁止沿用无测量方法的 80%、95% 等口号;
  • 版本交付必须列清范围、非目标、基线、测量方法、已知限制与恢复方案;版本门禁按产品、质量、安全、AI、运行、发布六类证据验收;
  • 覆盖率按实例、设计、可执行、严格有效、人工验收五类口径分别报告,分母互不推导、互不替代,禁止混用。

    • 上述约束共同决定了产品的实现底线:无论版本如何演进,可审计、可追溯、人工负责与失败关闭的原则均不可放宽。

    （来源:02-PRD总纲 §7、§8;05-功能模块重构方案 §3.4、§5.6;22-MVP版本规划v2.0 §7、附录C;34-认证授权设计 §1、§7、§8）

    2.5 假设和依赖

    本产品的需求建立在以下假设之上,若假设不成立,相应需求的有效性需要重新评估:

  • 项目当前尚无应用代码与生产数据,文档阶段只执行契约迁移,不执行数据库数据迁移;
  • 试点阶段存在一个真实但可控的 Workspace 与 Release,能够完成"来源、策略/计划/用例、Web/API 代码、执行、分析/Defect/报告、人工审核"的完整证据链;
  • 测试组织能够提供具备审核与批准权限的人力资源,持续承担正式产出物审核、外部写入批准与报告签署责任;
  • AI 生成物始终需要人工审核,任何版本都不假设无人测试或全自动发布;

  • 数据库:多租户隔离依赖数据库行级安全,应用使用非 owner、无 BYPASSRLS 身份连接,只读查询也须在显式事务内执行。

    • 上述假设与依赖构成产品外部环境的基本画像,相关能力未就绪时,相应需求应降级或推迟,而不应通过放宽安全边界来迁就。

    3.3 关键规则

  • 1. WorkItem 状态机：`BACKLOG → READY → IN_PROGRESS → PENDING_REVIEW → REWORK(→IN_PROGRESS)/APPROVED → DONE`，支持 `BLOCKED/CANCELLED`；DONE 为终态，重新工作须新建修订 WorkItem（05 §5.5.4）。
  • 2. `requiresReview=true` 的工作项不得从 IN_PROGRESS 直接进入 DONE；进入 PENDING_REVIEW 前必须存在带版本的 OUTPUT Artifact（05 §5.5.4）。
  • 3. 进入 APPROVED 前必须存在已解决的 ReviewTask 和审核人签名；固化的 Artifact 版本必须与审核目标版本一致，并发修改则审核失效并回到 PENDING_REVIEW（05 §5.5.4）。
  • 4. BLOCKED 必须记录结构化原因、责任方和恢复条件；用户主动暂停 = BLOCKED + blocked_reason=USER_PAUSED，状态机不新增 PAUSED（裁决 2026-08-14 B4）。
  • 5. ReviewTask 绑定 `artifactType/artifactId/artifactVersionId/contentDigest/policyType`；审核动作 APPROVE/REQUEST_CHANGES/REJECT 且只追加；审核人不得批准自己无权批准的产出物，AI Agent 永远不能作为正式批准人（10-PRD §4；05 §5.5.7）。

  • 8. 最终允许动作取"用户 RBAC ∩ Agent 权限 ∩ Workflow 节点权限"的交集，任一层拒绝即 fail-closed（05 §5.5.10）。

    6.3 关键规则

  • 2. 脚本身份与代码版本拆分：AutomationScript（稳定身份）→ AutomationScriptVersion（不可变代码版本）→ 用例绑定/检查运行/ReviewTask/执行引用；MANAGED 与 GIT 只能有一个权威代码源，分支名和"最新提交"不得作为正式执行证据（05 §5.8.1/§5.8.4）。
  • 3. 试运行沙箱量化验收口径（裁决 B2-8）：进程非 root 运行、工作目录只读挂载、默认零外网（网络命名空间禁出站）、单次执行超时上限（默认 120s）、产出目录白名单；每条均有可执行检查命令（13-PRD §3）。
  • 4. 执行只接收已批准脚本版本和完整依赖/运行时指纹；运行时临时修复产生候选新版本，不覆盖已冻结版本（13-PRD §3）。
  • 5. 代码正文和 Secret 分离；脚本只引用 secretRef，日志/Trace 中不得出现明文（13-PRD §3）。
  • 6. API 代码绑定 APIContractVersion；契约变化触发影响分析而不是静默重生成覆盖；用例新版本发布后既有脚本不会自动宣称继续有效（05 §5.8.5）。
  • 7. Locator 自愈默认只在单次运行尝试；正式资产变更走 Diff 和 ReviewTask（13-PRD §3）。
  • 8. 强制检查不可人工备注绕过：Secret 扫描、静态检查、隔离试运行等阻断项失败时拒绝批准；例外必须走单独、高权限、限时且可审计的豁免流程（05 §5.8.8）。
  • 9. 正式执行默认只能执行 PUBLISHED 版本；PENDING_REVIEW 版本仅限隔离试验 WorkItem 中运行，结果标记 EXPERIMENTAL，不进入正式质量报告或发布门禁（05 §5.8.11）。
  • 10. Git 模式：仓库凭证归平台管理 Integration/Secret；AI 创建分支、提交、推送或 PR 属于外部写入，必须遵循 EXTERNAL_WRITE 策略（05 §5.8.9）。

    7.1 模块定位

    本模块将批准后的测试资产转化为完整、可观察、可复现的执行证据，以可复现、可授权、可观察的方式运行人工/自动化测试并保存不可变事实。它拥有 ExecutionPlan、Task、Result、Log 和 Evidence，不拥有对失败的业务解释、Defect 或报告结论。

    7.3 关键规则

  • 1. ExecutionTask 状态与业务结论分离：`PENDING/QUEUED/RUNNING/COMPLETED/FAILED/CANCELLED/TIMED_OUT/BLOCKED`；COMPLETED 表示任务调度与采集完成，用例业务结论只看 ExecutionResult 的 `PASSED/FAILED/SKIPPED/ERROR/INCONCLUSIVE`（14-PRD §3）。
  • 2. `FAILED` 表示被测行为未满足断言；`ERROR` 表示环境、脚本、Runner 或平台未完成有效验证；二者不可合并（14-PRD §3）。
  • 3. 重跑创建新 Batch/Task attempt，不覆盖旧结果（14-PRD §3）。
  • 4. ExecutionPlanVersion 必须固定 TestCaseVersion、AutomationScriptVersion、ExecutionContractBaseline（由 APIContractBaseline 复制精确版本+运行时映射/认证/脱敏快照，裁决 2026-08-14 批次二）、Environment 和数据/Mock/Locator 等引用及摘要（14-PRD §3）。
  • 5. ExecutionContractBaseline 创建后不可变；执行前若基线引用已撤销、权限失效或必需凭证不可用，ExecutionTask 转 `BLOCKED`，不得自动切换到"最新版"（05 §5.10.7）。
  • 6. ResultAnalysis 只能引用 ExecutionResult，不能反写其状态或正文（14-PRD §3）。
  • 7. 未检查不能计为通过，`INCONCLUSIVE` 不能被报告为契约一致（裁决 B2-2）；TestReport 必须同时展示执行基线摘要、已检查 Operation 数、偏差数、未检查数和不可判定数（05 §5.10.8）。
  • 8. 暂停 = status=BLOCKED + blocked_reason=USER_PAUSED，语义由原因码承载、状态机不新增 PAUSED（裁决 B2-4，字段落 33 t_execution_task）。
  • 9. Runner 失联：租约到期后按策略创建新 attempt；原 attempt 标记 ERROR 并保留证据；Runner 缺少所需能力时任务在执行前 BLOCKED，不得运行后静默降级（05 §5.8.11）。

    第 8 章 质量分析与缺陷（Quality Analysis & Defects）

    8.1 模块定位

    本模块把原始结果转化为经测试人员确认的分析、Bug、报告和质量结论，形成"执行后处理"闭环，同时区分原始证据、AI 推断、人类确认和最终发布结论；减少失败分析、提 Bug 和报告整理的重复劳动，避免 AI 推断污染执行事实或直接影响外部系统/发布。

    正式产出物：ResultAnalysis、Defect（DefectVersion）、TestReport、CoverageReport。

    能力需求要点人工控制

    流水线关联触发、运行、回调和回执外部写入与触发范围受授权

    （来源：15-PRD-SkillCenter §3）

    8.3 关键规则

  • 1. ResultAnalysis 与 ExecutionResult 分离；分析可被推翻但结果事实不被改写；AI 推断必须标记为 `INFERRED`，不得伪装为执行事实（15-PRD §4；05 §5.9.5）。
  • 2. FailureCluster 只聚合失败，不存外部缺陷键，不代表缺陷成立；聚类拆分、合并或重新计算不得改写已批准 DefectVersion 的证据快照（05 §5.9.2）。
  • 3. Defect 稳定根和不可变版本分离于生命周期状态；未存在批准版本时不得进入 `OPEN`，更不得外部提交；REJECTED/DUPLICATE 均须保存理由（05 §5.9.3）。
  • 4. 每个 DefectSyncAttempt 绑定 DefectVersion、Integration、操作、payloadDigest、approvalId 和幂等键；所有正式缺陷外部写入均须在调用前获得人工 `EXTERNAL_WRITE` 批准，不得通过租户开关降级为 AI 自主提交（05 §5.9.8）。
  • 5. V1 手工外部同步同样创建 DefectSyncAttempt 记录并绑定批准（执行者为人，裁决 B2-4），不绕过 EXTERNAL_WRITE 契约；回执与幂等键照常落库（15-PRD §4）。
  • 6. TestReport 必须固定 scopeSnapshot 和 executionSnapshot，签署后内容不可变；更正产生新版本；必须披露契约检查摘要（裁决 B2-2）（15-PRD §4）。
  • 7. CoverageReport 是执行覆盖率正式产出物（裁决 B2-1）：按批准的分母口径与快照生成；设计覆盖分析（需求→用例映射）归第 5 章测试策划与设计，两概念不共用实体（15-PRD §4）。
  • 8. AI 建议不能自动放行/阻断发布；确定性门禁规则也必须版本化和可解释；质量门禁依赖不可用时返回不可判定，不能默认放行（15-PRD §4/§6）。
  • 9. RESOLVED 只表示声称已修复；转 VERIFIED 必须关联 `REGRESSION_VERIFICATION` 证据（Release、环境、用例版本、脚本版本、ExecutionResult）并由获授权人员确认；AI 只能提出"建议验证通过"（05 §5.9.9）。

  • 1. Agent 最终权限 = 发起人当前 RBAC ∩ AgentVersion 权限 ∩ Workflow 节点权限 ∩ WorkItem/环境/集成策略 − 显式 Deny − humanOnly；任一层缺失即拒绝（16-PRD §3）。
  • 2. 默认：网络 deny-all、Secret 空、外部写入 deny、正式资产写入/批准 deny、Subagent 委派深度受限；Agent 不得以用户拥有的批准权代表用户作 ReviewDecision（16-PRD §3）。
  • 3. Skill 是原子能力，Agent 是职责/权限/工作流边界；不得按"一项 Skill 配置一个 Agent"机械映射（03-术语表 §11）。
  • 4. 无有效校准记录时（21 号 §4 + 裁决 B2-3），模型分数只排序、不驱动自治；校准记录过期、评测跌破门槛、误放/误阻超警戒线时按 21 号 §6.1 降级触发，回退并重建校准（16-PRD §6）。
  • 5. Trace 缺失或 checker 异常：不得给 PASS，不得进入正式审核的"可批准"状态（16-PRD §6）。
  • 6. 模型/Prompt/Skill/Workflow 版本变化：原校准记录失效，回退 L1 并重评（16-PRD §6）。
  • 7. 独立平台评审 Agent（qf-platform-reviewer）不在 agents.json 和 Supervisor 委派列表内，不接受生产 Agent 派工，也不能反向调度生产 Agent（裁决 2026-08-14 批次二）。
  • 8. 主流程：WorkItem + 用户授权 → 锁定版本 → 结构/权限预检 → 节点执行与 Trace → 确定性检查/独立验证（INDEPENDENT_VERIFY 介入点，构成三层证据第二层）→ 到 human checkpoint 创建 ReviewTask 并暂停 → 人工决定后由业务应用服务发布（16-PRD §5）。

    AC-01 Skill 与 Agent 不混同

  • Given `coverage-analyzer`是Skill；
  • When Workflow调用它；

    （来源：20-非功能需求 §1；22-MVP版本规划 §6）

    12.1 性能与容量

    本节覆盖 Web、REST API、AI 步骤、执行调度和证据报告五类对象的性能测量义务。性能需求的核心不是写死某个数字，而是把"测量—基线—批准"固化为版本门禁：V1 开发前建立单 Workspace 试点负载模型，每个版本的目标值以压测报告批准，不从旧规划继承任何未经证明的数字。

    NFR-001 性能目标批准门禁 — 系统应在每个版本交付前，基于已批准的工作负载模型完成压测并形成基线报告；描述：任何延迟、吞吐、容量或并发目标值必须附测量方法、环境、数据规模与统计口径，经项目负责人批准后方可作为该版本交付门禁，未经批准的数字不得用于宣称版本达标。验收：版本交付评审包含压测报告与批准记录；凡无基线或工作负载的目标（如并发数、P95 延迟）一律标记为不可验收（对齐 20 号 AC-04）。

    （来源：20-非功能需求 §1、§2、§10 AC-04）

    NFR-002 API 响应延迟 — 系统应在批准的试点负载模型下，使 95% 的 API 请求在批准的目标延迟内响应（候选目标如 500ms，须经基线批准后生效），并按 P50/P95/P99 分层测量；描述：延迟统计按 operationId、读写类型、数据量与租户维度分层，与吞吐、错误率、饱和度一并报告。验收：压测报告含 P50/P95/P99、吞吐、错误率、饱和度四项及分层明细，经批准后归档，超预算触发告警。

    （来源：20-非功能需求 §2）

    NFR-003 Web 前端性能 — 系统应测量并建立 LCP、INP、CLS、首个可操作时间和页面错误率的基线；描述：测量按页面、设备、网络、冷热缓存分层，核心审核工作台不得因前端资源加载阻塞人工审核流程。验收：每个版本提供分层基线数据，核心页面无未解释的布局偏移与输入延迟回归。

    （来源：20-非功能需求 §2）

    NFR-004 AI 步骤延迟与成本 — 系统应按 interventionKey 及模型、Prompt、Skill、Workflow 版本分层测量 AI 步骤的首个结果延迟、完整结果延迟、成功成本、超时率和人工接管率；描述：AI 步骤指标不与普通 API 指标混算，模型版本变化后必须重新测量。验收：AI 步骤报告按介入点与精确版本分层，超时与接管率触发熔断或降级条件（见 12.8）。

    （来源：20-非功能需求 §2；21-AI介入点降级矩阵 §4）

    NFR-005 执行调度与容量 — 系统应测量执行调度的排队时间、启动时间、有效并发与资源利用率，并建立容量基线与错误预算；描述：测量按 Runner 能力、测试类型和环境分层；队列积压、Runner 失联与资源不足必须可观测并可触发降级。验收：容量报告含分层基线，错误预算消耗超限时产生告警并可溯源到调度事件。

    （来源：20-非功能需求 §2、§3）

    本节小结：性能与容量需求以"先基线后批准"为总闸，五类对象各有必测指标与分层维度；任何目标值缺失测量证据即不可验收，这一原则同样适用于后续所有质量类别。

    （来源：20-非功能需求 §1、§2）

    12.2 安全保密

    本节覆盖认证、授权、多租户隔离、Secret 保护、Agent 安全、供应链安全、数据保护与安全测试八项。总体原则是默认拒绝、纵深防御、fail-closed：认证成功不等于有权访问任何 Workspace，管理员身份不自动扩散为业务权限，任一授权环节缺失即拒绝。

    NFR-006 认证与身份管理 — 系统应支持 OIDC/OAuth2 授权码加 PKCE（必要时启用 MFA）的人工身份认证，以及短时服务令牌或 mTLS 工作负载身份的服务认证；描述：JWT 令牌必须携带并校验 iss、sub、aud、iat、exp、jti 与身份类型，用户离职或禁用后立即失效；本地开发 Profile 使用随机盐 scrypt 存储密码、HttpOnly 与 SameSite=Strict Cookie、双提交 CSRF 与登录限流。验收：认证测试覆盖令牌伪造、过期、audience 不匹配与重放场景，均被拒绝；WebSocketTicket 一次性绑定资源且不扩大权限。

    （来源：34-认证授权设计 §2、§10 AC-05；20-非功能需求 §5）

    NFR-007 授权默认拒绝与审核授权 — 系统应按平台、租户、Workspace、资源四级作用域实施 RBAC，权限含 resourceType、action、scopeTypes、riskLimit、conditionSchema 与 humanOnly 标记；描述：正式产出物批准、报告签署、外部写入批准、门禁放行与豁免、Skill/Agent/Workflow 发布均为人类专属能力；Approver 是 ReviewTask 中的临时职责而非全局角色，每次审核绑定 artifactType、artifactId、artifactVersionId 与 contentDigest，服务端按"验证身份—重读版本摘要—解析策略—计算绑定—校验职责分离—执行 blockingChecks—追加决定"七步算法批准。验收：跨租户访问、IDOR、角色或作用域提升、自批、陈旧批准（STALE_ARTIFACT_VERSION）等负向用例全部被拒绝并记录 DENY；管理员与 Agent 均不能绕过该算法。

    （来源：34-认证授权设计 §4、§5、§10 AC-01/AC-03；05-功能模块重构方案 §5.11）

    NFR-008 多租户数据隔离 — 系统应在每个事务内以参数化方式注入已验证的租户与主体上下文，所有租户表启用并强制行级安全（ENABLE 且 FORCE RLS），应用连接角色非表 Owner、无 BYPASSRLS；描述：上下文缺失、格式错误或与授权决定不一致时请求终止；连接池归还前事务结束，禁止会话级 SET 造成串租户；跨租户资源存在性不得通过 404/403 差异泄漏。验收：跨租户失败关闭测试（20 号 AC-01）在各层通过：服务、API、数据库均拒绝且不泄漏资源存在性，审计记录脱敏事件；RLS 配置随迁移验收测试执行。

    （来源：34-认证授权设计 §7、§10 AC-04；33-数据库Schema设计 §1、§13）

    NFR-009 Secret 保护 — 系统应将主密钥存放于 KMS/Vault，数据以 AES-256-GCM 或经评审的 AEAD 双信封加密，数据库只保存密文、nonce、keyVersion 与访问元数据；描述：Secret 通过引用使用，明文只存在于受控执行服务的短时内存，元数据读取与明文使用为不同权限；API 永不返回 secretValue 或 encrypted_value，密钥材料不写入普通配置表，支持按租户与 Workspace 轮换并记录使用审计。验收：Secret 泄漏与越权读取用例全部失败关闭，任何 API 响应、日志、Trace、产出物与 Agent 上下文均不出现明文密钥。

    （来源：34-认证授权设计 §8、§9；20-非功能需求 §5；33-数据库Schema设计 §1）

    NFR-010 Agent 与机器身份安全 — 系统应使 Agent 权限等于发起用户当前权限、AgentVersion 允许权限、WorkflowVersion 节点权限、WorkItem 授权快照与环境策略的交集，再减去显式 Deny 与 humanOnly 能力；描述：Agent 默认零网络、无 Secret、无外部写入，每次工具调用前重新校验，策略或发起人权限变化时令牌撤销或运行熔断；Agent 不得继承平台或租户管理员宽泛权限，不得持久化用户令牌或 Secret，不得自行扩大委派深度，不得提交 ReviewDecision。验收：Agent 尝试批准、越权工具调用、权限扩大请求均被拒绝并转 BLOCKED 或 PENDING_REVIEW，审计可追溯（对齐 21 号 AC-01、34 号 AC-02）。

    （来源：34-认证授权设计 §6、§10 AC-02；21-AI介入点降级矩阵 §1）

    NFR-011 供应链安全 — 系统应锁定依赖版本、维护 SBOM 与签名来源，执行 SAST/SCA 扫描，并对恶意 Skill 实施隔离；描述：AutomationScript 与 Skill 的引入须经过静态安全检查与人工发布审核；Runner 在隔离环境中执行，默认零外网出站。验收：供应链安全测试（依赖投毒、恶意 Skill、任意代码执行）通过；未经安全扫描与审核的 Skill 或脚本不得进入可执行状态。

    （来源：20-非功能需求 §5；QF-RSK-012；05-功能模块重构方案 §5.8.8）

    NFR-012 数据保护与隐私 — 系统应对证据执行分类分级、最小采集、脱敏、访问控制与保留删除策略；描述：日志与 Trace 不得记录令牌、Secret、隐藏思维链或不必要的敏感正文，仅保留决策摘要与引用；测试数据按敏感度分级并支持生成、脱敏与清理策略；真实 LLM 接入前的出站数据评测与脱敏策略未完成时，不得将测试数据送出受控边界。验收：证据脱敏与访问控制用例通过；对越权读取敏感证据的请求全部拒绝并审计。

    （来源：20-非功能需求 §5、§7；33-数据库Schema设计 §8；QF-RSK-013）

    NFR-013 安全测试基线 — 系统在每个里程碑提供安全测试证据，至少覆盖跨租户、IDOR、角色或作用域提升、自批、陈旧批准、Secret 泄漏、SSRF 与出站绕过、提示注入、恶意文件和依赖供应链十类场景；描述：M1 准出前须通过 031 号整改定义的六条负向用例（悬空引用、跨租户、审核绑定漂移、溯源断链、环依赖、跨版本绑定）与"禁止 AI 自批"负向用例。验收：安全测试报告逐用例记录结果与证据位置；任何用例失败不得以文档说明替代运行时证据。

    （来源：20-非功能需求 §5；V1里程碑执行对照表 §5 准出压力；QF-REQ-031）

    本节小结：安全保密需求以"默认拒绝、人工专属、失败关闭、不泄漏存在性"为四根支柱，身份、授权、隔离、Secret、Agent、供应链、数据与测试八项互为纵深；任何高价值动作都必须逐次重新授权并落不可变记录。

    （来源：34-认证授权设计 §1；20-非功能需求 §5）

    12.3 可用性与可靠性

    本节定义可用性测量口径、外部依赖韧性、取消重放幂等、消息传递、恢复演练与用户可用性六项。可用性不以"进程存活"为口径，而以用户旅程的 SLI 为度量。

    NFR-014 可用性 SLI 口径 — 系统应按用户旅程定义 SLI（如草稿生成可用、审核提交可用、执行结果回传可用），不以进程存活替代可用性；描述：每个 SLI 配置测量窗口、统计口径与错误预算，目标值在部署拓扑与业务等级明确后批准。验收：SLI 定义表与错误预算配置经批准归档，版本报告按 SLI 口径汇报而非进程存活率。

    （来源：20-非功能需求 §3）

    NFR-015 外部依赖韧性 — 系统应对外部 LLM、Defect、Git、CI、KMS 与 Runner 设置超时、预算、熔断和明确降级策略，不无限重试；描述：LLM 持续超时且备用策略不可用时应停止自动节点、保留草稿与 Trace，将 WorkItem 置为阻塞或回退低自治等级，不得发布正式资产。验收：外部依赖故障注入演练（LLM 限流、集成超时、KMS 不可用）均按预定降级路径执行，无静默继续与无限重试。

    （来源：20-非功能需求 §3、§10 AC-02）

    NFR-016 取消、重放与幂等 — 系统应支持 WorkItem、ExecutionTask 与 AgentSession 的取消、重放和幂等；描述：重放创建新的 attempt 并保留旧证据，重试受预算与幂等约束（V1 默认一次受控重试），超过边界后才转 BLOCKED；取消他人运行需相应权限。验收：取消、超时与受控重试用例通过，重放后证据链可追溯到原失败记录，无覆盖历史事实。

    （来源：20-非功能需求 §3；05-功能模块重构方案 §5.5.12；QF-REQ-043）

    NFR-017 消息传递可靠性 — 系统在采用至少一次传递时，消费者应以稳定事件 ID 或幂等键去重；描述：状态改变在本地事务内写业务数据与 Outbox 候选事件，消费者幂等处理，事件包含 eventId、sequence 或 offset、租户与 Workspace、资源与版本、occurredAt 与 traceId。验收：消息重投与乱序场景下业务状态不重复推进，去重效果有测试证据。

    （来源：20-非功能需求 §3；31-系统架构设计 §3）

    NFR-018 故障恢复与演练 — 系统应定期演练 Runner 失联、队列积压、数据库故障、对象存储故障、LLM 限流与外部集成超时六类场景；描述：RTO/RPO 在部署拓扑与业务等级明确后批准，V0 阶段只定义恢复步骤与证据要求，不预设数值承诺。验收：演练记录含场景、处置步骤与恢复证据；恢复后新 attempt 引用原失败记录，历史证据完整保留。

    （来源：20-非功能需求 §3）

    NFR-019 用户可用性与无障碍 — 系统应使核心任务、审核、Diff、结果与错误流程支持键盘操作、语义化标签、焦点管理与非颜色提示；描述：对 AI 结论展示证据、限制、版本、可修改内容与人工责任，不使用误导性的"AI 已批准"表述；长任务显示阶段、预计或已用时间、取消、降级与恢复条件。验收：V1 以 WCAG 2.2 AA 检查清单和真实用户任务测试建立基线，审核工作台无障碍缺陷不迟于该版本关闭。

    （来源：20-非功能需求 §9）

    本节小结：可用性与可靠性以用户旅程 SLI 为度量、以外部依赖熔断为韧性、以取消重放幂等为恢复底座、以演练为持续验证；可用性目标数字同样遵循先基线后批准。

    （来源：20-非功能需求 §3）

    12.4 可维护性

    本节覆盖契约驱动、兼容代际、数据库可维护与代码文档质量四项，目标是让系统在版本演进中保持契约可解析、迁移可重跑、变更可追溯。

    NFR-020 契约驱动开发 — 系统应以 OpenAPI 与事件契约为外部契约的唯一来源，operationId 全局唯一，Schema 引用可解析；描述：核心链（策略、计划、用例、执行、分析）共 41 个路径、53 个 operation 的响应与请求 schema 必须在目标版本落地为具体定义，不得引用 Generic 或未定义块，并可通过 openapi-spec-validator 校验。验收：核心链 operation 全部为具体 schema 且 validator PASS，无 Generic 响应残留，运行时 operation 数与 KNOWN_DEFERRED 台账对账一致。

    （来源：20-非功能需求 §8；V1里程碑执行对照表 §4；QF-REQ-005）

    NFR-021 兼容代际管理 — 系统应使 API 兼容代际与产品版本分离，首个产品交付代际为 /api/v1；描述：破坏性变更遵循 32/37 号迁移规则，版本计划不得以兼容性为由取消人工审核、外部写入批准、报告签署、权限隔离与可追溯性。验收：代际变更清单、迁移规则与回退方案随版本发布，未申报的破坏性变更在契约扫描中被拦截。

    （来源：22-MVP版本规划 §1；20-非功能需求 §8；31-系统架构设计 §9）

    NFR-022 数据库可维护性 — 系统应通过 Alembic 迁移管理 schema，迁移支持空库升级、重跑、降级或恢复并附带 RLS 测试；描述：迁移由 qf_owner 角色执行，运行期严禁使用 qf_owner 或 postgres 连接；目标 DDL 在 Gate D 采用直接替换，不编写虚构的数据迁移成功声明。验收：迁移在空库与既有库上可重复执行，回滚后数据与权限一致，RLS 策略测试随迁移通过。

    （来源：20-非功能需求 §8；33-数据库Schema设计 §1、§14）

    NFR-023 代码与文档质量 — 系统代码应通过类型检查、lint、单元、契约、集成与 E2E 分层验证；描述：测试覆盖率只作为风险信号，不设脱离代码类型的统一百分比；文档变更须同步术语、领域、API、DB、PRD 与治理文档并追加 CHANGELOG 条目。验收：CI 中分层检查全绿，文档变更与 CHANGELOG 一一对应，权威源无不可解释冲突。

    （来源：20-非功能需求 §8；QF-REQ-002）

    本节小结：可维护性以"契约唯一、代际分离、迁移可重跑、变更留痕"为验收主线，静态文档通过不等于运行时验证，V1 需 Spike、迁移、契约与 E2E 证据。

    （来源：31-系统架构设计 §10）

    12.5 可扩展性

    本节定义架构演进、Runner 扩展、数据扩展与契约扩展四项。扩展性不追求一步到位的微服务，而是按实测负载分阶段演进。

    NFR-024 架构演进路径 — 系统应采用模块化单体起步，按负载分离 Agent Worker 与 Runner，再基于实测瓶颈拆服务、建立弹性资源池与故障域；描述：V1 采用 Modular Core 加 Agent Worker、Runner 与 PostgreSQL、对象存储，按需引入 Redis；模块边界是代码与数据 Owner 边界，不等同于必须独立部署的微服务。验收：部署演进表（V0、Stage 4 本地、V1、V2、V3）与负载证据一致，任何拆分决策附实测依据。

    （来源：31-系统架构设计 §9）

    NFR-025 Runner 与执行扩展 — 系统应支持 Runner 注册、能力声明、租约、心跳与资源池分配；描述：V1 提供单资源池 Runner 并支持 DRAINING 状态，V2 支持多 Runner 调度、失败恢复与资源配额，V3 支持弹性与区域隔离；执行环境为隔离容器或沙箱，被测网络与代码执行为高风险边界。验收：Runner 心跳丢失检测、租约过期、能力不足拒绝分配均有运行时证据。

    （来源：31-系统架构设计 §6；33-数据库Schema设计 §3；QF-REQ-039）

    NFR-026 数据扩展 — 系统应在真实查询与数据规模证据建立后，再决定向量、JSONB 与全文索引，不预设所有 JSONB 字段均需 GIN 索引；描述：正文与制品保存对象存储引用与 digest，复杂受控结构使用 JSONB，检索层使用 PostgreSQL 加 PGVector。验收：索引决策附查询模式与数据量证据，检索性能随数据增长有测量记录。

    （来源：33-数据库Schema设计 §1、§13.4；31-系统架构设计 §1）

    NFR-027 契约扩展与三方对账 — 系统新增介入点、operation 或表时应保持 21 号介入点矩阵、32 号 API 与 33 号数据库三方对账一致；描述：新集成通过 IntegrationConfig 注册并受出站 allowlist、操作、作用域与逐次授权约束；AI 自治等级变更必须版本化、审批并支持立即回退。验收：三方对账表随 L1 扫描基线维护，新增项无未闭合对账差异（对齐 QF-REQ-036）。

    （来源：QF-REQ-036；21-AI介入点降级矩阵 §3；34-认证授权设计 §8）

    本节小结：可扩展性以实测驱动为原则，架构、Runner、数据与契约四层均不得在缺乏证据时提前扩容或承诺规模数字。

    （来源：31-系统架构设计 §9；20-非功能需求 §1）

    12.6 合规与审计

    本节覆盖审计完整性、保留导出、数据出域与外部写入合规四项，目标是让每一次高价值动作都可复核、可导出、可追责。

    NFR-028 审计完整性 — 系统应对正式批准或发布、外部写入、执行启动或取消、Secret 使用、角色或策略变更、Agent 高风险工具调用、门禁放行或豁免记录只追加的 AuthorizationDecision；描述：记录至少包含主体、身份类型、动作、资源及版本与摘要、适用策略版本、RoleBinding 快照、条件结果、ALLOW 或 DENY、原因码、traceId 与时间；不得记录 Secret、完整令牌或不必要的敏感正文。验收：审计链不可篡改，任一决策可回溯到策略版本与绑定快照；审计链中断触发安全高优先级告警。

    （来源：34-认证授权设计 §9；20-非功能需求 §7）

    NFR-029 记录保留与导出 — 系统应按证据分类分级配置保留与删除策略，删除默认归档，存在历史引用时阻止物理删除并返回依赖信息；描述：审计日志支持保留、导出与受限查询，平台运维跨租户查询走专用、审计、最小化的后台流程。验收：归档与依赖拦截用例通过，导出内容经脱敏校验。

    （来源：20-非功能需求 §5、§7；33-数据库Schema设计 §1；34-认证授权设计 §7）

    NFR-030 数据出域合规 — 系统在接入真实 LLM 前必须完成数据出站评测、脱敏与区域策略评估，未通过评测前保持确定性 Provider 或 L0 模式；描述：LLM 配置含数据区域、路由策略、配额与预算，出站目标受 EGRESS_DENIED 错误码保护。验收：接入准入报告含出站评测、脱敏验证与区域策略证据，无评测不得接入（对齐 QF-RSK-005、QF-RSK-013）。

    （来源：QF-RSK-005/013；32-API规范 §错误码；21-AI介入点降级矩阵 §2 L0）

    NFR-031 外部写入合规 — 系统对 Defect、代码仓库、质量门禁豁免等外部写入默认拒绝，每次写入须经独立人工批准并绑定固定 payload；描述：V1 手工同步同样落 DefectSyncAttempt 记录、批准记录与回执；同步操作携带幂等键与 payloadDigest，冲突返回 EXTERNAL_SYNC_CONFLICT，不得假报成功。验收：外部写入无批准即拒绝；手工同步记录可逐条回溯到批准、负载摘要与回执（对齐 QF-REQ-025、QF-RSK-010）。

    （来源：QF-REQ-025；QF-RSK-010；21-AI介入点降级矩阵 §1；32-API规范 §错误码）

    本节小结：合规与审计以"只追加、可导出、出站受控、外部写入逐次批准"为底线，任何版本演进均不得削弱。

    （来源：22-MVP版本规划 §1；05-功能模块重构方案 §5.13.6）

    12.7 可观测性

    本节定义全链路关联、遥测采集、告警与失败分类四项。可观测性是 AI 治理与审计的基础设施，所有请求、工作项、会话与外部尝试都必须可关联、可回放。

    NFR-032 全链路关联 — 系统应使所有请求、WorkItem、AgentSession、ExecutionTask 与外部 SyncAttempt 使用 traceId 或 correlationId 贯通关联；描述：traceId 贯穿 API、WorkItem、Agent、Runner 与外部 attempt，跨域引用固定 ID、versionId 与必要的 contentDigest。验收：任一报告或 Defect 可从结果反查输入资料、策略计划、用例、代码版本、执行结果、分析、审核记录与 Agent Trace。

    （来源：20-非功能需求 §7；31-系统架构设计 §8；05-功能模块重构方案 §5.5.12）

    NFR-033 遥测采集范围 — 系统应采集结构化日志、指标与分布式 Trace，并记录 Agent、Skill、Prompt、Workflow 的精确版本、工具调用、输入输出摘要与 verdict；描述：授权 ALLOW 或 DENY、ReviewDecision、版本发布、Secret 使用与外部回执均须入遥测；不持久化隐藏思维链。验收：采集清单与 20 号 §7 至少一致，采样与保留策略经批准。

    （来源：20-非功能需求 §7；31-系统架构设计 §5）

    NFR-034 告警与安全事件 — 系统告警阈值必须基于基线与错误预算批准；描述：跨租户访问、humanOnly 越权、Secret 外泄与审计链中断始终作为安全高优先级事件，数据质量、队列、Runner、成本、错误预算与降级状态纳入常规告警。验收：告警规则清单附阈值批准记录，安全事件可实时触达处置角色。

    （来源：20-非功能需求 §7）

    NFR-035 失败分类 — 系统应对失败至少区分业务 FAIL、平台或环境 ERROR、权限 DENY、人工 BLOCK 与 CANCEL 或 TIMEOUT 五类；描述：分类进入 Trace 与指标口径，不得混淆业务失败与环境错误；降级原因码、版本与恢复条件随记录保留。验收：故障注入样本的分类准确率有测试证据，报告与看板按分类口径展示。

    （来源：31-系统架构设计 §8；21-AI介入点降级矩阵 §6.2）

    本节小结：可观测性以"贯通、分层、批准、分类"为四要素，既是运维能力也是 AI 治理证据链的一部分。

    （来源：20-非功能需求 §7；31-系统架构设计 §8）

    12.8 AI 自治与降级

    本节是 AI 治理的非功能底座，对应 21 号矩阵的六项硬性要求。产品目标不是让 AI 替测试人员作最终质量判断，而是让 AI 承担可委派的收集、生成、执行、分析与整理工作，人工负责审核、批改、例外处理与全局质量控制。

    NFR-036 人工硬门不可绕过 — 系统应保证八类正式产出物（策略、计划、用例、自动化代码、结果分析、Defect、测试报告、知识条目）不得被 AI 自动批准或发布；描述：AI 运行不得拥有 ReviewDecision，Workflow 尝试直接置 APPROVED 或 PUBLISHED 时授权被拒绝并创建或保留 ReviewTask；TenantAdmin 开关不能绕过底线。验收：对"禁止 AI 自批"的负向用例（含独立验证裁决表 t_verify_verdict 落点）在 M1 准出前全绿（对齐 21 号 AC-01/AC-02）。

    （来源：21-AI介入点降级矩阵 §1、§7 AC-01/AC-02；V1里程碑执行对照表 §5）

    NFR-037 自治等级受控 — 系统应使新介入点默认 L1，已有固定输入输出契约、最小权限、可观测 Trace、失败回滚与人工硬门的介入点可默认 L2；描述：L3 只有在代表性 Golden Set 达到经批准质量门槛，并完成影子运行、误放误阻评估与成本延迟基线后才可上调；等级变更必须版本化、审批、记录 AuthorizationDecision 与 AuditLog 并支持立即回退。验收：介入点矩阵的默认等级与升级证据一致，无校准记录的介入点不得执行 L3 编排。

    （来源：21-AI介入点降级矩阵 §2、§3）

    NFR-038 校准记录治理 — 系统应使每个 AI 阈值引用一组经批准的版本化校准记录，至少包含 interventionKey、被评测对象精确版本、数据集版本与适用范围、指标定义、阈值、样本量与人工基线、生效与过期时间、回退等级；描述：没有有效校准记录时，模型分数只用于排序或提示，不得自动触发资产变更、缺陷提交、质量门禁或 L3 执行。验收：校准记录在 t_calibration_record 落库并有注册与查询 API；对无校准介入点的越权自治用例全部失败关闭（对齐 21 号 AC-03、QF-REQ-006）。

    （来源：21-AI介入点降级矩阵 §4、§7 AC-03；QF-REQ-006；33-数据库Schema设计 §11）

    NFR-039 降级触发与运行行为 — 系统应在命中任一降级触发条件（输入来源、精确版本、内容摘要或授权上下文缺失或变化；触达 allowlist 外资源；Workflow 循环、超时、预算超限、重复失败或 Runner 能力不足；关键路径、来源冲突、职责分离或强制人工检查点；校准过期、评测跌破门槛或误放误阻超警戒；模型、Prompt、Skill 或 Workflow 版本变化未重新评测）时立即停止当前自动步骤并按介入点回退至 L1 或 L0；描述：降级必须停止未开始节点、保留已完成产物与 Trace、把 WorkItem 置为 BLOCKED 或 PENDING_REVIEW、记录原因码版本与恢复条件，不得静默切换模型后继续发布。验收：对越权、循环、超时、版本陈旧四类触发的熔断用例（21 号 AC-04）通过，降级证据完整可审计。

    （来源：21-AI介入点降级矩阵 §6.1、§6.2、§7 AC-04）

    NFR-040 恢复与重放 — 系统应在问题修复、权限重新计算、必要人工决定完成且受影响输入重新锁定后恢复；描述：恢复重放创建新的 run 或 attempt 并引用原失败记录，不覆盖历史证据；被审资产可写或输入快照不完整时独立验证裁决禁用。验收：恢复路径用例验证新 attempt 与原记录引用关系，证据链完整无覆盖。

    （来源：21-AI介入点降级矩阵 §6.3；05-功能模块重构方案 §5.5.12）

    NFR-041 AI 质量分层报告 — 系统应对每个介入点分别报告机器检查、独立验证与人工验收三层结果，不把任一层替代另一层；描述：重点监控人工修改率、误放率、误阻率、越权率、幻觉引用率、降级率、成本与延迟；模型、Prompt、Skill、Workflow 或数据分布变化后重新评测，线上异常触发 L1 或 L0 回退；无版本化校准记录的分数只作排序或提示。验收：分层报告样例齐全，指标口径与 20 号 metricKey 映射一致，无基线数字不得宣称提升。

    （来源：20-非功能需求 §6；21-AI介入点降级矩阵 §4；QF-REQ-026/029）

    本节小结：AI 自治与降级以"人工硬门、等级受控、校准先行、熔断留痕、恢复可重放、分层报告"六项为治理闭环，是本产品区别于普通 AI 功能的质量底线，任何版本不得突破。

    （来源：21-AI介入点降级矩阵 §1、§6；22-MVP版本规划 §1）

    12.9 非功能需求总验收

    第 12 章全部条目的总体验收以 20 号 Given/When/Then 门禁与 22 号版本门禁为框架：性能与容量、可用性与可靠性目标必须在基线批准后生效（AC-04）；AI 依赖不可用时不发布正式资产（AC-02）；幂等冲突不产生第二个业务副作用（AC-03）；跨租户失败关闭（AC-01）。版本发布须同时满足产品、质量、安全、AI、运行与发布六类门禁证据要求。

    （来源：20-非功能需求 §10；22-MVP版本规划 §7）

    第 13 章 数据与接口

    本章规定系统的数据模型概要、接口约定与外部接口。数据与接口共同构成可追溯性、多租户隔离与集成安全的技术底座：所有跨域引用固定 ID、versionId 与必要 contentDigest，外部契约由 OpenAPI 与事件契约驱动。

    13.1 数据模型概要

    （来源：33-数据库Schema设计 §1、§2；V1里程碑执行对照表 §6）

    （来源：34-认证授权设计 §7；33-数据库Schema设计 §13.1、§13.2）

    13.2 接口约定

    系统对外提供 OpenAPI 定义的目标 API 契约，当前状态为 draft，尚不是已发布线上兼容面；产品版本（V0 至 V3）与 API 兼容代际（/api/v1）分离。契约解析口径为 79 个路径、104 个 operation（快照 grep 口径为 78 个路径、102 个 operation，差异属解析口径，列入对照表未核实项）。接口约定要点如下：

    认证与授权：全局安全方案为 BearerAuth（JWT）与 CookieAuth（qf_access）双通道；JWT 至少携带并校验 iss、sub、aud、iat、exp、jti 与身份类型；Web 使用 HttpOnly、SameSite=Strict Cookie 加双提交 CSRF；实时订阅使用经 REST 鉴权后签发的一次性 WebSocketTicket；服务间使用短时工作负载身份或 mTLS，网关清除客户端伪造的身份 Header，服务端不信任客户端角色 Header。

    （来源：32-API规范 §security、§components；34-认证授权设计 §2、§3）

    幂等：所有写操作（POST）要求携带 Idempotency-Key 请求头（16 至 128 字符）；相同键绑定相同 payload 时返回原结果，相同键提交不同 payload 时返回冲突（IDEMPOTENCY_CONFLICT）且不产生第二个业务副作用；异步写操作返回 WorkItem 或 attempt 资源，不以 HTTP 200 掩盖后台失败。

    （来源：32-API规范 §components 参数；20-非功能需求 §4、§10 AC-03）

    分页：列表查询统一使用 page（最小 1，默认 1）与 pageSize（1 至 200，默认 20）参数，分页响应随列表信封返回。

    （来源：32-API规范 §components 参数）

    错误码与信封：成功响应使用 ResponseEnvelope（code、message、traceId），错误使用 ErrorEnvelope（code、message、details、traceId），code 枚举包括 VALIDATION_FAILED、UNAUTHORIZED、INVALID_CREDENTIALS、CSRF_VALIDATION_FAILED、RATE_LIMITED、SETUP_ALREADY_COMPLETED、FORBIDDEN、NOT_FOUND、CONFLICT、IDEMPOTENCY_CONFLICT、INVALID_STATE_TRANSITION、REVIEW_REQUIRED、SEPARATION_OF_DUTIES_VIOLATION、STALE_ARTIFACT_VERSION、EGRESS_DENIED、SECRET_ACCESS_DENIED、DATA_SOURCE_MISSING、RUNNER_CAPABILITY_MISSING、EXTERNAL_SYNC_CONFLICT、DEPENDENCY_UNAVAILABLE、INTERNAL_ERROR 共 21 个业务错误码；每次响应必须携带 traceId 供全链路关联。

    （来源：32-API规范 §components schemas）

    版本代际与契约收敛：核心链（策略、计划、用例、执行、分析）41 个路径、53 个 operation 的响应与请求 schema 必须为具体定义，不得引用 Generic 或未定义块；破坏性变更遵循 32/37 号迁移规则；运行时 operation 数进入 KNOWN_DEFERRED 台账对账，防止静默漂移；M1 至 M5 各里程碑按对照表 §4 承担对应的路径组收敛义务。

    （来源：V1里程碑执行对照表 §4；20-非功能需求 §8；QF-REQ-005）

    实时通道：WebSocket 只投递 ExecutionTask、WorkItem、AgentTrace 与 Workspace 事件，高价值命令仍走 REST；事件包含 eventId、sequence 或 offset、租户与 Workspace、资源与版本、occurredAt 与 traceId。

    （来源：31-系统架构设计 §3）

    13.3 外部接口

    外部接口按集成类型分四类，全部受出站 allowlist、操作范围、Workspace 作用域与逐次授权约束。

    LLM 网关：通过 t_llm_config 管理 Provider、endpoint_ref、模型目录、路由策略、配额与预算，凭据以 Secret 引用方式保存；V1 以确定性 Provider 起步，真实模型须通过 M5 黄金集评测与准入报告（质量、成本、延迟、降级、数据出站策略齐备）后才可替换；出站目标受 EGRESS_DENIED 保护，数据区域与脱敏策略在接入前评测。

    （来源：33-数据库Schema设计 §3；V1里程碑执行对照表 §2 M5；QF-RSK-005/013）

    缺陷系统（Jira 等）：通过 t_integration_config 注册目标，t_external_defect_link 保存厂商中立的外部映射与同步状态，t_defect_sync_attempt 记录每次写入尝试；每次 CREATE、UPDATE、COMMENT、TRANSITION 等外部写入须先经人工批准（EXTERNAL_WRITE 能力），携带幂等键与 payloadDigest，冲突与回执逐次留档；V1 手工同步同样落同步尝试、批准记录与回执，自动双向同步为 V2 能力。

    （来源：33-数据库Schema设计 §10；05-功能模块重构方案 §5.9；QF-REQ-025）

    CI 与代码仓库：Git 集成以完整 commit SHA、文件路径与 blob SHA 冻结代码版本（source_mode=GIT），仓库写入另行人工批准；CI 流水线（t_pipeline_config、t_pipeline_run）与规则型质量门禁为 V2 能力，V1 不自动阻断；流水线触发归属在 PRD 层明确后落版本规划。

    （来源：33-数据库Schema设计 §8、§10；QF-REQ-042；22-MVP版本规划 §4）

    KMS 与身份提供者：主密钥存放于 KMS/Vault，OIDC/OAuth2 身份提供者经 mTLS 或工作负载身份接入；所有外部集成凭证只存密文引用，凭据轮换与使用审计受平台管理。

    （来源：34-认证授权设计 §2、§8；33-数据库Schema设计 §3）

    15.3 需求变更流程

    需求变更按"变更申请、影响评估、裁决、版本更新、回退"五步闭环管理。变更申请：任何需求变更（范围、优先级、契约、非功能目标）由提出方提交申请，说明理由、期望版本与影响范围，V1 期间优先级调整须同时说明对里程碑验收证据的影响。影响评估：评估变更对八模块能力归属、04 领域模型、32 号 API、33 号数据库与 21 号治理矩阵的对账影响，执行 L1 一致性扫描与正反向追踪检查，识别是否触及跨版本不变项或安全底线；凡涉及非功能目标数值的变更，须附基线或测量证据，不得以新数字替换未经批准的旧数字。裁决：由项目负责人按版本规划原则拍板，高风险裁决（触碰底线、跨版本拉项、契约代际变化）留 AuthorizationDecision 与审计记录，并同步 53 号审计流程复核；关键关闭项引入独立复审，避免自证闭环。版本更新：裁决通过后在权威源同批落地，同步 CHANGELOG 并标注每能力项的 MUST、SHOULD、LATER、Owner 与验收证据；API 代际变更遵循 32/37 号迁移规则，数据库变更按 38 号迁移批次、种子与回滚约定执行；发布时同时满足产品、质量、安全、AI、运行与发布六类门禁。回退：自治等级、配置与集成变更支持立即回退并记录回退原因；数据与证据类变更回退创建新 attempt 或新版本并引用原记录，不覆盖历史证据；无法回退的破坏性变更须在评估阶段声明并纳入发布已知限制。

    （来源：05-功能模块重构方案 §5.13.7、§十；22-MVP版本规划 §7；33-数据库Schema设计 §14；QF-REQ-048）
