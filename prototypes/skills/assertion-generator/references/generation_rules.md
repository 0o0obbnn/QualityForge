# 详细生成规则

## 弱断言分类

断言命中以下任一模式即分类为**弱**：

| 模式 | 为什么弱 |
|---|---|
| 只查状态码（`status == 200`） | 所有 happy-path 响应都返回 200，对 body 零校验。 |
| 只查存在性（`response is not None`） | 只确认存在，不确认正确。 |
| 只查类型（`isinstance(x, int)`） | 只查形状，不查取值。 |
| 恒真（`True == True`、`1 == 1`） | 同义反复，不可能失败。 |
| 无字段引用 | 对被测系统没有做出任何断言。 |

断言若校验具体字段取值、状态迁移或多字段关系，则为**强**。

该分类是语法层的——读取的是断言的表达式模式，不是运行时行为。
因此它快（不执行）但保守：被判「弱」的断言在上下文里可能很强，
被判「强」的也可能实际上很弱。mutation 门禁（逐条断言验证）才是
最终裁决；本检查只是早期过滤器。

结构有效性先于分类：每条断言必须有 `assertion_id`、`expression`、
`expected`，以及 `target` 或 `field`。只有 target 而无可执行比较
的，按 `INVALID_ASSERTION_STRUCTURE` 拒绝。

## 批次比例检查

```
assertion batch
       │
       ▼
  classify each: weak | strong
       │
       ▼
  weak_ratio = count(weak) / count(total)
       │
       ▼
  weak_ratio > threshold ?  REJECT  :  PASS
```

阈值取自 strategy contract。典型默认值 0.3（批次中至多 30% 为弱）。
超阈值的批次被 REJECTED，并附弱断言 ID 清单——生成器必须强化这些
断言后重新提交。

## 为什么是批次检查，不是逐条检查

逐条验证回答「这条断言对不对」。批次检查回答「这批断言值不值得
验证」。两者互补：

- 40 条强断言的批次 → 全部验证（每次验证的价值都高）。
- 40 条弱断言的批次 → 不验证，退回生成器。mutation 测试确实会
  拒掉其中大多数，但那等于把 mutation 预算浪费在根本不该以这种
  形态生成的断言上。

批次检查是预算保护者：它阻止验证流水线把昂贵的 mutation 测试
周期花在结构上就低值的批次上。
