# Assertion Verifier 流水线参考

三段式流水线的详细参考。`scripts/verify.py` 是第 1、3 段的可执行
编码；本文档是 mutator 目录、阈值与降级规则的权威来源。两者若有
分歧：脚本决定*行为*，本文档决定*意图*——通过评审对齐，不允许
静默处理。

## 阈值（冻结的默认值）

按风险等级划分的 mutation 分数阈值。这些是下限，不是目标值。

| 风险等级 | 阈值 | 适用场景 |
|---|---|---|
| `low` | 0.50 | 非关键路径上的普通断言。大多数 mutant 必须被杀死。 |
| `medium` | 0.70 | 业务规则断言（在 IR 中绑定 `rule_id`）。要求较强的杀死能力。 |
| `high` | 0.85 | 关键路径断言（认证/支付/权限，以人工审核的枚举为准）。接近全杀；与强制检查点相邻资产的 ≥0.9 置信分层精神一致。 |

为什么是这些数字而不是「100%」：mutation 测试存在等价 mutant
问题——有些 mutant 与原程序语义完全相同，任何测试都杀不死。
要求 1.0 等于因 mutator 的伪影惩罚断言，而不是惩罚真实弱点。
上述下限为等价 mutant 留了余量，同时仍能抓住主要失败模式
（几乎杀不死任何 mutant 的弱断言/幻觉断言）。

### 阈值调参

这些是已文档化的默认值。真实部署应利用下游 knowledge 记忆的
校准数据调参：如果评审者持续放行 medium 风险等级上得分 0.55 的
断言，说明该等级阈值过严；如果评审者不断拒绝 0.75 分的断言，
说明过松。调参闭环在下游 knowledge retention / 下游治理报表
（governance reporting）里，不在这里——本 skill 消费阈值，
不动态设定阈值。

## 降级规则

证据缺失时流水线只降级（变严），绝不放松。

| 缺失的证据 | 影响 | 原因 |
|---|---|---|
| 跳过第 2 段（无 Fixture 快照、无 contract stub） | 第 3 段阈值**上调** 0.05。 | 断言可靠的佐证证据变少，mutation 门禁必须补偿。跳过第 2 段不可能让断言*更容易*通过。 |
| 跳过第 1 段 | 不允许。第 1 段强制且廉价；没有降级路径，只有「未运行 = REJECT」。 | 契约违反是确定性的；推迟到后面只会浪费第 3 段预算。 |
| `high` 风险跳过第 3 段（无 mutant） | 硬 REJECT。 | mutation 门禁对高风险断言是强制的。跳过它正是本 skill 要防的失败模式。 |
| `low` 风险跳过第 3 段 | 可以仅凭第 1+2 段 PASS，但该断言的有效覆盖标记为 `unconfirmed`，下游覆盖统计永不计为 `verified`。 | 低风险断言可以不走完整门禁，但覆盖统计必须反映更弱的证据。 |

不变式：**证据缺失要么抬高门槛、要么降低可计入的覆盖，绝不允许
两者都原地不动。** 一条证据更少却静默放行断言的流水线，表演的是
验证剧场。

## Mutator 目录

第 3 段注入的故障集合。并不穷尽——真实部署会按语言/领域扩展。
要点在于每个 mutator 都瞄准一类弱断言会漏掉的 bug。

| Mutator | 改动什么 | 什么样的断言能抓住它 |
|---|---|---|
| `off_by_one` | 索引/循环边界中的 `i` ↔ `i±1` | 边界值断言（如 `len(items) == 10`、`price == 9.99`） |
| `flip_boolean` | `==` ↔ `!=`；`True` ↔ `False` | 布尔字段上的精确相等断言 |
| `null_where_value` | 把取值替换为 `null`/`None` | 非空/存在性断言（`response.body.user_id is not None`） |
| `wrong_enum_member` | 把枚举值换成同枚举的兄弟值 | 枚举断言（`status in {"PAID","REFUNDED"}`） |
| `remove_field` | 删除响应字段 | Schema/存在性断言（字段必须存在） |
| `type_coercion` | 取值 `int` ↔ `str` | 类型断言（`isinstance(x, int)`） |
| `constant_swap` | `0` ↔ `1`、`""` ↔ `" "`、`[]` ↔ `[None]` | 取值敏感断言（只查 `is not None` 的弱断言会活下来） |

`constant_swap` 与 `null_where_value` 是最能稳定抓住「AI 生成的
`assert x is not None`」式弱断言的两个 mutator——如果一条断言
在两者之下都存活，它几乎可以肯定没有验证任何有意义的东西。

### 这里不算 mutator 的东西

- **控制流 mutant**（删除某个 `if` 分支）。这类与行/分支覆盖重叠，
  已有更廉价的技术覆盖。mutation 门禁的价值在*取值层*故障，
  不在结构层。
- **性能 mutant**（拖慢响应）。那属于下游性能测试生成
  （Performance Test Generator），不在这里。

## 成本预算

Mutation 测试是最昂贵的阶段。按风险等级设定每条断言的预算上限
——这些是上限，不是目标。低于预算是好事；超预算说明 mutator
集合过大或断言过宽。

| 风险等级 | 每条断言 mutant 数 | 墙钟预算 |
|---|---|---|
| `low` | 0（第 3 段可选）或 ≤3 | — |
| `medium` | ≤8 | ≤30s |
| `high` | ≤15（完整目录子集） | ≤120s |

如果单条高风险断言吃光了全部预算，说明该断言过宽（一次测了太多
东西），应由断言生成步骤拆分后再重新验证。成本压力作为 REPAIR
回传上游，而不是变成向下的降门槛。

## 三类失败（给评审者的回顾）

评审者查看一条 REJECTED 断言时，报告必须写清抓住的是*哪一类*
失败：

1. **幻觉（Hallucinated）**——第 1 段 REJECT
 （FIELD_NOT_IN_CONTRACT、RULE_NOT_IN_IR）。
 断言引用了 IR 中未定义的东西。
2. **弱（Weak）**——第 3 段 REJECT 且分数低，但第 1 段干净。
 断言与契约一致，但几乎杀不死 mutant。
3. **同义反复（Tautological）**——第 2 段（可用时）报告该断言
 对所有可能响应都成立，或第 3 段 `constant_swap`/`null_where_value`
 mutant 全部存活。

不同类别路由到不同的修复指引，交给断言生成步骤：幻觉 → 重新
绑定到正确的 IR 元素；弱 → 强化成精确取值或枚举断言；同义反复 →
改写为校验有区分度的取值。路由修复指引是调用方 skill 的职责；
本 skill 只负责分类。
