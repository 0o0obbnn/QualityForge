# 全量提取协议

本协议用于任何领域的需求、接口或项目资料，不包含特定项目的模块名、字段名或业务规则。

## 1. 先声明提取模式

- `full`：目标是覆盖全部相关输入内容，可以用于“完整、全部、全量”结论。
- `representative`：仅验证若干模块、页面或流程，只能输出 `PARTIAL_PASS`。

不得在执行结束后把抽样结果改写成全量结果。

## 2. 建立来源单元台账

将输入拆成可对费用单元：章节、正文规则块、表格、图片/原型、接口定义、数据字典和引用依赖。每个单元记录：

```json
{"unit_id":"UNIT-001","source_id":"SRC-001","kind":"table","locator":"<可定位位置>","relevant":true,"status":"processed","reason":null}
```

状态仅允许 `processed / review_required / skipped / unavailable`。默认正文权威模式下，图片仍登记到台账，但使用 `relevant=false / skipped`，不参与正文覆盖率。项目资料缺失状态必须从 `qa-requirement-review` 资料依赖评审导入，不得由本 Skill 仅根据需求文字自行判定。

当正文明确使用“规则见图、字段见原型”等方式把图片作为唯一需求来源时，该图片属于相关来源。仅在运行环境具备多模态能力时直接核验原图；否则将受影响范围标为 `unavailable`，不扩散阻塞到无关正文功能。

### 引用依赖投影

`reference_dependency` 来源单元由资料依赖评审导入，使用以下一种 `reference_type`：

- `internal_reference`：“同网页端一致”、“复用某页面”等当前来源集内部继承。本 Skill 把评审已确认的目标定位映射为功能关系。
- `external_artifact`：附件、标准、数据字典、云盘文件等已存在但未随输入提供的权威资料。
- `existing_baseline`：“同当前一致”、“与历史接口一致”等需要现网、旧版或历史契约才能确认的基线。
- `pending_artifact`：“需提供接口文档”等需求明确声明尚待交付的资料。

每次出现保留评审产物的 `dependency_id / locator / quote / reference_key / finding_ids`。本 Skill 新增 `blocking_scope`、`resolved_reference.target_id` 和图关系；不改写评审对资料可用性的结论。

`blocking_scope` 必须遵循最小可证范围：引用句可明确对应到一个或多个最小功能时写入 `atomic_ids`；仅在引用句只能证明所属功能、无法再收窄时使用 `function_id` 回退。例如“导出格式见附件”只影响“导出”，不影响同页的“查询”或“重置”。回退必须在产物中保留原文证据，不允许为获得更少的 BLOCKED 而猜测范围。

## 3. 第一遍：只登记原始出现项

对所有相关来源单元逐一提取，不在本阶段合并：

- 功能动词、角色、触发、前置条件和结果；
- 页面操作、系统任务、接口行为和校验行为；
- 每一次字段出现，包括原文名称、所在区域、字段角色、原文属性及证据；
- 状态、枚举、公式、限制、提示语和引用依赖。

字段出现项示例：

```json
{
  "occurrence_id":"OCC-001",
  "field_id":"FLD-001",
  "name_as_written":"<原文字段名>",
  "function_id":"FUN-001",
  "surface":"query_condition",
  "role":"input",
  "evidence":[{"source_id":"SRC-001","locator":"<位置>","quote":"<原文>"}]
}
```

## 4. 第二遍：拆功能点和最小功能

功能点按业务目标、角色、生命周期和结果分组，不按标题机械复制。最小功能必须具备：

```text
明确触发 + 单一动作 + 可观察结果
```

最小功能分类可为：

- `business_action`：产生业务结果的人工行为；
- `system_job`：定时或事件触发的系统行为；
- `interaction`：查询、重置、查看、导出、上传、下载等可独立验证操作；
- `validation`：具有独立触发和错误结果的校验行为；
- `integration`：接口请求、响应或外部系统交互。

多条共享同一触发和结果呈现方式的校验规则可以作为一个最小功能的规则/分支；触发、处理阶段或结果不同则拆分。

除标题外，还要逐表扫描按钮、操作、状态操作和接口/服务清单，并逐段扫描明确能力动词。表格中的按钮、提交、取消、导出等属于行为候选，不属于业务字段候选。

## 5. 第三遍：字段归一化

只允许在原始出现项完整后去重：

1. 比较业务对象。
2. 比较输入、输出、列表、详情、接口请求/响应等上下文。
3. 比较字段角色和规则。
4. 全部一致才合并；无法确认时保留两个字段。
5. 回显、掩码、复制、计算或转换使用字段血缘关联。

输入方向与展示/响应方向不得自动合并。嵌套“触发条件—提示语”表先形成独立校验记录，再按功能、字段名和输入方向关联；提示语明确命名但目录缺失的复合子字段，应新增带派生来源的输入字段出现项。

`aliases` 只用于同一对象、同一上下文和同一规则下的同义名称，不能替代字段血缘。

## 6. 属性级来源

以下属性分别声明来源状态，不能用字段级 `confirmed` 一次性覆盖：

```json
{
  "attribute_provenance": {
    "business_object":"inferred",
    "data_type":"derived",
    "required":"explicit",
    "sensitivity":"inferred"
  }
}
```

- `explicit`：原文直接定义。
- `derived`：可以由原文规则确定性计算或转换得到。
- `inferred`：分析判断，需要复核。
- `unresolved`：资料不足或存在冲突。

## 7. 第四遍：反向缺口扫描

从来源单元反查产物，而不是只从产物反查来源：

- 每个相关章节是否至少产生功能、字段、规则或明确的“无产物”结论；
- 每张表的每一行是否已登记或说明排除原因；
- 每个操作动词是否进入最小功能或排除决策；
- 每个字段出现项是否归入业务字段；
- 每个业务字段是否绑定最小功能；
- 每个引用是否已分类，内部继承是否定位目标，外部资料、现有基线和待提供资料是否记录受影响范围；图片是否已登记，以及是否被正文明确提升为相关来源。

图片核验直接基于原图的多模态观察。运行环境不支持多模态时跳过普通原型图；不得使用 OCR 文本替代对字段角色、状态、交互关系或正文冲突的视觉判断。

## 8. 结论规则

仅结构合法：`STRUCTURAL_PASS`。

代表性范围结构和语义均通过：`PARTIAL_PASS`。

全量范围、来源单元无遗漏、属性来源完整、语义复核通过：`PASS`。

存在结构错误、无证据结论或未声明的来源遗漏：`FAIL`。
